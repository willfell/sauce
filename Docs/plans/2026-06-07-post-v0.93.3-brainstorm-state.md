## 3 — THE big new finding: applyExternalPlugins is warning-only

**This is the most important content in this doc.** It changes how every future cycle that uses `external_plugins[]` should be designed.

### The discovery
v0.93.3's design (committed at `910288d`) asserted: *"applyExternalPlugins (already in platform/install.js) installs plugins listed in any mechanism's external_plugins[]"*. **This is false.** During S2 dogfood, `applyExternalPlugins` ran for convenience + sc-bridge but neither new-tab-default-page nor smart-connections was actually installed on the workshop vault.

Grepping `platform/install.js:2687-2792` revealed the function's docstring is explicit:

> applyExternalPlugins — for each item that declares external_plugins[], read .obsidian/community-plugins.json and warn (Notice + history) for any required dep that is not currently enabled. **the installer cannot install Obsidian community plugins itself, so this is a detection-and-surface-up helper, not a remediation step.**

Actual plugin install logic lives in `platform/bootstrap.js:120`'s `phaseFetchPlugins`, which iterates `mf.external_plugins || []` and calls `fetchPlugin(id, repo, vaultPath)` per id. **But phaseFetchPlugins is only called during `sauce bootstrap` (fresh-vault first-install), not during `sauce update` / `platform/install.js`.**

### The consequence for v0.93.3 contract
- **Fresh consumer vaults** running `sauce bootstrap` → both new-tab-default-page + smart-connections auto-installed via phaseFetchPlugins reading every subscribed mechanism's `external_plugins[]`. Then `applyCommunityPluginData` (during the standard install pass) scaffolds new-tab-default-page's data.json.
- **Existing consumer vaults** running `sauce update --bump-pins` (after `brew upgrade sauce`) → neither plugin auto-installs. The user sees:
  - `applyCommunityPluginData: convenience prereq plugins missing (new-tab-default-page); skipped` (Notice fires when plugin dir is absent — `required:true` not needed for this Notice)
  - `<mechanism> requires plugin <id>: (no reason). Install + enable in Settings → Community plugins.` (Notice fires only for `required:true` deps)
- User must manually install both via Settings → Community plugins → Browse → Search → Install → Enable. After manual install, the NEXT `sauce update` pass will run `applyCommunityPluginData` to scaffold data.json.

### The plugin-already-installed-but-not-enabled case
Headspace's pre-cycle state had smart-connections installed AND enabled but **new-tab-default-page neither installed nor enabled**. After the cycle:
- `.obsidian/plugins/new-tab-default-page/` directory does NOT exist
- `.obsidian/community-plugins.json` does NOT contain it
- Obsidian's "Installed plugins" list shows nothing for it (because Obsidian's list reads from `.obsidian/plugins/<id>/manifest.json` directories)
- **A restart will not change this** — restart only rescans existing directories; it does not download plugins.

The user must use Settings → Community plugins → **Browse** (not Installed) to fetch + install. This is the documented gap.

### Why this matters for future cycles
Every future cycle that wants to "declare an external plugin required" via mechanism `external_plugins[]` will hit this same gap. v0.94.0's recommended scope is **extending `platform/install.js` with `applyExternalPluginInstall`** to close it. See § 4.

### Open design questions for v0.94.0 brainstorm
1. **Where does the new helper live?** New `applyExternalPluginInstall` in install.js? Or factored to `platform/install-lib/fetch-external-plugins.js` for testability + parity with bootstrap-lib? Bootstrap already uses `bootstrap-lib/fetch-plugin.js` — extracting could mean both call the same code.
2. **Idempotence semantics.** What if `.obsidian/plugins/<id>/` exists but is empty / corrupt? Force re-fetch? Skip? Probably skip-if-present-and-has-main.js (mirror bootstrap's check).
3. **`required:true` behavior.** Today `applyExternalPlugins` only Notices on missing `required:true` deps. Should `applyExternalPluginInstall` install only `required:true` deps, or ALL declared `external_plugins[]`? Probably ALL (mirror bootstrap's behavior; `required` becomes the "loud about missing" flag rather than the "actually install" flag).
4. **Subscription gating.** Should the install respect the subscription's mechanism set (only install plugins for mechanisms that are subscribed) or the workshop's full mechanism set? Probably subscription-set (mirror what `applyCommunityPluginData` does).
5. **Notice on success.** Today bootstrap silently fetches plugins. Should the update-time helper emit a Notice on each install (`applyExternalPluginInstall: installed X.Y.Z (chrisgrieser/obsidian-new-tab-default-page)`)? Yes — user-visible change deserves audit.
6. **--no-install-externals flag.** Where does it live? `sauce update --no-install-externals`? Persisted in `ranch/platform-config.json`? Probably both options (CLI flag overrides config).
7. **GitHub release-asset fetch failures.** What if the plugin's GitHub repo is unavailable / 404 / rate-limited? Bootstrap fails loud (landmine #17). update should fail loud too — but should one bad plugin block the entire install? Probably no (warn + continue, mirror applyExternalPlugins's never-throws posture for the warning emission).
8. **CLAUDE.md observation note.** Should landmine #17 (bootstrap network posture) get a v0.94.0 entry noting the second network gateway?
9. **Backfill for v0.93.3 declarations.** Does v0.94.0's first `sauce update` on an existing consumer (post-upgrade) trigger the auto-install for the two v0.93.3 plugins? Yes — that's the whole point. v0.94.0 result doc should call this out as the load-bearing consumer story.

## 5 — Lessons from v0.93.3 execution worth carrying into v0.94.0+

These are NEW lessons (not in the prior state doc) that the v0.94.0+ brainstorms should internalize:

### 5.1 — Verify the helper does what the design assumes BEFORE designing the manifest delta
v0.93.3's whole design rested on "applyExternalPlugins installs plugins." One grep + one read of `platform/install.js:2687` would have surfaced the gap before the brainstorm closed. **For v0.94.0 specifically**: before authoring `applyExternalPluginInstall`, verify (by reading code, not memory) that:
- `bootstrap-lib/fetch-plugin.js` is callable from outside `bootstrap.js` (or extract it cleanly)
- `applyCommunityPluginData`'s prereq gate (which checks ALL declared external_plugins[]) is compatible with the new install order
- `community-plugins.json` write semantics in install.js are the same as bootstrap.js (atomic + backup + JSON-shape guard)
Don't trust the prior cycle's narrative as a stand-in for the actual code.

### 5.2 — TDD against the REAL install path, not just bootstrap
v0.93.3's BS18 + BS19 invoke `runBootstrap` directly with `skipInstaller: true` — they exercise `phaseFetchPlugins`, not `applyExternalPlugins`. They establish a regression net for the fresh-bootstrap path but DID NOT catch the install.js gap. For v0.94.0's TDD cases: at least one case must invoke `platform/install.js` end-to-end on an existing-vault scenario (plugin dir absent → install ran → plugin dir present + enabled).

### 5.3 — In-cycle bump rule for per-cycle VERSION pins
v0.93.3 surfaced an unplanned-for sweep: bumping `package.json` / `platform/manifest.json:workshop_version` triggered failures across `HC-V0891/V0900/V0920/V0930/V0931-VERSION-*` blocks that had hardcoded the prior value. Plans should explicitly list this sweep as part of the workshop-bump stage. For v0.94.0 specifically: grep `platform/test/run-helper-cases.js` for `"0.93.3"` and bump all hardcoded matches to `"0.94.0"` as a stage step. (Captured in landmine #16 v0.93.3 observation.)

### 5.4 — ranch/platform-subscription.json lockstep with workshop manifest
Workshop self-install dogfood requires `ranch/platform-subscription.json`'s workshop_version + per-mechanism pins to match the workshop manifest, else install correctly refuses to "downgrade" the subscription. v0.93.3's S2 dogfood failed initially because ranch's `convenience` pin was at 0.2.4 while workshop manifest was at 0.3.0. **Plans should include explicit ranch/platform-subscription.json bumps as part of S1.4 (workshop bump) or S2 (dogfood)**, not assume `sauce update --bump-pins` will handle it (the workshop doesn't run `sauce update`; it does direct dogfood).

### 5.5 — Plan preconditions can be stale by the time execution starts
v0.93.3's plan was written assuming "10 modified files + 8 failing HCs" in the working tree. By the time execution started, that drift had already been absorbed into the v0.93.2 tag itself — the working tree was clean and preflight was GREEN. The plan's elaborate S0.1 → S0.5 baseline-cleanup investigation completed in 3 minutes as a no-op. **For v0.94.0**: if there's any delay between plan-write and execution, re-verify the plan's preconditions (working-tree state, preflight state, HEAD vs tags) as the first execution action.

### 5.6 — Mid-execution scope adaptation is OK when surfaced clearly
The user accepted v0.93.3's contract redefinition (warning-only ships as-is; full auto-install deferred to v0.94.0) rather than pause-and-expand the cycle. This is the right tradeoff when the cycle is mid-flight and the scope gap is documentable + has a clear next-cycle home. **For v0.94.0**: if a similar gap surfaces, surface it explicitly with options (extend scope, redefine contract, stop and redesign) rather than silently expanding.
