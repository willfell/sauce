# MeetingLeafActions — design (v0.125.0)

## Mission

Meeting notes (`type: meeting`) render a Breadcrumb + SpaceNavButtons chrome row but — unlike to-do and scratch — **no leaf-action button row**. This cycle adds `MeetingLeafActions`: a button row on meeting leaf notes giving quick in-context actions the user asked for: **New Task**, **Add to Project**, **Edit Attendees**. It's the next per-blueprint nav surface in the note-chrome arc (after the v0.122.0–v0.124.1 mechanism + adoption work).

Same shape as `ToDoLeafActions` / `ScratchLeafActions`: a `customJS` class that renders a flex row of `AccentButton`s. The row slots into `Meeting.md` after SpaceNavButtons (before the first SectionLabel), and a heal injects it into existing meeting notes — consistent with the v0.124.0 Option-B "heal existing notes" precedent.

## Decided in brainstorming (2026-06-19, autonomous per user direction to execute)

- **Three buttons:** New Task · Add to Project · Edit Attendees. (YAGNI — the user's "…etc." is deferred; nav is already covered by SpaceNavButtons.)
- **Reuse over rebuild:** New Task delegates to the existing `ToDoCreateTask` dialog; Add to Project uses `app.fileManager.processFrontMatter` + a `dv.pages` project list; only Edit Attendees needs a new (bespoke) modal.
- **No hard cross-blueprint dependency.** New Task **gracefully degrades**: at click it checks `customJS.ToDoCreateTask` and shows a Notice if to-do isn't installed. Add to Project / Edit Attendees only read `spice/projects` / `spice/people` notes (no hard dep on those blueprints).
- **Logic in static helpers** (headlessly testable via the `run-todo-dialog.js` `new Function()` pattern); DOM/modal rendering is thin and verified by dogfood (browser-only), matching the codebase's `ToDoCreateTask` precedent.
- **Heal existing meetings** (extend `applyNoteChromeHeal`) so deployed meeting notes get the row, idempotent + content-safe.
- **No new mechanism.** The modal-overlay boilerplate lives as a private helper inside `meeting-leaf-actions.js` (shared by the two pickers). A shared `dialog` mechanism is over-engineering for two pickers (YAGNI).

## 1. The `MeetingLeafActions` helper

New file `platform/blueprints/meetings/helpers/meeting-leaf-actions.js` — a single `customJS` class, mirroring `ToDoLeafActions`/`ScratchLeafActions`:

- `async render(dv)` — embed-guard (`if (dv.container.closest('.markdown-embed')) return;`), render-gen counter to avoid duplicate fires, clear container, build a flex row (`display:flex; gap:12px; margin:0.5em auto; justify-content:center; align-items:stretch; max-width:600px; flex-wrap:wrap;`), then render three `customJS.AccentButton.render(row, { label, icon, onClick, flex: true })` buttons.
- Buttons + handlers: `New Task` → `_onNewTask(dv)`, `Add to Project` → `_onAddToProject(dv)`, `Edit Attendees` → `_onEditAttendees(dv)`.
- Icons: reuse the icon strings the to-do/scratch helpers use (plus / folder / users from `customJS.Icons` if available, else inline SVG fallback — match the existing helpers' icon sourcing).

**Static helpers (the testable surface — pure, no DOM/app):**
- `MeetingLeafActions.resolveProjectPreselect(cur, projectList)` → from the note's `project` frontmatter (`"[[Name]]"` or empty) and a `projectList` of `{slug,name}`, return `{type:'project', slug, name}` if a project matches, else `'today'`. Used by New Task.
- `MeetingLeafActions.stripWikilink(s)` → `"[[Q3 Planning]]"` → `"Q3 Planning"` (and passthrough for plain strings / empty).
- `MeetingLeafActions.buildAttendeeFrontmatter(selectedNames)` → returns `{ attendees: ["[[A]]",…], people: [...] }` (people kept in sync with attendees, matching the template's creation behavior).
- `MeetingLeafActions.personStubBody(name, isoNow)` → the `---\ntype: person\n…` stub string (mirrors the creation-time add-new-person stub) for the "add new person" path.

**Instance/DOM methods (dogfood-verified, not headlessly tested):** `render`, `_onNewTask`, `_onAddToProject`, `_onEditAttendees`, `_openModal`.

## 2. Button mechanics

### New Task
```
_onNewTask(dv):
  if (!customJS?.ToDoCreateTask?.open) { new Notice("Install the to-do blueprint to create tasks from meetings."); return; }
  const projects = _listProjects(dv);                       // dv.pages('"spice/projects"').where(type==="project") → {slug,name}
  const dest = MeetingLeafActions.resolveProjectPreselect(dv.current(), projects);
  customJS.ToDoCreateTask.open({ preselectTab: "one-shot", preselectDestination: dest });
```
The meeting's project becomes the task's preselected destination; with no project it defaults to `'today'`. 100% existing infra; the dialog owns task creation.

### Add to Project
A single-select project picker (modal) listing all projects + a "(none)" / "Clear" option:
```
_onAddToProject(dv):
  const projects = _listProjects(dv);                       // [{slug,name}]
  open a modal listing project names (+ "(none)"); on choose:
    const file = app.vault.getAbstractFileByPath(dv.current().file.path);
    await app.fileManager.processFrontMatter(file, fm => { fm.project = name ? `[[${name}]]` : ""; });
    new Notice(name ? `Added to ${name}` : "Cleared project");
```
Reuses the canonical `processFrontMatter` write (per `finance-frontmatter.js`) + the entity-create `all_projects` enumeration. No hard dep on the project blueprint (reads notes only; empty list → just "(none)").

### Edit Attendees
A multi-select people picker (modal) — the one genuinely new piece:
```
_onEditAttendees(dv):
  const people = _listPeople();                             // spice/people/*.md basenames, excl. "People"
  const current = (dv.current().attendees||[]).map(stripWikilink);
  open a modal: a checkbox/chip per person (pre-checked if in current) + an "+ Add new person" text input + Save/Cancel.
    add-new: create spice/people/<name>.md (via vault.create with personStubBody) if absent, add to selection.
    Save:
      const file = app.vault.getAbstractFileByPath(dv.current().file.path);
      const { attendees, people } = MeetingLeafActions.buildAttendeeFrontmatter(selectedNames);
      await app.fileManager.processFrontMatter(file, fm => { fm.attendees = attendees; fm.people = people; });
      new Notice(`Attendees updated (${selectedNames.length})`);
```
`attendees` and `people` are written in sync (the template sets them equal at creation). The PeopleRendering chips re-render on Cmd+R / next dataview refresh.

## 3. Modal infrastructure

No shared Modal class exists; `ToDoCreateTask` rolls its own overlay. To avoid duplicating that boilerplate across the two pickers, add a private `_openModal({ title, build })` helper inside `meeting-leaf-actions.js`:
- Builds the fixed overlay (`.sauce-meeting-modal-overlay`, `position:fixed; inset:0; rgba backdrop; flex-center; z-index:9999`) + a modal panel (`var(--background-primary)`, border, radius, `width:min(440px,92vw); max-height:80vh; overflow:auto`).
- Dismissal: click-outside + Escape keydown listener (removed on close), exactly mirroring `ToDoCreateTask._renderOverlay` lines 162–185.
- `build(panel, close)` callback renders the picker body + wires a close fn.
- Defensive: removes any prior `.sauce-meeting-modal-overlay` before opening.

This keeps the modal scoped to the meetings helper (no new mechanism), reused by Add-to-Project and Edit-Attendees.

  No `---` between SpaceNavButtons and the leaf-action row (chrome grammar — they're one chrome unit, matching Project To-Do where leaf-actions follow nav with no divider).

## 5. Heal: inject the row into existing meetings

Extend `applyNoteChromeHeal._healNoteChromeBody` (meeting branch) in `platform/install.js`: after breadcrumb injection + H2→SectionLabel + divider cleanup, inject a `MeetingLeafActions` dataviewjs block immediately after the first `SpaceNavButtons` block if absent. Idempotent (skip when `class: "MeetingLeafActions"` already present), fence-aware, content-safe (insert-only; never removes/alters a non-target line), `.sauce-backup` already handled by the driver. Targets `type: meeting` leaf notes (the same set the heal already processes).
- Placement: find the first `SpaceNavButtons` dataviewjs fence, insert the MeetingLeafActions block after its closing ```` ``` ````.
- **Skip hubs (firm decision):** leaf actions (New Task / Add to Project / Edit Attendees) act on the current note's frontmatter *as a meeting leaf*, so they're meaningless on a Meeting Hub. Some vaults (accuris) carry `type: meeting` on hub notes, so the heal must additionally skip any note bearing the `meetings-hub` tag. The injection condition is: `type === "meeting"` AND not tagged `meetings-hub` AND has a `SpaceNavButtons` block AND no existing `MeetingLeafActions` block. The template invocation is in `Meeting.md` (leaf template) only — `Meeting Hub.md` does not get the row.
