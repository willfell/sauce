# v0.73.0 — kanban-progress architectural cleanup + activity-feed efficiency pass — DESIGN

**Status:** Active design — supersedes `2026-05-21-activity-feed-kanban-progress-design.md` (v0.72.x cycle, closed).

**Author:** main session agent, working from `Docs/prompts/2026-05-22-post-v0.72.1-v0.73.0-handoff.md`.

**Goal.** Move the kanban-board sync out of the daily-dashboard hot path, persist `<details>` open/closed state across re-renders, expose a manual re-sync via the Obsidian command palette, and audit `activity-feed.js` for efficiency wins. Ship as one bundle to all 4 consumer vaults.

**Why this cycle.** v0.72.1 added an in-singleton once-per-day cache so `syncAllBoards` is now zero-write on cached calls — but it still re-iterates every kanban board on every Dataview re-render. On vaults with active background plugins (smart-connections), the dashboard re-renders mid-scroll, the page resets to the top, and `<details>` toggles snap back to the default state. Removing the call from render + persisting toggle state eliminates both symptoms regardless of who's firing the re-render.

## Architecture decisions

### A. Startup-script trigger replaces inline render-time trigger

**Decision.** `KanbanStatusSyncInit` is a customjs startup-script class. customjs invokes its `invoke()` method at plugin init time. `invoke()` kicks off an async helper that retries until Dataview's API resolves, then calls `customJS.KanbanStatusSync.syncAllBoards(dv, today)` exactly once per vault session.

**Why `invoke()`, not `onload()`.** Precedent: `ToDoMigrateInit.invoke()` + `ProjectTaskCreateListenerInit.invoke()` are the canonical shape in the workshop. customjs's startup-script protocol calls `invoke()` on each registered class. The handoff referenced `onload()` informally; the platform invariant is `invoke()`.

**Why dataview-readiness retry.** customjs and dataview both register at plugin init, but their relative load order is not guaranteed across consumers / Obsidian versions. Probe-with-backoff (250ms × up to 30s) handles the race without coupling to plugin-load-order tweaks.

**Idempotence.** `KanbanStatusSync` already caches `_lastSyncDay` / `_lastSyncResult`; a second `invoke()` (from customjs's "rerun startup scripts on file change" toggle) is a no-op cache-hit. We do NOT add another `_initialized` guard in the init class — the cache below already enforces single-execution.

**Visibility.** Emit `new Notice("Kanban status synced: N moved, M archived across K boards")` ONLY when `synced + archived > 0`. Cache-hits, no-op runs, and Dataview-not-ready failures stay silent in the Notice surface (console.log/warn for diagnostics).

### B. `<details>` state persistence

**Decision.** Persist open/closed state per `<details>` element to a JSON file at `<vault>/ranch/cache/dashboard-section-state.json`. Read at render-time and override the passed-in `defaultOpen` if a key exists. Write on the `toggle` event.

**State file shape:**

```json
{
  "_version": 1,
  "states": {
    "sauce-daily-dashboard:tasks":    true,
    "sauce-daily-dashboard:meetings": true,
    "sauce-daily-dashboard:activity": false,
    "sauce-activity-feed:cowork":     true,
    "sauce-activity-feed:project":    true,
    "sauce-activity-feed:scratch":    false
  }
}
```

**Namespacing.** Top-level dashboard sections use `sauce-daily-dashboard:<sectionKey>` where `<sectionKey>` is the lowercased section title (`tasks`, `meetings`, `activity`). Inner activity-feed groups use `sauce-activity-feed:<bucketKey>` where `<bucketKey>` is the post-`bucketRules` group key (`cowork`, `project`, `kanban`, `scratch`, etc.).

**Why `ranch/cache/`.** `ranch/` is the canonical platform-managed runtime-plumbing tree (per landmine #11 + architecture.md). `ranch/cache/` is a NEW subdirectory created on first toggle. It's not git-managed in consumer vaults (the existing `.gitignore` in each consumer's vault root already excludes `ranch/cache/`-shaped paths via `*.cache` or by being absent — we are not introducing a new ignore rule, and the file is small + regeneratable).

**No installer involvement.** We do NOT add an installer step to materialize this file. It's a pure runtime artifact created on first toggle. Missing-file is a normal case — read returns `{}`, render uses the passed-in `defaultOpen`, write creates the file lazily.

**Atomic writes.** Last-write-wins; no merge logic. Each toggle reads the full state object, mutates one key, stringifies-and-writes the whole thing. Errors are swallowed silently (state persistence is best-effort UX polish, never blocks render).

**Read posture.** Each `_renderSection` / `_renderFramedGroup` call reads the state file via `app.vault.adapter.read(path)`. This is fast (small file, OS page cache) and per-render — no in-memory cache, no invalidation logic. If state read throws (file missing, malformed), default-open semantics apply.

**Bucket key alignment.** The activity-feed renderer applies `bucketRules` BEFORE rendering — pages get re-grouped under bucket keys (e.g., all `cowork-*` types fold into `cowork`). Persistence uses the post-bucket key as the dedup unit, so toggling `cowork` once persists across re-renders even when the underlying type-key population shifts.

### C. Manual re-sync command

**Decision.** Inside `KanbanStatusSyncInit.invoke()`, register an Obsidian command:

```javascript
app.commands.addCommand({
  id: "kanban-status-sync:resync-now",
  name: "Sauce: Re-sync kanban boards",
  callback: async () => { /* bypass cache + run sync */ }
});
```

The callback nulls the cache fields on `customJS.KanbanStatusSync`, fetches a fresh Dataview API handle, computes today's date, and runs `syncAllBoards`. Surfaces the result via `new Notice`.

**Why command-palette over slash-commander.** Lighter dependency surface — no new ranch/scripts/slash-commander entry, no .obsidian/plugins/slash-commander/data.json mutation. The `app.commands.addCommand` API is built into Obsidian core, available at runtime.

**Idempotence guard.** Wrap `app.commands.addCommand` in a `this._commandRegistered` boolean check inside `invoke()`. customjs's startup-script rerun toggle would otherwise register the command twice on hot-reload.

### D. Activity-feed efficiency audit — what we'll actually change

This is a tightening pass, not a rewrite. The 10 audit items break down as:

| # | Concern | Action |
|---|---------|--------|
| 1 | DataArray vs Array boundaries | Verify — current code already calls `.array()` once per query path. No code change unless the audit surfaces a violation. |
| 2 | `_query.inWindow` short-circuit | Verify — current loop returns true on first in-window hit. No code change. Add comment explaining the contract. |
| 3 | `pickLatest` allocations | Verify O(N × K) bound is acceptable for realistic K. No cache change — K is small (≤2 in practice). |
| 4 | Bucket-merge sort | Verify — current code sorts inside the bucket loop, once per bucket. No code change. |
| 5 | metaBuilder/getSubtitle precedence | Verify — current code: metaBuilder branch wins (`if (typeof metaBuilder === "function")` first; `else if (typeof getSubtitle === "function")`). Add an inline comment in the framed renderer documenting the precedence. |
| 6 | groupPreviewBuilder + Part B | **Decision.** `groupPreviewBuilder` fires for groups in the manifest's `defaultClosed[]` set, NOT for groups closed at render-time per persisted state. Rationale: the builder represents a curated default-view affordance; user-toggled state is transient and shouldn't change what the preview shows. Document in the renderer. |
| 7 | DOM allocations in framed renderer | Audit `_renderFramedGroup`. Already uses `createEl` not `innerHTML`. The chevron SVG is currently set via `innerHTML` — keep (it's a one-off, fewer allocations than a hand-built DOM tree). No change unless the audit surfaces flat wins. |
| 8 | `_resolveTimeWindow` native-Date fallback | Keep. The Node test harness uses the fallback. Removing it would require porting the harness to a moment stub everywhere. |
| 9 | Manifest description bloat | Trim to v0.5.x + v0.6.x + v0.7.x narratives only. Older history retained in workshop git log + cycle-history.md. |
| 10 | Harness tightening | Add 3 new runtime asserts: AF-V073-1 (tsKeys with 3 keys present, any-in-window passes), AF-V073-2 (groupPreviewBuilder fires for defaultClosed group, suffix present), AF-V073-3 (Luxon-shaped timestamp goes through Luxon-toFormat path on Dataview-style page). |

Aim is backward-compatible — the v0.7.0 callers (daily@0.13.0 SpaceDailyDashboard) must work unchanged.

## Risks + mitigations

| Risk | Likelihood | Mitigation |
|---|---|---|
| customjs startup-script doesn't fire on a consumer due to plugin-load-order race | Low (precedent: ToDoMigrateInit + ProjectTaskCreateListenerInit both work) | Dataview-readiness retry-with-backoff inside `invoke()`. Notice on hard failure. |
| State file write thrashes on rapid toggle | Low (toggle is user-paced) | No debouncing — last-write-wins is fine for UX state. |
| Part B race: render reads state file mid-write | Low | `app.vault.adapter.read` is sync-on-error → falls back to default-open. UX cost is negligible. |
| Removing the inline `syncAllBoards` call regresses today's first-render kanban data | Mitigated | Init script runs at vault boot, before the first daily-note render in a session. Cache fires on subsequent renders. Worst-case: first render of the day shows stale kanban data; second render shows it correctly. Acceptable. |
| Activity-feed harness AF-V073-3 (Luxon path) requires a Luxon-shaped stub | Low | Stub `toFormat("h:mm a")` directly in the test setup. No real Luxon dep needed. |
| `defaults vs persisted` divergence in groupPreviewBuilder confuses users | Low | Documented decision (item D-6 above). Builder fires for manifest-`defaultClosed[]`, not state-closed. Stable rule. |

## Open questions (resolved)

1. **Q.** Should the state file live under `.obsidian/` or `ranch/`?
   **A.** `ranch/cache/` — `.obsidian/` requires extending the 18-path allowlist (landmine #12) for a runtime-managed file the installer never touches. `ranch/` is the canonical platform-runtime tree and the file is created by user toggling, not by the installer.

2. **Q.** Should state persistence be a new mechanism for reuse across other Sauce surfaces?
   **A.** No. Handoff is explicit: "No new mechanism for state persistence — it's a couple of helper functions added to the relevant files. Keep it lightweight." YAGNI — if a third surface needs it, extract then.

3. **Q.** Does the `groupPreviewBuilder` invocation gating change with Part B?
   **A.** No — see decision D-6 above. Builder fires for manifest-`defaultClosed[]`, not for state-closed groups. Stable contract.

4. **Q.** Should `KanbanStatusSyncInit.invoke()` skip its work entirely if the cache is already populated?
   **A.** Yes — that's how the cache works. The init script calls `syncAllBoards`; the cache short-circuits internally. No extra guard needed in the init class.

5. **Q.** What about kanban-status-sync's existing depends_on relationship to dataview?
   **A.** `depends_on customjs-guard >=1.0.0` is declared. Dataview is implicit — every Sauce vault has Dataview JS enabled (via `applyCommunityPluginData` in v0.21.1). The init script's retry-loop is the runtime safety net.

The smart-connections diagnostic (whether disabling that plugin stops the scroll resets) is independent of this cycle. The architectural cleanup ships either way. If the user reports back mid-cycle:
- **Resets stop with smart-connections OFF:** add a new landmine #24 to `Docs/landmines.md` documenting that dataviewjs blocks re-execute on smart-connections embedding-queue activity. The cycle's fix remains correct.
- **Resets persist with smart-connections OFF:** root cause is elsewhere; document in the result doc + leave the next-cycle handoff to investigate.

Either way the fix shipping in v0.73.0 is value-add (Part A removes our code from the hot path; Part B makes the UX stable regardless of who fires the re-render).
