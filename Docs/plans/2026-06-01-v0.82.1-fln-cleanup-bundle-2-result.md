### FLN-v82-2 — `resetSourceContributions` + per-item-loop wiring (S1/S1.1/S2 + S8/S8.1)

`platform/install.js`'s rules-merge layer was appending rather than deduping `rule_fragments`. Every dogfood install added ~15 path_glob fragments (~40 lines each); HEAD-of-v0.82.0 had 14 duplicate copies of each path_glob — file had ballooned to 7929 lines / 281 entries. The fix introduces a new `resetSourceContributions(contributions, sourceName)` helper that clears all existing contributions from a named source before rewriting them, and wires it into the per-item install loop. The one-time S8 dogfood run applied the cleanup: `ranch/rules/cowork.json` shrank from 7929 → 635 lines / 281 → 22 entries.

**Mid-cycle discovery — landmine #16 + cowork PATCH bump:** S8 ran the full dogfood install but `install.js`'s per-item version-skip guard (line 223) saw cowork's version unchanged (still 0.21.0) and short-circuited the per-item loop, bypassing `resetSourceContributions` entirely. S8 implementer applied the cleanup via an ad-hoc Node script to validate the fix directly. S8.1 added a cowork PATCH bump (0.21.0 → 0.21.1) to clear the version-skip guard and exercise `resetSourceContributions` end-to-end through the real production install path. The original cycle plan called for cowork unchanged; this is a mid-cycle scope expansion. See "Plan-template wisdom" in the sequencing section.

**S0 design pivot:** S0.3 divergent-bodies verification surfaced that `ranch/rules/cowork.json` had TWO scope shapes — the object form (`scope: { path_glob: "...", extends: "..." }`) AND the string form (`scope: "..."`) — not one. The original dedup key design (`(path_glob, extends)` as the unique key) would have catastrophically dropped all string-scope entries on the dedup pass. The design pivoted to per-source-reset semantics: each install-time source gets its contributions cleared + re-written atomically, preserving any contributions from other sources entirely. See "S0 design pivot discovery" in the sequencing section.

**HC cases:** HC-V0821-A1.1a (resetSourceContributions creates from empty), A1.1b (resetSourceContributions overwrites existing same-source entries without touching other-source entries), A1.2 (end-to-end install deduplicated: re-running install against a target with prior cowork contributions produces exactly 1 copy per fragment, not N+1), A1.3 (source isolation: two-source scenario; resetting source A leaves source B's contributions untouched). 4 sub-asserts in `run-helper-cases.js`.

### FLN-v82-3 — parseYamlIsh hyphen-key support (S3/S4)

Pre-existing limitation in `platform/blueprints/cowork/helpers/context-builder-dry-run.js`'s `parseYamlIsh()` function (line 35): the flat-key regex `^([a-z_]+):` silently dropped keys with hyphens. Custom kinds with hyphenated names (e.g., `lharries-whatsapp`, `sharepoint-online`, `my-custom-kind`) could not appear in `user-preferences.md` — `parseYamlIsh` would silently skip those lines and the whole stanza would be ignored. One-line change: widened the regex from `/^([a-z_]+):/` to `/^([a-z_][a-z0-9_-]*):/`.

**HC cases:** HC-V0821-B1.1 (hyphenated top-level key parses correctly), B1.2 (value under a hyphenated key is accessible). 2 sub-asserts in `run-helper-cases.js`.

### FLN-v81-1 — semver-helper extraction (S5)

Three test harness files (`run-cowork-smoke.js`, `run-claude-surface.js`, `run-helper-cases.js`) each hardcoded the regex `/^0\.(8|9|[12]\d)\.\d+$/` as a cowork-version floor assertion — accepting cowork versions 0.8.x–0.29.x. This was a partial mitigation applied inline at v0.81.0's S7 when bumping to 0.20.0 broke the prior `/^0\.(8|9|1\d)\.\d+$/` ceiling. The hardcoded regex pattern was duplicated in 3 files, creating a ceiling at 0.30.x that would require another lockstep 3-file edit.

S5 extracts a new helper `platform/test/helpers/semver-helper.js` exporting `versionAtLeast(version, floor)` (returns true when `version >= floor` per semver major.minor.patch ordering). The 3 cowork-version-floor assertion sites across the 3 test files are refactored to call `versionAtLeast()` instead of the hardcoded regex. The ceiling disappears: adding cowork 0.30.0+ or even 0.100.0 requires no harness edits.

**Note:** this FLN covers floor checks (version >= minimum). Exact-version checks (e.g., `run-cowork-smoke.js`'s V0750-VERSION pin) are a DIFFERENT failure mode — see FLN-v821-1 in "Cycle-specific FLNs surfaced" below.

No HC cases for FLN-v81-1 itself (the existing 3 sites serve as the regression guard; no new assertions added). Refactor-only.

### FLN-v79-5 — CS-MIG-1 manifest-derived counts (S6/S7)

`platform/test/run-claude-surface.js` previously asserted CS-MIG-1's skill-entry count (38) and total-contribution count (47), plus the per-kind sub-counts (38 skill entries, 3 mechanism entries, 6 other entries), as 4 hardcoded magic numbers. Every time a new cowork `claude_surface[]` entry was added, two lockstep edits were required in `run-claude-surface.js` AND the manifest — easy to miss, fragile under version drift.

S6 introduces a `manifest.claude_surface[]` groupBy derivation: the test now reads `platform/manifest.json` at runtime, groups `claude_surface[]` entries by `source`, and derives the expected counts (skill entries = entries with source `cowork`, total = all entries, etc.). S7 removes the 4 hardcoded magic numbers (47/38/3/6), replacing them with the derived values.

**CS-MIG-1 count posture UNCHANGED at 47/38/3/6** — the manifest itself is unchanged; only the assertion mechanic changed. Any future `claude_surface[]` addition automatically updates the expected counts without requiring a harness edit.

**HC cases:** HC-V0821-C1.1 (derived total-contribution count matches manifest), C1.2 (derived skill-entry count matches manifest), C1.3 (derived mechanism-entry count matches manifest), C1.4 (derived other-entry count matches manifest). 4 sub-asserts in `run-claude-surface.js`.

## Sequencing observations + corrections

### S0 design pivot discovery

S0.3 verification surfaced that `ranch/rules/cowork.json` had TWO scope shapes — the object form (`scope: { path_glob: "...", extends: "..." }`) and the string form (`scope: "..."`) — not one. The original `(path_glob, extends)` dedup key would have caused catastrophic data loss on the string-scope class: every string-scope entry would have been dropped on the dedup pass (no `path_glob` key to match on). The design pivoted to per-source reset semantics: each named source gets its contributions cleared + re-written atomically on each install run. Per-source reset is strictly safer than key-based dedup — it never touches contributions from other sources, and doesn't require an explicit unique-key invariant.

**Confirms the value of pre-commit S0 verifications for FLN cleanups touching real-world data.** Any cleanup-style FLN that modifies an accumulator (rules, contributions, fragments) on real production files should include a pre-execution data-shape verification step (S0) to catch design-assumption gaps before committing a buggy fix. Generalized as FLN-v821-3.

### S1 review caught duplicate sub-assert labels

The plan itself had `HC-V0821-A1.1` on two distinct assertions. Surfaced by the spec reviewer + code quality reviewer passes on S1's output. S1.1 (a 1-commit label fix) renamed them to `A1.1a` / `A1.1b` before S2 merged the implementation. The rename was a 5-line change to the test file only; zero behavioral impact.

**Plan-template wisdom:** when a single sub-assert slot exercises two related but distinct invariants (here: "creates from empty" vs. "overwrites-without-cross-source-contamination"), use the a/b suffix convention upfront in the plan. This keeps CI output unambiguous (both `A1.1a PASS` and `A1.1b PASS` are visible individually) and avoids a corrective commit mid-cycle.

### S8 landmine-#16 collision

The design assumed dogfood install would naturally exercise the new `resetSourceContributions` path and validate end-to-end dedup. In practice, `install.js` line 223's per-item version-skip guard short-circuited cowork (its version was still 0.21.0 from v0.82.0), and the per-item loop body — including the new `resetSourceContributions` call — was never reached via the normal install path. S8's implementer applied the cleanup via an ad-hoc Node script to at least validate the cleanup output on disk. S8.1 then added a cowork PATCH bump (0.21.0 → 0.21.1) to clear the version-skip guard and exercise the full production path end-to-end.

**Plan-template wisdom:** when a cycle introduces new logic INSIDE the per-item install loop (e.g., `installItem`-internal logic like `resetSourceContributions`), always plan a co-occurring blueprint version bump on the affected blueprint to clear the version-skip guard during dogfood. Without the bump, the new in-loop code is untested via the production install path even when dogfood "succeeds". Generalized as FLN-v821-2.

### S8.1 also bumped V0750-VERSION assertion

`run-cowork-smoke.js` had a hardcoded `V0750-VERSION` exact-version pin asserting cowork `=== 0.21.0`. S8.1 bumped it from 0.21.0 to 0.21.1 to match the new cowork version. This is a DIFFERENT failure mode from the floor-pins that FLN-v81-1 refactored: `versionAtLeast()` covers floor checks (version >= minimum); exact-version pins (version === X) are a distinct pattern. Exact pins are brittle in a different way — they pass between bumps but break the moment any version moves. Worth a follow-up FLN to audit all exact-version assertions and either (a) extend `semver-helper.js` with a `versionEquals()` export or (b) migrate exact-version pins to floor checks where semantically appropriate. Generalized as FLN-v821-1.

## Cycle-specific FLNs surfaced during v0.82.1 execution

### FLN-v821-1: V0750-VERSION-style exact-version assertions

`run-cowork-smoke.js` carries a hardcoded `V0750-VERSION` exact-version pin asserting `cowork === X.Y.Z`. When cowork bumped from 0.21.0 to 0.21.1 at S8.1, this pin broke and required a manual edit. This is structurally different from the floor-pin problem FLN-v81-1 solved: `versionAtLeast(version, floor)` handles `>=` checks; exact-match checks (`===`) aren't covered.

**Candidate fix:** extend `platform/test/helpers/semver-helper.js` with a `versionEquals(version, expected)` export, and refactor all `=== "x.y.z"` version-assertion sites to call it. Alternatively, audit each exact-pin site and migrate to floor checks where semantically appropriate (a released blueprint at `0.21.1` will never regress to `0.21.0`, so `versionAtLeast("0.21.1")` is often the right check). ~2 stages (inventory + refactor).

### FLN-v821-2: installItem version-skip + new in-loop mechanism interaction

When new logic is introduced INSIDE the per-item install loop (e.g., `resetSourceContributions` added to the cowork `installItem` path), the version-skip guard at `install.js:223` short-circuits the loop body if the blueprint's version hasn't changed since the last install. This means a new mechanism can exist in the code but never execute during dogfood unless a version bump clears the guard.

**Candidate fix:** make the plan template for any cycle touching `installItem`-internal logic include a mandatory co-occurring blueprint PATCH bump as part of the dogfood stage. Alternatively, add a mode flag (e.g., `--force-reinstall`) that bypasses the version-skip guard for a single dogfood run without a version change. Either approach prevents the silent-skip landmine. Document in `Docs/landmines.md` as landmine #23 candidate.

### FLN-v821-3: S0 verification pattern for cleanup FLNs

The v0.82.1 S0.3 divergent-bodies check caught a fundamental design-assumption error (two scope shapes, not one) before committing the buggy dedup key. This averted a potential catastrophic data loss (string-scope entries dropped silently). The pattern deserves codification: any cleanup-style FLN that touches an accumulator (rules, contributions, fragments) on real-world production files should always include a pre-execution data-shape verification step in S0 to enumerate all value shapes the accumulator contains, not just the shapes the cycle author is aware of.

**Candidate fix:** add a "S0 data-shape verification" protocol to the plan-template for cleanup cycles. The protocol: for each file the fix will modify, run a grep/jq audit of the shape-space before writing any code. Map all shapes to the fix design; if any shape is unhandled, pivot the design before S1. ~0 stages (doc-only; add as a plan-template note in the cleanup cycle template or in `Docs/agent-guides/build-test-verify.md`).
