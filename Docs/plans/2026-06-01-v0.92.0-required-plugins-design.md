# v0.92.0 — required-plugins design

## Problem

Two Obsidian community plugins are de-facto required by current sauce behavior but are NOT enforced by the platform installer:

1. **`new-tab-default-page`** (chrisgrieser/obsidian-new-tab-default-page) makes every new tab land on the active daily note in Reading Mode. The `convenience` mechanism already owns adjacent "what happens when you open a tab" behavior (`alwaysOpenInNewTab`, `Cmd+T → daily-notes:goto-today`, `defaultViewMode: preview`), but does not install or configure this plugin. The user has it working in `accuris-sauce` and wants every consumer vault to get the same behavior automatically.

2. **`smart-connections`** (brianpetro/obsidian-smart-connections) writes the `.smart-env/multi/*.ajson` vector index that the `smart-connections-bridge` mechanism reads via its Node CLI (`sc-bridge.js`). Scheduled jobs and skills (`cowork:gather-semantic-related`, `cowork:gather-semantic-memory`) depend on that index. The bridge mechanism ships the reader but does not declare the plugin as a prerequisite, so a vault that subscribes to the bridge without manually installing SC silently produces empty / stale results.

Both gaps are one-line manifest deltas on existing mechanisms.

## Approach

Single MINOR workshop cycle. Two mechanism manifest edits. No new mechanism, no new installer helper, no new file shipped.

| Surface | Before | After | Bump |
| --- | --- | --- | --- |
| `convenience` mechanism | 0.2.4 | 0.3.0 | MINOR (new behavior: 1 plugin + settings) |
| `smart-connections-bridge` mechanism | 0.1.1 | 0.2.0 | MINOR (new behavior: required external plugin) |
| `workshop_version` | 0.91.0 | 0.92.0 | MINOR |

### Why convenience (not a new mechanism)

The `convenience` mechanism already owns the "open-in-new-tab + daily + preview-mode" cluster:
- `app_settings.alwaysOpenInNewTab: true` (platform manifest, but works in concert)
- `hotkeys: [{command_id: "daily-notes:goto-today", modifiers: ["Mod"], key: "t"}]`
- `community_plugin_settings: [{id: "dataview", settings: {…}}, {id: "obsidian-tasks-plugin", settings: {…}}]`

Adding `new-tab-default-page` here is one cohesive cycle. A dedicated mechanism would split related behavior across two files for no gain.

### Why mark `smart-connections` as `required: true`

The `applyCommunityPluginData` helper in `platform/install.js` already understands `external_plugins[].required`: when a downstream `community_plugin_settings[]` entry depends on a plugin that's missing AND marked required, it raises a Notice and aborts rather than silently skipping. Since `smart-connections-bridge` is non-functional without SC's index, hard-fail is the correct posture. No settings entry will exist for SC (install-only), but the required flag still gates the bridge's `applyCommunityPluginData` call.

### Why no SC settings entry

Accuris-sauce's `.obsidian/plugins/smart-connections/data.json` is essentially empty (`installed_at` + `last_version` only). The user's actual SC config is the plugin's own defaults. Baking `community_plugin_settings[]` for SC would:
- carry a schema the SC author may change between plugin minor versions
- fight the plugin's first-run wizard
- require the user to enumerate exact keys they want enforced

Install-only is the lighter-touch correct choice for now. A future cycle can add settings if/when the user identifies specific keys to lock.

## Test plan

Two existing harnesses cover the surface; we add small cases rather than new files.

### `platform/test/run-bootstrap.js`

Existing test: subscribed manifests' `external_plugins[]` are unioned with `foundational_plugins[]`, mapped against the mocked obsidian-releases community-plugins index, and union-merged into `.obsidian/community-plugins.json` via `mergeCommunityPlugins`.

**New cases:**

- **convenience-with-new-tab-default-page** — subscribe convenience, assert `community-plugins.json` contains `new-tab-default-page` AND that the bootstrap fetched the resolved repo from the mocked index.
- **smart-connections-bridge-required** — subscribe smart-connections-bridge, assert `community-plugins.json` contains `smart-connections` AND that the `required: true` flag is preserved through `bootstrap.js`'s plugin-set computation (the install.js downstream gating depends on it).

Mock the community-plugins index entries for both plugin ids so the harness doesn't actually hit GitHub.

### `platform/test/run-helper-cases.js` (covers `applyCommunityPluginData`)

**New case:**

- **convenience-writes-new-tab-default-page-data-json** —
  - Fresh vault: applyCommunityPluginData writes `<vault>/.obsidian/plugins/new-tab-default-page/data.json` with `{"whatToOpen":"daily-notes","filePath":"","mode":"reading-mode","compatibilityMode":false}`.
  - Second run: idempotent (no `.sauce-backup` because no diff).
  - Vault with pre-existing different settings: writes `.sauce-backup` once, overwrites with declared settings.

No new case needed for SC since it has no settings entry — the `external_plugins[]` declaration is fully covered by run-bootstrap.

`npm run test` (or whatever invokes every `platform/test/run-*.js`). No regressions in:

## Out of scope

- **No change to `foundational_plugins[]` in platform manifest.** Both plugins are mechanism-scoped — consumers that disable `convenience` or `smart-connections-bridge` should not get the plugins. Mechanism-scoped is the correct posture.
- **No CSS / snippet / hotkey changes.** new-tab-default-page is self-contained.
- **No SC settings baked.** Install-only (see "Why no SC settings entry" above).
- **No migration logic.** Idempotent install: vaults that already have either plugin installed manually keep their existing settings; the writer is `mergeCommunityPlugins` (union + dedupe) + `applyCommunityPluginData` (diff-with-backup overwrite).
- **No new installer helper.** `applyExternalPlugins` + `applyCommunityPluginData` already do everything we need.

## Risks & mitigations

| Risk | Mitigation |
| --- | --- |
| New tab plugin's data.json schema changes between plugin versions, breaking our baked settings | Schema is small (4 keys) and stable across recent plugin versions. If it ever drifts, `applyCommunityPluginData` writes `.sauce-backup` before overwriting, so user / next cycle can adapt. |
| SC plugin id changes upstream | Obsidian's community-plugins.json id is the canonical key; the SC plugin is well-established and the id `smart-connections` has been stable since 1.x. Low risk. |
| `required: true` on SC causes installer to refuse on existing vaults where SC isn't installed yet | This is the intended posture — but the same install pass also runs `applyExternalPlugins` BEFORE `applyCommunityPluginData` (verified: `install.js:1071` then `install.js:1080`), so SC will be installed in the same run before its required-flag is checked. |
| Workshop self-install fails because the workshop vault somehow lacks one of these plugins | Workshop is a consumer of itself, so the same install pass installs the plugin if absent. Pre-flight: the workshop vault already has both plugins (verified in accuris; workshop dogfood follows same path). |
