# v0.113.0 design — schema registry + linter

## 0. Posture

One JSON file + one Node script + one Markdown guide. Pure additive workshop-side tooling. Zero deps. Matches v0.112.0 conventions exactly — anyone who can read `scripts/workshop-status.js` can read `scripts/lint-schemas.js`.

The registry is **manually authored**. The lint script doesn't try to discover schemas; it asserts that the manually-authored index is internally consistent. That's the minimum-viable shape — orphan-detection and auto-discovery are v0.113.x PATCH candidates if they prove necessary.

## 1. Registry file — `platform/schemas-index.json`

### 1.1 Location

`platform/schemas-index.json` (workshop-relative). NOT `Docs/schemas/` — Docs/ is for prose; the index is a structured artifact consumed by tooling. Sits alongside `platform/manifest.json`.

### 1.2 Top-level shape

```json
{
  "_comment": "Index of every schema-shaped surface in the Sauce workshop. See Docs/agent-guides/schemas.md for authoring guidance. Verified by scripts/lint-schemas.js (release:preflight gate).",
  "schema_version": 1,
  "schemas": [
    { ... entry 1 ... },
    { ... entry 2 ... },
    ...
  ]
}
```

`schema_version: 1` is the version of the **index file format itself**, not of any schema. This lets future cycles evolve the entry shape without breaking the linter.

### 1.3 Entry shape

```json
{
  "id": "cowork-eod-review-sidecar",
  "kind": "sidecar-schema",
  "owner": { "type": "blueprint", "name": "cowork" },
  "source": "platform/blueprints/cowork/data/schemas/eod-review@1.0.0.json",
  "accepted_versions": ["1.0.0", "1.1.0", "1.2.0", "1.3.0", "1.4.0"],
  "validator": "platform/blueprints/cowork/helpers/validate-sidecar-helper.js",
  "consumers": [
    "platform/blueprints/cowork/skills/orchestrators/eod-review/SKILL.md"
  ],
  "notes": "EOD review sidecar. Latest schema_version is 1.4.0 (v0.101.0)."
}
```

Required keys: `id`, `kind`, `owner`, `source`.
Optional: `accepted_versions`, `validator`, `consumers`, `notes`.

### 1.4 `kind` enum

```
sidecar-schema           — JSON Schema doc validating a per-cadence sidecar.
rule-fragment-bundle     — A blueprint manifest's rule_fragments[] block.
contract                 — A platform-level contract (e.g. scheduled-job-contract.json).
data-file                — A blueprint's static data file with implicit schema.
workshop-manifest        — platform/manifest.json or ranch/platform-subscription.json.
learned-state-schema     — A versioned learned-state shape (e.g. learned_weights schema 5).
entity-create-prompts    — A new_entity_buttons[].prompts schema in a blueprint manifest.
helper-read-contract     — Implicit schema a helper assumes about page.X / opts.Y reads.
```

## 2. Lint script — `scripts/lint-schemas.js`

### 2.1 Contract

```
$ node scripts/lint-schemas.js [--check] [--list] [--json] [--verbose]
```

**Default (no flags):** runs `--check` mode (the preflight-suitable contract). Exits 0 on success, 1 on any hard failure.

### 2.2 Validations

**Hard failures (exit 1):**
- Index file missing or unparseable.
- `schema_version` ≠ 1 (future-format mismatch — refuse to run until the script is updated).
- Duplicate `id` across entries.
- Missing required key (`id` / `kind` / `owner` / `source`).
- `source` file does not exist on disk.
- `validator` is set but file does not exist.
- `kind` not in the enum.
- `owner.type` not in `{blueprint, mechanism, workshop}`.
- `owner.type === "blueprint"` but `owner.name` is not in the blueprint manifest's name field.
- `owner.type === "mechanism"` but `owner.name` is not in the manifest's mechanism list.

**Soft warnings (exit 0 but print to stderr):**
- `consumers[]` entry path does not exist.
- `accepted_versions` set but `source` file's JSON Schema `schema_version.enum` doesn't include all of them (drift check, when the source is a JSON Schema).

### 2.3 Output modes

- `--check` (default): summary only. On success: `lint-schemas: N schemas indexed, 0 issues`. On failure: per-failure line + total count + exit 1.
- `--list`: `<id> · <kind> · <owner.type>:<owner.name> · <source>` one per line. Exit 0 regardless (informational).
- `--json`: `{ summary: {...}, schemas: [...validated...] }`.
- `--verbose`: per-entry validation lines.

### 2.4 Implementation notes

- Pure node, zero deps. `fs.readFileSync` + `path` only.
- No `glob` — paths are explicit in the index.
- ANSI color via raw escapes (`\x1b[31m...\x1b[0m`); auto-disabled for non-TTY or `--json`.
- ~200 LOC budget.

## 3. Schemas guide — `Docs/agent-guides/schemas.md`

### 3.1 Scope

Short (~150 lines) doc covering:

1. **What schemas exist in Sauce** — the 8 surface categories from the brief.
2. **The registry index** — where it lives + entry shape + `kind` enum + how to add a new entry.
3. **The linter** — `npm run lint-schemas` + flags + when it fires (preflight + manual).
4. **When designing a new feature**:
   - First, `npm run lint-schemas -- --list` to see what already exists.
   - Read the schema sources the lint surfaces for any contract you'll touch.
   - If you're adding a new schema, add it to the index in the same commit.
5. **Schema versioning conventions** — when to bump `accepted_versions[]`, when to mint a new entry.
6. **Cross-links** — to `build-test-verify.md` (preflight context), `landmines.md` (contract bump rules, esp. #16 + #20).

## 7. Out-of-scope (explicit)

- **No runtime validation.** Schemas aren't checked at install / render / fire time.
- **No consumer-side mechanism.** Workshop-only.
- **No new schema files.** Pure index of existing surfaces.
- **No auto-discovery.** Manual seeding only.
- **No `sauce schemas` CLI verb.** npm script only (brew tap stale).
- **No version-pin drift detection** (e.g. "helper code references schema vX but index says vY"). That's a v0.113.1 PATCH candidate.
- **No orphan detector** (schemas in known dirs but not in the index). v0.113.x PATCH.
- **No `workshop-status.js` schema row.** Stretch; left out to keep cycle bounded.

## 8. Decisions locked at brief

1. **Manual seeding > auto-discovery.** Auto-discovery makes the registry implicit; manual seeding makes it intentional. We get exactly what we choose to track.
2. **Workshop-side only.** Brew tap is stale; consumer-visible mechanism is a separate cycle (Stage B → v0.114.0+).
3. **One JSON file > many.** Splitting per-blueprint adds discovery cost; consolidating to one file makes the linter trivial.
4. **`schema_version: 1` on the index itself.** Future-proofing for entry shape evolution.
5. **Soft warnings for stale consumers.** Hard failure would block PRs that touch a consumer without updating the index. Soft warning surfaces drift without blocking.
