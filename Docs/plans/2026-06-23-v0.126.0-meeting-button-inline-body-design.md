# Meeting button inline_body parity — design (v0.126.0)

## Mission

v0.125.0 shipped `MeetingLeafActions` and wired it into the **Templater** `Meeting.md` template + the install heal. It did **not** update the entity-create button's `inline_body` in `meetings/manifest.json`. The button is the primary UI path for creating a meeting (the "New Meeting" button rendered on the day's Meetings Hub) — so newly button-created meetings still get the bare scaffold (frontmatter + SpaceNavButtons) and **no MeetingLeafActions row**. Heal eventually injects the row on the next `sauce update`, but new notes feel broken until then, and they still miss every SectionLabel block (Attendees / Agenda / Notes / Action Items) that the Templater path supplies.

This cycle adds **structural parity** between the two creation paths by promoting the button's `inline_body` to include the same static-renderable chrome the Templater template emits: MeetingLeafActions plus the four SectionLabel section markers.

## Why now

- Real-user repro: a meeting created on 2026-06-23 via the button (`Product Technology Happy Hour-2026-06-23.md`) landed as `frontmatter + SpaceNavButtons` only. No action row, no sections, no agenda. Heal back-filled MeetingLeafActions on the next `sauce update` but everything else stayed missing — silently surprising.
- The drift is structural (two creation paths, only one updated) and will keep happening every time a new chrome block lands. Fixing it once narrows the surface; leaving it means every future `Meeting.md` change needs a "did you also update inline_body?" checklist item.
- Heal cannot save us here: heal is conservative + insert-only by design, so it cannot back-fill SectionLabel sections without risking content clobber. The button is the right place to render them at creation time.

## Decided

- **Promote inline_body to full chrome parity** — emit the four SectionLabel blocks (Attendees / Agenda / Notes / Action Items) plus the MeetingLeafActions block, in the same order as `Meeting.md`. The Templater-only pieces (attendee suggester loop, attendee bullet list, attendee-driven `## Attendees` chip block) are deliberately left **only** in the Templater path — entity-create cannot run Templater syntax and the attendee picker UX belongs to that flow.
- **No new Templater syntax in inline_body.** Every block added is a static `dataviewjs` invocation. The button's frontmatter_template already carries `attendees: []` + `people: []` — empty arrays are the correct default for button-created notes (the user did not pick attendees at creation, they will use the Edit Attendees leaf action).
- **Block order matches `Meeting.md`** exactly: Breadcrumb already lives in inline_body? No — and that is another v0.125.0 omission. Add the Breadcrumb block before SpaceNavButtons to match note-chrome standard (the heal back-fills Breadcrumb on existing notes; the button path should emit it at creation too).
- **Frontmatter unchanged.** Skip any new fields. `attendees`, `people`, `project` already exist; `tags` already exists; `summary` already exists.
- **Bump meetings 0.10.0 → 0.11.0** (MINOR — new behavior at the creation path; backward-compatible with consumers because the new blocks are additive).
- **Bump workshop 0.125.0 → 0.126.0** (MINOR — blueprint behavior change).
- **No new mechanism, no new helper, no new tests.** The static helpers tested in v0.125.0's `run-meeting-leaf-actions.js` are unchanged. Manifest-schema asserts in `run-helper-cases.js` continue to gate manifest shape.
- **Heal already covers existing notes** — `applyNoteChromeHeal` injects MeetingLeafActions into pre-v0.125.0 meetings, and v0.124.0 added Breadcrumb back-fill. No heal changes needed; the SectionLabel sections explicitly do NOT get back-filled (content-safety — heal cannot tell a note is "empty enough" to insert sections without risking clobber, and existing meeting notes likely have their own ad-hoc sections already).

## 1. The patch

Single file: `platform/blueprints/meetings/manifest.json`.

`new_entity_buttons[0].inline_body` becomes (block order matches `Meeting.md` template lines 67–110):

````
```dataviewjs
await dv.view("ranch/views/customjs-guard", { class: "Breadcrumb" });
```

```dataviewjs
await dv.view("ranch/views/customjs-guard", { class: "SpaceNavButtons" });
```

```dataviewjs
await dv.view("ranch/views/customjs-guard", { class: "MeetingLeafActions" });
```

```dataviewjs
await dv.view("ranch/views/customjs-guard", { class: "SectionLabel", args: [{ text: "Attendees", top: true }] });
```

```dataviewjs
await dv.view("ranch/views/customjs-guard", { class: "SectionLabel", args: [{ text: "Agenda" }] });
```

-

```dataviewjs
await dv.view("ranch/views/customjs-guard", { class: "SectionLabel", args: [{ text: "Notes" }] });
```

```dataviewjs
await dv.view("ranch/views/customjs-guard", { class: "SectionLabel", args: [{ text: "Action Items" }] });
```
````

Notes on what is intentionally NOT here:

- **No attendee chip-rendering block** (`PeopleRendering.renderMentionList`) — that block in `Meeting.md` works off the suggester-loop's pre-populated attendees frontmatter. For a button-created meeting, attendees start empty; the user wires them up via Edit Attendees and the chips appear in subsequent renders only if a chip-rendering block exists in the note. We add it here so the experience matches Templater-created notes the moment the user fills attendees in.
- Actually, **add the PeopleRendering chip block** under the Attendees SectionLabel (parity with `Meeting.md` lines 83–89). It is a static `dataviewjs` block; the user gets an empty chip row at creation, populated on Cmd+R after Edit Attendees. **REVISED:** include it.

Revised inline_body order:

````
Breadcrumb
SpaceNavButtons
MeetingLeafActions
SectionLabel "Attendees" (top: true)
PeopleRendering.renderMentionList
-
SectionLabel "Agenda"
-
SectionLabel "Notes"
SectionLabel "Action Items"
````

(The `-` placeholders mimic the Templater template's empty-bullet stubs for Agenda/Attendees — gives the user a single-dash starting point.)

Manifest description append: a `v0.11.0 PATCH` clause documenting the parity bump.

Manifest `version` bump: `0.10.0` → `0.11.0`.

## 5. Open follow-ups (NOT this cycle)

- Other entity-create buttons (to-do, scratch, project sub-types) — audit their inline_body against the Templater templates for the same drift class; defer to a v0.127.0 audit cycle if drift is widespread.
