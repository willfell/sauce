## What shipped

v0.77.0 replaces v0.76.0's namespace-regex MCP detection with a
tool-pattern-signature model that is robust against any future MCP
server naming — including UUID-namespaced enterprise gateways like
Outlook M365. Workstream B reworks `mcp-skill-map.json` to schema v2.0.0
(per-capability `tool_patterns[]` + `required_count`) and adds the
`detectCapabilities` helper that classifies each MCP namespace by
inspecting its tool NAMES rather than its namespace string. Workstream C
ships fully-adaptive unknown-MCP handling: namespaces that don't match
any known capability surface in an interactive loop where the user
classifies them as known-override (use one of the 4 known question sets)
or custom (define a new kind inline with a free-text `what_matters`
note); the YAML composer + parser learned the `key: |` literal-block
form to round-trip multi-line `what_matters` content byte-stably.
Workstream D + E land the v1 → v2 schema migration: the `mcps.gmail`
key is renamed to `mcps.email`, `mcps.imessage` is renamed to
`mcps.chat`, and the helper applies these renames declaratively from
the v2 schema's `rename_from_v1` field on every load. Workstream F's
schema-validation work was folded into S1/S2 — every load now asserts
the `mcp-skill-map.json` schema_version equals `2.0.0` before
classification proceeds.

The four workstreams unblock the accuris machine's cowork:context-builder
invocation, which previously matched zero MCPs (the Outlook UUID
namespace defeated v0.76.0's regex, and Accuris-internal MCPs — ADO,
Backstage, NewRelic — were unhandled). With v0.77.0, Outlook M365 is
detected as `calendar + email + chat` from one namespace via the
capability-subset model; the three internal MCPs surface in the
unknown-MCP loop with their tool lists for user classification.

Workshop 0.76.0 → 0.77.0. Cowork 0.15.0 → 0.16.0. 11 new harness cases
all in `run-cowork-smoke.js` — no new harness files; file count stays
at 23.

## Per-workstream narrative

### Workstream B — tool-pattern detection (`detectCapabilities` helper)

**What shipped:** `platform/blueprints/cowork/content/context/mcp-skill-map.json`
schema rewritten to v2.0.0. The file now carries top-level
`schema_version: "2.0.0"` and a `capabilities[]` array (4 entries:
calendar, email, chat, finance — `email` and `chat` are the v2 renames
of v1's `gmail` and `imessage`). Each capability declares
`tool_patterns[]` (regex literals matching tool NAMES like
`list_events`, `create_event`, `send_email`) and `required_count` (the
minimum number of distinct patterns a namespace must satisfy to qualify
as that capability). The known catalogue stays Minimum-4 (calendar /
email / chat / finance); expansion is a v0.78.0 candidate. The
companion helper `detectCapabilities(mcpToolMap)` (added to
`context-builder-dry-run.js`) iterates each namespace's tool list,
counts pattern matches per capability, and returns a flat
`{capability: [namespace, ...]}` mapping plus a `served_by[capability]`
breadcrumb recording which namespace contributed each capability hit.
HC-V0770-A1..A3 cover the new shape (single-namespace single-capability;
single-namespace multi-capability via Outlook UUID synthetic; UUID
namespace successful match).

**What we learned:** v0.76.0's regex matched literal vendor names
(`Google_Calendar`, `Gmail`, `Apple_iMessage`, …). The accuris machine's
real namespace was a UUID with no vendor string to match. Pattern
detection on tool NAMES side-steps the namespace string entirely —
`list_events + create_event` identifies a calendar capability whether
the namespace is `Google_Calendar`, `mcp__outlook__abc-123-uuid`, or
`mcp__internal_corp__xyz`. The capability-subset model is the second
half: a single MCP namespace can satisfy `calendar` AND `email` AND
`chat` simultaneously by having tools matching all three pattern sets
(Outlook M365 does exactly this). `served_by` records the namespace
behind each match so the orchestrators can route follow-up calls to
the right server. Cleaner than per-MCP classification — the data shape
matches reality (one server, multiple capabilities) instead of forcing
a one-to-one model that breaks the moment an enterprise gateway shows
up.

### Workstream C — custom-kind + unknown-MCP handling

**What shipped:** `cowork:context-builder` SKILL.md (S7) gains an
"unknown-MCP loop" phase between detect and interview. For every
namespace that produced zero capability hits, the skill surfaces the
namespace plus its tool list and asks the user one of three actions:
(1) classify as known-override (route to one of the 4 known question
sets — useful when a namespace exposes a known capability under a
non-standard tool-name vocabulary), (2) classify as custom kind (define
a new kind name + a free-text `what_matters` paragraph describing what
matters about it), or (3) skip. Custom-kind data shape: per-MCP block
in user-preferences.md gets a `kind: custom`, `kind_name: <user-typed>`,
and a multi-line `what_matters: |` literal-block YAML field. The
composer + parser (`composeYaml` / `parseYamlIsh` in
`context-builder-dry-run.js`) learned the YAML `key: |` literal-block
form — required for byte-stable round-trip preservation (HC-V0770-C2:
re-run with `per_mcp_actions.<custom>: 'Skip'` must produce an
identical file). HC-V0770-C1..C4 cover the four cases: custom-kind
inline definition, custom-kind round-trip preservation, known-override
routing, and skip behavior.

**What we learned:** The YAML literal-block extension was the
load-bearing detail. v0.76.0's compose handled flat scalars
(`key: value`) and arrays (`key: [a, b]`); the `what_matters` field
needed to be multi-line free text, which forced the `key: |` form. The
implementation: composer emits `key: |\n  line1\n  line2\n`; parser
detects the `|` sentinel and reads continuation lines based on
indentation. Round-trip stability matters because HC-V0770-C2 re-runs
context-builder with `per_mcp_actions.<custom-kind>: 'Skip'` and asserts
the file is byte-identical to the first run — any whitespace drift
on the literal block breaks the assertion. Lesson: free-text
preferences need YAML literal blocks, not scalars; round-trip
byte-stability requires symmetric whitespace discipline at both ends.

### Workstream D + E — v1 → v2 schema migration (`migrateV1ToV2`)

**What shipped:** S3 added failing tests for the migration:
HC-V0770-D1 covers a v1 file with `mcps.gmail` + `mcps.imessage`
loaded against a v2 schema — the helper must rename keys to
`mcps.email` + `mcps.chat` on load, preserving all nested per-MCP
fields. HC-V0770-E1 covers the temp-vault test path (no materialized
vault copy, no workshop blueprint dir) — the helper must fall back to
its `__dirname/../content/context/mcp-skill-map.json` to resolve the
schema. S4 implemented `migrateV1ToV2(parsed, schema)`: a one-pass
function that consults the v2 schema's `rename_from_v1` field on each
capability (`{ "email": { "rename_from_v1": "gmail" }, "chat": { "rename_from_v1": "imessage" }, ... }`)
and applies each rename if the old key exists in the parsed user-prefs.
Runs at the top of `run()` before existing merge logic. Both
HC-V0770-D1 and HC-V0770-E1 went green.

**What we learned:** Migration inside the helper is essentially free
once the renames are declarative. The v2 schema's `rename_from_v1`
field is the source of truth — no separate migration command, no
imperative migration code, no version-checking branch. Each capability
that was renamed in v1 → v2 declares its old name; the helper applies
all renames in one pass. Adding a future v3 capability with a different
old name is one schema edit, not a code change. The helper-location
fallback (Workstream E1) was a separate insight: the
context-builder-dry-run.js helper needs to resolve `mcp-skill-map.json`
from one of three locations (consumer vault `spice/cowork/content/context/`;
workshop `platform/blueprints/cowork/content/context/`; helper's own
`__dirname/../content/context/`) — the third is the fallback that
makes tests work in a temp vault with no materialized blueprint copy.
Production deploys always satisfy one of the first two paths; the
third is purely for testability.

### Workstream F — schema v2.0.0 validation

**What shipped:** Folded into S1 (failing test) + S2 (implementation).
The helper now asserts `parsed.schema_version === "2.0.0"` on every
`mcp-skill-map.json` load before classification proceeds; missing or
mismatched schema_version throws. HC-V0770-B1 covers the assertion;
HC-V0770-B2 covers a malformed schema (missing required field) failing
the validator.

**What we learned:** Schema validation is cheap and load-bearing.
Without it, an out-of-date `mcp-skill-map.json` (left over from a
v0.76.0 install) silently mismatches v2 expectations and the helper
either crashes deep in detection or returns garbage. The early
schema_version assertion is one line that catches the entire class of
"stale schema file" bugs in installation residue. v0.78.0 candidate:
expand the validator to per-capability field requirements (require
`tool_patterns` non-empty, `required_count >= 1`, etc.) rather than
just the top-level version.

## Lessons learned

1. **Capability-subset model.** v0.76.0 assumed each MCP namespace was
   ONE kind — a one-to-one mapping between namespace and capability.
   Real-world enterprise gateways break this model: Outlook M365 (and
   most internal corporate MCP servers) bundle multiple capabilities
   under one namespace. The v0.77.0 set-membership matching lets the
   same namespace satisfy `calendar` AND `email` AND `chat`
   simultaneously, with `served_by` recording which namespace each
   capability came from. This is cleaner than per-MCP classification
   because it matches the data: one server, many capabilities. Lesson:
   when modeling a many-to-many relationship as one-to-one, the model
   breaks the moment a counterexample shows up — better to embrace the
   many-to-many shape up front, even if the initial known set is all
   one-to-one.

2. **Tool-pattern detection vs namespace regex.** v0.76.0's regex
   matched literal vendor names (`Google_Calendar`, `Gmail`,
   `Apple_iMessage`, `Plaid`). The accuris machine's UUID namespace
   defeated this entirely — no vendor string to match against. v0.77.0
   detects on tool NAMES (`list_events` + `create_event` identifies a
   calendar capability regardless of namespace). Tool naming is more
   stable than namespace naming because tools live inside the MCP
   protocol where naming conventions are dictated by what the tool
   does; namespaces are vendor-controlled and arbitrary (UUIDs, vendor
   prefixes, internal-product names, etc.). Lesson: detect on the
   stable surface of an API, not the volatile one.

3. **YAML literal blocks needed for free-text fields.** v0.76.0's
   compose handled flat scalars (`key: value`) and inline arrays
   (`key: [a, b]`). Workstream C's `what_matters` field is multi-line
   free text — required adding the `key: |` literal-block YAML syntax
   to both `composeYaml` and `parseYamlIsh` (the round-trip needed to
   be byte-stable for HC-V0770-C2's Skip re-run preservation test).
   Lesson: free-text content needs different YAML primitives from
   structured scalars; the parser and composer must be symmetric to
   preserve byte-stable round-trip.

4. **Migration inside the helper is essentially free.** `migrateV1ToV2`
   is one new function that runs at the top of `run()` before the
   existing merge logic. The rename hints live in the v2 schema's
   `rename_from_v1` field — declarative, no separate migration command
   needed, no imperative version branching. Adding a hypothetical v3
   migration would mean adding a `rename_from_v2` field on whichever
   capability gets renamed; the helper picks it up automatically.
   Lesson: declarative migration via schema metadata is cheaper than
   imperative migration code, and zero-friction at the consumer side
   (auto-applied on first load).

5. **Helper-location fallback for testability.** HC-V0770-E1's temp
   vault has neither the materialized vault copy (no
   `spice/cowork/content/context/mcp-skill-map.json`) nor the
   workshop's `platform/blueprints/cowork/content/context/mcp-skill-map.json`
   (the test runs in a synthetic temp dir, not the workshop). Adding
   a `__dirname/../content/context/mcp-skill-map.json` fallback to the
   helper's map-resolution logic lets the test pass without polluting
   the fixture. Production deploys always have one of the first two
   paths available; the third is purely for testability. Lesson:
   helpers that read companion files from a vault should fall back to
   their own `__dirname` siblings — this makes them self-contained for
   testing without breaking the consumer-vault path semantics.

6. **TDD across 4 workstreams held.** All 3 failing-test stages (S1,
   S3, S5) landed with expected FAILs; all 3 implementation stages (S2,
   S4, S6) turned them green. The known-kind-rename test (HC-V0760-F1+F2
   update in S2's Task 4) caught a downstream inconsistency in the
   existing test before it could ship — when the v1 `gmail` key got
   renamed to v2 `email`, the older HC-V0760 assertions still referenced
   `mcps.gmail` and had to be updated lockstep. Lesson: when renaming
   a structural field touched by existing tests, the field-rename
   commit MUST update the pre-existing test assertions in the same
   stage; otherwise the next preflight catches it and a separate
   maintenance commit is required.

  sections.

  consumption work; the small READ-side contract that the 5
  orchestrators call into.

**Adaptive-detection refinement:**
- **Expand known catalog** — current catalog is intentionally Minimum-4
  (calendar / email / chat / finance). Strong candidates for v0.78.0:
  drive (file storage MCPs — Google Drive, Dropbox, S3),
  code-platform (GitHub / GitLab), project-tracker (Linear / Jira /
  ADO), monitoring (NewRelic / Datadog / PagerDuty). The custom-kind
  path covers everything else for now.
- **Promote frequently-used custom kinds to known** — Once observed
  usage data exists (post-v0.77.0 deployment), promote the most-common
  user-defined custom kinds into the known catalog so they get
  hand-curated question sets instead of free-text `what_matters`.

  vault's user-preferences.md to declare it inherits from another
  vault's preferences (`inherits_from: ../other-vault/spice/cowork/context/user-preferences.md`).
  Useful for users with multiple vaults sharing personality + cross-cutting
  priorities. Would need a resolution-order spec.
