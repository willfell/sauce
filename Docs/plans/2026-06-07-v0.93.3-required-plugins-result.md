## CONTRACT REDEFINED — what v0.93.3 actually delivers vs. what the design promised

**The original design assumed `applyExternalPlugins` in `platform/install.js` installs plugins from any mechanism's `external_plugins[]`. This is wrong.** `applyExternalPlugins` (install.js:2693) is explicitly *"a detection-and-surface-up helper, not a remediation step"* — it reads `.obsidian/community-plugins.json` and emits a Notice + history-warning for any required dep that is not currently enabled. It never calls `fetchPlugin`.

Actual plugin install lives in `phaseFetchPlugins` (`platform/bootstrap.js:120`), which iterates `mf.external_plugins || []` and calls `fetchPlugin` per id. But this runs only during **fresh-vault bootstrap**, not during `sauce update` (platform/install.js) invocations.

**Concrete consequence:**
- **Fresh consumer vaults** going through `sauce bootstrap` → both plugins WILL be installed and (for new-tab-default-page) configured automatically, because phaseFetchPlugins iterates `external_plugins[]` from every subscribed mechanism's manifest.
- **Existing consumer vaults** running `sauce update --bump-pins` → both plugins will NOT be installed automatically. The user will see:
    - `[Notice] applyCommunityPluginData: convenience prereq plugins missing (new-tab-default-page); skipped`
    - `[Notice] smart-connections-bridge requires plugin smart-connections: (no reason). Install + enable in Settings → Community plugins.`
  The user must then install both plugins manually via Settings → Community plugins. After install + enable, the next `sauce update` (or even another non-update install pass) will run `applyCommunityPluginData` to scaffold new-tab-default-page's `data.json`.

**Dogfood reflects this contract:** the workshop self-install passed (exit 0) but the workshop's own `.obsidian/community-plugins.json` does NOT include `new-tab-default-page` or `smart-connections` post-install. That's the honest existing-consumer state; closing it requires v0.94.0 work (carry-forward).

## Lessons

- **Verify the helper does what the design assumes BEFORE designing the manifest delta.** The design's whole architecture rested on "`applyExternalPlugins` installs plugins listed in any mechanism's `external_plugins[]`" — one grep + one read of install.js would have surfaced the gap before the brainstorm closed. Settings-shape verification for new-tab-default-page was done well; helper-behavior verification was not. Cost: mid-cycle redefinition + a carry-forward.
- **TDD against the real install path, not just bootstrap.** BS18 + BS19 pass because they invoke `runBootstrap` directly with `skipInstaller: true` — they exercise `phaseFetchPlugins`, not `applyExternalPlugins`. They establish a regression net for the fresh-bootstrap path but DON'T catch the install.js gap. A future v0.94.0 cycle will need cases that invoke `platform/install.js` end-to-end on an existing vault to validate the auto-install extension.
- **Settings-shape verification against an installed vault before authoring `community_plugin_settings[]`.** new-tab-default-page's data.json schema is small (4 keys) and was empirically verified against accuris-sauce before the manifest edit. Avoided guessing. `applyCommunityPluginData` already correctly skips when the plugin dir is missing — the helper's prereq gate is doing exactly what it should.
- **`required: true` is documentation-of-intent** for mechanisms that don't currently use the gated-helpers (`applyVendoredThemes` / `applyAppearance` / `applyStyleSettings`). The flag is real and consumed by `_externalPluginsSatisfied`, but for the bridge today it doesn't change behavior — it only adds a more prominent Notice via `applyExternalPlugins`. Forward-looking, not behavior-changing.
- **In-cycle bump rule (landmine #16) was not surfaced in the plan.** Hardcoded VERSION-pin assertions across 5 prior cycles' HC blocks all required "0.93.2" → "0.93.3" bumps. This is standard per-cycle hygiene but the plan didn't list it as an S1.4 sub-step. Captured here for future cycles' plan-writing: any package.json/workshop_version bump implies a sweep across HC-V0*-VERSION-* assertions.
- **`ranch/platform-subscription.json` lockstep with workshop manifest is required for self-install dogfood to pass.** The install correctly refuses to "downgrade" a mechanism that the subscription pins to an older version. For workshop dogfood, this means S1.4-equivalent bumps must also land in ranch/platform-subscription.json (no `sauce update --bump-pins` runs on the workshop itself; manually edit). Captured as an implicit step that the plan should have called out.

## Carry-forward

- **v0.94.0 candidate: `external_plugins[]` auto-install from `platform/install.js`** (Recommended next). Extend the install pass to call `fetchPlugin` for any mechanism's `external_plugins[]` whose plugin dir is absent, mirroring `phaseFetchPlugins` semantics. Likely the right home is a new `applyExternalPluginInstall` step that runs BEFORE `applyExternalPlugins` (the existing warning helper). New TDD cases: an existing-vault scenario where the plugin dir is absent → after install, dir is present + community-plugins.json includes id. Closes the v0.93.3 gap for existing consumers.
- **Echoes-warning reword** — `[!warning]+ Semantic index not available` should be reworded to "Semantic memory warming up — Echoes will appear once Smart Connections has indexed (typically 10-30 min on first run)." Touches `cowork:gather-semantic-related` contract; its own design discussion. Bundle into v0.94.0 if scope permits.
- **Five queued sub-themes from the post-v0.93.2 brainstorm** still in flight: (1) platform de-personalization PATCH; (2) connector / knob ergonomics MINOR; (4) cross-machine wrapper alignment; (5) vault-config schema migration. Carry into the handoff.
- **Future option:** bake specific Smart Connections settings (model choice, embed exclusions, etc.) into `community_plugin_settings[]`. Deferred until a specific configuration drift problem appears.
