# v0.119.1 — recurring-section merge + materialize_once PATCH — result

## Shipped

PATCH cycle closing two consumer bugs surfaced on the accuris vault immediately post-v0.119.0
deploy. Both bundled into v0.119.1 per user direction ("resolve within the next path that
you've mentioned").

### Bug 1 — Duplicate "Recurring Today" SectionLabel blocks

**Symptom (accuris, 2026-06-16 18:56 UTC):** After v0.119.0 deploy + sentinel heal, user created
a new recurring task (`get your life together`) via the +New Task dialog. On next render of
`ToDo-2026-06-16.md`, the daily now shows TWO "Recurring Today" SectionLabel blocks — one with
the new task, the other with the pre-existing two tasks (`test recurring task` +
`Monitor this Dashboard`).

**Root cause:** `ToDoDailyRecurring.insertRecurringIntoToday` ALWAYS inserts a fresh SectionLabel
block at the position immediately after the `ToDoDailyRecurring` dataviewjs anchor — it never
checks whether a "Recurring Today" block already exists. v0.7.0's additive sentinel correctly
materializes only NEW registry entries (one per second render call), but each call routes through
the same insert-new-block path. Two materialize calls → two blocks.

**Fix:** `insertRecurringIntoToday` now detects an existing "Recurring Today" SectionLabel block
via `RECURRING_LABEL_RE`. When found: append new task lines to the end of the existing section
(boundary detected via the next dataviewjs block / next H1-H2 / EOF). When absent: fall through
to original create-new-block behavior. Idempotent at the line level — repeated calls with the
same lines emit them once each, no duplication.

**Heal migration:** NEW `mergeDuplicateRecurringSections` in `platform/install.js` (wired into
the `applyToDoBlueprintMigration` pipeline immediately after `applyRecurringSentinelV070Migration`).
Walks every `spice/to-do/**/ToDo-*.md`. For each daily with ≥2 "Recurring Today" SectionLabel
blocks: keep the first; collect task-line bodies from every subsequent block; append them to the
first block's section; drop the redundant SectionLabel blocks. `.sauce-backup/<ts>/` snapshot
before write. Idempotent. Failure-loud per-file.

### Bug 2 — Recurring Tasks registry overwrite on every install (pre-existing, since v0.116.0)

**Symptom:** During the v0.119.0 deploy chain, `Recurring Tasks.md` was overwritten on accuris +
headspace with the empty template; user's accumulated recurring task entries went to
`.bak`. (Restored manually post-deploy.)

**Root cause:** The to-do manifest's `{{module_directory}}/Recurring Tasks.md` files[] entry
(added in v0.116.0, commit `4365d8ca`) was declared WITHOUT `materialize_once: true`. The
installer therefore re-materializes the file from source whenever the source SHA differs from
the installed file's SHA. Any cosmetic template update (v0.5.0 SectionLabel migration, v0.5.1/.2/.3
polish, v0.7.0 this cycle) silently nukes user content.

**Fix:** Added `"materialize_once": true` to the manifest entry. Once a user has a populated
registry, subsequent installs leave it alone. Future template changes need migrations (the same
pattern the daily-note template + cowork templates follow).

## Carry-forwards

- **`cowork:doctor`-style scan** for other `files[]` entries declaring user-mutable destinations
  WITHOUT `materialize_once: true`. The to-do registry case is fixed; an audit cycle would catch
  any similar latent traps across other blueprints (e.g., per-engagement memory files, user-edited
  templates, etc.).
- **Capability promotion** — `insertRecurringIntoToday`'s merge logic is bespoke per blueprint;
  a shared "append-to-section-or-create" primitive in `platform/customjs/` would let other widgets
  reuse the same fix shape.
- **Smoke-checklist line item** in `Docs/agent-guides/smoke-checklists/to-do.md`: verify creating
  a 2nd, 3rd recurring task on the same daily lands in the same "Recurring Today" block.

## Lessons captured

1. **v0.7.0's additive sentinel + insertRecurringIntoToday's create-new-block were a contradiction.**
   The sentinel correctly materializes new tasks on each call; the insert correctly anchors at the
   ToDoDailyRecurring dataviewjs block. Together they produce duplicate blocks. The fix to one
   half (v0.7.0 sentinel) silently broke the other (insert never assumed multi-call). Lesson: when
   changing a function's invocation pattern from "once per day" to "many times per day", audit
   ALL downstream functions in the chain for the assumption. Listed as carry-forward in v0.119.0
   under "Lessons" #2 (plan-code shipped a self-test breakage twice) — the same shape happened here:
   plan + design assumed `insertRecurringIntoToday` was idempotent at the block level. It is not.
   Adding a HC-V0119-INSERT-* family would have caught this at preflight.

2. **`materialize_once` is opt-in but should be the default for user-mutable destinations.** The
   to-do registry was declared in v0.116.0 without the flag; the bug went undetected for FOUR
   workshop versions (0.116.0 through 0.119.0) because most users didn't accumulate enough
   recurring tasks for the loss to be visible. A future cycle should audit every `files[]` entry
   whose dest is under `{{module_directory}}/` (user content space) and either add
   `materialize_once: true` OR convert to a migration-based materialization.

3. **Heal migrations need golden-fixture coverage that mirrors the production bug shape.**
   HC-V0119-MERGE-1..7 use a fixture that exactly mirrors accuris's broken daily (two SectionLabel
   blocks, the same task lines). The fixture is now committed and serves as the regression test
   forever. Future heal-migrations should follow the same pattern: capture the production-broken
   shape as a fixture, then assert the heal produces the desired shape AND is idempotent on a
   second run.
