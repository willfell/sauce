# v0.118.0 — recurring-task fix + flexible task creation (MINOR)

## Root cause (investigated + reproduced 2026-06-16)

**Symptom (user report):** On the +New Task dialog's **Recurring** tab, the Create button never enables — "no matter what I do, it will not be clickable." v0.116.1 claimed to fix this (forward-declared `updateSubmit` closure binding); it did not, because that was a misdiagnosis.

**Root cause:** The Obsidian customJS plugin stores **instances** under `window.customJS.<ClassName>` (proven: `SectionLabel.render`, `DocSearch.matches`, `FinanceMath.fmtMoney` are all **instance** methods and work in production; the `customjs-guard` dispatches `customJS[Class][method].call(klass, …)`). But `RecurrenceParser` declares its public methods as **`static`** (`isSupported`, `matches`, `_parse`). A static method is on the constructor, NOT the instance — so `window.customJS.RecurrenceParser.isSupported` is `undefined`, and calling it **throws** `TypeError: …isSupported is not a function`.

In the dialog, `validatePayload()` (todo-create-task.js:118) calls `window.customJS.RecurrenceParser.isSupported(g)`. The throw propagates out of `updateSubmit()` before it reaches `submit.disabled = false`, so the button stays disabled forever on the recurring tab. The one-shot tab is unaffected (it never touches RecurrenceParser).

**Reproduced headlessly:** with `customJS.RecurrenceParser` set to a *class*, the button enables (38/38-style repro). Set to an *instance*, `isSupported` throws and the button stays disabled — exactly the reported symptom. The existing harness masked the bug by never setting `customJS.RecurrenceParser`, so the gate was skipped and validation passed.

**Blast radius beyond the dialog (same defect):**
- `ToDoDailyRecurring` (todo-daily-recurring.js:122, 164) calls `customJS.RecurrenceParser.isSupported` / `.matches` → recurring **materialization** throws live.
- `ToDoDailyCarryover` (todo-daily-carryover.js:139) calls `customJS.TaskParser.parseTasks` — `TaskParser.parseTasks` is **`static`** → carryover task-parsing throws live (falls through only when customJS.TaskParser is *absent*, not when its method throws).

**Convention violated:** customJS-consumed helper classes must expose their consumed methods as **instance** methods (like SectionLabel / FinanceMath / DocSearch). `static` is fine only for methods called by class name within the same file, or in Node harnesses.

## Part A — Bug fix

1. **`RecurrenceParser`**: add **instance** methods `isSupported(grammar)` and `matches(grammar, dateMoment, opts)` that delegate to the existing statics (`return RecurrenceParser.isSupported(grammar)` etc.). Keep the statics — internal `_parse` calls and `run-recurrence-parser.js` rely on them. Zero blast radius.
2. **`TaskParser`**: add an instance method `parseTasks(content)` delegating to the static.
3. **Sweep** for any other `customJS.<X>.<method>` where `<method>` is `static` (candidates surfaced in the customJS usage scan); fix each by adding an instance delegator.
4. **Defense-in-depth** (after root cause, per systematic-debugging): wrap the three call sites — `validatePayload`'s isSupported gate, `ToDoDailyRecurring`'s isSupported/matches, `ToDoDailyCarryover`'s parseTasks — in try/catch so a throwing/absent helper **degrades gracefully** (grammar-only validation / skip) instead of bricking the surface. The instance-method fix removes the throw; the try/catch is belt-and-suspenders against future regressions.

## Part C — Flexible task creation (feature)

On **both** tabs of the dialog (one-shot + recurring):

- **Link a note** — a searchable dropdown (filter input + `<select>` of note basenames, capped + filterable) labeled "Link a note (optional)". Selecting a note inserts `[[Note Name]]` into the **title** field (append with a leading space; idempotent-ish — no duplicate insert of the same link back-to-back). Note enumeration reuses the vault-listing approach already in `_loadProjectList` but broadened to notes (cap ~500, basename + path).
- **Add link** — a small control: a `label` text input + a `url` text input + an "Insert link" button. Clicking composes `[label || url](url)` via a pure static `composeMarkdownLink(label, url)` helper and appends it to the **title**. URL must be non-empty; basic `http(s)://` / `obsidian://` / mailto tolerance (don't over-validate).

The **title remains the single free-text field** (simple); both inserters are optional affordances (flexible). `serializePayloadToLine` already uses `payload.title.trim()` verbatim, so `[[note]]` and `[label](url)` flow into the `- [ ] …` line and render as live links in Obsidian. Verify no bracket-stripping anywhere in the serialize path.

## Part D — Feature tests

- Pure static `composeMarkdownLink(label, url)`:
  - `('spec','https://x/y')` → `[spec](https://x/y)`
  - `('', 'https://x/y')` → `[https://x/y](https://x/y)` (url as label fallback)
  - empty/whitespace url → `null` (no insert)
- `serializePayloadToLine` preserves a title containing `[[Acme]]` and `[spec](https://x)` verbatim.
- DOM-stub: selecting a note in the picker appends `[[Note]]` to the title input + updates `state.title`; clicking Insert-link appends `[label](url)`.
