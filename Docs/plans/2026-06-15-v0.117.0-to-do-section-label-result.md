# v0.117.0 — to-do v0.5.0 SectionLabel polish + template fix

## The cycle-defining bug

User reported on 2026-06-15 evening, ~30 min after v0.116.1 deploy: their freshly-created daily note `spice/to-do/2026/06-June/ToDo-2026-06-15.md` had only TWO dataviewjs blocks (`SpaceNavButtons` + `ToDoLeafActions`). None of the v0.4.0 sections (Carryover / Recurring / Project Groups / Unassigned Meetings) appeared. They also called the raw `## Owned Tasks` H2 headings "tacky" and asked for the finance-style polish.

`git log -- platform/blueprints/to-do/templates/Today\ To-Do.md` revealed the load-bearing miss: **the template hadn't been touched since `e455cbf` (v0.3.3, June 11 era)**. My v0.116.0 S8 `Write` call to update the template either silently no-op'd (Write-after-no-Read TDZ-like behavior) or never reached the file. Only the two NEW templates (Project To-Do.md, Recurring Tasks.md) got created; the existing Today To-Do.md stayed at v0.3.3 shape across v0.116.0 + v0.116.1. Consumer vaults never had the helper blocks.

`applyToDoBlueprintMigration` reshaped EXISTING old notes during install — but new dailies created via Templater still came out v0.3.3 shape because Templater is the path, not the migration.

## Lessons (load-bearing)

1. **`Write` tool silently no-ops on existing files not yet Read in this conversation thread.** v0.116.0 S8 attempted to overwrite `Today To-Do.md` (existed since v0.3.3) but the Write returned success for the two NEW templates only — the existing-file overwrite silently dropped. The bug landed in v0.116.0, persisted through v0.116.1, and was caught only by user smoke. **Rule:** after any cycle that intends to overwrite existing files, run `git log -- <intended-files>` to verify the commit actually touched them.

2. **The Templater path is the dominant template source, not the migration step.** `applyToDoBlueprintMigration` reshapes existing notes, but new notes created via the To Do nav button go through Templater, which uses `ranch/templates/Today To-Do.md`. If the template is wrong, every new daily is wrong — regardless of how good the migration is.

3. **SectionLabel as the canonical visual primitive needs a runtime dep edge.** Adding `depends_on: project >=1.21.0` to to-do v0.5.0 is correct (project owns the helper), but it requires consumer vaults AND test fixtures to subscribe to project. `run-cli.js` TD-CLI test broke until I added `project` to the test's subscription; production vaults already had it.

4. **H2 → SectionLabel is a generalizable migration pattern.** The `_rewriteH2ToSectionLabel(body, headingPattern)` helper now handles any `## <Heading>` → `<dataviewjs SectionLabel(text: ...)>` rewrite. Future blueprints that want to adopt SectionLabel can reuse this pattern (extract from install.js if needed).

5. **`appendAuditRow` + `trimAuditTable` need to tolerate BOTH legacy H2 AND new SectionLabel forms** during the migration window. `_findAuditSectionStart` looks for either. Once both consumer vaults migrate, the legacy branch can be retired.
