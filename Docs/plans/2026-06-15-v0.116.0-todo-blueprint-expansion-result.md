## Approach taken

Thin sauce layer atop `obsidian-tasks-plugin` (already foundational in `platform/manifest.json:foundational_plugins[]`, configured via `convenience` mechanism's `taskFormat=dataview`):
- Markdown checkbox is single source of truth.
- Tasks plugin owns recurrence syntax + priority + due/scheduled fields.
- Sauce owns sectioning, dialog, per-project rollups, meeting routing, daily-note materialization.
- Sauce-defined `[project:: [[X]]]` inline-field extension for routing (Tasks plugin ignores unknown fields).
- Provenance fields: `[from:: [[ToDo-YYYY-MM-DD]]]` (carryover), `[recurring_from:: [[Recurring Tasks]]]` (recurrence materialization).

Critical invariant: materialized recurring lines DO NOT carry `[recurrence::]` (preventing Tasks plugin from spawning a duplicate next-instance when the user checks the materialized copy). Registry lines retain `[recurrence::]` and are templates — never checked off directly.

## Lessons + observations

1. **Tasks-plugin recurrence + Dataview interaction caveat surfaced as a design constraint.** Per [Obsidian Tasks docs / Dataview integration](https://publish.obsidian.md/tasks/Other+Plugins/Dataview), Dataview doesn't understand recurrence — checking off a Dataview-rendered recurring task creates a "done" marker without spawning the next instance. v0.4.0 ships materialized lines WITHOUT `[recurrence::]` so the Tasks plugin doesn't double-regenerate. Carry-forward: route in-daily checkbox clicks through `Tasks: Toggle Done` for proper recurrence handling.

2. **Wikilink-in-inline-field regex is greedy/non-greedy hazardous.** REC-4 failure: `/\[\w+::\s*[^\]]+\]/g` consumes `[project:: [[Headspace]` (stopping at first `]`) and leaves `]]` behind. Fix: alternation `/\[\w+::\s*(?:\[\[[^\]]+\]\]|[^\]]+)\]/g`. Codified in todo-daily-recurring + todo-daily-project-groups + dialog `_cleanTaskText`.

3. **Project-linked recurring tasks materialize into `## Recurring Today`, not project sections.** Design intent was "fire into the project's daily section". Implementation reality: the project sections are LIVE rendered by `ToDoDailyProjectGroups` (which reads project To-Do notes + meetings, not today's daily). Routing materialized recurring into anchor comments in live-rendered sections is v0.117.0 polish; v0.4.0 ships project-linked recurring with their `[project::]` tag visible in Recurring Today.

4. **Workshop subscription does NOT include the to-do blueprint** (workshop self-install dogfood is curated). Seed-vault DOES include it. When the workshop catalogue bumps to-do@0.4.0, seed-vault's subscription pin must be bumped in lockstep, or per-item install rejects with "subscription pins X but workshop has Y" (landmine #24 — same posture either direction).

5. **`applyOrphanedHelperCleanup`'s `KNOWN_ORPHANS` list scales naturally with each retiring helper.** v0.116.0 added 2 entries (todo-migrate-modal.js, todo-migrate-init.js). The cross-cutting cleanup step has now removed 5 orphan helpers across v0.108.0 + v0.116.0.

6. **Skipped (deferred) deliverables vs. design:**
   - **HC-V0116-TODO-* contract family in run-helper-cases.js** — design spec'd ~30 cases; shipped ~0 new HC-V0116 cases (relying on TD-HC-1 widening + existing FA-EXTENDS coverage). Carry-forward.
   - **Behavioral suite `run-v0116-todo-overhaul.js`** — design spec'd ~30 cases against DOM stubs. Shipped 0 (pure-helper harnesses cover the same algorithms at a lower fidelity). Carry-forward.
   - **HC-V0116-SEED-MIGRATE-* family + pre-migration seed-vault data** — design spec'd ~14 sub-asserts. Shipped 0 explicit ones; the seed-migrations harness still GREEN (75/75) because v0.116.0 migrations are no-ops on the existing seed (no v0.3.3-shape daily notes; no project folders).
