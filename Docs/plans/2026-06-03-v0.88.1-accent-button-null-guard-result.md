# v0.88.1 — accent-button-null-guard — result

**Hot-fix PATCH following v0.88.0 deploy** — design + plan are implicit (this entry is the canonical write-up).

## What landed

- `accent-button@0.1.0 → 0.1.1`: `(opts.icon || "")` null-guard in the `innerHTML` concat.
- `people@0.5.0 → 0.5.1`: `PersonNavButtons` passes a real Lucide `arrow-left` SVG icon to AccentButton instead of `icon: null`; label drops the now-redundant `←` arrow character.
- Workshop `0.88.0 → 0.88.1`. Preflight `version-sync ok: 0.88.1` ALL GREEN.

## Why

Post-v0.88.0 deploy, the user opened a freshly-created person note (`spice/people/Patryk Szelagowski.md`) and saw the back-button rendering as the literal text:

```
null ← Back to People
```

Root cause traced to `platform/mechanisms/accent-button/accent-button.js:42`:

```js
btn.innerHTML = opts.icon + `<span>${opts.label}</span>`;
```

When `opts.icon` is `null`, JavaScript's `null + "<span>..."` evaluates to the literal string `"null<span>..."`. `PersonNavButtons` is the only caller in the codebase that passes `icon: null` (intentionally — it wanted an icon-less back-link). The bug has been latent since `accent-button@0.1.0` shipped — pre-v0.88.0, the dataviewjs block in person notes never executed because every person note was broken from the templater double-fire. v0.88.0 cleaned up that creation path, which **unblocked the render path** and surfaced this latent bug for the first time.

Two coordinated fixes shipped together:
1. **Mechanism defensive fix.** `accent-button.js:42` now `(opts.icon || "")` — defends against any future caller passing nullish icon.
2. **Caller UX upgrade.** `person-nav-buttons.js` now passes a real Lucide `arrow-left` SVG icon (matching the existing Lucide-user icon used in the identity row above the button). Label drops `←` since the icon conveys direction.
