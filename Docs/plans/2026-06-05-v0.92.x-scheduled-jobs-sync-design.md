# v0.93.0 — scheduled-jobs sync design

## 1 — Context

### 1.1 — Why this cycle exists

Cowork (claude.ai's scheduled-task feature) is the cron runtime for the 5 daily/weekly/monthly cadences. The scheduled task's prompt body lives in claude.ai's UI and outside the sauce vault entirely. No mechanism in v0.91.x detects when the Cowork wrapper drifts from canonical structure — the user has to remember to re-paste after every v-bump that touches the wrapper contract.

### 1.2 — Drift surface

The canonical wrapper structure is currently maintained as conversational artifacts:
- Workshop session 2026-06-05 produced `/Users/willfellhoelter/notes/sauce/accuris-sauce/Planning/cowork-scheduled-job-wrappers-v0.91.3.md` as the source of truth for the 5 v0.91.3-aligned accuris wrappers.
- User manually paste-replaces each Cowork task body when shipping a v-bump.
- No automated check that the Cowork-side wrapper matches the canonical for the current sauce/cowork version.

### 1.3 — Versioned-contract risk

Each new v-bump adds enforcement clauses to the wrapper as belt-and-suspenders:
- v0.91.1 — explicit OUTPUT PATH non-negotiable.
- v0.91.2 — explicit FRONTMATTER non-negotiable.
- v0.91.3 — CONNECTIVITY + deferred-tool + DATAVIEWJS canonical-pattern clauses.

Wrapper drift makes the cron run with stale enforcement. The cost compounds every cycle.

## 2 — Decisions

Brainstorm decisions (2026-06-05 session):

| ID | Decision | Rationale |
|---|---|---|
| **B1** | One file per engagement; 5 numbered sections with fenced code blocks; per-section HTML-comment version tags. | Matches user's current manual artifact shape (zero retraining); single staleness signal per engagement; one-way-door analysis favors single-file (can absorb per-cadence introspection later if needed). |
| **B2** | Lean frontmatter (6 fields + warnings array): type, engagement_id, sauce_version, cowork_version, contract_version, generated_at, generated_by, warnings. | Single timestamp is THE staleness signal; rich frontmatter is YAGNI. Per-section HTML-comment tags carry per-cadence introspection when needed. |
| **B3** | Canonical contract in versioned `scheduled-job-contract.json` data file at `platform/blueprints/cowork/data/`. Substitution tokens use `{{$varname}}` (distinct from installer's `{{template_variables}}`). | Matches platform non-negotiable #4 ("all platform metadata is JSON"); clean data/logic separation; HC-fixture-testable independently of helper code; landmine #20 substitution-token validator applies. |
| **B4** | Fully dynamic — contract.json contains NO MCP brand strings ("M365" / "Apple-MCP" / "ADO" / etc.). Dispatch lines computed kind-by-kind from `prefs.mcps`. New MCP shapes work without contract changes. | User requirement: "every vault has its own connections, nothing is default, flexible for any user's connection needs." Brand-agnostic; future-MCP-agnostic. |
| **B5** | `cowork:` blueprint namespace — orchestrator at `platform/blueprints/cowork/skills/orchestrators/sync-scheduled-jobs/SKILL.md`. NOT elevated to `platform:` mechanism. | Contract is intrinsically cowork-version-pinned; engagement vocabulary already lives in cowork; zero CLI surface churn; user's existing `/cowork ...` slash-command pattern. One-way-door favors starting at blueprint; refactor to mechanism only if non-cowork scheduled jobs ever land. |

The preamble's `{{$sauce_version}}`, `{{$cowork_version}}`, `{{$contract_version}}` substitution points require those three tokens be added to `substitution_tokens` (helper-computed from inputs):

| Token | Source | Computation |
|---|---|---|
| `$sauce_version` | caller-supplied `sauce_version` arg | direct copy |
| `$cowork_version` | caller-supplied `cowork_version` arg | direct copy |
| `$contract_version` | `contract.contract_version` | direct copy |

These three tokens are added to the `substitution_tokens` map alongside the 10 originally enumerated, bringing the total to 13 declared tokens.

### 4.2 — `wrapper_template` storage decision

Each `wrapper_template` is a multi-line JSON string ~60-90 lines (~330 lines total across all 5 cadences). v0.93.0 ships them EMBEDDED in contract.json (Option A from brainstorm). Total file size ~500-700 lines.

Rationale: matches existing platform patterns (read-user-preferences-helper's WIKILINK_PEOPLE_RULE.body is a multi-line JS string; engagement-types/<type>.json has multi-line strings). Single artifact; one HC-fixture-testable surface. FLN-v93-1 queued for the day editing-ergonomics become an issue.

### 4.3 — `shared_clauses` reference convention

Wrapper templates reference shared clauses via `{{shared.<key>}}` tokens (distinct prefix from `{{$varname}}`). Helper resolves at substitution time. Avoids duplicating dvjs block + sub-skill boilerplate 5 times.

### 4.4 — Substitution-token validation per landmine #20

Validator function inside `compose-scheduled-job-wrappers-helper.js` enforces 4 modes:

1. **Mode 1 — undeclared `{{$varname}}`:** every `{{$<name>}}` in any template must exist as a key in `substitution_tokens`. Catches typos.
2. **Mode 2 — unknown shared key:** every `{{shared.<key>}}` must exist as a key in `shared_clauses`. Catches typos.
3. **Mode 3 — invalid token format:** any string matching `/\{\{[^}]*\}\}/` that does NOT match `/\{\{(\$[a-z_]+|shared\.[a-z_]+)\}\}/` is rejected. Guards against `{{template_variables}}` accidentally landing in contract.json (where installer's substituteLenient could pick it up).
4. **Mode 4 — post-render leak:** AFTER substitution, the rendered wrapper MUST NOT contain any `{{` substring. Catches missed tokens.

HC fixtures explicitly test all 4 modes (typo, unknown shared key, installer-token-leak, post-render miss).

### 4.5 — Per-engagement substitution computation (helper-side)

| Token | Source | Computation |
|---|---|---|
| `$engagement_id` | `vault-config.engagements[<id>].id` | string copy |
| `$engagement_label` | `vault-config.engagements[<id>].label` | string copy; fallback to id + warning |
| `$mcp_dispatch_lines` | `user-preferences.mcps` | iterate `connected == true` entries; emit `"<kind> served-by <served_by>"`; join with `"; "`; zero connected → fallback string + warning |
| `$voice_notes_excerpt` | `user-preferences.personality.notes` | first 200 chars; newlines stripped; `…` suffix if truncated; empty → empty string + warning |
| `$sauce_version` | caller-supplied `sauce_version` arg | direct copy |
| `$cowork_version` | caller-supplied `cowork_version` arg | direct copy |
| `$contract_version` | `contract.contract_version` | direct copy |
| `$schedule_hint`, `$frontmatter_type`, `$output_path_template`, `$orchestrator_skill_name`, `$sub_skill_name`, `$cadence_tone_hint` | `contract.cadences[<cadence>].<field>` | direct passthrough |

Total: 13 declared substitution tokens (10 originally enumerated in §4.1 + 3 added for the preamble's version references).

### 4.6 — Schema versioning

`contract_version` bumped at every cycle that changes the schema OR wrapper_template content. Mirrors cowork blueprint version exactly. Helper asserts `contract_version === cowork_blueprint_version` at runtime; mismatch → emits Notice + sets `warnings: [contract_version_mismatch]` in output frontmatter but CONTINUES (defensive — doesn't block sync output on slight drift).

### 4.7 — Per-cadence opt-out

A `disabled: true` field on any cadence skips its wrapper in output (helper emits a DISABLED stub section instead). Default omitted = enabled. Use case: personal engagements that don't run midday-tripwire override per-engagement-type via `engagement-types/<type>.json` `scheduled_jobs.disabled_cadences: ["midday-tripwire"]`; helper consults.

## 5 — `compose-scheduled-job-wrappers-helper.js` API contract

Pure JS, no I/O, no clock, no randomness. Caller supplies all timestamps + version strings → fully deterministic + golden-fixture-testable.

### 5.1 — Signature

```js
composeScheduledJobWrappers({
  engagement,              // vault-config.engagements[<id>] record
  prefs,                   // parsed user-preferences.md JSON
  engagement_type_data,    // engagement-types/<engagement.type>.json
  contract,                // parsed scheduled-job-contract.json
  sauce_version,           // current workshop_version
  cowork_version,          // current cowork blueprint version
  generated_at,            // ISO timestamp WITH TZ (caller supplies — never clock-read internally)
  generated_by             // skill ID + version (e.g. "cowork:sync-scheduled-jobs@1.0.0")
}) → {
  file_md: string,         // full output file (frontmatter + preamble + 5 sections)
  warnings: string[],      // array of warning tokens (non-fatal)
  status: "ok" | "failed:<reason>"
}
```

### 5.2 — Behavioral steps

1. **Input validation.** Verify all required keys + types. Fail with `failed:input:<field>:<reason>`.
2. **Contract structural validation.** Verify contract has `contract_version`, `cadence_order`, `substitution_tokens`, `shared_clauses`, `cadences` keys; every cadence in `cadence_order` exists in `cadences`; every cadence has 7 required fields. Fail with `failed:contract:invalid-shape:<which>`.
3. **Substitution-token preflight (4-mode landmine #20 validator).** Per §4.4. Fail on any mode miss.
4. **Compute engagement-level substitution map.** Build `engagement_substitutions` keyed by token name. Per §4.5.
5. **Contract version mismatch check.** If `contract.contract_version !== cowork_version`: push warning `contract_version_mismatch:<contract_version>:<cowork_version>`. Continue.
6. **Resolve disabled cadences.** Compute from `engagement_type_data.scheduled_jobs.disabled_cadences[]` ∪ `contract.cadences[<cadence>].disabled`. Each entry warns `cadence_disabled:<cadence>:<source>`.
7. **Compose frontmatter** per §6.1 file anatomy (canonical 8-field order: type, engagement_id, sauce_version, cowork_version, contract_version, generated_at, generated_by, warnings).
8. **Compose preamble** from `contract.preamble_template` (with engagement-level substitutions applied).
9. **Compose per-cadence sections.** For each cadence in `contract.cadence_order`:
   - Build cadence-specific substitution map (engagement + cadence fields).
   - Substitute `wrapper_template`.
   - Run Mode 4 post-render leak check.
   - Emit section: heading + HTML version tag + 4-backtick fenced block.
10. **Disabled-cadence stubs.** For disabled cadences: emit DISABLED stub section per §6.3 (slot preserved, section <N> stays mapped to canonical cadence).
11. **Return result.** `{ file_md, warnings: deduped + sorted, status: "ok" }`.

### 5.3 — Error token taxonomy

- `failed:input:<field>:missing` or `failed:input:<field>:wrong-type:<got>`
- `failed:contract:invalid-shape:<which>`
- `failed:contract:cadence-order-mismatch`
- `failed:contract:substitution-token-undeclared:$<name>:cadence-<cadence>`
- `failed:contract:unknown-shared-key:<key>:cadence-<cadence>`
- `failed:contract:invalid-substitution-format:<token-text>:cadence-<cadence>`
- `failed:contract:unrendered-token-after-substitution:cadence-<cadence>`

### 5.4 — Warning token taxonomy

- `contract_version_mismatch:<contract_version>:<cowork_version>`
- `no_connected_mcps_in_prefs`
- `empty_voice_notes`
- `engagement_label_fallback_used`
- `cadence_disabled:<cadence>:<source>`

### 5.5 — Idempotence + exports

Pure function. Same input tuple → byte-identical `file_md`.

```js
module.exports = {
  composeScheduledJobWrappers,    // top-level entry
  composeMcpDispatchLines,        // sub-helper, exported for unit tests
  validateContract,                // sub-helper, exported for unit tests
  substituteTemplate               // sub-helper, exported for unit tests
};
```

### 6.2 — Key design choices

- **Fence convention: 4 backticks for outer code fence.** Wrapper text contains triple-backtick ` ``` ` dataviewjs block markup; CommonMark spec requires outer fence longer than inner sequences.
- **Conditional warnings callout.** Empty `warnings: []` → callout OMITTED entirely (not rendered as empty callout). Non-empty → one `> ` line per token. Avoids noise on clean generations.
- **Collapsed "How to use" callout** (`[!info]-`). Default-folded; user sees section headers + fenced blocks immediately.
- **Per-section HTML-comment version tag.** `<!-- section_contract_version: <version> -->` immediately after each `## <N>` heading. Invisible in preview; greppable. Future per-cadence introspection.
- **Horizontal rule between sections.**
- **Section heading format.** `## <N> — cowork-<cadence>-<engagement_id> (<schedule_hint>)`.
- **Frontmatter field order is canonical** (testable by golden fixtures).

### 6.3 — Disabled-cadence rendering

When a cadence is disabled:

```markdown
## <N> — DISABLED — cowork-<cadence>-<engagement_id>
<!-- section_contract_version: <version> -->
<!-- disabled_by: <engagement-type | contract> -->

> [!example] This cadence is disabled for <engagement.label>
> Reason: disabled via <engagement-type | contract>. If this is wrong, edit
> `spice/cowork/context/engagement-types/<engagement.type>.json` and re-run sync.

---
```

Section numbering stays sequential (slot preserved). Section <N> = cadence <X> mapping stays stable across regenerations.

### 6.4 — Byte-level invariants

- Frontmatter field ORDER: type, engagement_id, sauce_version, cowork_version, contract_version, generated_at, generated_by, warnings.
- Section ORDER: from `contract.cadence_order`.
- Blank-line counts: canonical per §6.1.
- Trailing whitespace on every line: stripped.
- Final byte: newline (POSIX).

### 6.5 — File size estimate

- Frontmatter: ~10 lines.
- H1 + preamble callouts: ~12 lines.
- Per-section: ~67-97 lines × 5 = ~335-485 lines.
- Footer: ~5 lines.
- **Total: ~360-510 lines per engagement file.**

Today's `Planning/cowork-scheduled-job-wrappers-v0.91.3.md` is ~295 lines for 5 cadences — close to the low end; helper-emitted version slightly longer due to per-section metadata + horizontal rules + conditional warnings callout.

## 7 — `cowork:sync-scheduled-jobs` orchestrator SKILL.md structure

### 7.1 — Section list

1. **Frontmatter** (~15 lines) — `name: cowork:sync-scheduled-jobs`, `description:`, `inputs: { engagement_id: string? }`, `outputs: { output_path, status, warnings[] }`, `tags: [cowork, sync, scheduled-jobs, user-invocable]`.
2. **`## What it does`** (~10 lines) — 2-3 sentence preamble + cross-reference to v0.91.x contract evolution.
3. **`## When to invoke`** (~8 lines) — first-time engagement setup; after every cowork MINOR bump; on user demand.
4. **`## Inputs`** (~8 lines) — optional `engagement_id`; auto-resolution follows v0.90.0 discover-people pattern.
5. **`## Pre-flight`** (~25 lines, 6 steps) — engagement resolution; read vault-config; read user-preferences; read engagement-types/<type>.json; read platform-installed.json; compute generated_at + generated_by.
6. **`## Compose`** (~10 lines, 3 steps) — resolve helper path; invoke composeScheduledJobWrappers; failure handling.
7. **`## Write`** (~20 lines, 5 steps) — compute output path; mkdir; backup-on-edit (`.sauce-backup`); Write tool; verify.
8. **`## Done`** (~10 lines, 3 steps) — Obsidian Notice summary; warnings list; next-step guidance.
9. **`## Failure modes`** (~15 lines) — full failure-token taxonomy.
10. **`## Harness testing`** (~10 lines) — fixture references.

### 7.2 — Step-level prose (orchestrator-internal flow)

```
## Pre-flight

1. Resolve engagement:
   - Read spice/cowork/context/vault-config.md → parse engagements[].
   - If engagement_id passed: look up; reject + Notice + exit if not found.
   - If not passed AND length == 1: use the only engagement.
   - If not passed AND length > 1: prompt user.
2. Read spice/cowork/context/user-preferences.md → parse → capture prefs.
3. Read spice/cowork/context/engagement-types/<engagement.type>.json → engagement_type_data.
   Missing → emit warning + use default {scheduled_jobs:{disabled_cadences:[]}}.
4. Read ranch/platform-installed.json → workshop_version (= sauce_version)
   + blueprints[].cowork.version (= cowork_version). Missing → hard fail.
5. Read {{module_directory}}/data/scheduled-job-contract.json. Materialized
   path: spice/cowork/data/scheduled-job-contract.json. Missing → hard fail.
6. Compute generated_at as ISO+TZ from engagement.timezone (default "America/Denver").
   Compute generated_by = "cowork:sync-scheduled-jobs@1.0.0".

## Compose

7. Resolve helper path: {{module_directory}}/helpers/compose-scheduled-job-wrappers-helper.js.
8. Invoke composeScheduledJobWrappers(...). Capture {file_md, warnings, status}.
9. If status starts with "failed:": emit Notice + exit non-zero. Do NOT write.

## Write

10. Compute output_path: spice/cowork/scheduled-job-wrappers/<engagement.id>.md.
11. Bash: mkdir -p "spice/cowork/scheduled-job-wrappers" (defensive on first run).
12. If output file exists: copy current content to <output_path>.sauce-backup
    (single-deep, overwrite-on-edit). Backup-write failure → hard fail.
13. Write file_md via Write tool. Failure → emit Notice + exit non-zero.
14. Verify: re-read; assert byte count ≥ 500; assert frontmatter parses.
    Failure → emit Notice + exit non-zero (file landed; user can inspect).

## Done

15. Emit Notice: "cowork:sync-scheduled-jobs complete — <engagement.label>
    @ sauce <sauce_version> / cowork <cowork_version> / contract <contract_version>.
    Output: <output_path>. Warnings: <count>."
16. If warnings[].length > 0: emit second Notice listing tokens.
17. Print "next step": "Open <output_path>, then paste each fenced block into
    the matching Cowork task in claude.ai."
```

### 7.3 — Critical design choices

- **No `## Gather` section** — orchestrator does no MCP-side gather.
- **No CRITICAL output-path callout** — output path is unambiguous (no resolver conflict).
- **No CONNECTIVITY / deferred-tool prose** — orchestrator doesn't dispatch.
- **No body-shape write-guard** — output is reference artifact, not atomic note; no 4th-layer defense needed.
- **Backup-on-edit `.sauce-backup`** — matches landmine #12 mechanic #2.

### 7.4 — Slash-command surface

`commands/cowork.md` source file gains entry for `/cowork sync-scheduled-jobs <engagement_id>`. Pattern matches existing `/cowork discover-people` + `/cowork find-missing-people`.

### 7.5 — Engagement-resolution duplication (FLN-v93-2)

Step 1's resolution algorithm is identical to 5 other cowork orchestrators. v0.93.0 will be the 6th carrier. **FLN-v93-2** queued: factor into shared `cowork:resolve-engagement` sub-skill. Not in v0.93.0 scope.
