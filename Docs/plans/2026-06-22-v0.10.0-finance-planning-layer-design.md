# Finance Planning / Lever / Allocation Layer — Design (finance v0.10.0 · workshop v0.128.0)

## 1. Why

The finance blueprint stores the *inputs and outcomes* of a money system (budgets, paychecks, debts, months) but owns **none of the policy**. A real consumer (headspace) runs a deliberate lever-based accountability system entirely as process + four markdown docs: an income-bound discretionary envelope, three ordered levers (discretionary → savings → debt-attack-last), a savings glide path, an overflow rule, and an avalanche set via each debt's `planned_monthly_payment`. Every smart number is computed in a human's head and re-keyed into config. This cycle moves that intelligence **into the blueprint** as a config entity + a `FinanceMath` allocation engine + a unified dashboard, so the system is reusable across vaults and no longer depends on the user's discipline.

**Acceptance test (held throughout):** the native feature must be able to *replace* the headspace hand-built system with no loss of fidelity — same envelope, same glide tiers, same overflow split, same avalanche-with-roll, same month-1 Apple util-bump exception. See §11.

## 3. Data model (two new entity types; everything else read live)

All new frontmatter is **additive**. No existing Budget/Paycheck/Debt/Month field changes.

### 3.1 `Finance Plan.md` (`type: finance-plan`, singleton, `spice/finance/` root)

Holds *only policy knobs*; every dollar derivable from another entity is derived, not stored.

```yaml
type: finance-plan
income_floor: 9000
fixed_living_monthly: 3851          # the one non-derivable line (rent/insurance/loans/utilities/phone)
attack_above_minimums: 570          # avalanche attack at the current tier
pay_periods_per_month: 2            # semi-monthly → per-check = monthly ÷ 2 (Apply uses this)
savings_glide:                      # concretizes the "taper" into explicit tiers
  - { under: 1500, monthly: 300 }
  - { under: 3500, monthly: 150 }
  - { at_or_above: 3500, monthly: 0 }
roll_freed_savings_to_attack: true  # when savings steps down a tier, freed money → attack (envelope stays constant)
overflow: { attack_pct: 80, flex_pct: 20 }
lever_order: [discretionary, savings, attack]
avalanche_order_by: apr             # rank targets by APR desc, tie-break smaller balance
attack_target_override:             # optional — generalizes the month-1 Apple util-bump
  debt: "[[Debt-Apple-Card]]"
  until_balance_below: 13950
cssclasses: ["wide"]
created_at: "<iso>"
```

**Shipped default (generalizable, no headspace numbers):** `income_floor: 0`, `fixed_living_monthly: 0`, `attack_above_minimums: 0`, `pay_periods_per_month: 2`, an empty-ish `savings_glide` with a single `{ at_or_above: 0, monthly: 0 }` tier, `roll_freed_savings_to_attack: true`, `overflow: { attack_pct: 80, flex_pct: 20 }`, `lever_order: [discretionary, savings, attack]`, `avalanche_order_by: apr`, no `attack_target_override`. A vault fills in real knobs once.

**Consequence of `roll_freed_savings_to_attack: true`:** when savings steps down a tier, that money moves to attack, so the **discretionary envelope is constant across tiers**: `floor − fixed − minimums − attack_above_minimums − tier1_savings`.

### 3.2 `savings-account` entity (`spice/finance/savings/Savings-<slug>.md`)

Mirrors the Debt pattern.

```yaml
type: savings-account
name: Emergency Fund
target: 5000
current_balance: 0                  # set via the "Edit balance" pill (snapshot-on-save)
last_updated: "<iso>"
balance_history:                    # source enum reuses Debt: install-seed | manual | skill
  - { date: "<iso-date>", balance: 0, source: "install-seed" }
cssclasses: ["wide"]
created_at: "<iso>"
```

The glide reads `current_balance` → picks the tier → drives `savings.contribution`. `source: "skill"` is reserved for the deferred Copilot sync.

## 4. The engine — `FinanceMath.computePlanState`

One new instance method (plus small helpers). Reads everything via existing readers (`readDebts`, `readPaychecksForMonth`, `readBudgetForMonth`) + two new (`readPlan`, `readSavings`). Returns one plan-state object; every widget is a thin view.

```js
customJS.FinanceMath.computePlanState(dv, monthKey) → {
  ok,                          // false + reason when no Finance Plan exists (degrade-gracefully)
  monthKey,
  inputs:   { incomeFloor, fixedLiving, minimums, savingsBalance, savingsTarget },
  envelope: { base, overageCarry, effective, planned, spent, left, over, status },
  savings:  { balance, target, tier, contribution, freed, toTarget },
  attack:   { base, freed, total },
  allocation: [ { debt, slug, balance, apr, min, attack, total, isTarget, paidOff } ],  // avalanche-sorted
  payoff:   { zeroDebtDate, months, killOrder: [ { debt, date } ] },
  overflow: { actualIncome, surplus, toAttack, toFlex },   // only when actualIncome > floor
  whatIf:   { skipAttackThisMonth: { weeksSlipped, newZeroDebtDate } },
  applyPlan:{ debtTargets: [ { slug, planned_monthly_payment } ], savingsContribution, savingsPerCheck }
}
```

### 4.1 New `FinanceMath` methods

- `readPlan(dv)` → the single `type === "finance-plan"` page, or `null`.
- `readSavings(dv)` → all `type === "savings-account"` pages from `spice/finance/savings`.
- `glide(savingsBalance, tiers)` → `{ tier, contribution }`. Tier match: first tier whose `under` exceeds balance, else the `at_or_above` tier. `tier` is its 1-based index.
- `computePlanState(dv, monthKey)` → the object above.
- `simulateAvalanche(debts, monthlyMinByDebt, attackTotal, targetResolver)` → `{ months, killOrder, zeroDebtDate }` (month-by-month sim, capped 600 iters; returns `months: Infinity`/`zeroDebtDate: "—"` if non-converging).

### 4.2 Algorithms (grounded in headspace numbers)

- **minimums** = Σ `debt.min_payment` over active debts (`current_balance > 0`) → `$1,330`.
- **savings** = `glide(balance, tiers)`; `freed = roll_freed_savings_to_attack ? (tiers[0].monthly − contribution) : 0`. At `$639.94` → Tier 1, contribution `$300`, freed `$0`.
- **attack.total** = `attack_above_minimums + freed` → `$570`.
- **envelope.base** = `floor − fixed − minimums − attack.total − contribution` = `9000 − 3851 − 1330 − 570 − 300` = **`$2,949`**.
- **overageCarry** = `max(0, ΣpriorActual − priorBase)` from the prior month's Budget (read via `readBudgetForMonth(prevMonthKey)` + the same `base` recomputed); `effective = base − overageCarry`. Live-derived; never written.
- **allocation**: rank active debts by `avalanche_order_by` (APR desc, tie-break smaller balance). Each active debt gets its `min`. The **whole `attack.total` goes to one target**: the `attack_target_override.debt` while `current_balance >= until_balance_below`, else the top-ranked active debt. `total = min + (isTarget ? attack.total : 0)`. The **roll is automatic** because targets are resolved from *current* balances each render.
- **payoff** = `simulateAvalanche(...)` → accurate `zeroDebtDate` + per-card `killOrder`.
- **overflow**: `actualIncome = monthIncome(paychecks)`; `surplus = max(0, actualIncome − floor)`; `toAttack = surplus × attack_pct/100`, `toFlex = surplus × flex_pct/100`. Section omitted when `surplus === 0`.
- **whatIf.skipAttackThisMonth**: rerun `simulateAvalanche` with month-1 attack zeroed; `weeksSlipped = round((monthsB − monthsA) × 4.345)`.
- **applyPlan**: `debtTargets[]` = each active debt's `{ slug, planned_monthly_payment: total }`; `savingsContribution` = the glide contribution (monthly); `savingsPerCheck = round(contribution / pay_periods_per_month, 2)`.

### 4.3 Degrade-gracefully (Q7 generalization)

- **No `Finance Plan.md`** → `ok:false, reason:"no-plan"`; widgets render a muted "Set up your Finance Plan" prompt.
- **No debts** → `allocation: []`, `attack` zeroed, `payoff.zeroDebtDate: "—"`; envelope still computes (floor − fixed − savings).
- **No savings account** → `savings.balance: 0`, tier 1; glide still resolves.
- **No budget for the month** → `envelope.planned/spent: 0`, `over: 0`; PlanBand shows the envelope ceiling only.
- **`income_floor: 0`** → envelope is informational (can go negative); `over` flag suppressed when floor is 0 (no underwater claim without a floor).

## 5. Widgets (thin read-only views of `computePlanState`)

Each is a single `async render(dv[,opts])`, embed-deduped via `dv.container.closest(".markdown-embed")`, hardcoded colors green `#16a34a` / amber `#b45309` / red `#dc2626`.

Idempotent (re-apply of identical values is a no-op: modal says "nothing to change").

## 6. Apply mechanism

On click, `FinancePlanDashboard` opens a confirm modal listing every write as a `before → after` diff:

```
Apply allocation to entities?
  Cap1 Platinum   planned_monthly_payment  855 → 1000   (lone target)
  Discover        planned_monthly_payment 1000 →  430   (rolled off)
  SCHEELS         planned_monthly_payment  235 →  235   (unchanged)
  Apple           planned_monthly_payment  380 →  380   (unchanged)
  Paycheck Defaults · Savings row  amount  150 →  150   (unchanged)
        [ Apply ]   [ Cancel ]
```

- **Debt targets**: for each `applyPlan.debtTargets[]`, resolve the `Debt-<slug>.md` file, `FinanceFrontmatter.update` → set `planned_monthly_payment`. Monthly granularity (flows to future paychecks via the existing `resolve_wikilinks` glue).
- **Savings row**: in `Paycheck Defaults.md`, find the `expenses[]` row with `category === "Savings"` (or `item === "Savings"`), set `amount = applyPlan.savingsPerCheck`. If no such row exists, the modal notes "no Savings row in Paycheck Defaults — add one" and skips (never invents schema).
- **Known wart (documented, not fixed here):** scaffolded paychecks carry the **full monthly** `planned_monthly_payment` on debt rows via `resolve_wikilinks`, while the Savings row is **per-check** — a granularity mismatch that predates this work. Apply writes the Savings row per-check to match the consumer's convention; the broader paycheck-row-granularity normalization is a carry-forward (§10).

## 11. Acceptance test — headspace replacement mapping

| Hand-built today | Native v0.10.0 |
|---|---|
| Envelope computed by hand ($2,950) | `computePlanState.envelope.base` from the plan |
| Underwater flag (eyeballed) | `PlanBand` over-flag (`planned > effective`) |
| Lever order + overage carry (Month-note prose) | `lever_order` + `overageCarry` (live-derived effective envelope) |
| Glide path (manual tier tracking) | `savings_glide` + `glide(savingsBalance)` → tier chip |
| Overflow rule (manual 80/20) | `overflow` config + `computePlanState.overflow` |
| Avalanche + roll (manual `planned_monthly_payment`) | `allocation[]` + `applyPlan` + one-click Apply |
| Month-1 Apple util-bump (manual override) | `attack_target_override` (until balance < 13950) |
| Savings balance (in a doc) | `Savings-Emergency-Fund.md` + Edit-balance snapshot |
| "Pull the debt lever costs N weeks" (one-off analysis) | `whatIf.skipAttackThisMonth.weeksSlipped` |

If each row holds after deploy + Cmd+R on headspace, the feature replaces the hand-built system.

## 12. Risks

- **Scope (landmine #27).** This is a >3-surface bundle — the exact shape that thrashed v0.116→v0.118. **Mitigation:** build in strict dependency order with a verification gate per surface (engine harness green → schemas lint green → scaffolds seed-harness green → widgets helper-cases green → manifest/pins check-version-sync green → full preflight + dogfood green), not a single big-bang preflight.
- **CustomJS cold-load (landmines #1–5).** All widget invocations use the `dv.view("ranch/views/customjs-guard", { class })` pattern (inherited from the existing inline bodies). No bare callsites.
- **Apply correctness.** Apply mutates live debt entities → guarded by a confirm-diff modal, idempotency, and `FinanceFrontmatter.update` atomicity. No silent writes.
- **Backcompat.** Zero new required fields on existing entities; `ok:false` until a plan exists; PlanBand injection append-only. Safe against the live headspace data.
