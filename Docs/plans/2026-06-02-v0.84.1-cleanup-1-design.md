# v0.84.1 cleanup-1 — design

Four small UX/correctness fixes bundled into one PATCH cycle. Driven by user-reported friction in the workshop dogfood:

1. Properties bar shows in every note by default.
2. Late-night scratches show up on the wrong day's hub or daily dashboard.
3. Daily dashboard's Tasks header counts only OPEN tasks — no signal for what was completed.
4. Scratch sub-group inside the Activity section ignores `defaultClosed: ["scratch"]` and renders open.

No new mechanisms, no new blueprints. PATCH bump on workshop + the four touched units. Bigger work (FLN-v84-1 Tier 2/3 memory, FLN-v84-2 cross-orchestrator wire-through) stays queued for v0.85.0 MINOR.

## §1 — Properties hidden as workshop default

**Surface.** `platform/manifest.json` line 32.

**Change.** `"propertiesInDocument": "visible"` → `"propertiesInDocument": "hidden"`.

**Why this is the entire fix.** The `applyAppSettings()` helper (`platform/mechanisms/platform-claude/helpers/apply-app-settings.js`, landed v0.26.1) rewrites `.obsidian/app.json` on every install. The 18-path allowlist already includes `propertiesInDocument` so nothing else needs touching. Workshop dogfood writes the new value into its own `.obsidian/app.json` on the next install; consumer vaults pick it up on the next `sauce update` or `sauce upgrade`.

**Behavior after install.** Obsidian no longer renders the YAML-frontmatter table at the top of any note. YAML on disk is unchanged. Cmd+P → "Add file property" + Obsidian's metadata menu remain the path for inline frontmatter edits.

**Risk.** Anyone using the properties bar as their primary frontmatter editor will lose the affordance. Acceptable: the platform owns frontmatter via templates + entity-create + claude_surface[], so direct frontmatter edits are already discouraged.

## §2 — Timezone: local everywhere, no UTC leaks

### §2.1 — `_coerceDay()` drops the Date branch

**Surface.** `platform/blueprints/scratch/helpers/scratch-day-list.js:18-28`.

**Current code (the bug):**

```javascript
_coerceDay(raw) {
    if (typeof raw === "string") return raw.slice(0, 10);
    if (raw && typeof raw.toISODate === "function") return raw.toISODate();
    if (raw instanceof Date && !isNaN(raw)) {
        const y = raw.getFullYear();
        const m = String(raw.getMonth() + 1).padStart(2, "0");
        const d = String(raw.getDate()).padStart(2, "0");
        return `${y}-${m}-${d}`;
    }
    return null;
}
```

**The bug.** YAML parses an unquoted `day: 2026-06-01` as a JS `Date` anchored at `2026-06-01T00:00:00.000Z`. The Date branch then calls `getFullYear/getMonth/getDate` — which return the LOCAL-TIME components of that UTC instant. In Mountain Time (UTC-6/7), midnight UTC is the previous evening, so `getDate()` returns `31` and the function returns `2026-05-31`. That scratch then attaches to the wrong day-hub for every Mountain-, Pacific-, or further-west user.

**Replacement:**

```javascript
_coerceDay(raw) {
    if (typeof raw === "string") return raw.slice(0, 10);
    if (raw && typeof raw.toISODate === "function") return raw.toISODate();
    // Intentionally no Date branch: a JS Date alone is timezone-ambiguous
    // (see scratch-day-list v?.?.? landmine note). If a scratch's `day:`
    // frontmatter parses as a Date, the user has an unquoted YAML value;
    // the day-frontmatter migration helper (§2.2) is the durable fix.
    return null;
}
```

A scratch with malformed `day` is dropped from `ScratchDayList` rather than silently mis-attributed. The migration helper (§2.2) eliminates the population that hits the dropped branch.

### §2.2 — One-shot day-frontmatter migration (customjs startup-script)

**Surface.** Two new files in the scratch blueprint:

- `platform/blueprints/scratch/helpers/scratch-day-migrate.js` — pure helper class `ScratchDayMigrate` exposing `migrate(file)` (per-file, takes Obsidian TFile) and `migrateAll()` (vault scan loop). Mirrors the test-friendly shape of `KanbanStatusSync`.
- `platform/blueprints/scratch/helpers/scratch-day-migrate-init.js` — startup-script class `ScratchDayMigrateInit` that calls `migrateAll()` once on vault boot. Mirrors `KanbanStatusSyncInit` exactly (Dataview-ready retry-with-backoff, max 30s, single-Notice on completion summary, registers manual command `Sauce: Re-migrate scratch day frontmatter` for cache-bypass).

**Manifest wiring.** Scratch `manifest.json` gains:

- `customjs_classes[]` grows: `ScratchDayMigrate`, `ScratchDayMigrateInit`.
- `customjs_startup_scripts[]` grows: `ScratchDayMigrateInit`.
- `files[]` grows: two new entries materializing the helpers into the vault.

This pattern is established (kanban-status-sync v0.2.0, sauce v0.73.0). No new manifest schema feature invented.

**What it does.** Scans `spice/scratch/**/*.md`, reads each file via `app.fileManager.processFrontMatter` (mobile-safe; no `vault.read` parse path). For each file:

- If `day` is already a quoted `YYYY-MM-DD` string (per `typeof` + regex `^\d{4}-\d{2}-\d{2}$`), skip.
- If `day` is missing or unparseable but the filename matches `Scratch-*-(\d{4}-\d{2}-\d{2})` OR the path contains a `/\d{4}-\d{2}-\d{2}/` segment, write `day: "YYYY-MM-DD"` from the captured date.
- If `day` parses as a Date object (i.e., the source YAML was unquoted), the `processFrontMatter` callback re-serializes the value as a string `"YYYY-MM-DD"` using the Date's LOCAL-time components — matching what Templater wrote at scratch-create time.
- If none of the above resolve to a `YYYY-MM-DD`, skip and emit a `console.warn` (debug-only; no Notice churn).

**Idempotency.** Subsequent runs are no-ops because all `day:` values are quoted strings (the typeof+regex skip path).

**Once-per-day cache.** Instance-level last-run timestamp on `ScratchDayMigrate` short-circuits same-session re-runs. Mirrors `KanbanStatusSync` v0.1.1's pattern. Manual command bypasses the cache.

**Workshop dogfood.** No legacy scratches under `spice/scratch/` in the workshop repo (verified at design time: `find spice/scratch -name "*.md" -not -name "Scratch.md"` returns empty in the workshop). Migration runs at workshop boot, finds zero work, exits clean. Consumer vaults are where this earns its keep.

**Test gate.** `HC-V0841-A2` exercises the pure helper `ScratchDayMigrate.migrate` with stub `processFrontMatter` against three fixture cases: (a) quoted `day: "2026-05-31"` — passes through unchanged; (b) unquoted `day: 2026-05-31` (parses as Date) — gets rewritten to `day: "2026-05-31"` using local-time components; (c) missing `day:` but filename `Scratch-2026-05-31-foo.md` — gets `day: "2026-05-31"` synthesized from the filename. Re-running the helper on the post-migration state produces zero changes.

### §2.4 — Activity-feed timestamp comparison: numeric, not lexicographic

**Surface.** `platform/mechanisms/activity-feed/activity-feed.js:349-368` (the `inWindow` closure inside `_query`).

**Current code (line 359):**

```javascript
} else if (ts >= start && ts <= end) {
    return true;
}
```

Both `ts`, `start`, `end` are ISO strings. String comparison works when offsets are identical. When a scratch was created in `-06:00` and the daily dashboard renders from `-07:00` (DST transition) or imported notes carry `Z` while local ones carry offsets, the comparison flips signs.

**Replacement:**

```javascript
} else {
    const tsMs = window.moment(ts).valueOf();
    const startMs = window.moment(start).valueOf();
    const endMs = window.moment(end).valueOf();
    if (Number.isFinite(tsMs) && tsMs >= startMs && tsMs <= endMs) return true;
}
```

The `Number.isFinite` guard short-circuits any malformed input back into the `anyFieldPresent`/mtime-fallback flow.

**Why moment.valueOf() is sufficient.** `window.moment(any-ISO-string)` parses the offset out of the string. `.valueOf()` returns absolute epoch ms. Two ISO strings that represent the same instant in different offsets compare equal. No new dependency; `window.moment` is already required by activity-feed.

**Test gate.** `HC-V0841-A3` runs `_query` with `tsKeys: ["created_at"]`, a `today` window in `-06:00`, and a fixture page whose `created_at` is the SAME INSTANT serialized in `Z`. Old code would have failed (lexicographic miss); new code passes.

## §3 — Daily-dashboard Tasks header: open · done

**Surface.** `ranch/scripts/daily/space-daily-dashboard.js:150-166` (`getTasks()`) and lines 209-245 (Tasks-section render).

**Change to `getTasks`:**

```javascript
const getTasks = () => {
    const open = [];
    const done = [];
    for (const todoPath of config.todoPaths) {
        const todoPages = dv.pages(`"${todoPath}"`)
            .where(p => p.file.name.includes(today));
        for (const page of todoPages) {
            for (const task of page.file.tasks) {
                const item = { text: task.text, parentPath: page.file.path };
                (task.completed ? done : open).push(item);
            }
        }
    }
    return { open, done };
};
```

**Change to render block:**

The section is rendered only when `open.length + done.length > 0`. The `hasContent` gate at line 172 keeps its current truthiness (any open OR done counts).

Header title:

```javascript
let title;
if (open.length === 0 && done.length > 0) {
    title = `Tasks (all done — ${done.length} today)`;
} else if (done.length > 0) {
    title = `Tasks (${open.length} open · <span class="sauce-tasks-done">${done.length} done</span>)`;
} else {
    title = `Tasks (${open.length})`;
}
```

The `<span class="sauce-tasks-done">` is consumed by a new CSS rule shipped via the styling mechanism's `sauce-callouts.css` cousin (or appended to it):

```css
.sauce-tasks-done {
    color: var(--color-green);
    font-weight: 600;
}
```

The rendered task LIST below still iterates only `open` (line 222 loop changes from `for (const task of tasks)` to `for (const task of open)`). Done items deliberately do not show up as struck-through — header surfaces the count, body stays focused on what's left.

**Why no `0 open · 0 done`.** The outer `if (open.length + done.length > 0)` gate prevents rendering an empty Tasks section.

**Test gate.** `HC-V0841-C1` exercises the three header forms by stubbing `dv.pages` with three task fixtures (3 open + 0 done → `Tasks (3)`; 3 open + 2 done → `Tasks (3 open · 2 done)`; 0 open + 4 done → `Tasks (all done — 4 today)`).

## §4 — Scratch auto-collapse regression in Activity feed

### §4.1 — Diagnosis

`space-daily-dashboard.js:339` passes `defaultClosed: ["scratch"]` to `customJS.ActivityFeed.render`. User reports that the scratch sub-group renders OPEN.

**S1 of implementation** is a read-only investigation: trace `defaultClosed` through `platform/mechanisms/activity-feed/activity-feed.js` to find where the group's `<details>` element is created and whether the `open` attribute is unconditionally set or whether `defaultClosed` is respected. Two candidate root causes:

- **Cause A (state-persistence override).** Dashboard section-state map in `ranch/cache/dashboard-section-state.json` (v0.73.0+) records user toggles. If activity-feed group state is co-mingled with section state, an earlier "user expanded scratch" event got persisted and now overrides the default on every render.
- **Cause B (plumbing regression).** A post-v0.10.0 edit to activity-feed renamed, reordered, or dropped the `defaultClosed` parameter on the group renderer. The opt arrives but is never read.

Fix is whichever cause is real:

- **If Cause A:** the scratch group's persisted state must be reset, OR the dashboard's persisted state must scope only to top-level sections (Tasks/Meetings/Activity) and never to sub-groups. Latter is the right answer — sub-group state is too granular for the persistence layer's invalidation story (e.g., what does "user expanded scratch" mean six months later when the scratch group is empty?). Code change: filter persistence keys to top-level section state only; sub-group state is render-time only.
- **If Cause B:** thread `defaultClosed` through to the `<details>` `open` attribute. If the group's name is in `defaultClosed` and there's no persisted user toggle, render without `open`. Otherwise honor persisted state.

### §4.2 — Test gate

`HC-V0841-D1` invokes activity-feed render with `defaultClosed: ["scratch"]`, no persisted state, and a fixture scratch page. Asserts the resulting DOM contains a `<details>` for the scratch group WITHOUT the `open` attribute. Independently of which cause was real, this assertion is the success criterion.

`HC-V0841-D2` invokes activity-feed render with `defaultClosed: ["scratch"]` AND a persisted user-toggle state of `{ "scratch": "open" }`. Behavior depends on Cause A vs B fix:

- If Cause A fix (sub-group persistence is dropped entirely): test asserts the group is STILL closed (persisted state was ignored because sub-group state is no longer persisted).
- If Cause B fix (plumbing): test asserts persisted state wins, so the group is open.

S1 investigation must decide which contract D2 enforces before implementation begins.

## §7 — Risk register

| Risk | Mitigation |
| --- | --- |
| Migration helper (§2.2) rewrites correctly-shaped frontmatter | Idempotency test (`HC-V0841-A2` step 3) re-runs on already-migrated fixture, asserts zero diffs. |
| `_coerceDay` returning null drops legitimate scratches | Migration helper runs BEFORE the dropped-branch is reachable in any consumer vault. Order matters: scratch blueprint manifest must list the migration step before any view re-render. |
| Numeric ISO compare breaks Dataview's Luxon-typed fields | `moment()` accepts Luxon DateTime via `.toJSDate()`; spot-test in S4 with a Dataview-typed fixture. If it fails, fall back to `String(ts)` coercion before parsing. |
| Persistence cleanup (Cause A) wipes user's section-toggle state | Migration is read-only on top-level keys; sub-group keys are dropped silently. Worst case: user re-toggles Tasks/Meetings/Activity once. Acceptable. |
| Properties-bar hidden breaks a workflow we don't know about | Reversible: any consumer can override locally via Obsidian's UI; the workshop default just changes the install-time value. |
