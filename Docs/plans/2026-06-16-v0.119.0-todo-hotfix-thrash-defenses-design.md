## Stage 1 — Hot fixes (consumer-facing)

### 1a — Additive sentinel for recurring-task materialization (bug b)

**Symptom (accuris, 2026-06-16):** Workshop is on 0.118.1. `ToDo-2026-06-16.md` line 10 has
`<!-- recurring-materialized-2026-06-16 -->`. User added "test recurring task" to
`Recurring Tasks.md` AFTER opening the day; the task never appears. Hand-deleting the sentinel
materializes it once, but the next mid-day registry edit is blind again.

**Root cause:** `ToDoDailyRecurring.insertRecurringIntoToday` writes a date-only sentinel and
short-circuits on `hasSentinel(content) → true`, conflating "already ran" with "nothing to do."
This is item #5 of the v0.118.1 postmortem (sentinel fragility) happening in production.

**Fix:** Sentinel becomes per-task identity set.

Old sentinel form: `<!-- recurring-materialized-2026-06-16 -->`
New sentinel form: `<!-- recurring-materialized-2026-06-16: a1b2c3d,e4f5g6h -->`

Where each comma-separated value is a 7-char `sha1` prefix of the registry entry's normalized
content (`replace(/\s+/g, ' ').trim()`).

**Render-time behavior** (`ToDoDailyRecurring.insertRecurringIntoToday`):

1. Parse registry → list of matching entries (existing parseRegistry logic, unchanged from v0.118.1).
2. Parse today's body → extract sentinel hash set:
   - Date-only (legacy): empty set
   - Empty-set: empty set
   - Full-set: parse comma-separated hashes
   - Absent: empty set
3. For each matching entry: compute hash. If hash NOT in set → materialize line into today, append
   hash to in-memory set.
4. Write updated sentinel: `<!-- recurring-materialized-<date>: <comma-joined-set> -->`. Includes
   empty form `<!-- recurring-materialized-<date>: -->` when no entries match (preserves the
   "we've run today" signal).
5. If post-render set equals pre-render set, skip file write (idempotency).

**Heal-existing migration** (`platform/install.js`, new step
`applyRecurringSentinelV070Migration`):

- Walk every `spice/to-do/**/ToDo-*.md`.
- For each `<!-- recurring-materialized-YYYY-MM-DD -->` (date-only, no colon): rewrite in place to
  `<!-- recurring-materialized-YYYY-MM-DD: -->` (empty set).
- Idempotent on re-run.
- Failure-loud per-file.
- `.sauce-backup/<ts>/` snapshot before mutating each file.
- Marker logic: skip files where the sentinel already has `: ` in it (already migrated).
- On the next Obsidian re-render, `ToDoDailyRecurring` re-runs and populates the set with current
  hashes — re-materializing whatever the registry currently says.

**Edge cases (acknowledged, documented in code comments):**

- Registry entry edited (title typo fixed): new hash → re-materializes; old materialized line stays
  (user can delete the duplicate). Acceptable tradeoff for v0.7.0; deeper identity (block-ids)
  deferred to v0.8.0+ if pain surfaces.
- Registry entry deleted: its hash stays in the sentinel set indefinitely. No harm (no re-add).
  Pruning deferred (YAGNI).
- Same task on multiple days: each day has its own date + set. No interaction.
- Hash collision: 7-char sha1 prefix = 268M combinations. For ~20 recurring tasks, collision
  probability is negligible.

### 1b — Markdown rendering in live-render to-do widgets (bug c)

**Symptom (accuris, 2026-06-16):** Cross-note to-do panel shows raw text like
`Take a look at Lambda migration thing that Evgenii [here](https://github.com/...)` and
`Send over docs to APM Instrumentation [[Patryk Szelagowski]]` — neither the `[label](url)` nor
the `[[wikilink]]` renders as a link.

**Root cause:** `ToDoDailyUnassignedMeetings._renderTaskRow` line 62 and
`ToDoDailyProjectGroups._renderTaskRow` line 117 both write `txt.textContent = ...`. `textContent`
writes raw characters — no markdown parse. Widget tests pass because they assert on
`_cleanTaskText(t.text)` string output, not on the rendered DOM. Item #2 of the postmortem
(no DOM-render coverage) surfacing as a real bug.

**Fix:** Hand-rolled tokenizer in each widget, emits raw `<a>` HTML matching the established pattern
from `platform/blueprints/daily/helpers/space-daily-dashboard.js:1225-1290`.

Two new private methods on each widget class (intentionally duplicated — two callsites only; per
`code-conventions.md` "three similar lines is better than a premature abstraction"):

```js
_tokenizeInline(text) {
  // returns ordered array of { kind: 'text'|'link'|'wikilink', ... }
  // kinds:
  //   { kind: 'text', value: '...' }
  //   { kind: 'link', label: '...', url: '...' }
  //   { kind: 'wikilink', target: '...', alias: '...' }
  // Order-preserving over the source string.
}

_renderInlineMarkdown(spanEl, text) {
  // tokenize → emit innerHTML with escaped text + proper <a> elements
  //   - external links:  <a href="${esc(url)}" target="_blank" rel="noopener noreferrer">${esc(label)}</a>
  //   - internal links: <a class="internal-link" data-href="${esc(target)}" href="${esc(target)}">${esc(alias||target)}</a>
  //   - plain text:      ${esc(value)}
}
```

`escapeHtml` is also a private method on each widget — copy-paste from space-daily-dashboard.js.

**Callsite swap** in both widgets:

```js
// Before:
txt.textContent = this._cleanTaskText(t.text);

// After:
this._renderInlineMarkdown(txt, this._cleanTaskText(t.text));
```

`_cleanTaskText` runs first (existing regex strips `[field:: value]` annotations) so the tokenizer
never sees them.

**HTML-injection safety:** Tokenizer always passes user-controlled strings (label, url, target,
alias, plain text) through `escapeHtml`. URLs additionally validated against a permissive scheme
allowlist (http:, https:, mailto:, obsidian:, file:); anything else is rendered as escaped text
instead of as a link href.

## Stage 2 — Verification net

### 2a — customJS static-vs-instance contract test (#1)

**New harness:** `platform/test/run-customjs-contract.js`. Zero-deps Node. Wired into
`release:preflight`.

**Algorithm — detect-by-shape:**

1. **Scan class definitions** under `platform/customjs/**/*.js` +
   `platform/blueprints/*/helpers/**/*.js` + `platform/blueprints/*/scripts/**/*.js`. Skip
   `platform/test/`, `platform/migrate/`, `platform/install.js`. Build map:
   `className → { file, members: [{ name, isStatic, kind: 'method'|'field' }] }`.
   - Class fields included (e.g., `static SCHEMA_VERSION = 5`) so property reads validate too.
   - Multiple definitions of the same class name → FAIL upfront.

2. **Scan callsites** for `customJS.<Class>.<member>` across `platform/`, `ranch/`, `commands/`,
   `spice/`, `.claude/`. Skip `node_modules/`, `.sauce-backup/`, `.git/`,
   `platform/test/seed-vault/`, `Docs/cycle-history.md`. Regex:
   `/\bcustomJS\.(\w+)\.(\w+)(?:\b|\()/g`. Captures both method calls and property reads.

3. **For each callsite (class, member):**
   - Class missing from defs → FAIL.
   - Member missing from class → FAIL (with list of declared members).
   - Shape: `hasInstanceMember = members.some(m => !m.isStatic)`.
   - If `hasInstanceMember && member.isStatic` → FAIL (the v0.116.0 / v0.118.0 bug shape).

4. **Report format:**

```
FAIL: customJS.RecurrenceParser.isSupported called at platform/blueprints/to-do/helpers/todo-create-task.js:42
  Class RecurrenceParser (platform/blueprints/to-do/helpers/recurrence-parser.js) has instance
  methods → customJS stores it as an instance.
  Member `isSupported` is declared `static` → not on the prototype → call throws at runtime.
  Fix: drop `static`, OR add instance delegator:
    isSupported(...a) { return RecurrenceParser.isSupported(...a); }
```

**Self-test fixtures** under `platform/test/fixtures/customjs-contract/`:

- `pass-instance-class.js` — instance method, instance callsite → PASS
- `pass-static-class.js` — all-static class, static callsite → PASS
- `fail-static-on-instance-class.js` — instance class + `static` member called (v0.116.0 bug
  shape) → FAIL with proper message
- `fail-unknown-member.js` — method name doesn't exist → FAIL
- `fail-multi-definition.js` — same class name declared twice → FAIL

**Harness cases:**
- CCONTRACT-1..5: each fixture asserted pass/fail
- CCONTRACT-6: scanner runs against live workshop tree; asserts zero failures (so future regressions
  break the build)
- CCONTRACT-7: edge case — scanner ignores `customJS.<Class>` references that are not member access
  (e.g., `if (customJS.Foo)`)

**Edge cases skipped (documented):**
- Dynamic dispatch (`customJS.X[varName]()`): out of scope.
- Destructured access (`const { method } = customJS.X; method()`): out of scope.
- Inherited members from `extends`: scanner reads only the direct class body. Extension classes
  are rare in customJS surface; deferred to a follow-on if it ever bites.

**Bug-(b) and bug-(c) value-prop:** Neither was a static-vs-instance bug, but CCONTRACT-6 would have
caught the v0.116.0 bug at preflight. The contract test is forward-looking.

**First-run failure policy:** If CCONTRACT-6 fails on first integration against the live workshop
tree, the surfaced violations are bugs to fix in THIS cycle (they would have been static-vs-instance
bugs latent in production). Do NOT add a baseline / grandfather mechanism for this harness — every
violation is a real bug class that already cost the v0.118.0 patch. Fixes are mechanical (drop
`static` or add instance delegator).

### 2b — Anchor lint + migration checklist + fixture landmine (#4)

**New lint:** `scripts/lint-display-markers.js`. Zero-deps. Wired into `release:preflight` after
`lint-schemas`.

**What it flags** (in `.js` files under `platform/**`, excluding `platform/test/`,
`platform/migrate/`, `platform/test/seed-vault/`, `platform/install.js`):

1. Regex literals anchored on markdown headings: `/^#{1,6} /`, `/^## Recurring Tasks/`, etc.
   Detection: regex literal contains `^#` followed by space.
2. String-prefix checks on heading patterns: `startsWith('## ')`, `indexOf('## ') === 0`,
   `=== '## Recurring Tasks'`, `match(/^### /)`. Detection: literal string starting with `## ` /
   `### ` etc. used in a `.match()` / `.startsWith()` / `.indexOf()` / equality context (line-level
   regex on the source).

**Default behavior:** WARN (preflight prints warnings but exits 0 unless threshold exceeded).
Threshold: any NEW warning relative to baseline.

**Baseline:** `scripts/lint-display-markers-baseline.json` (committed). Format:
`{ "warnings": [ { "file": "...", "line": N, "snippet": "..." } ] }`. Regenerated by
`npm run lint-display-markers -- --update-baseline`. Avoids first-run flood: existing patterns
grandfathered; new ones must be either fixed or explicitly opted out.

**Opt-out marker:** `// lint-display-markers:allow <reason>` on the same line as the flagged
construct. Reason required (parsed for non-empty content after `:allow `).

**Anchor convention note** — `Docs/agent-guides/code-conventions.md` gains a new section "Stable
anchors vs display markers":

```markdown
### Stable anchors vs display markers

Parsers MUST NOT key on display-mutable markers (headings, SectionLabel text labels) that future
cosmetic migrations may rewrite. Instead, key on stable anchors:

- HTML comments — `<!-- recurring-entries -->`, `<!-- recurring-materialized-... -->`
- Frontmatter fields — `recurring_section_start: true`
- Block-ids — `^todo-recur-abc123`
- Native dataviewjs invocations (whose code never changes shape)

Display markers (FLAGGED by `scripts/lint-display-markers.js`):
- `^# `, `^## `, `^### ` heading regex
- SectionLabel text labels (e.g., `text: "Recurring Tasks"`)
- Markdown formatting characters as section delimiters

Migrations legitimately match old display forms (in `platform/migrate/`); those files are
excluded from the lint by default.
```

### 2d — Cycle-discipline + dispatcher-contracts landmines (#6, #10)

Two new numbered entries in `Docs/landmines.md`:

**Landmine #N1 — Cycle scope discipline: smaller is faster**
```
v0.116.0 → v0.118.1 thrashed 8 cycles to ship a working to-do dialog because v0.116.0 bit off
8 new customJS classes + a recurrence engine + a +New Task dialog all at once. The bigger the
bundle, the more failure modes hide inside each other. When a feature exceeds 3 distinct surfaces
(class, schema, template, dialog, widget, migration), split into smaller cycles where each is
verified end-to-end before the next.
Counter-examples: v0.94.0 (single demo-driving blueprint) and v0.113.0 (single index + linter)
shipped clean on first try because scope was held tight.
Source: v0.118.1 cycle postmortem item #6.
```

**Landmine #N2 — Verify dispatcher / loader contracts before designing against them**
```
"Verify helpers before design asserts them" (existing rule) extends to runtime dispatchers and
loaders:
- customJS stores classes as instances (`new Class()`) → methods called via `customJS.X.method`
  must be on the prototype (non-static). Static methods are NOT visible to the dispatcher.
- Templater copy executes in source context, not vault context.
- installer runInstall is subprocess-spawning, not in-process.
Before designing a new consumer of a dispatcher: grep the dispatcher's loader code AND read one
working consumer to confirm the contract.
Catalog: Docs/agent-guides/code-conventions.md § Dispatcher contracts.
Source: v0.118.1 postmortem item #10; reinforced by v0.93.3 + v0.94.0.
```

**`code-conventions.md` § Dispatcher contracts** — new subsection summarizing:

```markdown
### Dispatcher contracts

| Dispatcher | Loading behavior | What it means for consumers |
| --- | --- | --- |
| customJS (CustomJS plugin) | `customJS.X = new X()` — stores instances | Members called via `customJS.X.method` must be non-static. Static-only utility classes are tolerated (detect-by-shape via `run-customjs-contract.js`). |
| Templater (`tp`) | Copies executing in source file context | `tp.file.creation_date(...)` resolves against the SOURCE file, not the destination. Always render template-injected values before scaffolding. |
| installer (`runInstall`) | Subprocess-spawning | Cannot share in-process state with caller. Errors propagate via exit codes + stdout; the calling process must catch + surface them. |

Adding a new dispatcher consumer: grep the dispatcher's loader code (e.g., search for `customJS`
assignment patterns or Templater's `evaluate` invocation), then read one working consumer to confirm
the contract before authoring the new one. v0.93.3 / v0.94.0 / v0.118.0 each paid this tax by not.
```
