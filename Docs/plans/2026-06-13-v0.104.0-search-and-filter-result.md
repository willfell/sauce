## Lessons (cycle-distinct)

### 1. Closing a multi-item ask across cycles is structurally sound when the items decouple cleanly

The original v0.102.0 ask had three items — sections / meetings link / search. Sections + meetings link shipped together at v0.102.0; search was deferred (v0.102.1 slot) because it could be layered on without blocking the structural moves. v0.103.0 then reframed the section model (single-page Confluence → hierarchical hubs), which raised the question: does v0.102.1's search design still apply? The answer at v0.104.0 was YES — the underlying need (in-page filter + tag chips + scoped-search escape hatch) is identical; only the surface map changed (Docs.md alone → Docs.md + every Section Hub). One helper consumed by two integration points cleanly absorbed both scopes. **Lesson:** when a multi-item ask defers items into future cycles, the deferred items don't auto-die just because an intermediate cycle reframes the surface. Re-read the original ask against the new model at scheduling time — if the user-need is unchanged and the surface is composable, the deferred design adapts. This is the third confirmation in three weeks (v0.95.1 anti-echo carrying forward across the v0.95.0 cowork-spine reframe; v0.102.1 search carrying forward across the v0.103.0 section-hubs reframe; THIS cycle).

### 2. The section-hub model gave us natural query scope per hub — no new schema field needed

The v0.103.0 design moved each section / sub-section to a first-class entity with its own hub note. That means each hub note has a UNIQUE folder path — `spice/projects/<slug>/docs/` for Docs.md, `spice/projects/<slug>/docs/<section>/` for Section Hub depth 1, `spice/projects/<slug>/docs/<section>/<sub>/` for Section Hub depth 2. DocSearch's `scopePath` arg + `recursive` flag are computed from the host hub's folder location at render time — no new frontmatter field, no new manifest schema, no migration. The hub note's filesystem path IS the query scope. **Lesson:** structural-hierarchy cycles (like v0.103.0) often pay forward unexpectedly — a future feature that needs "scope" gets it for free because the structural cycle already encoded scope as filesystem hierarchy. When designing a structural cycle, surface the latent affordances it creates ("each hub is also a scope boundary; each folder is also a query boundary") in the design doc's Carry-forward section, so future cycles can find them.

### 3. Re-render-on-keystroke works fine at <500 docs

The v0.104.0 design considered three filter-application strategies: (a) per-keystroke full re-render (chosen); (b) per-keystroke partial DOM diff; (c) debounced re-render (e.g., 150ms). Picked (a) at design time because real-world scopes are bounded (single-project ≤ 100 docs typical; even a heavily-used project caps around 30-50 docs based on accuris observation). Verified at S2.1 + S2.2 implementation time by reading the existing `ProjectDocsIndex.render` body — the full render loop is O(docs) with no per-doc network or async work, so per-keystroke re-render at 30 docs is sub-millisecond. **Lesson:** for in-vault helpers, the "performant" choice (debounce, virtual DOM diff) often costs more code complexity than the "simple" choice (full re-render) for any sub-1000-item scope. Defer the optimization until a real-world scope hits the regression. Codified as a carry-forward candidate (v0.104.x debounce only if/when a >500-doc project surfaces).
