# v0.99.0 — sparse-signal feedback — result

## TL;DR

Makes the v0.98.x learning loop correct for a user who gives sparse, prose-flavored feedback. Before this cycle, a surfaced-but-unticked kind counted as a SKIP, skips pushed weights down and counted toward warmup graduation — so a never-ticking user uniformly demoted everything, and after graduation (headspace deadline: 2026-06-16) the silence-built weights would have become authoritative. Three structural moves landed in one MINOR cycle:

1. **Engagement-gated learning days (ingest side).** Each (engagement, day) is classified ENGAGED / TAP-ONLY / SILENT at the 03:00 reconciler by re-reading yesterday's notes (NEW `reconcile-cowork` Step 3.4, restating the deterministic `classifyEngagementDay` contract inline). Only ENGAGED days emit observations (ticks AND skips), run decay, and progress warmup. A lazy one-tap can never demote anything; silence can never build authority.
2. **Prose-first capture (v=3).** The EOD feedback section reorders: one-tap `Useful: [ ] yes [ ] no` at the very top, the free-text typing fence directly below it (the PRIMARY channel), per-kind Mattered/Didn't-like lists + knobs keep their exact v=2 mechanics but render below, collapsed. Sentinel bumps to `v=3`; parsers tolerate v=1, v=2, AND v=3. A `<kind>:` line-prefix in the prose gets deterministic section scoping (`parseKindPrefixLines` — the LLM interprets intent but cannot mis-route the kind).
3. **Satisfaction series (schema 4).** The one-tap logs a rolling 30-day yes/no series into `learned_weights.totals.satisfaction[]` via `appendSatisfaction` — the platform's first cheap KPI, and the v0.99.1 doctor's first self-grading input. `learned_weights` bumps schema 3 → 4 (`normalizeLearnedWeightsV4`: adds `totals.engaged_days[]` + `satisfaction[]`; `warmup_until` retired/null). The ONE-TIME silence-reset migration keeps weight + ticks, ZEROES silence-contaminated skips, and forces every kind back into warmup — defusing the 2026-06-16 silent-graduation deadline by construction. Graduation rule is now `engaged_days.length >= 7` AND `ticks + skips >= 7`. `applyIntentKindTicks` makes uprank prose count as a kind tick.

No new scheduled job; no contract bump (0.35.1 holds); NO new substitution tokens; NO new installer write surfaces under user-owned paths. Strict mode added to the three touched helpers.

## Discoveries and lessons

### 1. RED-phase coincidental greens — version-tolerant parsers need NEW-field asserts

`FEEDBACK_SENTINEL_RX` is generic (`v=(\d+)`), so the v=2 parser already accepted v=3 bodies — HC-V0990-PARSE-A2 passed before any code change. GATE-A5 was also green at S1.1, by design: `evaluateWarmup`'s code is unchanged in this cycle — only its CALL semantics shifted (the caller now passes engaged-day counts instead of calendar days). 24 of 26 were genuinely RED. **Lesson: when a parser is version-tolerant by regex, RED cases must assert the NEW field (satisfaction), not just the new version string — a version-string assert against a tolerant parser proves nothing.**

### 2. Pure-data helpers must deep-copy EVERYTHING, and version gates must coerce types

Quality review caught two latent bugs in the S1.4 V4 normalizer: (a) `Object.assign({}, eng.totals)` aliased the caller's `engaged_days` / `satisfaction` / `scanned_days` arrays straight through the V3 normalizer — mutating the normalized output mutated the caller's input; (b) the migration gate `priorVersion !== 4` would re-run the DESTRUCTIVE silence-reset on a string `"4"` — plausible after LLM/YAML round-trips (the V3 normalizer already tolerated string `"1.1.0"`, precedent that string versions occur in the wild). Both fixed at S1.4.1 (`f805324`) with test pins added to HC-V0990-SCHEMA-A5. **Lesson: pure-data helpers must deep-copy every nested structure they return (not just the top level), and any version gate guarding a destructive migration must `Number()`-coerce before comparing — a string version that re-triggers a one-time reset is data loss.**

### 3. Adding a gate to a multi-step OI requires sweeping EVERY step + Idempotency + Failure-modes

S1.5 added Step 3.4's gate, but spec review found 4 ambiguities the 3am LLM could not have resolved: (a) does totals bookkeeping (notes_scanned, scanned_days) run on TAP-ONLY/SILENT days? (b) a stale "ZERO signal → no writes" Failure-modes line contradicted sub-step 13a's normalize-on-first-touch; (c) the learned_weights skeleton still initialized `warmup_until` that 13a retires; (d) Step 12 was missing the ENGAGED-only annotation Step 11 had. All fixed at S1.5.1 (`00f92cf`). **Lesson: gate consequences must enumerate what RUNS, not only what SKIPS — every step, the Idempotency block, and the Failure-modes block must each answer "what happens on a gated day?" explicitly, or the fire-time LLM resolves the ambiguity for you.**

### 4. `external_plugins[]` entries are live dependencies on a third-party index

`realclaudian` (an auto-install default since v0.94.0) was DELISTED from the upstream obsidian-releases index (verified 2026-06-12; only forks remain), so `applyExternalPluginInstall` errored on every real install and integration-smoke went RED mid-cycle — it was GREEN at S0 hours earlier. Fixed at S1.7.1 (`c249a1a`): removed the dead entry; convenience 0.4.0 → 0.4.1; installed copies in consumer vaults untouched (the installer never uninstalls). The helper's loud error-level posture WORKED — it caught a real ecosystem regression rather than silently shipping a broken install path. **Lesson: every `external_plugins[]` entry is a standing dependency on a third-party index that can change under you between commits. v0.99.1 doctor seed: index-presence drift for declared external plugins is a doctor-checkable KPI.**

### 5. Fixtures without a consuming runner rot silently

The compose-feedback-capture fixture dir (5 cases) pinned v=2 truth, was consumed by ZERO runners (grep-verified at review), and would have misled any future regeneration or shape audit that treated it as golden. Regenerated to v=3 at S1.2.1 (`3c21105`). **Lesson: every fixture dir needs a consuming harness or deletion — "golden" files no test reads are landmines, because they assert nothing while LOOKING like ground truth.**

### 6. Subagent harness reports need controller verification

The S1.7 implementation subagent reported bootstrap 125/1 and called the failure pre-existing; a direct controller re-run showed 85/0 — the real failure was integration-smoke's realclaudian error (Discovery 4), not bootstrap at all. **Lesson: trust-but-verify applies to harness COUNTS, not just code claims — re-run the suites yourself before accepting a subagent's pass/fail summary, especially when the summary explains a failure away.**
