# v0.129.0 — Automated release pipeline (design)

**Date:** 2026-06-23
**Status:** approved (brainstorm), pending implementation-plan
**Topic:** End-to-end release automation — per-component semver from conventional commits, single release-PR gate, auto-tag → existing `release.yml` → tap auto-merge → brew.

## Problem

Cutting a release today is four manual acts (per `Docs/agent-guides/build-test-verify.md` § Release workflow):

1. **Decide** the next version number (human judgment).
2. **Edit** `platform/manifest.json` `workshop_version` + `package.json` `version` (lockstep, gated by `check-version-sync.js`) **and** the 34 independently-versioned components (13 blueprints + 21 mechanisms).
3. **Create + push** the annotated tag `v<X.Y.Z>` (currently a hard user-approval gate).
4. **Merge** the auto-opened `willfell/homebrew-sauce` formula PR.

Goal: develop → merge to main → tap one button → everything else (versioning of all components, tagging, GitHub release artifacts, brew formula update) cascades automatically, using semantic-versioning rules driven by the conventional commits already in use.

## What already exists (do not rebuild)

- **Conventional commits** are the established norm (`feat(scope):`, `fix(scope):`, multi-scope).
- **`release.yml`** fires on a `v*.*.*` tag push → `preflight` job (full `release:preflight`) → `bump-tap` job (computes tarball sha256, patches `Formula/sauce.rb` in `willfell/homebrew-sauce`, opens a PR via `peter-evans/create-pull-request` using `TAP_PR_TOKEN`).
- **`ci.yml`** runs `release:preflight` on every push/PR to main (macos + ubuntu matrix) plus a real `brew install` + fresh-vault bootstrap smoke on macOS.
- **`check-version-sync.js`** gates `package.json.version === manifest.workshop_version`.
- The manifest **already declares each component's source `path`** (`blueprints/meetings`, `mechanisms/breadcrumb`, …) — free commit→component attribution.

## Decisions (locked during brainstorm)

| Fork | Decision |
| --- | --- |
| Versioning scope | **Full per-component semver** — every blueprint + mechanism bumps independently, plus the umbrella `workshop_version`. |
| Autonomy / gate | **Single release-PR gate** — bot maintains one standing release PR; merging it (one tap) is the only human checkpoint; tag + release + tap-merge + brew all cascade from that merge. |
| Engine | **Thin custom bumper** living in `scripts/release/`, reading/writing `platform/manifest.json` directly (no second source of version truth). **Zero-dep, vendored** — see note below. |

> **Engine deviation from brainstorm (zero-dep, not npm libs).** The brainstorm chose "thin custom over libs (`semver` + `conventional-commits-parser`)." Implementation discovery overrides this: `scripts/` here is **zero-dep by explicit house rule** (`rebaseline-seed.js`: *"Zero-dep. Node built-ins only. Failure-loud."*), and `semver` is only an undeclared transitive today. The conventional-commit grammar we need is small and fully under our control. So we **vendor** a ~40-line commit classifier + a ~15-line semver-inc in `scripts/release/lib/`, rather than add npm dependencies. This honors the house rule, removes all CI `--omit=dev` dependency-resolution risk, and shrinks supply-chain surface. Functional behavior is identical to the approved design. The vendored parser is fully exercised by `run-release-bumper.js`. |
| Bump policy | **Standard semver.** Pre-1.0 component: `fix/perf/refactor`→patch, `feat`→minor, `feat!`/`BREAKING CHANGE`→minor (0.x has no stable contract), `chore/docs/test/style`→no bump. Post-1.0: `feat!`→major. Crossing to 1.0 and any manual override via a `Release-As: X.Y.Z` commit footer. |
| Attribution | **Path-based** via the manifest `path` field; commit type/scope used only to classify bump level, never for attribution (mis-scoped commits still attribute correctly). |

## Architecture & data flow

```
 develop ─► merge feature work to main (ci.yml green, as today)
                    │
                    ▼  push:main
   ┌────────────────────────────────────────────────────────────┐
   │ release.yml :: prepare-release  (NEW; runs on push to main) │
   │   scripts/release/compute-release.js                        │
   │    1. git log since last v* tag                             │
   │    2. attribute each commit → component dir (manifest path) │
   │       + a "platform/umbrella" bucket for shared roots       │
   │    3. conventional-commits-parser → per-component bump level │
   │    4. semver.inc → new per-component + umbrella versions     │
   │    5. rewrite platform/manifest.json (+ package.json)        │
   │    6. regenerate version-pin snapshot fixture + changelog    │
   │    7. open/UPDATE one standing release PR (peter-evans)      │
   └────────────────────────────────────────────────────────────┘
                    │
       you tap "merge" on the release PR  ◄── the single gate
                    │
                    ▼  push:main (merge commit, msg "chore(release): vX.Y.Z")
   ┌────────────────────────────────────────────────────────────┐
   │ release.yml :: tag-on-release-merge  (NEW; if release commit)│
   │   creates + pushes annotated vX.Y.Z using RELEASE_PAT        │
   │   (PAT required so the tag push re-triggers the jobs below)  │
   └────────────────────────────────────────────────────────────┘
                    │
                    ▼  push:tag v*.*.*
   ┌────────────────────────────────────────────────────────────┐
   │ release.yml :: preflight → bump-tap  (EXISTING, unchanged)   │
   │   + NEW final step: gh pr merge <tap-pr> --squash            │
   └────────────────────────────────────────────────────────────┘
                    │
                    ▼  post-release-PR-merge (separate job on main)
   ┌────────────────────────────────────────────────────────────┐
   │ release.yml :: rebaseline-seed  (NEW; post-merge only)       │
   │   seed:prev + seed:rebaseline → commit chore(seed) to main   │
   └────────────────────────────────────────────────────────────┘
                    │
                    ▼
        brew upgrade sauce serves the release
                    │
   (boundary) consumer vaults: sauce update --bump-pins runs on
              YOUR machine — GitHub cannot reach them.
```

**Core idea:** the bumper never tags. It only maintains a *release PR* holding all computed version edits + changelog; the PR always reflects "what would ship right now" because every push to main force-updates the same release branch. Merging it is the one decision; tag creation keys off that merge; from the tag onward, the *existing* `release.yml` runs unchanged plus a one-line tap auto-merge.

## Components

### 1. `scripts/release/compute-release.js` (the bumper)

Thin orchestrator. Responsibilities:

- **Range:** `git describe --tags --abbrev=0 --match 'v*'` → commits since last tag (`git log <tag>..HEAD --name-only`).
- **Attribution:** for each commit, map changed file paths against manifest `path` prefixes → set of affected components. Paths under shared roots (`platform/helpers`, `platform/install.js`, `platform/cli`, `platform/bootstrap-lib`, `scripts/`, `Docs/`, `.github/`, root files) → **umbrella only**.
- **Classification:** the vendored classifier extracts `type`, `scope`, `!`/`BREAKING CHANGE`. Map to bump level per the policy table. A commit affecting N components contributes its bump level to each.
- **Compute:** per component, take the max bump level among its commits; vendored `inc`. Umbrella `workshop_version` = max bump level across all components that changed this release (always bumps if anything ships). Honor `Release-As:` footer override (forces exact version for the scoped component, or umbrella if unscoped).
- **Version records the write path updates (all hand-synced today — grounding confirmed there are several per component):**
  1. `platform/manifest.json` — catalogue entry `version` per component + top-level `workshop_version` + `date`.
  2. `platform/blueprints/<c>/manifest.json` / `platform/mechanisms/<c>/manifest.json` — the per-component manifest's own `version` (the **second** version record per component; the catalogue is *not* generated from it — both are hand-maintained today and must agree).
  3. `ranch/platform-subscription.json` — `workshop_version` + per-component subscription pins.
  4. `package.json` — `version` (lockstep with `workshop_version`; `check-version-sync.js` backstop).
  - **Explicitly NOT touched:** `scheduled-job-contract.json#contract_version` — grounding showed it is `0.35.1` while cowork is `0.40.2`, i.e. it is an **independently hand-versioned contract, not a cowork mirror** (landmine #20's "mirror exactly" wording is stale). Forcing a mirror would corrupt it.
- **Default `--dry-run`; writes only under `--write`.** Default invocation prints the computed plan (components, old→new, changelog preview) and writes nothing — mirrors `scripts/rebaseline-seed.js`. The write path is guarded behind an explicit `--write` flag so the tool is inert-by-default and cannot corrupt version state unless deliberately invoked. The harness exercises the write path against synthetic fixtures, never the real repo.
- **Vendored helpers (zero-dep):** `scripts/release/lib/conventional.js` (parse `type(scope)!: subject`, detect `BREAKING CHANGE`/`BREAKING-CHANGE` in body/footer, detect `Release-As:` footer) + `scripts/release/lib/semver-inc.js` (split `X.Y.Z`, bump one level, zero the lower fields). Both are pure functions with full harness coverage.

What it does **not** do: tag, push, touch the seed (post-merge only, §3), or modify any test assertion (the lockstep-collapse is staged separately — §3).

### 2. `platform/test/run-release-bumper.js` (harness)

Loads the vendored libs + `compute-release.js` in a sandbox; feeds synthetic commit fixtures + a fixture manifest written to a `mkdtemp` dir; asserts:

- vendored `conventional.js`: header parse (`type`, `scope`, `!`), `BREAKING CHANGE`/`BREAKING-CHANGE` footer detection, `Release-As:` footer extraction, malformed-header tolerance (returns null → no bump);
- vendored `semver-inc.js`: patch/minor/major increments zero the lower fields correctly;
- path-attribution correctness (single component, multi-component commit, shared-root→umbrella-only);
- bump-level classification (`fix`→patch, `feat`→minor, `feat!`→minor@0.x / major@≥1.0, `chore`→none);
- umbrella = max bump across changed components;
- `Release-As:` override forces the exact version;
- write path (`--write` against the temp fixture): updates catalogue + per-component manifest + ranch pins + package fixture consistently; leaves `contract_version` untouched;
- idempotence (running twice over the same range is stable);
- cleans up its temp dir in a `finally`.

Wired into `release:preflight` (appended after `run-finance-plan-state.js`) so it gates every PR + push + tag, exactly like the other 50+ harnesses.

### 3. Lockstep handling — staged (this PR vs. verified follow-up)

Grounding revealed the lockstep is more intricate, and more landmine-rich, than the brainstorm assumed. Rather than blind-rewrite load-bearing assertions in one autonomous pass, it is split:

**In this PR (Phase 0):** the bumper's `--write` path updates *all* version records listed in §1 (catalogue, per-component manifests, ranch pins, package.json) consistently. **No existing test assertion is modified.** Because the bumper is not yet wired into any workflow (no `release.yml` edits live), nothing is blocked by deferring the assertion collapse — the existing `HC-V0*-VERSION-*` assertions continue to pass against `0.128.x` exactly as today.

**Deferred to Phase 0b (verified follow-up, before Phase 1 goes live):** collapse the manual version-pin toil in `run-helper-cases.js`. Grounding surfaced three non-obvious invariants this collapse MUST preserve, each of which would have been silently broken by a naive snapshot rewrite — they are why this is deferred rather than rushed:

1. **`contract_version` is independent, not a cowork mirror** (`0.35.1` vs cowork `0.40.2`). It must stay out of any version-snapshot equality.
2. **`ranch/platform-subscription.json` can lead `package.json`/`manifest` within a minor.** The existing assertions are written as *within-minor range regexes* (`/^0\.128\.\d+$/`) precisely to tolerate this intra-cycle patch drift — that idiom is the evidence the invariant is real (the three files happen to be aligned at `0.128.2` right now, but the harness is built to survive them diverging by a patch). Any collapse must preserve this tolerance (e.g. compare major.minor against the snapshot, allow patch to differ), or it goes red the moment they drift.
3. **Two version records per component** (catalogue + per-component manifest) plus the subscription pin — all three must be cross-checked, not just one.

The Phase 0b mechanism remains the **generated snapshot fixture** `platform/test/fixtures/component-versions.snapshot.json` that the bumper regenerates, with the converted assertions cross-checking each independent mirror against it at the correct tolerance (exact for component pins that are exact today; major.minor for the workshop/package/ranch triple). Self-check: every converted assertion must be TRUE against the live repo before the change lands; any case that resists safe conversion is left as-is.

- **`package.json.version`** — bumper writes it in lockstep now; `check-version-sync.js` remains the backstop gate (unchanged).

### 4. GitHub wiring (`release.yml` edits — authored, user-pushed)

> **Constraint:** Claude's OAuth scope rejects pushes touching `.github/workflows/*.yml`. The `release.yml` diff is delivered as a Markdown patch doc (`Docs/plans/2026-06-23-v0.129.0-release-yml-patch.md`); the user applies + pushes that one file. The bumper + harness (Phase 0) are pushable normally. This maps cleanly onto the phased rollout (Phase 0 = Claude-pushable; Phase 1 = user applies workflow + secret).

Three additions to `release.yml`:

- **A. `prepare-release`** — trigger `push: branches: [main]`; `permissions: { contents: write, pull-requests: write }`. Runs `compute-release.js`, opens/updates the standing release PR on a fixed branch via `peter-evans/create-pull-request`. Idempotent.
- **B. `tag-on-release-merge`** — trigger `push: branches: [main]`, guarded `if: startsWith(commit message, 'chore(release):')`. Creates + pushes the annotated `v<X.Y.Z>` tag **using `RELEASE_PAT`** (a default-`GITHUB_TOKEN` tag push will NOT re-trigger the tag-keyed jobs — GitHub loop-prevention; the PAT is the price of leaving the existing tag jobs untouched).
- **C. Tap auto-merge** — append one step to the existing `bump-tap` job: `gh pr merge <pr> --squash --delete-branch` via `TAP_PR_TOKEN` (`--auto` if the tap later gains required checks).
- **D. `rebaseline-seed`** — trigger `push: branches: [main]`, guarded on the release commit; runs `seed:prev` + `seed:rebaseline`, commits `chore(seed): rebaseline to vX.Y.Z` to main. **Post-merge only** — never on the release-PR branch (per the v0.124.0 + v0.128.0 on-branch-rebaseline trap).

**One-time user setup:** push the `release.yml` change; create `RELEASE_PAT` (fine-grained PAT, `contents: write` on `willfell/sauce`). `TAP_PR_TOKEN` already exists.

## Boundaries (honest scope limits)

- **Consumer vaults are out of GitHub's reach.** The pipeline ends at "brew serves the release." Propagating into `ero`/`accuris`/`headspace` still means `sauce update --bump-pins` on the user's machine, per vault. Caveat: `--bump-pins` only updates **already-subscribed** items; a new transitive dep needs a manual per-consumer JSON edit (`lesson_bump_pins_no_transitive_add`).
- **Optional follow-on (separate cycle, not this one):** a `sauce sync` that loops known vaults running `--bump-pins` for each.
- **This cycle does not bump its own version or tag.** The PR delivers Phase 0 tooling at the current `0.128.0` (no version drift → preflight green). The version bump + tag for shipping this work is the user's gated act at release time (and, once Phase 1 is live, the bumper itself would compute it).

## Testing

- New harness `run-release-bumper.js` (§2), wired into `release:preflight`.
- `compute-release.js --dry-run` validated against the last real release: must reproduce `v0.128.0`'s component bumps from `v0.127.x..v0.128.0` commits before Phase 1 goes live.
- Workshop dogfood (`node platform/install.js --vault . --auto-approve`) green before push.
- CI (`ci.yml`) green on the PR (macos + ubuntu preflight + brew smoke).

## Rollout (irreversible parts last)

1. **Phase 0 (pushable by Claude; THIS PR):** vendored `lib/` + `compute-release.js` (dry-run default, write behind `--write`, updates all version records but no test assertions), `run-release-bumper.js` wired into `release:preflight`, the `release.yml` patch doc. Zero behavior change — nothing wired to a workflow yet. Validated by the harness + `--dry-run` against the live history.
2. **Phase 0b (verified follow-up, Claude-pushable):** collapse the `run-helper-cases.js` version-pin toil into the snapshot fixture, preserving the three invariants in §3. Done with the maintainer reachable to confirm each invariant; not rushed into the Phase 0 PR.
3. **Phase 1 (user applies):** push the `release.yml` diff + create `RELEASE_PAT`. The release PR begins opening on each push to main; user hand-inspects the first one or two before merging — auto-tag live but watched.
4. **Phase 2:** flip on tap auto-merge (`bump-tap` final step). Full hands-off cascade.

## Risks

- **Seed-rebaseline timing** is the single most delicate piece (bitten twice: v0.124.0, v0.128.0). Implementation must confirm exact sequencing against those cycle notes; design keeps it strictly post-merge in its own job.
- **Mis-attribution** of a shared-root commit that should have bumped a component: mitigated by the release-PR gate (human sees the computed bumps) + `--dry-run` validation.
- **Vendored commit-classifier correctness** vs. a battle-tested npm parser: mitigated by full harness coverage of the grammar we actually use (header parse, `!`/`BREAKING CHANGE` detection, `Release-As:` footer, multi-component scopes) — and we control the commit grammar, so unsupported edge cases can't appear without a corresponding test.
- **Branch-protection interaction:** if PR-gated branch protection is later enabled, `tag-on-release-merge` + `rebaseline-seed` commits to main need an exempt actor (the `RELEASE_PAT` identity).
