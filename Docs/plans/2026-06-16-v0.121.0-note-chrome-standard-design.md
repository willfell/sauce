# Note-chrome standard (vault-wide)

## Context

Nav flow, section headings, horizontal-rule spacing, breadcrumbs, and new-note open
behavior are inconsistent across the 13 blueprints. The project blueprint (v0.109.0 visual
overhaul) and the finance blueprint already model most of what "right" looks like; the rest
have drifted. This spec defines ONE canonical top-of-note grammar, promotes the project-only
rendering primitives into shared mechanisms so a single script drives each concern across
every blueprint, fixes two button bugs and the new-note edit-mode bug, and lays down lint +
per-blueprint heal migrations + seed coverage so the standard holds on deploy with confidence.

Brainstorming decisions (2026-06-16): grammar = **breadcrumb → nav → rules**; breadcrumb =
**config-driven shared mechanism**; narrow-width buttons = **wrap to more rows**; delivery =
**Approach 1 (mechanisms + per-blueprint declarations)**; `# H1` titles = out of scope.

## Goals

1. A single documented grammar every blueprint template conforms to.
2. Breadcrumb in **every** blueprint, rendered by one shared, config-driven mechanism.
3. Section labels (not `## H2`) everywhere, via one shared mechanism.
4. Buttons: icon + label, centered, fill width, **wrap** on narrow screens, never overflow,
   never jitter on hover.
5. Newly created notes open in **read/preview** mode — never edit-with-title-selected.
6. Existing consumer notes healed via idempotent migrations; covered by seed-vault asserts.
7. Standard routed into `CLAUDE.md` + an agent-guide so it is followed while developing.

## Non-goals

- Removing or restyling `# H1` note titles (left as-is).
- The unified single-call `NoteChrome` renderer (Approach 2) — possible later consolidation,
  not this arc.
- Spreading `DocSearch` to all blueprints (out of scope; revisit separately).

## 1. The canonical grammar

```
[Breadcrumb]          live-rendered; renders NOTHING on a top-level hub (no parent)
SpaceNavButtons       global nav bar
---
<BlueprintNav>        per-blueprint row (centered, fills width, wraps)
---
[<SectionNav>]        ONLY when inside a section/leaf (e.g. + New Doc / + New Section)
---
<content>             SectionLabel sections — NO ## H2/### H3, NO --- between content sections
```

Rules:

- Exactly **one** `---` between each nav tier. Never doubled (`---`\n`---`), never with a
  blank line gap above/below. (Fixes scratch `nav → ⏎ --- ⏎ ⏎ ---` and the project empty
  rule bands.)
- **No `---` between breadcrumb and the global nav bar.** The breadcrumb is a thin trail that
  sits directly above the bar.
- **Top-level hub** (`Projects.md`, `Trips.md`, `Finance.md`, etc.): no breadcrumb; starts at
  the global nav bar; its blueprint row is the centered `+ New X` button; then `---`; then a
  `SectionLabel` ("All Projects") — never `## All Projects`.
- This **extends**, not contradicts, `project-blueprint-ui.md §3`: that rule ("no `---`
  between sections") governs **content** sections (SectionLabel owns those). The `---` here are
  **nav-tier separators** only.

## 2. Button rules (all nav tiers + EntityCreate)

- Icon (icons mechanism) + label on every button.
- Centered, `flex: 1` to fill width, **`flex-wrap: wrap`** so buttons wrap to additional
  centered rows when too narrow — never truncate, never overflow.
- Label-span safety net: `white-space: nowrap; overflow: hidden; text-overflow: ellipsis`.
- **Hover-jitter fix**: `accent-button.js` currently rebuilds `cssText` via string `.replace()`
  on hover (duplicate props → micro-reflow → New Doc / New Section jump to one side). Replace
  with mutation of individual style properties (`btn.style.background = …`), matching the
  pattern `space-nav-buttons.js` already uses for its hover handlers.

## 3. New-note open mode

- Every create+open path opens the note in **read/preview** mode with no title selection.
- Add a shared helper `openInReadMode(file)` (in the `convenience` mechanism) that does
  `getLeaf(...).openFile(file)` then forces `setViewState({..., state: { mode: "preview" }})`.
- Route ALL create+open sites through it:
  - `entity-create.js` (two `openFile` sites: existing-file branch + new-file branch).
  - `nav-buttons` action handlers (`createFromTemplate`, `runTemplaterTemplate`, `openLink`).
  - `ranch/scripts/project/project-task-create-listener.js` and any other `openLinkText`
    create sites surfaced during the v0.121.0 audit.
- `app_settings.defaultViewMode:"preview"` is already set platform-wide; this closes the
  brand-new/empty-note gap where Obsidian overrides it into edit mode. Journal-from-nav is the
  reproduction case.

## 4. Section labels

- No `## H2` / `### H3` used as a section heading in any note body → `SectionLabel`.
- `# H1` note titles unchanged (non-goal).

### 5.1 Breadcrumb declaration schema (starting contract — finalize in v0.121.0 plan)

Per-blueprint manifest gains a `breadcrumb` block, type-dispatched on the note's frontmatter
`type`. Each trail segment resolves a **label** and (for ancestors) a **link target** from
frontmatter fields or path derivation; the current note is the last segment, plain text, no
link. Illustrative:

```json
"breadcrumb": {
  "types": {
    "doc-note": {
      "ancestors": [
        { "label": "fm:project_title|path:1", "link": "fm:project|path-hub" },
        { "label": "Docs", "link": "path:docs-hub" }
      ],
      "current": { "label": "fm:title|file:basename" }
    },
    "meeting": {
      "ancestors": [{ "label": "Meetings", "link": "hub:meetings" }],
      "current": { "label": "file:basename" }
    }
  }
}
```

Resolver order of precedence + the exact field-reference grammar (`fm:`, `path:`, `hub:`,
`file:`) is finalized in the v0.121.0 plan, with the project blueprint migrated onto it first
as the proof (must reproduce today's `proj / Docs / Architecture` output exactly).

Top-level hubs declare no `current`/ancestors (or are omitted) → breadcrumb renders nothing.

## 7. Migration plan

- **Live-rendered chrome needs no migration.** Promoting `SectionLabel`/`Breadcrumb` to
  mechanisms with unchanged class names reflects on Obsidian reload. Migrations target
  **static body text only**: injected breadcrumb `dv.view` call, literal `---`, `## H2`
  headings, deprecated literal blocks.
- **One heal migration per blueprint** — `applyXxxChromeHeal(vault, ...)` in
  `platform/install.js`, modeled on `applyDocsHubButtonRepair` (~install.js:2077): per-note
  try/catch, `.sauce-backup` snapshot, history events, **idempotent**, fails loud but never
  throws. Each migration:
  1. injects the `Breadcrumb` `dv.view` call as the first chrome block where missing;
  2. normalizes nav-tier `---` (collapse doubles + blank gaps, insert missing rules);
  3. rewrites `## H2`/`### H3` section headings → `SectionLabel` dataviewjs blocks;
  4. removes deprecated blocks (project's stray New Doc).
- **Stable-anchor matching** (landmines: stable-anchors-vs-display-markers): key on dataviewjs
  invocation substrings + frontmatter, never on display markers. Migrations legitimately match
  the **old** `## H2` form and are exempt from the display-marker lint.
- **materialize_once guard** (lesson, v0.119.1): templates that materialize under
  `{{module_directory}}/` must keep `materialize_once: true` so cosmetic template diffs never
  overwrite user content — body changes flow through migrations, not template re-copies.

## 8. Testing plan

- **Seed-vault** (`platform/test/run-seed-migrations.js` + `seed-vault/`): per migration, add
  an `HC-V0XYZ-SEED-MIGRATE-CHROME-<blueprint>-*` family. Seed a note at pre-migration shape
  (literal `## H2`, doubled `---`, no breadcrumb call); assert post-install: breadcrumb call
  present, correct `---` grammar, SectionLabel block present, `.sauce-backup` snapshot exists,
  user content preserved, idempotent on 2nd install. Rebaseline forward at each cycle close.
- **Renderer harness** (DOM-stub, like `run-v0109-projects-overhaul.js`): assert `Breadcrumb`
  builds the correct trail per blueprint type (incl. project parity), and button rows wrap
  (no overflow) without hover jitter.
- **Lint gate** in preflight (§5).
- **Manual dogfood**: Cmd+R smoke on the workshop's own `spice/` notes per blueprint — the one
  thing headless seed tests cannot cover: real Obsidian rendering + open-mode behavior.
