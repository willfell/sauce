## What shipped

v0.75.1 closes all six v0.75.0 deploy carry-forwards and first-fire correctness issues. Six workstreams ran against the same patch-level release: Workstream A adds a four-source precedence helper (`_resolveWorkshopPath`) to `cmd-update.js` so `sauce update --bump-pins` finds the brew-installed workshop even when `ranch/platform-installed.json` has `workshop_path: null` — which it does on every pre-v0.75.1 consumer vault. Workstream B collapses `cmd-update.js`'s legacy git-fetch + reset path (dead since brew distribution) into a thin delegation to `bootstrap.phaseRunInstaller`, making `sauce update` end-to-end against non-git consumer vaults for the first time. Workstream D threads the `--quiet` flag through `sc-bridge.js`'s `loadIndex` function so non-fatal "skipping unparseable .ajson" stderr warnings are actually suppressed. Workstream E adds a one-line write to `install.js` so the top-level `workshop_version` field in `ranch/platform-installed.json` is refreshed on every install. Workstream G strips 93 emoji characters from 15 engagement-template prompt files (3 engagement types × 5 cadences) and installs a fail-closed audit harness gate HC-V0751-A1. Workstream H tightens morning-briefing step 14's semantic-warning misfire condition (gated on step 12b having actually run) and aligns the warning text verbatim with `gather-semantic-related`'s orchestrator integration contract. Per-vault deploy of v0.75.1 is now a one-command flow: `sauce update --bump-pins`.

Workshop 0.75.0 → 0.75.1. Cowork 0.14.0 → 0.14.1. smart-connections-bridge 0.1.0 → 0.1.1. Engagement-types 0.3.0 → 0.3.1. 11 new harness cases.

## Per-workstream narrative

### Workstream A — `_resolveWorkshopPath` helper + `--workshop-path` flag

**What shipped:** New `_resolveWorkshopPath(installed, argv, hooks)` helper in `platform/cli/cmd-update.js` with four-source precedence: (1) `argv.workshopPath` (explicit `--workshop-path` CLI override), (2) `installed.workshop_path` (preserved when present from a prior v0.75.1+ install), (3) ancestry walk from `process.execPath` — climbs the directory tree looking for a `libexec` ancestor that contains a `platform/` subdirectory, which is the brew-installed layout, (4) throws `Could not auto-detect workshop_path. Pass --workshop-path <path> explicitly.` when all sources are empty. The helper is exported as `module.exports._resolveWorkshopPath` so HC-V0751-B1..B4 can exercise all four branches directly without invoking the full CLI. `handleBumpPins` now delegates to the helper. `run()` parses a new `--workshop-path <path>` flag and threads it through.

**What we learned:** The workshop self-install case (`node platform/test/run-install.js .`) goes through a different path than a brew consumer — no `libexec` ancestor exists in the workshop repo's directory tree. This means auto-detection (source 3) never fires for workshop dogfood. That's fine: the workshop doesn't use `sauce update --bump-pins`; it uses `run-install.js` directly. The `--workshop-path` escape hatch (source 1) covers any unusual deploy scenario. The `hooks` parameter (`{ _execPath }`) was critical for making HC-V0751-B3 testable without mocking `process.execPath` globally — a small but important testability design.

### Workstream B — `sauce update` brew-aware (collapse to thin wrapper)

**What shipped:** Removed the block from `cmd-update.js` line 128 through line 173 (the "standard sauce update flow" — `git fetch origin main`, `git reset --hard`, `npm install`, progress-step prints, migration hint). This path has been dead architecture since brew distribution landed in v0.36.0: consumer vaults are not git checkouts; `git fetch` fails immediately with `fatal: not a git repository`. The replacement is one line: `await _runInstaller(ctx)`. Three helper functions removed (`_gitExec`, `_npmInstall`, `_printMigrationHint`). Two now-unused `require()` calls removed (`child_process.spawnSync`, `visual/section`). Net ~30 lines deleted.

**What we learned:** The test deletion pattern is important: when a refactor removes code that a test exercises via a testable hook (HC-V0751-C2 used `ctx._gitExec`), the test must be updated too. HC-V0751-C2 was written to assert `!gitFetchCalled` after `cmdUpdate.run(ctx, [])` — but after S4, the `_gitExec` context hook is never called because the dispatch path that used it was deleted. The case still PASSes (the assertion `!gitFetchCalled` is trivially true), which is the correct outcome. Lesson: test assertions on deleted-code-path stubs can go silent-green; confirm they're measuring the right thing.

### Workstream D — sc-bridge `--quiet` actually suppresses stderr

**What shipped:** Threaded `flags` parameter through `loadIndex(vaultRoot, flags)` in `sc-bridge.js`. The non-fatal `process.stderr.write` at the `.ajson` parse-failure catch block now fires only when `!(flags && flags.quiet)`. The two callers (`semanticSearch`, `findRelated`) pass `flags` through. Fatal errors (missing vault, bad args, unknown op, unhandled exceptions) are unaffected — they always emit. Header JSDoc updated to document `--quiet` and clarify that `--json` is accepted for forward-compat but no-op (stdout is JSON regardless).

**What we learned:** Threading `flags` explicitly (option a) rather than using a module-scope `_quietMode` boolean (option b) is the right call for a single-file CLI: it keeps the function pure, avoids cross-test state pollution, and makes the dependency obvious. The single suppressable warning is in `loadIndex`'s catch block; identifying it correctly up front (rather than trying to suppress all stderr) kept the change minimal.

### Workstream E — `installed.workshop_version` refresh

**What shipped:** One line inserted in `platform/install.js` just before the `writeJson` call for `ranch/platform-installed.json`:
```
installedNow.workshop_version = manifest.workshop_version || installedNow.workshop_version || null;
```
This ensures the top-level `workshop_version` field is in sync with the workshop manifest that drove the install. Pre-v0.75.1, only per-blueprint and per-mechanism versions were refreshed; the top-level field stayed null on every consumer vault post-bootstrap.

**What we learned:** The `manifest` variable at that point in `install.js` is the workshop manifest — not the blueprint manifest — which is exactly what we want. The fallback chain (`|| installedNow.workshop_version || null`) handles the edge case where a fixture workshop has no `workshop_version` in its manifest (HC-V0751-E1 exercises the happy path; the fallback is defensive). This is the kind of one-line fix that takes two cycles to land because it's not blocking anything visibly — it only matters when you try to verify what version is installed.

### Workstream G — emoji strip from 15 engagement-template prompts

**What shipped:** 93 emoji characters stripped from all 15 prompt files (3 engagement types × 5 cadences: morning-briefing, midday-tripwire, eod-review, weekly-review, monthly-review). The strip script handled three emoji ranges plus variation selector (`\u{FE0F}`) and zero-width joiner (`\u{200D}`), and collapsed double-space artifacts in callout headers and markdown headings. HC-V0751-A1 is an inline top-level block in `run-cowork-smoke.js` that greps all 15 files for any of the three emoji ranges and fails with a file-by-file violation count — a fail-closed gate against future reintroduction.

**What we learned:** The S0 baseline check specified `baseline emoji count: 93`, but the strip script reported ~180+ characters removed — because each multi-byte emoji is 4 bytes in UTF-8 but counts as one "character" in the regex match API. The `chars removed` output from the script counted bytes-removed-from-the-string, not emoji-glyph-count. The HC-V0751-A1 harness counts emoji regex matches (glyphs), not bytes — so the gate correctly asserts 0 glyphs. The discrepancy between S0's "93 emoji" and the script's char-removal count caused brief confusion; lesson: clarify "emoji count" vs "byte count" in any strip-script output.

### Workstream H — morning-briefing semantic-warning misfire fix

**What shipped:** Two edits to morning-briefing `SKILL.md` step 14:

1. **Misfire gate:** added `ONLY IF step 12b ran` (i.e., `calendar_signal.events.length > 0`) as a precondition for emitting the semantic index unavailable warning. Previously the condition was based solely on `related_signal.status` without requiring step 12b to have run. A calendar-empty fire would have step 12b never execute, yet the `semantic_index_unavailable` check could still trigger depending on state from a prior run.

2. **Canonical text alignment:** replaced the inline warning text `"Smart Connections index is not built for this vault. Run the SC index from the Obsidian ribbon to enable related-context callouts."` with the verbatim string from `gather-semantic-related`'s `## Orchestrator integration contract` section: `"Smart Connections index absent or anchor not indexed — semantic gather skipped."` (note the em-dash). HC-V0751-H2 asserts both the sub-skill's canonical text AND that the orchestrator uses it verbatim, and that the old stale text is absent.

**What we learned:** The stale warning text exists in BOTH the morning-briefing orchestrator AND potentially other orchestrators that integrate `gather-semantic-related` (eod-review, weekly-review). This cycle only fixed morning-briefing because that's where the misfire was observed. eod-review and weekly-review likely carry the same stale text and same misfire risk — the cross-orchestrator H fix is a v0.75.2 carry-forward. A single source of truth living in the sub-skill's `## Orchestrator integration contract` section is the right pattern; the carry-forward work is applying the same pattern to the remaining two orchestrators.

## Lessons learned

1. **install.md SOURCE vs DEST architectural trap.** The v0.75.0 cycle wrote upgrade documentation to `.claude/commands/install.md` (the CONSUMER-VAULT MATERIALIZED DEST), not to the SOURCE template at `platform/mechanisms/platform-claude/commands/install.md`. Every subsequent `sauce reinstall` overwrites the dest from the source, silently wiping the hand-written upgrade notes. This cycle backfilled both the v0.74.0→v0.75.0 section and the v0.75.0→v0.75.1 section into the SOURCE. Lesson: all install.md upgrade documentation must be written to the SOURCE template and then rematerialized. Consider a `check-claude-surface` harness that asserts the dest content matches what the source would produce.

2. **S0 emoji baseline arithmetic: the "93 emoji" vs "180+ chars removed" discrepancy.** The S0 baseline stated `baseline emoji count: 93` — this was the correct emoji glyph count (regex matches). But the strip script reported ~180+ characters removed (bytes/codepoints, not glyph count, since multi-byte emoji are 4 bytes each in UTF-16 string operations). The HC-V0751-A1 harness uses regex match count (glyphs), which is the right measure. Lesson: always specify the unit when describing character counts involving emoji: "emoji glyph count" vs "chars/codepoints removed".

3. **Cross-orchestrator stale text in eod-review / weekly-review.** The H fix applied to morning-briefing. Both eod-review and weekly-review integrate `gather-semantic-related` and very likely carry the same stale warning text (`"Smart Connections index is not built for this vault..."`) and the same misfire risk (step 12b gating). This was scoped out of v0.75.1 because the only observed misfire was in morning-briefing. Carry-forward to v0.75.2.

4. **Test-deletion-on-refactor.** HC-V0751-C2 asserted `!gitFetchCalled` after calling `cmdUpdate.run(ctx, [])`. After S4 deleted the git-fetch dispatch path, the `ctx._gitExec` hook is never called — but the assertion `!gitFetchCalled` trivially passes (it was never set to true). The test remains structurally valid but is no longer testing anything interesting. Future cycles that refactor around this case should consider whether it still measures a meaningful invariant or should be rewritten.

5. **`run-install.js` dual-mode: the rematerialization pattern.** `node platform/test/run-install.js .` runs the full installer against the workshop's own vault (the workshop as its first consumer). When a platform-claude source template is updated, this command rematerializes the corresponding dest file. This is the correct pattern for keeping source and dest in sync — and it replaces the pre-v0.75.1 manual "run `sauce reinstall`" step. Always remember to run `run-install.js .` after editing a source template in `platform/mechanisms/platform-claude/commands/`.

6. **`cmd-update.js` manifest hoist necessity for Workstream E.** Workstream E needed to write `manifest.workshop_version` into `installedNow` inside `install.js`. The `manifest` variable at that code point is the workshop manifest (not a blueprint manifest), which is exactly what we need. But this was not obvious from reading the surrounding code: the manifest variable was loaded much earlier and threaded implicitly through the install flow. Lesson: when patching install.js, read ~100 lines before and after the target anchor to confirm what `manifest` refers to at that point.

7. **TDD red-green discipline on six workstreams.** The plan called for failing tests first (S1, S3, S5, S7, S9) then implementation (S2, S4, S5, S8, S10). All five failing-test stages landed with the expected FAILs; all five implementation stages turned them green. No implementation stage introduced unexpected regressions in the pre-existing harness suite. This is the third consecutive cycle (v0.73.0, v0.74.0, v0.75.0) where the full TDD discipline held across all workstreams. The pattern is working.

8. **`_resolveWorkshopPath` testability via hooks parameter.** HC-V0751-B3 needed to fake `process.execPath` to point into a temp directory hierarchy without actually changing the real process property. The `hooks = { _execPath }` optional parameter pattern lets the harness inject a fake exec path without touching module state. This is a lightweight, composable testability seam that sidesteps the need for `proxyquire` or full process mocking.

9. **Patch-level cycle scoping worked.** Six workstreams, all carry-forwards from a single prior cycle, landed in a single patch-level release. The workstreams were genuinely independent (each touched different files; no cross-workstream dependencies except the shared CLI entry point). This made the TDD staging clean: each workstream's failing tests didn't interfere with other workstreams' passing cases, and the preflight remained green at every checkpoint.

10. **`sauce update --bump-pins` for workshop-self-vault still requires `--workshop-path`.** The auto-detection walks `process.execPath` ancestry looking for a `libexec/platform/` directory. When running via `node` directly (not via a brew-installed binary), the execPath is the system node binary (`/usr/local/bin/node` or `/opt/homebrew/bin/node`) — no sauce libexec in its ancestry. This is documented in the SOURCE template's new upgrade section. The `--workshop-path` override covers this case explicitly.

## Carry-forward items (v0.75.2 / v0.76.0)

**From v0.75.0 (still open):**
- **sc-bridge fallback anchor when calendar empty.** Bridge stays cold under v0.75.1 (step 12b still gated on calendar events). v0.75.2 candidate: fire sc-bridge with a vault-root anchor (or last daily note) to keep the embedding model warm and gather broader context even on calendar-empty days.
- **`--subscribe <mech>=<ver>` CLI flag.** New-in-workshop mechanism subscription still requires a manual `jq` edit. v0.75.2 candidate: explicit per-mechanism opt-in without hand-editing JSON.
- **sc-bridge cold-start latency profile.** Still no real morning-briefing fire data with non-empty calendar. Defer until first post-deploy fire observed.
- **Cycle-history backfill (v0.50.0 → v0.62.0).** Narratives lost; backfill from `Docs/plans/` is possible but low priority.

**New from v0.75.1:**
- **Apply H fix to eod-review + weekly-review orchestrators.** Both integrate `gather-semantic-related` and likely carry the same stale warning text and same misfire risk as morning-briefing pre-v0.75.1. Same two-part fix: (1) gate the warning on step 12b having run, (2) align text verbatim with canonical contract. v0.75.2 candidate.
- **Make HC-V0751-A1 registry-driven (auto-detect new engagement types).** HC-V0751-A1 hardcodes the three engagement-type names (`personal`, `w2-fte`, `consulting`) in the test. If a new engagement type is added, the audit won't cover its prompts. Registry-driven variant: read `platform/blueprints/cowork/engagement-types/*.json` to discover the list dynamically, then walk all of their `prompts/` directories.
- **Factor shared test utilities out of `run-install.js` and `run-cli.js`.** Both files define `assertEqual`, `assertTrue`, and a `UNIT_TEST_MODE` pattern. These are copy-pasted between files. A `platform/test/harness-utils.js` shared module would eliminate duplication and guarantee consistent behavior across harnesses.
- **check-claude-surface harness.** The install.md source-vs-dest gap would be caught by a harness that: (1) runs the materialization logic against each source template, (2) diffs the output against the committed dest, (3) fails if they diverge. This prevents the v0.75.0 style mistake (hand-editing the dest instead of the source) from persisting across cycles undetected.
