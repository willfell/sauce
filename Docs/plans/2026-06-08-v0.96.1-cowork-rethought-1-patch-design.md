# v0.96.1 cowork-rethought-1-patch — design

> [!info]+ Status
> DRAFT — auto-execute authorized per user instruction "implement, deploy, deploy to all vaults". Subagent-driven flow against main with push gated to S5.

## 0. Origin

Two gaps surfaced during the v0.96.0 deploy reflection:

1. **Multi-engagement `learned_weights` nesting.** v0.96.0 design §5.2 called for a nested shape (`learned_weights.<engagement_id>.{per_kind, totals}`) when a vault has multiple engagements. We shipped the single-engagement shape (top-level `engagement_id`, `per_kind`, `totals` keys under `learned_weights:`). Works today because both consumer vaults (accuris, headspace) have one engagement each. Silently breaks the moment a second engagement is added to either vault — `learn-from-checks` Step 4 aborts with `failed:contract-violation:engagement-mismatch`.

2. **Silent cron failure mode.** If a scheduled job fails (claude.ai UI hiccup, MCP connection drops, transient compose-body error), no atomic note gets written and there's no visible signal. The user only notices missing notes by accident — sometimes days later.

This patch fixes both with minimal new surface.

## 1. Scope

Two independent rails, both PATCH-sized.

### 1.1 What ships

- **Rail M (Migration):** Auto-detect legacy single-engagement `learned_weights:` shape; rewrite as nested `learned_weights.<engagement_id>.{per_kind, totals}` on first read. `composeFinalPreferences` reads from `learned_weights[engagement_id]`. Existing v0.96.0 users get migrated transparently on first post-patch synthesize-day fire.
- **Rail H (Heartbeat):** New sub-skill `cowork:check-heartbeat` walks `.cowork.json` sidecars in `spice/cowork/daily/<last-N-days>/` to compute per-cadence last-fire timestamps. Compares against expected windows derived from `scheduled-job-contract.json`'s `schedule_hint` per cadence. Emits a warning callout to today's `memory.md` if any expected cadence is overdue.
- **Synthesize-day post-step extension** wiring check-heartbeat invocation alongside the v0.96.0 learn-from-checks call.

### 1.2 What does NOT ship (out of scope this patch)

- W2 (full structured-output API rewrite) — still parked for cowork-rethought-2 territory
- Memory salience / decay / supersession — separate design problem, still parked
- Per-item L2R + Thompson sampling — still requires production data first
- Per-skill SemVer + versioning CI — separate cycle
- Cron heartbeat WRITE surface (separate `heartbeat.json` or frontmatter field). Sidecars already carry `generated_at` per fire — we leverage that.
- Migration of in-flight cron jobs (the wrapper template is unchanged at the prose level — no claude.ai UI updates needed for this PATCH).

## 3. Rail M design — multi-engagement learned_weights nesting

### 3.1 Frontmatter shape

**Legacy v0.96.0 (single-engagement):**

```yaml
learned_weights:
  schema_version: "1.0.0"
  engagement_id: "personal"
  per_kind:
    calendar: { weight: 1.20, ticks: 18, skips: 4, warmup: false, last_updated: "2026-06-08" }
    email:    { weight: 0.85, ticks: 7,  skips: 15, warmup: false, last_updated: "2026-06-08" }
  totals:
    notes_scanned: 24
    notes_with_any_tick: 19
    warmup_until: "2026-06-15"
    upgrade_notice_emitted: false
    scanned_days: ["2026-06-07"]
```

**New v0.96.1 (nested-by-engagement):**

```yaml
learned_weights:
  schema_version: "1.1.0"
  engagements:
    personal:
      per_kind:
        calendar: { weight: 1.20, ticks: 18, skips: 4, warmup: false, last_updated: "2026-06-08" }
        email:    { weight: 0.85, ticks: 7,  skips: 15, warmup: false, last_updated: "2026-06-08" }
      totals:
        notes_scanned: 24
        notes_with_any_tick: 19
        warmup_until: "2026-06-15"
        upgrade_notice_emitted: false
        scanned_days: ["2026-06-07"]
    consulting:    # NEW: a second engagement added later gets its own block
      per_kind: {}
      totals:
        notes_scanned: 0
        notes_with_any_tick: 0
        warmup_until: "2026-06-15"
        upgrade_notice_emitted: false
        scanned_days: []
```

Schema_version bumps 1.0.0 → 1.1.0 to signal the shape change. Future cycles can branch on schema_version.

### 3.2 Migration semantics (lazy, idempotent)

`learn-from-checks-helper.js` gains a private `_normalizeLearnedWeights(raw)` that:

1. **Already-nested shape detection:** if `raw.engagements` exists OR `raw.schema_version >= "1.1.0"` → already nested, return as-is.
2. **Legacy single-engagement detection:** if `raw.engagement_id` exists at top level AND `raw.per_kind` exists at top level → legacy v0.96.0 shape. Migrate by wrapping under `raw.engagements[raw.engagement_id]`. Bump `schema_version` to `1.1.0`. Drop top-level `engagement_id` (now keyed under engagements).
3. **Empty / absent:** return a fresh nested skeleton with no engagements.

The migration is **lazy** — runs at `learn-from-checks` read time, NOT at `sauce update` time. First post-patch fire for each consumer vault migrates that vault's `user-preferences.md` on its way to writing the next set of weights.

### 3.3 Reader path: `composeFinalPreferences`

`composeFinalPreferences({ ..., learned_weights, engagement_id })` now:

1. Calls `_normalizeLearnedWeights(learned_weights)` to handle either shape.
2. Reads `normalized.engagements[engagement_id]?.per_kind` for the weight lookup.
3. If the engagement_id key is missing under `engagements`, treats as warmup (no weights applied yet) — composeFinalPreferences behavior is identical to "all kinds in warmup" / fresh-engagement state.

### 3.4 Writer path: `cowork:learn-from-checks`

`learn-from-checks` Steps 3-4 rewrite:

- **Step 3 (LAZY-INIT):** If `learned_weights:` is entirely absent OR is the legacy shape, normalize to nested. If the engagement's slot under `learned_weights.engagements[engagement_id]` is absent, initialize a fresh per-engagement skeleton.
- **Step 4 (engagement-mismatch guard):** REMOVED. The nested shape eliminates the mismatch case — each engagement has its own block.

Step renumbering preserves the existing 12-step Steps section minus the removed Step 4. Final 11 steps.

## 4. Rail H design — cron heartbeat

### 4.1 Behavior

Synthesize-day's final post-step (after learn-from-checks) invokes `cowork:check-heartbeat`. The sub-skill:

1. Reads `scheduled-job-contract.json` to learn expected cadences + their `schedule_hint`s.
2. Reads engagement's enabled cadences from `vault-config.md` `engagements[].cadences{}`.
3. For each enabled cadence: walks `spice/cowork/daily/<last-30-days>/<date>/<cadence>.cowork.json` (or `<basename>-cold.cowork.json` for lens_shift) and finds the most recent `generated_at` timestamp.
4. Compares last-fire timestamp against expected freshness window per cadence:
   - `morning-briefing`, `eod-review`, `midday-tripwire`, `capture-tick`: expected within 36 hours
   - `weekly-review`, `synthesize-week`: expected within 8 days
   - `monthly-review`: expected within 35 days
   - `lens_shift`: expected within 8 days (Saturday cadence)
5. If any expected cadence has no fire within its window → emit a warning callout to today's `memory.md` listing the missed cadences + their expected vs actual last-fire.

### 4.2 The warning callout

```markdown
> [!warning]+ Cron heartbeat anomaly — Mon Jun 9, 2026
> Some scheduled cadences haven't fired within their expected windows:
>
> - **morning-briefing**: last fired 2026-06-07 08:00:14 (expected: within 36 hours)
> - **eod-review**: never fired (expected: within 36 hours of enable)
>
> Investigate the scheduled-job configuration in claude.ai's Cowork UI, or run `/cowork sync-scheduled-jobs <engagement_id>` to refresh the paste-blocks. Confirm the job's task ID exists + is enabled.
```

The callout fires once per `synthesize-day` run. If the user fixes the cron and the next day's check-heartbeat sees no anomalies, no callout is emitted (silent on green).

### 4.4 Cadence freshness windows (data-driven)

A new `data/cadence-freshness-windows.json` ships:

```json
{
  "schema_version": "1.0.0",
  "windows_hours": {
    "morning-briefing": 36,
    "midday-tripwire": 36,
    "eod-review": 36,
    "capture-tick": 36,
    "weekly-review": 192,
    "synthesize-week": 192,
    "monthly-review": 840,
    "lens_shift": 192
  }
}
```

User can override per-cadence by hand-editing — the helper reads from `<vault>/.claude/skills/cowork/data/cadence-freshness-windows.json` and falls back to workshop source if absent.

### 4.5 Edge cases

- **First-fire post-patch:** sidecars from before v0.96.0 don't exist for legacy notes; the walk falls back to "0 fires in window" → cadence appears missed. Mitigation: warning callout includes "(no v0.96.0+ sidecars found — first-fire scenario; revisit tomorrow)" message when ALL enabled cadences show 0 fires.
- **lens_shift cadence not enabled:** if `engagement.cadences.lens_shift` is undefined or false, lens_shift is skipped from freshness evaluation entirely.
- **Engagement has minimal cadences enabled:** the check evaluates only `engagement.cadences[<cadence>] === true` — never alarms for cadences the user has explicitly disabled.
- **Vault directory missing for date range:** if `spice/cowork/daily/` is empty (brand-new vault), all cadences appear missed; warning emits the first-fire mitigation message above.

## 7. Trade-offs

### 7.1 Accepted

1. **schema_version bump in learned_weights** (1.0.0 → 1.1.0). Read-side accepts both shapes; write-side only emits 1.1.0. Migration is lazy on first read. No big-bang.
2. **Heartbeat reads sidecars, not a dedicated heartbeat file.** Means heartbeat detection depends on Rail W's sidecar write succeeding. If the cron fire fails BEFORE composing-body completes, no sidecar exists for that fire — but the fire is undetectable anyway (no atomic note was written either). Reasonable.
3. **One-day-lag for heartbeat detection.** If today's morning briefing fails, the warning surfaces in tomorrow's synthesize-day. User notices within ~30 hours, not real-time. Acceptable per "silent failure mode" framing.
4. **No new wrapper template / no consumer cron updates needed.** Patches that change cron prompts require sync-scheduled-jobs re-runs + claude.ai UI edits — friction for the user. This patch deliberately avoids that surface.

### 7.2 Rejected (this patch)

1. **Eager migration via `sauce update` install step.** Would require installer changes per-blueprint. The lazy approach is simpler + idempotent.
2. **Dedicated heartbeat.json write surface.** Adds write coupling to every orchestrator. Sidecars already carry the data.
3. **Per-cadence override flags for heartbeat suppression.** YAGNI — heartbeat is silent on green; only fires when there's a real anomaly.
4. **Real-time heartbeat (cron-frequency check).** Would need a separate cron job firing every hour. Excessive — daily check via synthesize-day is enough.
