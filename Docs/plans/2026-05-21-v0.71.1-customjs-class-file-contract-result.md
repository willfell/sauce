## Root cause

customJS evaluates each `.js` file under its `jsFolder` via this contract (visible in `.obsidian/plugins/customjs/main.js`):

```js
const def = _default(`(${file})`, f);  // eval("(<file-contents>)")
const cls = new def();
window.customJS[cls.constructor.name] = cls;
```

The expression `(${file})` wraps the entire file body in parentheses. Inside parentheses, the body must be a SINGLE EXPRESSION — typically a class expression like:

```js
(class ActivityFeed { render(dv, opts) { ... } })
```

This works because `(class X { ... })` is JavaScript's "class expression" form (vs. `class X { ... }` as a top-level class declaration). The whole file body becomes one expression that evaluates to the class constructor, `new def()` instantiates it, and customJS registers the instance.

**v0.5.0 broke this contract** by introducing a file-scope `_humanCase` helper BEFORE the class:

```js
function _humanCase(key) { ... }
class ActivityFeed { ... }
```

Wrapped: `(function _humanCase(key) { ... } class ActivityFeed { ... })` → `SyntaxError: Unexpected token 'class'`. The wrapping treats `function _humanCase` as a function expression, then encounters `class` where it expects an operator (comma, semicolon, etc.) — parse fails.

When the parse fails, customJS silently fails to register the class. Downstream consumers (`SpaceDailyDashboard`) see `customJS.ActivityFeed === undefined` and emit "ActivityFeed mechanism unavailable" wherever the activity panel would render.

**Why the bug appeared in accuris but not headspace:** identical files in both vaults, identical customJS plugin, identical customJS data.json. The asymmetry was a CACHE artifact — accuris's user explicitly reloaded customJS (which triggered re-scan and exposed the broken file), while headspace's customJS still held the pre-v0.71.0 ActivityFeed instance in memory and was reading from it on every daily-note render. Both vaults are broken at file level; only one had the cache cleared.

## Fix

```js
// BEFORE (v0.5.0 — broken)
function _humanCase(key) {
  if (typeof key !== "string" || key.length === 0) return key;
  return key.split(/[-_]/).map(function (w) {
    return w.length === 0 ? w : (w.charAt(0).toUpperCase() + w.slice(1));
  }).join(" ");
}

class ActivityFeed {
  // ...
}
```

```js
// AFTER (v0.5.1 — fixed)
class ActivityFeed {
  // v0.5.1 (sauce v0.71.1) BUGFIX: _humanCase moved from file-scope to instance
  // method to satisfy customJS's class-file contract.
  _humanCase(key) {
    if (typeof key !== "string" || key.length === 0) return key;
    return key.split(/[-_]/).map(function (w) {
      return w.length === 0 ? w : (w.charAt(0).toUpperCase() + w.slice(1));
    }).join(" ");
  }
  // ...
}
```

Call site update in `_renderFramedGroup`:

```diff
-      : _humanCase(key);
+      : this._humanCase(key);
```

Considered as a load-order disruption hypothesis but ruled out: all 6 parse cleanly with `node --check`, no class-name collisions, and they sort AFTER `activity-feed` alphabetically.
4. Inspected customJS plugin source: discovered the `eval(`(${file})`)` contract.
5. Tested the contract directly in Node: `node -e 'eval("(" + src + ")")'` → `SyntaxError: Unexpected token 'class'`.
6. Confirmed by moving `_humanCase` inside the class and re-running the test: `OK: render is function: true`.
7. Identified that headspace's customJS still held the v0.4.1 ActivityFeed in memory (pre-v0.71.0 install), explaining the apparent asymmetry between the two vaults.
