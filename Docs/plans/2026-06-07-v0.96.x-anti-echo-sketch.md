# v0.96.x cowork anti-echo — design sketch

> [!info]+ Naming note
> Original draft was titled `v0.90.x-anti-echo-sketch.md` from an outdated reading of the sequencing decision (which named v0.90.0 as the auto-update-prefs slot). v0.90 has long since shipped — workshop is at v0.95.0. The auto-update-prefs work has moved to the open v0.96.0+ territory; this sketch anchors to that.

## 0. Origin

Surfaced in conversation 2026-06-07 evening while explaining the cowork memory layer end-to-end. The framing question: *does cowork limit creativity for the sake of consistency?* Honest audit: form is constrained for memory continuity (load-bearing), voice is parameterized to be the **user's** fingerprint (not a generic AI's), content is generative — BUT the memory loop has an unaddressed gravity well. Yesterday's synthesis lands in tomorrow's prompt → tomorrow's output reinforces that frame → tomorrow's tick captures the reinforced behavior → next synthesis confirms it. The user is part of the loop (read the frame → behave according to it → tick captures). This is the **echo**.

No shipped or planned cycle pushes against it. v0.87 semantic retrieval will *amplify* it (past similar notes pulled in by similarity to today's notes). The right moment to introduce anti-echo is **alongside auto-update prefs** (the open v0.96.0+ slot inheriting from the deferred distill-week / auto-update arc) — because that's when the echo could lock in *persistently* (in config, not just in transient prompt context).

## 1. Scope

Ship three composable knobs that intervene at the three closure points of the echo loop:

| Closure point | Knob | Cadence |
|---|---|---|
| synthesize-day picks one narrative thread | `render_aspects.anti_echo` — forces one "outside yesterday's frame" callout in atomic notes when included | per orchestrator fire |
| morning-briefing reads yesterday's frame | `lens_shift` cadence — once-weekly MB fire with `read_memory: false` | weekly |
| Same theme reappears N days running | `cowork:capture-frame-drift` — background tripwire that flags stuck frames | daily, post-synthesize-day |

Each knob is independently toggleable per engagement. None ships standalone; the set composes. But the **architecturally honest one is `lens_shift`** — it's the only true break (cold-MB read with no memory). Knobs 1 and 2 still route through an LLM that has read yesterday's frame.

**Out of scope:**

- Semantic retrieval anti-echo (different mechanism — addressed when v0.87 ships, not here).
- Auto-pruning of memory.md ticks or syntheses (no retention policy in scope; carry-forwards persist as data).
- Voice-contract anti-echo (the voice contract is user-defined and stable; not the loop closure mechanism).
- Reducing dependency on `read-memory` (load-bearing for continuity — anti-echo augments, not replaces).
- Cross-engagement anti-echo (per-engagement scope; an echo in personal doesn't contaminate w2-fte memory).

## 2. Architecture

### 2.1 Knob 1 — `render_aspects.anti_echo` (daily, micro)

New render aspect, default `"skip"` for all engagement-types. When set to `"include"` per engagement (via `engagement.overrides.render_aspects.anti_echo: "include"`), the compose-body step in atomic-note orchestrators receives yesterday's carry-forward bullets as an **exclusion set** and adds one required callout near the end of the body:

```markdown
> [!question] Outside yesterday's frame
> {{One thing today's gather surfaced that yesterday's carry-forward did NOT
>  name. If nothing qualifies, say so explicitly: "today's gather largely
>  continued yesterday's threads."}}
```

The "say so explicitly" branch is load-bearing. If the LLM manufactures novelty when there genuinely is none, you get noise. The explicit-null branch keeps the output honest AND surfaces signal: three days in a row of "today's gather largely continued yesterday's threads" *is itself* the drift signal for Knob 2 to catch.

**Eligible cadences:** morning-briefing, midday-tripwire, eod-review. Skipped for weekly-review and monthly-review (those operate at a higher granularity where contrast is less meaningful).

**Implementation surface:**
- `platform/blueprints/cowork/engagement-types/{personal,w2-fte,consulting}.json` — add `anti_echo: "skip"` to `render_aspects` defaults.
- `platform/blueprints/cowork/helpers/compose-body-helper.js` — accept `excluded_themes[]` parameter, inject the anti-echo callout when `render_aspects.anti_echo == "include"`.
- `platform/blueprints/cowork/skills/skills/plan-dispatch/SKILL.md` — derive `excluded_themes[]` from yesterday's `memory.md` carry-forward bullets (read via existing `read-memory` sub-skill).
- `platform/blueprints/cowork/skills/orchestrators/{morning-briefing,midday-tripwire,eod-review}/SKILL.md` — pass `excluded_themes[]` through to compose-body.

### 2.2 Knob 2 — `cowork:capture-frame-drift` (background tripwire)

New lightweight sub-skill at `skills/skills/capture-frame-drift/SKILL.md`. Scheduled to fire daily, post-synthesize-day. Reads last N day-syntheses (default 5) + carry-forwards, extracts top-3 token themes from each (cheap LLM call), evaluates:

- Same 3-token set appears in ≥4 of last 5 days → flag `frame_repeat`.
- Single named person OR project dominates ≥60% of carry-forwards in window → flag `subject_dominance`.
- ≥3 consecutive days of "today's gather largely continued yesterday's threads" (from Knob 1) → flag `explicit_null`.

When any flag fires, appends a non-loud callout to TOMORROW's `memory.md` synthesis section (NOT to the briefing — the memory file, so it's visible to next-day MB read but doesn't crowd the user's morning hub):

```markdown
> [!warning]- Frame may be stuck
> The carry-forward has named {{theme}} on {{N of last M}} days.
> Is this still the live frame, or has the system locked onto a stale spine?
> Consider: read today's MB cold (lens-shift cadence), or revise vault-config.
```

This is the **named echo**. It doesn't prevent the loop — it gives explicit acknowledgment that the system noticed, both to the user (visible in memory.md) and to next-day MB (which reads memory.md and now has "frame may be stuck" in its context).

**Implementation surface:**
- `platform/blueprints/cowork/skills/skills/capture-frame-drift/SKILL.md` — new sub-skill body.
- `platform/blueprints/cowork/helpers/capture-frame-drift-helper.js` — theme extraction + window evaluation.
- `platform/blueprints/cowork/skills/orchestrators/synthesize-day/SKILL.md` — post-write step invoking capture-frame-drift.
- `platform/blueprints/cowork/engagement-types/*.json` — add `frame_drift` to `tripwire_aspects` defaults (personal: include; w2-fte: include; consulting: include).

### 2.3 Knob 3 — `lens_shift` cadence (weekly, macro)

New cadence in `engagement-type.supported_cadences`, default-enabled Saturday mornings (or user-configurable). Fires a morning-briefing exactly once with `read_memory: false` (skip pre-flight step 3a entirely — no synthesis read, no overnight tick read, no carry-forward bullets in context).

Writes to a distinct slug: `morning-briefing-cold-<engagement>.md` with `type: cowork-morning-briefing-cold`. Frontmatter gets a `companion_to:` field pointing at that day's normal morning-briefing if one fires (Saturday MB may or may not be enabled per engagement). The Daily Hub renders companion pairs side-by-side via a new `CoworkLensShiftCards` CustomJS class.

The user reads both outputs and **sees the echo with their own eyes**. What did warm-MB surface that cold-MB didn't? = the carry-forward gravity. What did cold-MB surface that warm-MB didn't? = what the echo was hiding.

This is the **empirical** anti-echo. Doesn't trust the system to detect its own bias; lets the user's eyes do the diff weekly.

**Implementation surface:**
- `platform/blueprints/cowork/engagement-types/*.json` — add `"lens_shift"` to `supported_cadences`; add to `default_cadences` per type (personal: enabled; w2-fte: enabled; consulting: enabled).
- `platform/blueprints/cowork/skills/orchestrators/morning-briefing/SKILL.md` — accept `--cadence lens_shift` flag → skip pre-flight 3a; switch atomic-note `type:` to `cowork-morning-briefing-cold`; set `companion_to:` if same-day warm fire detected.
- `platform/blueprints/cowork/data/scheduled-job-contract.json` — register `lens_shift` cadence with default cron `0 7 * * 6` (Saturday 07:00).
- `platform/blueprints/cowork/helpers/compose-scheduled-job-wrappers-helper.js` — emit lens_shift wrapper block as part of `sync-scheduled-jobs` output.
- `platform/blueprints/cowork/content/customjs/CoworkLensShiftCards.js` — new CustomJS class; embeds in Daily Hub.

## 3. Implementation sequencing

Three knobs, three stages. Each stage closes a SUBSET of the loop; later stages depend on earlier stages' surfaces.

| § | Stage | Surface | What ships | Cycle slot candidate |
|---|---|---|---|---|
| 1 | S1 | anti_echo render aspect + compose-body excluded_themes | Knob 1 fully wired through morning-briefing + midday-tripwire + eod-review | v0.96.0 (or paired with auto-update-prefs cycle) |
| 2 | S2 | capture-frame-drift sub-skill + tripwire_aspects entry | Knob 2 wired into synthesize-day post-step | v0.96.x PATCH after S1 settles |
| 3 | S3 | lens_shift cadence + cold MB variant + Daily Hub companion cards | Knob 3 as new background cadence | v0.97.0 MINOR (new cadence surface = MINOR) |

**Why this sequence:**

- S1 first because it's the lowest-risk surface change (one new render aspect, no new orchestrator) and because S2 depends on it (the "explicit_null" drift flag reads S1's emit pattern).
- S2 second because it's a passive tripwire — once S1 has produced ≥5 days of carry-forwards with anti_echo enabled, drift detection has signal to evaluate.
- S3 last because it's the most architecturally invasive (new cadence, new atomic-note type, new CustomJS class, new scheduled-task wrapper). Lower-priority to ship — the user can manually do a cold MB fire any time via the existing `--no_memory` debug flag (if one exists; if not, add as part of S3 prep).

## 4. Sequencing relative to the open v0.96.0+ arc

Per memory + the post-v0.93.3 brainstorm state doc, the open arc post-v0.95.x is:

- v0.95.1 — migrator (in flight)
- v0.96.0+ — open territory; auto-update prefs (deferred from old v0.90.0 slot) lives here

**Anti-echo is a sibling of auto-update prefs, not a successor.**

Reasoning: auto-update prefs closes the write-back loop — the system starts editing its own `priorities`, `render_aspects`, microscopes based on observed patterns. *That's the moment the echo could lock in for real* — bias is no longer just in transient prompt context, it's in the persistent config. Without anti-echo, auto-update prefs is a faster path to a locked-in stale frame.

**Suggested co-shipping:**

- **v0.96.0 MINOR** = distill-week + auto-update prefs (read-side) WITH anti_echo Knob 1.
- **v0.96.1 PATCH** = Knob 2 (capture-frame-drift), informed by ≥1 week of v0.96.0 production data.
- **v0.97.0 MINOR** = Knob 3 (lens_shift) + any anti-echo refinements identified from v0.96.x operation.

Alternatively, if auto-update prefs is too large to bundle with Knob 1: ship anti-echo as a standalone v0.96.0 PATCH-arc BEFORE auto-update prefs lands, so the safety net is in place before the write-back loop closes.

## 5. Trade-offs

### 5.1 Accepted

- **Knobs 1 and 2 still route through the LLM that read yesterday's frame.** Contrast-against-X requires holding X in mind. There's a real upper bound on how much novelty injection the system can do from inside its own loop. Accepted because Knob 3 (the true break) is the most expensive to ship and the lighter knobs may be sufficient in practice — empirical question, answered by living with v0.96.0.
- **Knob 1 can produce explicit-null spam.** If the user genuinely is heads-down on one project for two weeks, every atomic note says "today's gather largely continued yesterday's threads." That's honest signal, not spam — but it WILL feel repetitive. Accepted because the explicit-null pattern is what Knob 2 needs to detect drift.
- **Knob 3 doubles MB cost on Saturdays per engagement with lens_shift enabled.** One extra full MB fire = one extra MCP gather sweep + one extra compose call. Accepted because it's once per week, not daily.

### 5.2 Rejected

- **"Force a second narrative thread in synthesize-day"** — was considered (require synthesize-day to produce BOTH a primary thread AND a shadow thread). Rejected because it doubles synthesis prose, complicates the voice contract, and makes carry-forward bullets noisy. Knob 1's single "outside yesterday's frame" callout is a leaner intervention at the same architectural point.
- **"Auto-prune stale carry-forwards"** — was considered (weekly sub-skill reads last 7 days of carry-forwards, asks LLM which have been resolved, removes from memory). Rejected for v0.96.x because it's its own design problem (resolution detection is hard; risk of pruning load-bearing items). Worth its own future cycle if anti-echo Knobs 1+2+3 prove insufficient.
- **"Cold-twin every day"** (Knob 3 daily instead of weekly) — rejected because doubling MB cost daily per engagement is too expensive for the marginal value. Weekly cold-fire is enough for the user to spot systematic gaps; daily becomes vault noise.

## 6. Open questions

1. **Does Knob 1 fire on a day with NO yesterday-memory?** (First day of a new engagement, or after a memory gap.) Proposed: skip the anti-echo callout entirely when `excluded_themes[]` is empty — no contrast possible.
2. **How does Knob 2 handle weekend gaps?** If user's engagement skips Saturday/Sunday cadences, the 5-day window may straddle 9 calendar days. Proposed: window is "last 5 days with a synthesis," not "last 5 calendar days."
3. **Knob 3's `companion_to:` linkage** — should the cold MB fire even if no warm MB fires that day? Proposed: yes, fire unconditionally; `companion_to:` is optional.
4. **Theme extraction in Knob 2** — LLM call or grep? An LLM call is more accurate but adds latency to synthesize-day. A keyword-grep over carry-forward bullets is cheap but brittle (misses paraphrasing). Proposed: start with LLM call (cheap small-context call); fall back to grep only if cost matters.
5. **Does Knob 1 interact with semantic-echoes callout (the existing v0.95.0 `render_aspects.semantic_related`)?** Anti-echo and semantic-echoes are nearly OPPOSITES — one surfaces novelty, the other surfaces similarity. Proposed: both can be enabled simultaneously; they serve different reflective surfaces. But UX needs review — back-to-back "outside yesterday's frame" + "semantic echoes" callouts could be tonally jarring.
