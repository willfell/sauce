# v0.118.1 result — recurring-materialization parseRegistry fix

## TL;DR

PATCH fixing a silent regression introduced in v0.117.0: `ToDoDailyRecurring.parseRegistry` matched on a literal `## Recurring Tasks` H2 heading that the SectionLabel migration had already replaced. Result: zero recurring tasks materialized onto any daily note from v0.117.0 onward. Fix widens the parser to accept both the SectionLabel form and the legacy H2.

---

## Root cause

`parseRegistry` reads the To-Do Recurring Registry to build the list of recurring task entries that should materialize onto each day's daily note. It determined the section start by scanning for the line `## Recurring Tasks`.

v0.117.0's `applyToDoBlueprintMigration` rewrote that H2 to a dataviewjs `SectionLabel "Recurring Tasks"` block on all existing registries. The write path (`insertRecurringIntoToday`) and the audit-log path (`_findAuditSectionStart`) were both updated for SectionLabel in v0.117.0 — but `parseRegistry` (the read path) was not. After migration, the section-start pattern never matched, so `parseRegistry` returned an empty array and no tasks were written.

The gap shipped because the existing regression test (`REC-10`) used a registry fixture with the legacy `## Recurring Tasks` H2 — the exact pre-migration form — so it continued to pass after v0.117.0. There was no fixture exercising the SectionLabel form.

Surfaced when a user created a recurring task with a daily recurrence rule that never appeared on the next day's daily note.

---

## Fix

`parseRegistry` now accepts both forms:

- **Section start:** either the legacy `## Recurring Tasks` H2 **or** a dataviewjs block matching `SectionLabel` + `"Recurring Tasks"` (case-insensitive content match within the block).
- **Section end:** any of — the SectionLabel `"Last 7 days of materialization"` dataviewjs block, any `## ` H2 heading, or EOF.

The legacy H2 forms are retained unconditionally so the parser is tolerant of vaults that were never migrated (e.g., newly-bootstrapped registries that a user seeded manually in the old shape, or vaults still on a pre-v0.117.0 install).

No changes to the write path, the audit path, or the scaffold template — those were already correct.

---

## Tests

Three new cases added to `run-todo-materialize.js`:

- **REC-12** — SectionLabel-form registry with one `every day` task. Parser returns 1 entry. Fails on the old parser, passes on the fix. This is the direct regression reproducer.
- **REC-12a** — SectionLabel-form registry where the task title contains `[[note-link]]` (inserted via v0.118.0's note-link picker). Parser preserves the wikilink verbatim in the returned title. Confirms the v0.118.0 note-link feature flows through correctly to materialized task lines.
- **REC-12b** — SectionLabel-form registry with the audit section present (`SectionLabel "Last 7 days of materialization"` block). Parser stops collecting at the section boundary and does not bleed entries from the audit area.

`REC-10` (legacy `## Recurring Tasks` H2 form) was not modified — it remains the guard that the legacy path continues to work.

## Lesson — lockstep read/write migration

When a migration changes a structural marker (H2 → SectionLabel, or any equivalent format change on a delimiter that multiple code paths key off), **all code paths that match on the old pattern must be updated in a single lockstep change** — not just the write/scaffold paths.

In v0.117.0:
- Write path (`insertRecurringIntoToday`) — updated for SectionLabel. ✓
- Audit path (`_findAuditSectionStart`) — updated for SectionLabel. ✓
- **Read path (`parseRegistry`) — missed.** ✗

The root reason `parseRegistry` was missed: its test fixture (`REC-10`) used the pre-migration H2 form, so it kept passing after v0.117.0 and there was no CI signal. The fixture was authored before SectionLabel existed and was never updated alongside the migration.

**Going forward:** after any marker-format migration, explicitly grep for every callsite that matches on the old pattern string and verify each one is either updated or wrapped with explicit tolerance for both forms. When writing the new test for the migration, add a fixture in the NEW form — not only in the old form — even if the old form is being preserved for tolerance. The new-form fixture is what would have caught this gap at v0.117.0.

## Sentinel note for already-open daily notes

Daily notes that were already opened and processed today carry a spent `recurring-materialized-<date>` sentinel in their body. The idempotency guard that reads this sentinel prevents double-materialization. This means today's already-opened daily note will **not** retroactively gain the recurring tasks — only future daily notes (tomorrow onward) will auto-populate from the next open. This is intentional and correct behavior; no additional migration is needed.
