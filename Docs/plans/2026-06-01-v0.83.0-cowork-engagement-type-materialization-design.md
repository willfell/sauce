## 1. Scope

Make engagement-type JSON manifests reachable at runtime on consumer vaults. Today, cowork's manifest declares `engagement_types[]` pointing at three `.json` files — but those files are NOT in `files[]`, so they never materialize. The 5 atomic-note orchestrators say "load engagement-type manifest" without specifying a path; on a consumer vault that path doesn't resolve, and the orchestrators silently degrade (default `tripwire_aspects = []` → early-exit; `render_aspects = {}` → skip every section).

This cycle:

1. Adds the three engagement-type JSONs to cowork's `files[]` so they materialize to `{{module_directory}}/context/engagement-types/<type>.json` (= `spice/cowork/context/engagement-types/*.json`).
2. Updates all 7 cowork orchestrators that consume the manifest at runtime to read the canonical materialized path.
3. Codifies the engagement-type JSONs as STOCK in `cowork-customization-contract.md` — they are platform-canonical contracts the orchestrators have hard-coded expectations against (aspect names, schema fields); user-customizing them would silently break orchestrators.
4. Bumps cowork (`0.21.1 → 0.22.0`, MINOR — new install surface) and the workshop (`0.82.1 → 0.83.0`, MINOR).

Out of scope (deferred):

- **FLN-v821-1** V0750-VERSION exact-pin refactor (extend `semver-helper.js` with `versionEquals`). Manual edit retained for this cycle's S6; full refactor is a v0.83.1 PATCH candidate.
- **FLN-v79-6** `classifyGap` heuristic expansion.
- **Override seam for engagement-type JSONs.** Drop the speculative override-merge logic in `bootstrap-vault` (lines 73-76) and `onboard-scheduled-jobs` (line 73). If a real need surfaces, a future cycle can ship `.local/engagement-types.local/<type>.json` mirroring landmine #22's `.claude/{commands,skills}.local/` pattern.

## 2. Architecture

### 2.1 Surface map (before vs after)

| Path | Before v0.83.0 | After v0.83.0 |
|---|---|---|
| `platform/blueprints/cowork/engagement-types/{personal,w2-fte,consulting}.json` | Source-only; referenced via `engagement_types[].manifest` pointer; **NOT** materialized. | Source-only; materialized to consumer via `files[]` (new) → `spice/cowork/context/engagement-types/`. |
| `<consumer>/spice/cowork/context/engagement-types/` | Does not exist. | NEW canonical materialized location (3 STOCK files; overwritten on every `sauce update`). |
| Atomic-note orchestrator SKILL.md "load engagement-type manifest" prose | No path specified → silent failure on consumer vaults. | Explicit Read at `spice/cowork/context/engagement-types/<engagement.type>.json`. |
| `bootstrap-vault` workshop+override scan | Reads workshop path + scans `<vault>/spice/cowork/engagement-types/` (no `context/`) for overrides; merges by id. | Reads materialized `spice/cowork/context/engagement-types/<type>.json` directly. No override scan. |
| `onboard-scheduled-jobs` workshop+override read | Composes `<workshop_path>/platform/blueprints/cowork/engagement-types/<type>.json` + checks `spice/cowork/engagement-types/<type>.json` consumer override. | Reads materialized `spice/cowork/context/engagement-types/<engagement.type>.json` directly. |

### 2.2 Why `context/engagement-types/` (and not `engagement-types/`)

All other cowork-materialized data files already live under `{{module_directory}}/context/`:

- `context/user-preferences.md` (USER-DRAFTABLE)
- `context/mcp-skill-map.json` (STOCK)
- `context/engagement-templates/<type>/**` (STOCK)
- `context/engagement-shared-templates/*` (STOCK)
- `context/vault-config.md` (USER-OWNED, materialized by bootstrap-vault)

Materializing engagement-types under `context/` makes the consumer-side surface consistent. The bootstrap-vault + onboard-scheduled-jobs orchestrators' current consumer-override-scan path (`spice/cowork/engagement-types/` — no `context/`) is inert (no real consumer has authored an override there) and the cleanup removes the divergence in one move.

### 2.3 Why STOCK (and not USER or USER-DRAFTABLE-WITH-BACKUP)

Engagement-type JSONs encode platform-canonical contracts:

- Aspect names (`cc_drift`, `calendar_drift`, `queue_growth`) are matched literally against orchestrator branch conditions (`midday-tripwire/SKILL.md:191-197`).
- `render_aspects` keys (`finance_block`, `invoice_prep`, `ai_committee`, `kanban_projects`, `inner_circle_imessage`, `semantic_related`) gate orchestrator step execution.
- `required_fields[]` drives bootstrap-vault's per-engagement interview.

A consumer renaming `cc_drift → credit_card_drift` or adding a non-canonical aspect would silently degrade the orchestrator without surfacing an error. STOCK semantics + customization-contract documentation set the right expectation; future override needs route through `.local/` per landmine #22.

### 2.4 Read mechanic in atomic-note orchestrators

Today, line 29 of `midday-tripwire/SKILL.md` reads:

> 2. **Resolve engagement.** Read `<vault>/spice/cowork/context/vault-config.md`; look up `engagement` by id. If not found, exit silently. Load engagement-type manifest; capture `render_aspects` AND `tripwire_aspects` (defaults to `[]` when field absent). If `tripwire_aspects.length == 0`, exit silently …

The vague "Load engagement-type manifest" becomes:

> Read the engagement-type manifest via the Read tool at `spice/cowork/context/engagement-types/<engagement.type>.json`. Parse as JSON; capture `render_aspects` AND `tripwire_aspects` (defaults to `[]` when field absent). If the file is missing or fails to parse, exit silently with a one-line Notice `cowork:midday-tripwire aborted -- engagement-type manifest unavailable at spice/cowork/context/engagement-types/<engagement.type>.json`.

Same shape (substituting orchestrator name + tripwire/render aspects per orchestrator role) for morning-briefing, eod-review, weekly-review, monthly-review (L27 in each).

### 2.5 Read mechanic in bootstrap-vault + onboard-scheduled-jobs

Both currently resolve the workshop path (via `workshop_path` substitution variable from `ranch/platform-config.json`) and scan a separate consumer-override location. With materialization in place, the workshop-path resolution is unnecessary and the override scan is removable:

- `bootstrap-vault/SKILL.md` step 8 collapses to: list `spice/cowork/context/engagement-types/*.json`, read each via the Read tool, capture as `engagement_types_registry`. Override-merge step removed.
- `onboard-scheduled-jobs/SKILL.md` step "resolve the engagement-type manifest" collapses to: Read `spice/cowork/context/engagement-types/<engagement.type>.json`. The "Compose `workshop_manifest_path`" + override-check + merge logic is deleted.

## 6. Risks + mitigations

### 6.1 FLN-v821-2 dogfood gate (mitigated by MINOR bump)

Per landmine #16 + FLN-v821-2, new logic inside `installItem`-internal loops requires a co-occurring blueprint version bump for the dogfood install to actually exercise the new code. This cycle's MINOR cowork bump (justified by the new install surface) naturally satisfies the requirement — no extra mechanic needed.

### 6.2 FLN-v821-1 manual touch

`run-cowork-smoke.js` carries a `V0750-VERSION` exact-version pin (`cowork === "x.y.z"` literal). Bumping cowork to 0.22.0 will break this until manually edited. S6 includes the edit. Full FLN-v821-1 fix (extend `semver-helper.js` with `versionEquals`) is deferred to v0.83.1 PATCH or later.

### 6.3 Override-merge removal in bootstrap-vault + onboard-scheduled-jobs

The current code paths scan `<vault>/spice/cowork/engagement-types/<type>.json` (no `context/`) for consumer overrides. If a real consumer has authored such an override (no evidence so far), the new materialized path (`context/engagement-types/`) lives one directory deeper, so the legacy override file becomes inert (not destroyed). Recovery path documented in the result doc: copy the override's diffs into the materialized file in the workshop, or wait for a future `.local/engagement-types.local/` seam.

### 6.4 What this does NOT guarantee

Even after deploy + `sauce update --bump-pins`, the accuris midday-tripwire silent no-op may not fully resolve. v0.82.0's WS-C investigation listed three "likely candidates":

1. Stale w2-fte.json at time of accuris's last run (timing-of-deploy — resolves with deploy).
2. Agent on accuris couldn't locate the manifest at all → defaulted aspects to `[]` (resolves with materialization — the target this cycle fixes).
3. Vault-specific override in `vault-config.md` masking manifest values (no evidence; not addressed here).

Cycle-close validation = post-deploy observation on accuris, not a unit-testable claim.

### 6.5 Snippet of risk this cycle does NOT introduce

- **No new helper.** files[] loop already handles the materialization; no installer code change.
- **No new claude_surface[] entry.** CS-MIG-1 counts unchanged (v0.82.1's manifest-derived assertion mechanic naturally absorbs any future changes anyway).
- **No mechanism bump.** Cowork blueprint internal change only.
- **No new harness file.** All sub-asserts land in `run-cowork-smoke.js`.
