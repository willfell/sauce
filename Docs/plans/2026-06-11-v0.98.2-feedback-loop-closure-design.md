# v0.98.2 — feedback-loop closure

## TL;DR

Closes the loop the user's 2026-06-10 vision described: ticks + knobs + prose captured by v0.98.1's EOD Rail L now get INGESTED nightly and APPLIED to the files that shape tomorrow's briefs. Three moves:

1. **Capture completes** — Rail L gains the explicit per-item DOWNVOTE list ("Didn't like:") the vision asked for, under a `v=2` sentinel; the item-ID → identity registry is persisted in the EOD sidecar (schema 1.1.0 → 1.2.0 additive).
2. **Ingest lands inside the existing nightly reconciler** (`reconcile-cowork`, 03:00, per-engagement, daily forever) — a deterministic pass rolls per-item ticks/downvotes/knobs into per-kind AND per-person/channel/topic weight deltas; an inline LLM pass extracts structured intents from the free-text fence, validated by a deterministic helper before anything applies.
3. **Apply with audit trail** — `learned_weights` (schema 2 → 3, nested per-kind entity maps, still in user-preferences frontmatter) updates directly with clamp + `.bak`; microscope `## What matters` appends only; voice corrections are PROPOSED to `memory/<eng>/voice-proposals.md` and approved by tick-to-approve in the next morning brief; coverage gaps queue to `memory/<eng>/coverage-queue.md`; every delta logs to `memory/<eng>/feedback-deltas.md` with a source quote.

Also fixes a regression-in-waiting found during absorption: the reconciler OI only parses the legacy `rating-block` sentinel, so post-v0.98.1 EOD notes (which emit `feedback-capture` instead) currently contribute ZERO signal to per-kind learning. v0.98.2's Step-3 extension restores EOD signal to the formula.

No new scheduled job; no contract bump; no new installer write surface under user-owned paths (all new per-engagement files are runtime-created by the reconciler session via Obsidian MCP — Safeguard 3 CI stays green by construction).

## Goal

User vision verbatim (2026-06-10 brainstorm; the v0.98.x arc's north star):

> "just saying thumbs up isn't enough. what if we added a section for didn't like? what if there was a section where i could provide feedback, and another job took what i liked, what i didn't like, my feedback, then updated the relevant files so that all scheduled jobs would then adjust the next day?"

v0.98.1 shipped "a section where i could provide feedback" (capture). v0.98.2 ships the remaining three clauses: "a section for didn't like" (structured downvote), "another job took what i liked, what i didn't like, my feedback" (reconciler ingest), "updated the relevant files so that all scheduled jobs would then adjust the next day" (apply + next-day consumption).

Per `Docs/cowork-vision.md`, this cycle advances **Adaptive memory loop (write-side compounding)** — the first cycle where user signal writes back into the files that shape future runs — plus the **Substance/Voice** tail (downvote completes the capture surface).

## Absorption discoveries that grounded this design (5)

The brainstorm ran absorption-first across the workshop + both consumer vaults. Five live-corpus facts the docs didn't carry, all load-bearing:

1. **`learned_weights` live in `user-preferences.md` FRONTMATTER**, not `memory/<eng>/learned_weights.json` (ecosystem doc § 7.2.5 is aspirational). Headspace carries `schema_version: 2`; accuris has NO version field; the helper's `_normalizeLearnedWeights` expects `"1.1.0"`. The schema-3 normalizer must accept all three shapes. The reconciler already owns this write path with `.bak` discipline — schema 3 migrates IN PLACE, no file move.
2. **EOD signal currently drops out of learning.** `reconcile-cowork.md` Step 3 greps only `cowork:rating-block`; v0.98.1 EOD notes emit `cowork:feedback-capture` instead. First affected fire: headspace 2026-06-11 EOD. v0.98.2 is therefore not purely additive — it restores a broken input.
3. **The item-ID → identity registry is not persisted.** `composeFeedbackCapture` returns `item_id_registry` but the sidecar stores only counts; the sidecar's `surfaced_items[]` uses a DIFFERENT id scheme (`<kind>-<eng>-<sha256-16>`, per-callout granularity, 5/day). Identity recovery for ticks requires persisting the registry (this design) or parsing wikilink labels (the fallback).
4. **Obsidian's Tasks plugin appends `✅ YYYY-MM-DD` to ticked lines** (live in headspace 2026-06-10 EOD: `- [x] Chat ✅ 2026-06-10`). The LLM reconciler tolerated it; deterministic parsers must too. All v0.98.2 tick regexes anchor on the prefix-through-wikilink and ignore trailing annotations.
5. **Accuris has zero feedback signal ever** (`notes_with_any_tick: 0`; its 2026-06-10 EOD omitted Rail L entirely) and its local vault copy sits at 0.98.0/0.36.0 (updates happen on the work machine). The design degrades gracefully on silent engagements: no signal → no deltas → no writes → one audit line.

Secondary divergences noted for the record: microscopes live at `spice/cowork/prompts/per-mcp/<kind>/microscope.md` (engagement-agnostic per vault), NOT `context/<eng>/microscopes/` as the ecosystem doc claims; accuris additionally carries inline `what_matters` blocks in `user-preferences.mcps.<kind>`. The append target for microscope deltas is the per-mcp microscope file; if absent for a kind, the delta parks as pending in `feedback-deltas.md` (this cycle never creates microscope files).

## Ingest pipeline (reconcile-cowork OI extensions)

### Step 3 (extended) — parse both sentinels

For each of yesterday's `.md` notes matching the engagement: if `rating-block` sentinel → existing kind-checkbox parse (now suffix-tolerant). If `feedback-capture` sentinel (v=1 or v=2) → rich parse. EOD contributes kind-level observations to the existing formula via: **kind tick = ≥1 mattered-tick in that kind; else kind skip.** This restores EOD to per-kind learning (discovery #2).

### NEW Step 3.5 — deterministic rollup (cowork:ingest-feedback contract)

Per the `ingest-feedback-helper.js` contract (re-stated inline in the OI, pure-MCP):

- **Per-item mattered tick** → entity delta **+0.05** on the item's person/channel/topic under its kind (identity via registry).
- **Per-item didn't-like tick** → entity delta **−0.10** (dislikes are rarer + stronger signal) AND counts toward the kind-skip side of the kind-level mapping.
- **Frequency knobs** → direct **±0.05** per-kind delta applied AFTER the formula + re-clamped (the v0.98.1 sketch, now real). `ambiguous` → no signal.
- **Ambiguous items** (sidecar flag) → no entity signal.
- Idempotency: per-day dedup via a new `totals.feedback_ingested_days[]` alongside the existing `scanned_days[]`.

### NEW Step 3.6 — free-text intent extraction (inline LLM pass)

Read the `free_text` content. Extract a JSON intent list against this schema:

```json
[{ "intent": "uprank | downrank | voice_correction | coverage_gap | frequency | other",
   "kind": "<kind, when scoped>", "entity": "<person/channel/topic, when named>",
   "source_quote": "<verbatim substring of the user's prose>",
   "proposed_target": "learned_weights | microscope:<kind> | voice-proposals | coverage-queue",
   "confidence": "high | medium | low" }]
```

**Validation rules (deterministic; the helper's contract, re-stated in OI):** unknown intent, missing/non-verbatim `source_quote`, target outside the four-value allowlist, or a `learned_weights` intent naming no kind → REJECTED: logged to `feedback-deltas.md` as `rejected`, never applied. `low` confidence intents are logged as pending, not applied. Hard suppression intents ("stop surfacing X's emails") → direct floor-set `weight = 0.10` on the named entity under the named kind.

### Steps 4–5 (extended) — learned_weights schema 2 → 3

Same file, same `.bak`-first rewrite of ONLY the `learned_weights:` block. Schema 3 shape per engagement:

```yaml
learned_weights:
  schema_version: 3
  engagements:
    headspace:
      per_kind:
        chat:
          weight: 1.150          # existing v0.96.0 formula, unchanged
          ticks: 12
          skips: 4
          warmup: false
          last_updated: 2026-06-12
          per_person:
            "Zhenzhen Su": { weight: 1.050, ticks: 1, downvotes: 0, last_updated: 2026-06-12 }
          per_channel:
            "Dev Enablement Channels": { weight: 0.900, ticks: 0, downvotes: 1, last_updated: 2026-06-12 }
          per_topic: {}
      totals:
        notes_scanned: 89
        notes_with_any_tick: 67
        scanned_days: [ ... ]
        feedback_ingested_days: [ "2026-06-12" ]
        warmup_until: 2026-06-16
```

**Entity weight math:** start 1.00; clamp [0.10, 3.00]; banker's rounding (3 places); +0.05 per mattered tick; −0.10 per didn't-like; light daily decay TOWARD 1.00 — explicitly `w' = 1.00 + (w − 1.00) × 0.995` (NOT `w × 0.995`, which would decay toward zero) — applied once per ingest run to every entity under the engagement, idempotent via `feedback_ingested_days[]`; free-text floor-set bypasses deltas (direct 0.10 with audit). Entity warmup analog: advisory until the entity has ≥3 observations.

**Normalizer tolerance (`_normalizeLearnedWeights` v3):** accepts on-disk `schema_version: 2` (headspace), missing version (accuris), legacy `"1.1.0"` (helper-era), and `3`. Migration is in-place and additive — `per_person/per_channel/per_topic` maps initialize empty; nothing existing is dropped.

### NEW Step 5.5 — apply non-weight deltas (each with its own posture)

| Target | Posture | Path |
| --- | --- | --- |
| Microscope `## What matters` | **APPEND-only** — one dated line per delta with source quote; never rewrites; user prunes later. If the kind has no microscope file → delta parks in feedback-deltas as `pending` (this cycle never CREATES microscope files) | `spice/cowork/prompts/per-mcp/<kind>/microscope.md` |
| Voice/personality corrections | **PROPOSED only** — durable entry in voice-proposals.md (id, exact append text, target file, source quote, status, expiry = +7 days) | `spice/cowork/memory/<eng>/voice-proposals.md` |
| Coverage gaps | Queued for user-schedule triage | `spice/cowork/memory/<eng>/coverage-queue.md` |
| Everything (applied, proposed, rejected, pending) | **Append-only audit log** — date · delta · old → new · source quote · target | `spice/cowork/memory/<eng>/feedback-deltas.md` |

Audit entry format (one `## <date> (run-id: fd-<ymd>-0300)` section per run):

```markdown
## 2026-06-12 (run-id: fd-20260612-0300)
- [weights] chat.per_person."Zhenzhen Su" 1.000 → 1.050 (+0.05 mattered ^item-chat-a7b3c9d "Zhenzhen PR #353 thread")
- [weights] email.per_person."Diana" 1.000 → 0.100 (floor-set; source: "stop surfacing Diana's emails")
- [knob] chat +0.05 (Fire chat: more)
- [microscope] chat APPEND: "<line>" (source: "<quote>")
- [voice] PROPOSED vp-20260612-1 → voice-proposals.md (source: "<quote>")
- [coverage] QUEUED: "<gap>" → coverage-queue.md
- [rejected] intent other/"<...>" — target outside allowlist
```

All four files are **runtime-created by the reconciler session via Obsidian MCP** when absent (frontmatter `type: cowork-feedback-deltas` etc.) — they are NOT installer-materialized and gain NO `files[]` entries (Safeguard 3 stays green by construction).

### NEW Step 5.6 — voice-proposal approval sweep

Parse yesterday's morning-briefing `.md` for the voice-proposals callout (see below). Per proposal line: `[x]` → apply the exact append text to the proposal's target file (append-only), mark `applied` in voice-proposals.md, audit-log. Untouched + past expiry → mark `expired` (inert, visible in the file). Proposals named in free-text as rejected ("no, don't change that") → `dismissed`.

## Consumption — how tomorrow's brief actually changes

One new rule in the shared microscope/voice clause + Step 2 of morning-briefing and eod-review OIs: when composing per-kind blocks, consult `per_kind.<kind>.per_person/per_channel/per_topic`:

- **≥ 1.20** → lead the section (surface first, fuller rendering)
- **≤ 0.50** → cap to one line
- **≤ 0.25** → omit, UNLESS the item carries a hard signal (direct @-mention, money movement, inner-circle going-dark per existing microscope contracts)
- Entities in warmup (<3 observations) → advisory only

Structural rules still WIN over voice on conflict; the thresholds are OI prose consumed at gather/compose time, deliberately NOT helper-enforced (rendering judgment is the LLM's lane; the WEIGHTS are deterministic).
