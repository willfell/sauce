## Root cause (full narrative)

**Symptom:** On the +New Task dialog's Recurring tab, the Create button never enables — "no matter what I do, it will not be clickable." v0.116.1 claimed to fix this by forward-declaring the `updateSubmit` closure; it did not, because that was a misdiagnosis.

**Actual root cause:** The Obsidian customJS plugin stores **instances** under `window.customJS.<ClassName>`. This is how all working customJS consumers operate: `SectionLabel.render`, `DocSearch.matches`, `FinanceMath.fmtMoney` are all **instance** methods, and the `customjs-guard` dispatches `customJS[Class][method].call(klass, …)`.

`RecurrenceParser` declared its public-facing methods as `static`. A static method lives on the constructor, NOT on the instance. So `window.customJS.RecurrenceParser.isSupported` is `undefined`, and calling `undefined(grammar)` throws `TypeError: window.customJS.RecurrenceParser.isSupported is not a function`.

In `validatePayload()` (todo-create-task.js), this throw propagates out of `updateSubmit()` before the `submit.disabled = false` line, so the button stays permanently disabled on the Recurring tab. The one-shot tab is unaffected — it never calls RecurrenceParser.

**Why the harness masked it:** The existing `run-todo-dialog.js` harness never set `window.customJS.RecurrenceParser` to an actual instance. The gate was skipped (treated as absent helper = skip validation = pass), so the harness was green while live Obsidian was broken. The reproducing test added in Part B is the permanent regression net for this class of defect.

**Blast radius:** `ToDoDailyRecurring` (todo-daily-recurring.js) called `customJS.RecurrenceParser.isSupported` and `.matches` — same throw, same outcome; recurring materialization bricked in live Obsidian. `ToDoDailyCarryover` (todo-daily-carryover.js) called `customJS.TaskParser.parseTasks` — `TaskParser.parseTasks` is also static — same defect; carryover task-parsing threw live.

## LESSON — customJS instance convention

**Any class consumed via `window.customJS.<ClassName>.<method>` MUST expose that method as an instance method.** `static` is valid only for:
- Methods called by class name within the same file (e.g., `RecurrenceParser._parse(...)` inside `recurrence-parser.js` itself).
- Methods called in Node harnesses where the class is `require`'d directly (not via `customJS`).

The convention is already the norm: `SectionLabel.render`, `FinanceMath.fmtMoney`, `DocSearch.matches`, `EntityCreate.render` — all instance methods. `RecurrenceParser` and `TaskParser` were the outliers that violated the convention and exposed the gap. When adding a new helper class: declare all externally-consumed methods as instance methods first; add static helpers only for internal logic.

The reproducing test pattern — `window.customJS.RecurrenceParser = new RecurrenceParser()` in the harness before calling `validatePayload` — is now the canonical contract that prevents regression.
