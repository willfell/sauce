## 3. Workstream A — `--bump-pins` workshop_path null fallback

### Problem

All 4 consumer vaults have `workshop_path: null` in `ranch/platform-installed.json`. `sauce update --bump-pins` errors with:

```
TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received undefined
    at Object.join (node:path:1339:7)
    at handleBumpPins (.../cmd-update.js:30:39)
```

The handler at `cmd-update.js:30`-ish reads `installed.workshop_path` unconditionally and feeds it to `path.join`. v0.75.0 worked around this in the deploy recipe with a per-vault `jq` patch; v0.75.1 fixes it in code.

### Approach (recommended)

Introduce a `resolveWorkshopPath(installed, argv)` helper in `cmd-update.js`. Precedence order:

1. `argv.workshopPath` — new `--workshop-path <path>` CLI flag, explicit user override.
2. `installed.workshop_path` — preserved when present (no behavior change for vaults with this field set correctly).
3. **Ancestry walk** — `path.dirname(process.execPath)` walked upward until a directory named `libexec` is found that contains a `platform/` subdirectory. This catches the brew install (`/opt/homebrew/Cellar/sauce/<ver>/libexec`) and any equivalent layout.
4. Throw with message: `Could not auto-detect workshop_path. Pass --workshop-path <path> explicitly.`

### Code sketch

```js
// platform/cli/cmd-update.js
function resolveWorkshopPath(installed, argv) {
  if (argv.workshopPath) return argv.workshopPath;
  if (installed.workshop_path) return installed.workshop_path;
  let dir = path.dirname(process.execPath);
  const root = path.parse(dir).root;
  while (dir !== root) {
    if (
      path.basename(dir) === 'libexec' &&
      fs.existsSync(path.join(dir, 'platform'))
    ) {
      return dir;
    }
    dir = path.dirname(dir);
  }
  throw new Error(
    'Could not auto-detect workshop_path. Pass --workshop-path <path> explicitly.',
  );
}
```

### Alternatives considered

- `brew --prefix sauce` shell-out — rejected. ~300ms cold latency, requires brew on PATH, OS-fragile (Linux brew prefix differs).
- `--workshop-path` flag only, no auto-detect — rejected. The silent-failure case (user runs `sauce update` not knowing about the flag) stays unfixed.
- Hardcoded `/opt/homebrew/opt/sauce/libexec` symlink — rejected. Doesn't work for non-default Homebrew prefixes (e.g., Linux `~/.linuxbrew`, Intel Mac `/usr/local`).

### Acceptance

- Consumer vault with `workshop_path: null` runs `sauce update --bump-pins` without manual jq-patching.
- Workshop's own self-install path (`node platform/test/run-install.js .`) continues working — the workshop's `process.execPath` ancestry resolves to the workshop's own `libexec` equivalent (or the explicit `--workshop-path` is passed in the test harness).
- Explicit `sauce update --workshop-path /nonexistent --bump-pins` falls through ancestry walk and errors clearly.

## 4. Workstream B — `sauce update` brew-aware

### Problem

After `sauce update --bump-pins` writes the new subscription file, the handler falls through to the "standard sauce update flow" (`cmd-update.js:128`-ish) which calls `git fetch origin main` against the consumer vault. Consumer vaults aren't git repos → fatal: not a git repository. This is a pre-existing bug from the pre-v0.36 `pantry/` git-checkout architecture; modern brew-distributed sauce has pantry shipped via brew, so there is nothing to fetch.

The v0.75.0 deploy worked around it by always following `sauce update --bump-pins` with `sauce reinstall --vault <path>`. v0.75.1 collapses this dual-command flow into a single `sauce update`.

### Approach (recommended)

Refactor `cmd-update.js`'s main handler to:

1. Parse argv (including `--bump-pins` from v0.75.0, plus new `--workshop-path` from A).
2. Resolve `workshop_path` via A's helper.
3. If `--bump-pins`, recompute subscription pins (existing logic at `handleBumpPins`).
4. Delegate to `cmd-reinstall.js`'s materialization flow.

**Net result:** `sauce update` becomes `sauce reinstall` with optional pre-bump. The git-fetch + `git reset --hard` paths are deleted entirely from `cmd-update.js`.

### Code sketch

```js
// platform/cli/cmd-update.js (after refactor)
async function handleUpdate(argv) {
  const installed = readPlatformInstalled();
  const workshopPath = resolveWorkshopPath(installed, argv);  // from A
  if (argv.bumpPins) {
    await handleBumpPins({ installed, workshopPath, argv });
  }
  // Delegate to reinstall flow
  const { handleReinstall } = require('./cmd-reinstall.js');
  return handleReinstall({ ...argv, workshopPath });
}
```

### Alternatives considered

- Two-path detection (brew context vs non-brew context) — rejected. There is no non-brew distribution model in flight; the legacy git-fetch path is dead code in modern consumer vaults.
- Keep `cmd-update.js` and `cmd-reinstall.js` as parallel commands — rejected. Currently two commands that materially do nearly the same thing (one with optional git-fetch, one without) is the confusing state v0.75.1 fixes.

### Edge case — workshop self-install

The workshop's own `node platform/test/run-install.js .` does not invoke `cmd-update` — it drives the installer directly. So this refactor does not touch the workshop-as-vault dogfood path. (Grep over `platform/test/run-install.js` for `sauce update | cmd-update | handleUpdate` returns zero hits.)

### Acceptance

- `sauce update --bump-pins` against a consumer vault that isn't a git repo runs end-to-end with `exit 0`. No "fatal: not a git repository" error.
- The two manual jq-patches (workshop_path + opt-in subscription) from the v0.75.0 deploy recipe become unnecessary for the next consumer deploy.
- `sauce update` (no `--bump-pins`) runs materialization without recomputing pins (preserves existing pins; refreshes claude_surface + materialized files).

## 5. Workstream D — sc-bridge `--quiet` / `--json` flag handling

### Problem

`smart-connections-bridge@0.1.0`'s argv parser accepts `--quiet` and `--json` flags but no codepath consumes them. Stderr warnings (`"skipping unparseable"` etc.) are unsuppressable even with `--quiet`; `--json` is documented but stdout has always been JSON regardless.

### Approach

- `--quiet`: gate every `console.warn` call inside `sc-bridge.js` behind a module-scope `quiet` boolean set from argv at startup. When `quiet`, swallow stderr warnings. Errors (`console.error`) still print.
- `--json`: stdout has always been JSON; the flag is currently no-op. Decision: keep accepting it (forward-compat with future non-JSON modes) but document in the bridge's README that it is no-op as of v0.1.1.

### Code sketch

```js
// platform/mechanisms/smart-connections-bridge/sc-bridge.js
const quiet = argv.quiet === true;
function warn(...args) {
  if (!quiet) console.warn(...args);
}
// Replace all console.warn calls in the file with warn().
```

### Acceptance

- `node sc-bridge.js index-status --vault . --quiet` produces zero stderr output.
- `node sc-bridge.js index-status --vault .` produces stderr warnings as before.
- README updated to clarify `--json` is currently no-op (stdout always JSON).

## 6. Workstream E — `installed.workshop_version` refresh on reinstall

### Problem

`cmd-reinstall.js` already updates per-blueprint and per-mechanism `version` fields in `ranch/platform-installed.json` but does not refresh the top-level `workshop_version` field. As a result, after `sauce reinstall`, `jq -r .workshop_version platform-installed.json` returns `null` (or a stale value) even though sub-component versions reflect the current install.

### Approach

Add one line to `cmd-reinstall.js` after subscription resolution: `installed.workshop_version = subscription.workshop_version`. The subscription file already carries the workshop version; we just propagate.

### Acceptance

- After `sauce reinstall` (or `sauce update --bump-pins` post-B), `jq -r .workshop_version ranch/platform-installed.json` returns the current workshop version (e.g., `"0.75.1"`).
- Existing per-blueprint and per-mechanism version refreshes continue unchanged.

### Approach

One-shot Node script (`platform/test/strip-emoji.js`, **not committed** — used once during cycle execution to perform the strip). The script:

1. Walks `platform/blueprints/cowork/content/context/engagement-templates/*/prompts/*.md`.
2. For each file, strips characters in the Unicode emoji ranges: `\u{1F300}-\u{1FAFF}` (symbols + pictographs), `\u{2600}-\u{27BF}` (misc symbols + dingbats), `\u{1F000}-\u{1F2FF}` (mahjong + playing cards), variation selector `\u{FE0F}`.

### Section-title edge case (midday-tripwire)

Personal `midday-tripwire.md` uses emoji as `## 🚨 Flagged charges` style section headers. Stripping leaves `## Flagged charges` — semantically clean, no information loss (section text already carries the meaning).

## 8. Workstream H — semantic-warning misfire fix + text alignment

### Problem

The 2026-05-22 headspace morning-briefing fire emitted:

```
> [!warning] Semantic index not available
> Smart Connections index is not exposed via MCP in this Claude Code runtime, so per-event "Related to" callouts are not appended. Open the Smart Connections ribbon in Obsidian to refresh the local index if you want this surfaced in future runs.
```

Two issues:

1. **Misfire.** The morning-briefing orchestrator's step 12b (semantic-related gather) is gated on `calendar_signal.events.length > 0`. Headspace's calendar gather returned empty (Calendar MCP returning no events) → step 12b did not run → no `related_signals[]` collected. Per the v0.75.0 orchestrator contract (`platform/blueprints/cowork/content/skills/morning-briefing/SKILL.md` step 14, around line 75-76 in installed copy), the `semantic_index_unavailable = true` set is only supposed to happen when step 12b ran AND any `related_signal.status` starts with `skipped:no-index` or `skipped:anchor-not-indexed`. With step 12b not running, `semantic_index_unavailable` should remain `false` (default), and no warning callout should have been emitted. The agent freelanced — emitted the warning anyway. The contract is correct; the prompt is unclear about the "step-12b-didn't-run" case.

2. **Text divergence.** The orchestrator's step 14 specifies warning text "Smart Connections index is not built for this vault. Run the SC index from the Obsidian ribbon to enable related-context callouts." The sub-skill `gather-semantic-related`'s `## Orchestrator integration contract` specifies "Smart Connections index absent or anchor not indexed — semantic gather skipped." These differ in wording, root-cause framing, and remediation suggestion. The agent further freelanced its own variant ("not exposed via MCP in this Claude Code runtime") which misrepresents the bridge's CLI architecture. Single source of truth needed.

### Approach

Two edits to `platform/blueprints/cowork/content/skills/morning-briefing/SKILL.md`, step 14:

**Edit 1 — misfire fix.** Tighten the condition that gates `semantic_index_unavailable = true`:

```diff
- If any `related_signal.status` starts with `skipped:no-index` OR `skipped:anchor-not-indexed`, set `semantic_index_unavailable = true`.
+ ONLY IF step 12b ran (i.e., `calendar_signal.events.length > 0`) AND any `related_signal.status` starts with `skipped:no-index` OR `skipped:anchor-not-indexed`, set `semantic_index_unavailable = true`. When step 12b did NOT run (calendar empty, or `render_aspects.semantic_related != "include"`), `semantic_index_unavailable` stays false and NO warning callout is emitted.
```

**Edit 2 — text alignment.** Replace orchestrator's inline warning text with a reference to the sub-skill's canonical text:

```diff
- Append ONE `> [!warning]- Semantic index not available\n> Smart Connections index is not built for this vault. Run the SC index from the Obsidian ribbon to enable related-context callouts.` callout after the Synopsis admonition.
+ Append ONE `> [!warning]- Semantic index not available\n> Smart Connections index absent or anchor not indexed -- semantic gather skipped.` callout after the Synopsis admonition. Text matches the canonical contract in `cowork:gather-semantic-related`'s `## Orchestrator integration contract` section. Do not paraphrase; copy exactly.
```

### Why not loosen step 12b's gate instead

An alternative would be to make step 12b run even on empty-calendar fires by anchoring off something else (open-threads list, active-projects list, recent atomic notes). That is the right path long-term but is a substantive design question — see "Out of scope" §I. v0.75.1 H is the minimal correctness fix for the misfire; the broader fallback-anchor design is its own brainstorm.

### Acceptance

- Calendar-empty morning-briefing fire emits zero `> [!warning]- Semantic index not available` callouts. The agent's run notes may still mention "no semantic gather attempted" in the run summary but the atomic-note structure is warning-free for this case.
- Calendar-with-events fire where sc-bridge returns `skipped:no-index` (or `skipped:anchor-not-indexed`) emits exactly one warning callout with canonical text matching the sub-skill contract.
- The existing v0.74.0 + v0.75.0 morning-briefing integration tests are updated to assert these two cases.
