# v0.77.0 — cowork-adaptive-detection (design)

**Status:** design — pending plan + execution.
**Date:** 2026-05-23.
**Cycle topic slug:** `cowork-adaptive-detection`.
**Predecessor:** v0.76.0 (cowork-interactive-context), tag `v0.76.0`, HEAD `cdc239b`.
**Trigger:** v0.76.0 shipped + deployed to all 4 consumer vaults, but the first real-world invocation on the accuris machine surfaced a fundamental gap: `mcp-skill-map.json` v1.0.0 matches MCPs by namespace regex against Google/Apple/Brex name-shapes. The accuris machine's connected MCPs include a Microsoft 365 gateway under UUID namespace `45224a84-...` (Outlook calendar + email + SharePoint + Teams chat), plus Accuris-internal MCPs (ADO, ArgoCD, Backstage, NewRelic, PagerDuty, etc.) — none match the v1 regexes. `detected_mcp_kinds = []`. The skill emits an "abort or do personality only" picker; the user is stuck.

The promise of cowork:context-builder was "adaptable to any environment". v0.76.0 delivered a closed catalog of 4 hardcoded kinds. v0.77.0 lifts that ceiling.

---

## 1. Cycle motivation

Two coupled workstreams against a single minor release (v0.77.0).

**Workstream B — tool-pattern detection (replace namespace regex).** The current detection layer (`mcp-skill-map.json` v1.0.0) matches MCP **namespaces** against regex patterns. This is fragile against:
- Enterprise MCP gateways that use UUID namespaces (Outlook/M365 on accuris)
- New MCP servers whose naming conventions weren't anticipated when v1 was written
- MCPs that bundle multiple capabilities under one namespace (Outlook = calendar + email + SharePoint + Teams)

The fix: match by **tool-name signatures** instead. Any MCP exposing `list_events` + `create_event` is a calendar — regardless of its namespace. Any MCP exposing `search_threads` + `send_message` is email. The matching becomes set membership on the tool list (`mcp__<ns>__<tool>` names), not regex on `<ns>`. An MCP can satisfy multiple kinds (capability-subset model): Outlook UUID matches `calendar` (via list_events/create_event) AND `email` (via search_threads/send_message) AND `chat` (via Teams chat tools) — all from the same namespace.

**Workstream C — fully-adaptive unknown-MCP handling.** Even with broader tool-pattern coverage, the v0.77.0 known catalog stays small (4 kinds: calendar, email, chat, finance). Any MCP that doesn't satisfy any known pattern (ADO, Backstage, NewRelic, scheduled-tasks, GitHub, etc.) was previously silently skipped. v0.77.0 instead **surfaces each unknown MCP and lets the user classify it** — either as a known kind (override the auto-detection if needed) OR as a custom kind they define inline with a free-text "what matters" note. The user teaches the skill about their environment, per-vault.

Together: B makes detection flexible; C handles what B can't. The user-preferences.md schema grows backward-compatibly to carry custom kinds alongside known ones.

## 3. Workstream B — tool-pattern detection

### Problem

`mcp-skill-map.json` v1.0.0 uses namespace regex matching:

```json
{ "mcp_kind": "calendar", "mcp_namespace_match": "^(plugin_)?[Gg]oogle_?[Cc]alendar$|...", "gather_skill": "cowork:gather-calendar" }
```

Each entry's `mcp_namespace_match` is a regex tested against the MCP namespace segment (e.g., `Google_Calendar` from `mcp__Google_Calendar__list_events`). This misses:
- UUID namespaces (Outlook M365 is `45224a84-...` on accuris)
- Anything not literally named after the vendor (corporate gateway names, internal MCP servers, scheduled-tasks utility MCPs)
- The fact that one MCP namespace can serve multiple "kinds" (Outlook = calendar + email + chat + drive)

### Approach

Restructure `mcp-skill-map.json` to v2.0.0 — match by **required tool names** instead. Schema:

```json
{
  "version": "2.0.0",
  "comment": "Maps capabilities to tool-pattern signatures. context-builder uses tool-name presence (not namespace regex) so enterprise gateways like Outlook/M365 (UUID namespace) are detected by what they expose, not how they're named.",
  "kinds": [
    {
      "kind": "calendar",
      "required_tools": ["list_events", "create_event"],
      "optional_tools": ["update_event", "delete_event"],
      "gather_skill": "cowork:gather-calendar",
      "rename_from_v1": null
    },
    {
      "kind": "email",
      "required_tools": ["search_threads", "send_message"],
      "optional_tools": ["list_drafts", "create_draft", "label_message"],
      "gather_skill": "cowork:gather-gmail",
      "rename_from_v1": "gmail"
    },
    {
      "kind": "chat",
      "required_tools": ["send_message"],
      "tool_alternatives": [["list_chats"], ["list_threads"], ["list_conversations"]],
      "gather_skill": "cowork:gather-imessage",
      "rename_from_v1": "imessage"
    },
    {
      "kind": "finance",
      "required_tools": ["list_expenses"],
      "optional_tools": ["list_cards", "list_transactions"],
      "gather_skill": "cowork:gather-finance-yesterday",
      "rename_from_v1": null
    }
  ]
}
```

### Detection algorithm

```
1. tools_by_namespace = {}  // <ns> -> set of tool names
2. For each available mcp__<ns>__<tool> in agent's tool list:
     tools_by_namespace[ns].add(tool)
3. detected_capabilities = []
4. For each kind in mcp-skill-map.json:
     For each <ns> in tools_by_namespace:
       all_required_present = kind.required_tools.every(t => tools_by_namespace[ns].has(t))
       alt_branch_matches  = (kind.tool_alternatives || []).some(alt => alt.every(t => tools_by_namespace[ns].has(t)))
       if (all_required_present || alt_branch_matches):
         detected_capabilities.push({
           kind: kind.kind,
           served_by: ns,
           matched_tools: [...intersection of required+optional+alts with tools_by_namespace[ns]],
           gather_skill: kind.gather_skill,
         })
5. unmapped_namespaces = [ns for ns in tools_by_namespace
                          if no entry in detected_capabilities has served_by === ns]
```

`tool_alternatives` is an OR-of-ANDs: any inner array fully matched satisfies the kind. Used for `chat` to cover iMessage (`list_chats` or whatever Apple's MCP exposes), Teams (`list_threads`), Slack (`list_conversations`) — all distinct API shapes for the same conceptual capability.

### Renaming (v1 → v2)

| v1 kind name | v2 kind name | Reason |
|---|---|---|
| `gmail` | `email` | The kind is "email" generally; Gmail was the only example v0.76.0 imagined. |
| `imessage` | `chat` | Same reason; iMessage was one example of conversational chat. |
| `calendar` | `calendar` | Unchanged. |
| `finance` | `finance` | Unchanged. |

Migration: existing user-preferences.md with `mcps.gmail` or `mcps.imessage` is rewritten with renamed keys on next `cowork:context-builder` invocation. The helper (`context-builder-dry-run.js`) reads `rename_from_v1` from the map and applies renames during merge. v0.76.0 deployed less than a day ago — only the workshop's own dogfood vault has any v0.76.0-shaped preferences; production impact is essentially zero.

### Acceptance

- HC-V0770-A1: tool-pattern detection finds Outlook UUID namespace as `calendar` via `list_events`+`create_event` set membership.
- HC-V0770-A2: same Outlook UUID also detected as `email` via `search_threads`+`send_message` (capability-subset model).
- HC-V0770-A3: `chat` kind matches any of the 3 `tool_alternatives` branches.
- HC-V0770-B1: v1 → v2 migration renames `mcps.gmail` to `mcps.email` on rewrite.
- HC-V0770-B2: same for `imessage` → `chat`.

## 4. Workstream C — fully-adaptive unknown-MCP handling

### Problem

After v0.77.0 Workstream B, the catalog stays at 4 known kinds. Any MCP not satisfying any known tool-pattern (ADO, Backstage, NewRelic, scheduled-tasks, GitHub, internal MCPs) is collected in `unmapped_namespaces[]` and silently skipped in v0.76.0's detection step. v0.77.0 surfaces them and lets the user define preferences.

### Approach

After Workstream B's detection step, the skill enters a new **unknown-MCP loop**:

```
For each <ns> in unmapped_namespaces:
  Show user:
    > MCP `<ns>` is connected. Its tools: `[tool_a, tool_b, ..., tool_n]`.
    > Classify this MCP:
    >   - calendar — use the calendar question set
    >   - email — use the email question set
    >   - chat — use the chat question set
    >   - finance — use the finance question set
    >   - custom — define a new kind inline
    >   - skip — don't capture preferences for this MCP

  If user picks known kind (calendar/email/chat/finance):
    Add to detected_capabilities with served_by=<ns>, override_classified=true.
    The question set runs as usual against this MCP later.

  If user picks "custom":
    Sub-flow:
      Q1: "What's a short name for this kind? (e.g., `ado`, `newrelic`, `backstage`)"
      Q2: "Briefly describe what you care about from this MCP. (1-3 sentences)"
      Q3: "Add another custom kind for this same MCP, or move on?"
        - same-MCP-different-kind — back to Q1 with a hint
        - move-on — exit sub-flow

    Each captured custom kind appended to detected_capabilities with:
      kind: <user's short name>
      served_by: <ns>
      custom_kind: true
      what_matters: <Q2 free-text>

  If user picks "skip":
    No-op; namespace stays in unmapped_namespaces for audit-receipt only.
```

### Custom-kind data shape

```yaml
mcps:
  ado:
    served_by: "986d1053-..."  # the Accuris-internal MCP gateway
    captured_at: "2026-05-24"
    custom_kind: true
    what_matters: |
      Active PRs waiting on my review.
      My tickets due this week.
      Blocked tickets with no comment in 3+ days.
  newrelic:
    served_by: "986d1053-..."
    captured_at: "2026-05-24"
    custom_kind: true
    what_matters: |
      Production alerts I'm on-call for today.
      Error-rate spikes >2x baseline.
```

The same MCP namespace (`986d1053-...`) serves multiple custom kinds — matches the Workstream B capability-subset principle.

### Cross-cutting questions update

`priorities[]` now spans both known and custom kinds — the user reorders ALL bound capabilities together. Personality questions unchanged.

### Acceptance

- HC-V0770-C1: dry-run with `unknown_namespace_classifications: { ado: { kind: "custom", what_matters: "..." } }` writes `mcps.ado.custom_kind: true` + `what_matters` block.
- HC-V0770-C2: re-run with same MCP still connected and user choice = "Skip" preserves the existing block.
- HC-V0770-C3: re-run with MCP disconnected marks the block `connected: false`, preserves `what_matters` and all other answers.
- HC-V0770-C4: user picks "calendar" override for an unknown MCP — that namespace's calendar question set runs and produces a normal `mcps.calendar` block with `served_by: <unknown-ns>, override_classified: true`.

## 5. Workstream D — backward compatibility

### Problem

v0.76.0 just shipped. Some vaults may have user-preferences.md files with `mcps.gmail` / `mcps.imessage` blocks captured against the v1 schema. v0.77.0 must read them cleanly and migrate them.

### Approach

The helper (`context-builder-dry-run.js`) reads existing user-preferences.md → detects v1-shaped keys via `rename_from_v1` lookup in the new map → migrates keys on next rewrite. Migration is in-place during the normal compose flow; no separate migration command.

```
For each (old_kind, new_kind) in rename_map (gmail→email, imessage→chat):
  if existing_prefs.mcps[old_kind] exists and existing_prefs.mcps[new_kind] does not:
    existing_prefs.mcps[new_kind] = existing_prefs.mcps[old_kind]
    delete existing_prefs.mcps[old_kind]
```

The `priorities[]` list also gets renamed: `["gmail", "calendar"]` → `["email", "calendar"]`.

### Acceptance

- HC-V0770-E1: backward-compat — v0.76.0-shaped user-preferences.md (mcps.gmail, mcps.imessage) reads cleanly, migrates to v2 shape on rewrite, preserves all per-block answers.

## 6. Workstream F — schema validation harness

### Problem

The v2 schema is more complex (required_tools / optional_tools / tool_alternatives). A future cycle could accidentally ship a malformed `mcp-skill-map.json`. A static schema-validation case prevents the regression.

### Approach

New case `HC-V0770-D1` in `run-cowork-smoke.js`: reads `mcp-skill-map.json`, validates:
- Top-level `version` field is `"2.0.0"`.
- `kinds[]` is non-empty.
- Each entry has `kind` (string), `required_tools` (array of strings), `gather_skill` (string).
- `tool_alternatives` (when present) is an array of arrays of strings.
- `rename_from_v1` (when present) is a string.

### Acceptance

- HC-V0770-D1: schema validates against v2 shape.

## 12. Open questions / known unknowns (carry-forward to v0.78.0)

- **5-orchestrator consumption of user-preferences.md.** Now genuinely the v0.78.0 priority. The 5 atomic-note-emitting orchestrators (morning-briefing / midday-tripwire / eod-review / weekly-review / monthly-review) read user-preferences.md at fire time. Custom-kind `what_matters` text becomes additional context fed into the orchestrator's prompt. Known-kind structured answers reorder `[!example]+` blocks per priorities and apply personality voice in narrative sections.
- **Custom-kind promotion to known.** After accumulated v0.77.0 usage, if multiple users (or multiple vaults) define `ado` or `newrelic` with similar what_matters, v0.78.0+ could formalize them as known kinds with hand-curated question sets.
- **Tool-pattern signature library expansion.** The Minimum-4 catalog is intentionally narrow. v0.78.0+ candidates: `drive` (Google Drive + SharePoint), `code-platform` (GitHub + ADO + GitLab), `project-tracker` (Jira + Linear), `monitoring` (NewRelic + Grafana + PagerDuty + Datadog).
- **Cross-vault preferences inheritance.** `inherits_from: <other-vault>` field on user-preferences.md frontmatter — share preferences across personal-vault and consulting-vault (or accuris and ero) without manual duplication. Substantive design question.
- **MCP tool description ingestion.** The detection step currently only sees tool NAMES. The Claude Code MCP registry exposes tool DESCRIPTIONS too — a future cycle could use NLP-style matching on descriptions ("returns calendar events" → calendar) as a fallback when tool names don't pattern-match. Substantial.

## 13. Conventions (recap)

- Explicit `git add <paths>` — never `git add -A`.
- Annotated tag at cycle close requires USER APPROVAL.
- `platform/mechanisms/platform-claude/commands/install.md` is the SOURCE template for `.claude/commands/install.md`. Always edit the source, then run `node platform/test/run-install.js .` to rematerialize the dest.
