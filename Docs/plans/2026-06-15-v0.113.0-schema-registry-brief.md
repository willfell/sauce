# v0.113.0 brief — schema registry + linter (Stage A)

## The ask

**"Across the board" schema tracking.** Today, schemas in Sauce live in eight different surfaces with no central index:

1. **6 cowork sidecar JSON Schemas** at `platform/blueprints/cowork/data/schemas/*@1.0.0.json`. Each file's `schema_version` enum lists 5 accepted versions (1.0.0 → 1.4.0). One physical file per cadence; multiple versions accepted within.
2. **scheduled-job-contract.json** at `platform/blueprints/cowork/data/scheduled-job-contract.json`, `contract_version: 0.35.1`. Landmine #20 requires it mirror cowork blueprint version.
3. **49 rule_fragments[]** across 13 blueprint manifests — cowork 24, finance 8, project 4, plus 12 others. Each defines `rules[]` + scope_glob — implicit per-entity frontmatter contracts.
4. **new_entity_buttons[].prompts[]** schemas in blueprint manifests — user-input shape for entity creation.
5. **learned_weights schema 2/3/4/5** — migration helpers in `platform/blueprints/cowork/helpers/ingest-feedback-helper.js` + `learn-from-checks-helper.js`. No central pointer.
6. **Cowork data files** (`kind-classifier-cache.json`, `kind-patterns.json`, `kind-titles.json`, `cadence-freshness-windows.json`, `mcp-skill-map.json`) — implicit schemas.
7. **Workshop manifest + subscription** — `workshop_version`, `blueprints[]`, `mechanisms[]` shape contracts.
8. **Helper read-contracts** — implicit; the source code is the contract. The "verify helpers before design asserts them" lesson has fired in 4+ cycles (v0.93.3, v0.94.0 × 2, v0.95.0, v0.108.0).

Stage A closes the **workshop-side** half: build a registry + linter so the contract is centralized at dev time. Stage B (consumer-side runtime validation as a mechanism) is deferred to v0.114.0+ pending signal.

## What the registry index looks like (one example)

```json
{
  "schema_version": 1,
  "schemas": [
    {
      "id": "cowork-eod-review-sidecar",
      "kind": "sidecar-schema",
      "owner": { "type": "blueprint", "name": "cowork" },
      "source": "platform/blueprints/cowork/data/schemas/eod-review@1.0.0.json",
      "accepted_versions": ["1.0.0", "1.1.0", "1.2.0", "1.3.0", "1.4.0"],
      "validator": "platform/blueprints/cowork/helpers/validate-sidecar-helper.js",
      "consumers": [
        "platform/blueprints/cowork/skills/orchestrators/eod-review/SKILL.md",
        "platform/blueprints/cowork/helpers/write-atomic-note-helper.js"
      ],
      "notes": "EOD review sidecar. Latest schema_version is 1.4.0 — v0.101.0 (sparse-signal-feedback). Schema is a JSON Schema draft-07 document; valid versions enumerated in the document's `schema_version` field."
    }
  ]
}
```

Fields per entry:
- `id` — kebab-case unique identifier.
- `kind` — enum: `sidecar-schema | rule-fragment-bundle | contract | data-file | workshop-manifest | learned-state-schema | entity-create-prompts`.
- `owner` — `{ type: blueprint|mechanism|workshop, name: "..." }`.
- `source` — workshop-relative path to the schema OR closest schema-shaped artifact (rule_fragment id reference for blueprint manifests).
- `accepted_versions` — array of strings; for files with a `schema_version` enum, list them.
- `validator` — workshop-relative path to the helper/script that validates instances of this schema. Optional.
- `consumers` — array of workshop-relative paths that reference / read this schema.
- `notes` — free-text context.

## What the linter does

`scripts/lint-schemas.js` walks `platform/schemas-index.json` and asserts:

1. **Every `source` file exists.** If missing, exit 1 with the offending entry id.
2. **Every `validator` file exists** (when set).
3. **Every `consumer` file exists.** Warns (doesn't fail) if a consumer reference is stale.
4. **No duplicate ids.**
5. **Every entry has the required keys** (id, kind, owner, source).

Flags:
- `--check` (default behavior; exits 1 on any failure).
- `--list` — emit a one-per-line summary `<id> · <kind> · <owner.name> · <source>`.
- `--json` — emit the full parsed registry as JSON.
- `--verbose` — print per-entry validation lines.

## Success criteria

1. `platform/schemas-index.json` exists with ≥ 15 seeded entries covering all 8 schema surfaces.
2. `node scripts/lint-schemas.js` exits 0 against the seeded index.
3. `npm run lint-schemas` works.
4. `release:preflight` chain includes lint-schemas; whole-suite GREEN preserved.
5. HC family `caseV0113Schema*` ≥ 10 sub-asserts.
6. `Docs/agent-guides/schemas.md` surfaced from CLAUDE.md router.
7. `workshop-status.js` can OPTIONALLY surface a one-line "schemas: N tracked / M with issues" via the cached lint output. (Stretch; not required.)
8. Workshop dogfood: exit 0.

## Non-goals (explicit)

- **No runtime validation.** Schemas aren't enforced at install or render time by this cycle — that's Stage B.
- **No new schema FILES.** This cycle indexes existing schemas; it doesn't introduce new ones.
- **No schema migrations.** Existing schema bumps (learned_weights v5 etc.) are not affected.
- **No cross-vault schema sync.** Consumer vaults don't gain a runtime registry. Workshop-only.
- **No `sauce schemas` CLI verb.** Brew tap is stale; same posture as v0.112.0 — npm script only.
- **No auto-discovery beyond the seed.** The registry is manually authored. Heuristic "find all JSON files in known dirs" is a v0.113.1 PATCH candidate.

## Risks

- **Manual seeding is incomplete or wrong.** First-pass index might miss a schema or mislabel one. Mitigation: lint runs in preflight (catches missing sources); user can correct as patterns emerge. The cost of a wrong entry is "lint passes when it shouldn't" — soft failure, not hard.
- **Index becomes stale.** New schemas land in PRs without adding to the index. Mitigation: a future v0.113.x can add an "orphan detector" walking known schema dirs and complaining about files not in the index.
- **Linter output is too noisy.** ~15+ entries × per-entry checks could spam stderr. Mitigation: default mode is summary-only; `--verbose` for per-entry.

## Action required from user post-deploy

1. Try `npm run lint-schemas` — confirm output is useful.

3. Pick whether to layer Stage B (consumer-side runtime mechanism) on top, OR wait for signal.
