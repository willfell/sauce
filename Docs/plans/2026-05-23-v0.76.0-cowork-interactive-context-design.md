**Status:** design — pending plan + execution.

## 1. Cycle motivation

Two classes of work bundle into this minor cycle.

**Class 1 — v0.75.1 carry-forwards (four bugs).** The v0.75.1 `_resolveWorkshopPath` ancestry-walk helper uses `process.execPath` (the Node-binary path) instead of `__filename` (the cmd-update.js source path). The walk never reaches the sauce libexec on real brew installs because `/opt/homebrew/Cellar/node/.../bin/node` has no `libexec/platform/` ancestor; the v0.75.1 test mocked `_execPath` and so the bug wasn't caught. Stale `installed.workshop_path` values (left behind when brew cleans up an old keg) are returned unconditionally and cause downstream `workshop manifest not parseable` failures. The v0.75.1 H morning-briefing fix did not propagate to eod-review (line 66) and weekly-review (line 82), which still emit the stale `"Smart Connections index is not built for this vault..."` text and carry the same misfire risk when the semantic-related step never runs. Three orchestrators (eod-review, weekly-review, monthly-review) emit literal "No prompt body to drive content; this run is a placeholder" stubs when `spice/cowork/prompts/<orch>.md` is empty — morning-briefing has a fallback to the engagement-template prompt; the other three don't.

**Class 2 — interactive-context personalization (the feature).** cowork's atomic notes are shaped by stock engagement-template prompts the user doesn't see. The user has no first-class way to (a) tell sauce what they care about from each MCP, (b) set priorities for what shows up first, (c) attach a voice/personality to output, or (d) safely add new MCPs without losing customization on the next `sauce update`. v0.76.0 ships a new `cowork:context-builder` orchestrator-tier skill — an idempotent, additive, MCP-aware interview that writes structured preferences into a new user-owned `spice/cowork/context/user-preferences.md` file. The 5 atomic-note-emitting orchestrators do NOT yet consume this file in v0.76.0; that consumption layer is v0.77.0. v0.76.0 establishes the file schema, the preservation contract, the boundary contract documentation, and a fail-closed harness so the consumption layer in v0.77.0 lands against a stable target.

## 3. Workstream A — `_resolveWorkshopPath` walks from `__filename`

### Problem

`platform/cli/cmd-update.js:22` reads:

```js
const startExecPath = (hooks && hooks._execPath) || process.execPath;
```

`process.execPath` is the Node binary (`/opt/homebrew/Cellar/node/.../bin/node`). Its directory chain contains no `libexec` ancestor whose `platform/` subdirectory exists. The ancestry walk runs to filesystem root and throws.

The v0.75.1 test HC-V0751-B3 mocked `_execPath` to a synthetic directory tree containing `libexec/platform/` — the bug was hidden by the mock. Every real `sauce update --bump-pins` against a v0.75.1+ consumer vault currently requires explicit `--workshop-path $(brew --prefix sauce)/libexec`.

### Approach

Replace the `process.execPath` source with `__filename` (cmd-update.js's own file path). When the workshop is brew-installed, cmd-update.js lives at:

```
/opt/homebrew/Cellar/sauce/<version>/libexec/platform/cli/cmd-update.js
```

The ancestry walk from `__filename`'s directory finds `libexec` at depth 2 (`...libexec/platform/cli` → `...libexec/platform` → `...libexec` — matches: `path.basename(dir) === 'libexec'` AND `fs.existsSync(path.join(dir, 'platform'))`).

### Code change

```js
function _resolveWorkshopPath(installed, argv, hooks) {
    if (argv && argv.workshopPath) return argv.workshopPath;
    if (installed && installed.workshop_path) {
        // Workstream B: validate before returning
        const candidate = installed.workshop_path;
        const manifestProbe = path.join(candidate, "platform", "manifest.json");
        if (fs.existsSync(manifestProbe)) return candidate;
        // fall through to ancestry walk (stale path)
    }
    // Workstream A: walk from __filename (or hook), NOT process.execPath
    const startFile = (hooks && hooks._callerFile) || __filename;
    let dir = path.dirname(startFile);
    const root = path.parse(dir).root;
    while (dir !== root) {
        if (
            path.basename(dir) === "libexec" &&
            fs.existsSync(path.join(dir, "platform"))
        ) {
            return dir;
        }
        dir = path.dirname(dir);
    }
    throw new Error(
        "Could not auto-detect workshop_path. Pass --workshop-path <path> explicitly.",
    );
}
```

### Acceptance

- `sauce update --bump-pins` against any v0.75.1+ consumer vault (with `workshop_path` either null OR pointing at a no-longer-installed keg) succeeds without `--workshop-path`.
- HC-V0760-B1..B3 update v0.75.1's existing helper-precedence tests to thread `_callerFile` instead of `_execPath`; existing branches (argv override, installed-valid, ancestry) continue passing under the new hook.
- HC-V0760-B4 (new) — helper falls through to ancestry walk when `installed.workshop_path` exists but points at a non-existent directory.

## 4. Workstream B — Stale `installed.workshop_path` invalidation

### Problem

When brew cleans up an old keg (e.g., `brew cleanup sauce` after upgrade), the `workshop_path` field stored in `ranch/platform-installed.json` becomes a dead path. v0.75.1's helper returns it anyway (line 21 — unconditional return when truthy). Downstream `JSON.parse(fs.readFileSync(workshopManifestPath))` fails with `workshop manifest not parseable at <stale-path>` (cmd-update.js:64).

### Approach

After reading `installed.workshop_path`, validate via filesystem probe: `fs.existsSync(path.join(stored, "platform", "manifest.json"))`. If absent, fall through to the ancestry walk (now fixed by Workstream A). The probe is one syscall — cheap; runs once per `sauce update`.

This is folded into the same code change as Workstream A above (the `// fall through to ancestry walk (stale path)` branch).

### Acceptance

- After a brew keg cleanup that invalidates the stored path, the next `sauce update --bump-pins` runs end-to-end (helper falls through to ancestry walk + Workstream A fixes the walk).
- HC-V0760-B4 (shared with A) covers this case.

## 6. Workstream D — Placeholder-stub fallback to engagement-template prompt

### Problem

Three orchestrators emit literal stub content when `spice/cowork/prompts/<orch>.md` body is empty:

- `eod-review/SKILL.md:60`: `> No prompt body to drive content; this run is a placeholder.`
- `weekly-review/SKILL.md:75`: same.
- `monthly-review/SKILL.md:59`: same.

morning-briefing has a fallback chain: when the user's prompt body is empty, it reads `spice/cowork/context/engagement-templates/<engagement.type>/prompts/morning-briefing.md` and uses THAT body. So morning-briefing only stubs when both user AND engagement-template prompts are empty. The other three cadences lack the fallback.

### Approach

Add the same fallback chain to eod-review, weekly-review, monthly-review. In each orchestrator's `## Write` phase, replace the "if prompt_body empty → stub" branch with:

```
- Read user prompt body at `spice/cowork/prompts/<orch>.md`. Strip frontmatter; capture body as `user_prompt_body`.
- If `user_prompt_body` is empty, read engagement-template prompt at
  `spice/cowork/context/engagement-templates/<engagement.type>/prompts/<orch>.md`.
  Strip frontmatter; capture body as `template_prompt_body`. Set `prompt_source =
  "spice/cowork/context/engagement-templates/<engagement.type>/prompts/<orch>.md"`.
- The body used for composition is `user_prompt_body || template_prompt_body`.
- If BOTH are empty, set `warning = "empty_prompt"` and compose the skeleton-compliant
  STUB body per the current contract.
```

`prompt_source:` frontmatter on the atomic-note already records which source drove the run — the fallback flips it from user-prompt to engagement-template path when used, which is observable.

### Acceptance

- HC-V0760-D1: eod-review fire with empty user-prompt + non-empty engagement-template renders engagement-template content; `prompt_source:` frontmatter reflects the engagement-template path; `warning:` is absent.

## 7. Workstream E — `preserve_if_exists` installer flag

### Problem

`platform/install.js` currently overwrites every file listed in a blueprint manifest's `files[]` entry on every `sauce reinstall`. This is correct behavior for stock content (engagement-templates, hub notes, scheduled-jobs.md). It is incorrect for files the user is meant to own and edit — e.g., the new `user-preferences.md` from Workstream F, but also (today, implicitly) `vault-config.md`, the 5 cowork prompt files, `active-threads.md`, `weekly-snapshot.md`. These files happen to be preserved today because they aren't in any `files[]` entry — bootstrap-vault writes them on first install. There is no enforcement that a future cycle won't accidentally add them to `files[]` and silently wipe user state.

### Approach

Add an optional `preserve_if_exists` boolean per `files[]` entry in blueprint manifests. When `true`, `install.js`:

1. Checks if the dest file already exists.
2. If exists, logs `preserved: <dest>` and skips the write.
3. If not, writes from source as usual (this is the first-install seeding path).

Default is `false` (current behavior).

```js
// platform/install.js — inside the files[] copy loop
const destExists = fs.existsSync(destAbsPath);
if (fileEntry.preserve_if_exists && destExists) {
    log(`preserved (user-owned): ${fileEntry.dest}`);
    continue;
}
// ... existing copy logic
```

Apply the flag to the new `content/context/user-preferences.md` template entry in cowork's manifest. Do NOT apply it to existing user-owned files in v0.76.0 — they aren't in `files[]` today, and adding them as `preserve_if_exists` entries is a separate scope decision (touches bootstrap-vault's seeding path; deferred).

### Acceptance

- HC-V0760-E1: installer skips a `preserve_if_exists: true` file when the dest already exists; writes when absent.
- New `user-preferences.md` template entry in cowork manifest seeds on first install; never overwrites on subsequent `sauce update` / `sauce reinstall`.

## 8. Workstream F — `cowork:context-builder` orchestrator-tier skill

### Problem

The user has no first-class way to personalize cowork rendering. Stock templates set the structure; user-owned per-cadence prompts (`spice/cowork/prompts/<orch>.md`) shape content but require manual editing of 5 separate files; no cross-cutting place to specify "personality" or "priorities" reusable across all 5 cadences.

### Approach

New orchestrator-tier skill `cowork:context-builder`. Lives at `platform/blueprints/cowork/skills/orchestrators/context-builder/SKILL.md`. Distributes via `claude_surface[]` to `.claude/skills/cowork/context-builder/SKILL.md`. Fully re-runnable; idempotent; additive.

**Interview flow (skill body's runtime contract):**

1. **Pre-flight.** Call `check-vault-routing` with `{ required: ["filesystem"] }`. Verify `spice/cowork/context/vault-config.md` exists (vault bootstrapped). If not, emit notice "cowork:context-builder requires vault-config.md — run cowork:onboard-scheduled-jobs first" and exit.

2. **Read current state.** If `spice/cowork/context/user-preferences.md` exists, parse it; capture `existing_prefs` (priorities, personality, mcps map). Else `existing_prefs = null`.

3. **Detect connected MCPs.** Inspect the agent's available tool list; scan tool names starting with `mcp__`. Group by MCP-namespace (`mcp__Google_Calendar__*`, `mcp__Gmail__*`, etc.). Build `detected_mcps[]`.

4. **Map MCPs to gather skills.** Read `spice/cowork/context/mcp-skill-map.json` (a small data file shipped with cowork). Each entry is `{ mcp_namespace: string, mcp_kind: string, gather_skill: string }`. For each detected MCP, look up `mcp_kind` (e.g., `calendar`, `gmail`, `imessage`, `finance`). Detected MCPs with no entry are listed under "MCPs without a wired gather skill — preferences not collected" and skipped.

5. **Interview loop (one round per mapped MCP).** For each `(mcp_kind, gather_skill)` pair, in priorities-ordered order if `existing_prefs.priorities` is set, else alphabetical:
   - If `existing_prefs.mcps[mcp_kind]` is absent (NEW): walk that MCP's question set.
   - If `existing_prefs.mcps[mcp_kind]` is present AND the MCP is currently connected: ask via AskUserQuestion: `"Update preferences for <mcp_kind>? (configured <captured_at>)"` with options `[Update, Skip, Clear]`. On Update, walk question set with existing values as defaults. On Skip, leave block unchanged. On Clear, delete block (skill writes the file without that mcp_kind on save).
   - If `existing_prefs.mcps[mcp_kind]` is present AND the MCP is NOT in `detected_mcps` (disconnected): set `connected: false` and `last_seen: <existing_captured_at>` in the block; do NOT ask any questions; preserve all answers.

6. **Cross-cutting questions.** Always re-ask priorities (single AskUserQuestion: rank the mapped-MCPs in order) and personality (4 single-selects: vibe / formality / pep_talk / length). Existing values populate as defaults.

7. **Compose new preferences structure.** Merge new answers into existing structure (preserving disconnected blocks). Bump `updated:` to today; set `updated_by: "cowork:context-builder"`.

8. **Write user-preferences.md.** Use the Write tool against `spice/cowork/context/user-preferences.md`. Frontmatter-only YAML; no body.

9. **Audit-receipt.** Emit a brief summary: `cowork:context-builder — added: [calendar]; updated: [gmail]; preserved-disconnected: [slack]; cleared: []`. Append a 5-row table per the v0.74.0+ skill convention.

**Question sets — inline in SKILL.md:**

Each MCP-kind gets a `## Question set — <kind>` section. Each question is a small structured stanza:

```
### Q1 — calendar.surface_event_kinds (multi-select)
Prompt: "Which calendar event kinds matter most for your morning briefing?"
Options:
  - conflicts          — overlapping events
  - focus-blocks       — 1+ hour gaps marked as focus time
  - prep-needed        — meetings missing agenda/notes
  - travel             — events with location field set
  - external           — events with attendees outside your org
  - all-day            — full-day events (out-of-office, holidays)
Output field: mcps.calendar.surface_event_kinds (string[])
```

4 MCP kinds × 3-5 questions each = 12-20 questions inline. Question content is the substance of v1; future cycles can refine wording, add MCP-kinds, or refactor to per-file storage.

**MCP-skill-map.json shape:**

```json
{
  "version": "1.0.0",
  "entries": [
    { "mcp_kind": "calendar", "mcp_namespace_match": "^mcp__(plugin_)?Google_Calendar__", "gather_skill": "cowork:gather-calendar" },
    { "mcp_kind": "gmail",    "mcp_namespace_match": "^mcp__claude_ai_Gmail__",            "gather_skill": "cowork:gather-gmail" },
```

## 9. Workstream G — boundary contract documentation

### Problem

The user's empirical observation (handoff §"Cowork customization-vs-stock boundary"): STOCK vs USER bucket is implicit. No agent-guide doc enumerates it. A future cycle could accidentally add a USER file to `files[]` and silently wipe state on next `sauce update`.

### Approach

New agent-guide doc at `Docs/agent-guides/cowork-customization-contract.md`. Enumerates per-file STOCK or USER status with rationale and the preservation mechanism (manifest entry vs bootstrap-vault seed vs `preserve_if_exists`).

```markdown
# Cowork customization contract

This guide enumerates which files in a consumer vault are STOCK (overwritten on
every `sauce update`) and which are USER (preserved across `sauce update`).

## STOCK — overwritten by `sauce update` / `sauce reinstall`

| Path | Source | Notes |
|---|---|---|
| spice/cowork/context/engagement-templates/**/*.md | platform/blueprints/cowork/content/context/engagement-templates/** | All 15 prompt files + 7 context defaults per engagement-type |
| spice/cowork/context/engagement-shared-templates/*.md | platform/blueprints/cowork/content/context/engagement-shared-templates/** | active-threads.md, vault-config.md, weekly-snapshot.md SEED templates only — NOT the runtime files at spice/cowork/context/ |
| spice/cowork/scheduled-jobs.md | platform/blueprints/cowork/content/scheduled-jobs.md | The cowork:onboard-scheduled-jobs skill rewrites this as the user adds/removes jobs; sauce reinstall reverts to template. |
| .claude/skills/cowork/**/SKILL.md | platform/blueprints/cowork/skills/** | All skill bodies are claude_surface-managed STOCK. |

## USER — preserved across `sauce update`

| Path | First-install source | Preservation mechanism |
|---|---|---|
| spice/cowork/context/vault-config.md | bootstrap-vault writes from engagement-shared-templates seed | Not in `files[]`; bootstrap seeds once. |
| spice/cowork/context/active-threads.md | bootstrap-vault writes empty | Not in `files[]`. |
| spice/cowork/context/weekly-snapshot.md | bootstrap-vault writes empty | Not in `files[]`. |
| spice/cowork/context/user-preferences.md | install.js seeds from template | `preserve_if_exists: true` in manifest. |
| spice/cowork/prompts/morning-briefing.md (+4 cadences) | onboard-scheduled-jobs writes from engagement-template prompts | Not in `files[]`. |

## Why USER files MUST stay out of `files[]` (or carry `preserve_if_exists: true`)

Adding a USER file to a blueprint's `files[]` without `preserve_if_exists: true`
will cause `sauce reinstall` to silently overwrite user state. The HC-V0760-A1
preservation harness fails closed against this mistake.

## When to add a new USER file

If a future cycle introduces another user-owned file:
1. Add the path to this contract document.
2. Choose preservation mechanism (seeded by bootstrap-vault, OR seeded by install.js
   with `preserve_if_exists: true`).
3. Add the path to HC-V0760-A1's USER-file list.
```

### Acceptance

- File written at `Docs/agent-guides/cowork-customization-contract.md`.
- Referenced from `CLAUDE.md` (router) and the new user-preferences.md template body.

```
## Phase: ensure user-preferences captured

delegate to context-builder. On no, continue.
```

## 16. Open questions / known unknowns (carry-forward to v0.77.0)

- **5-orchestrator consumption of user-preferences.md.** v0.77.0 will wire morning-briefing / midday-tripwire / eod-review / weekly-review / monthly-review to read user-preferences.md via a new sub-skill `cowork:read-user-preferences`. Open: how exactly do priorities reorder `[!example]+` blocks (priority-of-content vs priority-of-section)? How does personality voice manifest in `> [!tip]` close text (style-prompt prefix vs structured rendering)?
- **MCP detection precision.** The `mcp__*` tool-name scan is heuristic. False positives (e.g., utility MCPs like context7) skip cleanly because mcp-skill-map.json regex won't match. False negatives (e.g., new MCP server with unusual prefix) are detected but unmapped → listed in audit-receipt but no questions asked. Acceptable for v1.
- **Non-interactive harness mode for cowork:context-builder.** HC-V0760-F1/F2 need to exercise the file-write contract without AskUserQuestion interactivity. Approach: skill body supports `dry_run_answers: {...}` input that bypasses AskUserQuestion and feeds canned answers. Plan stage will finalize the dry-run contract shape.
- **Question wording for the v1 question sets.** Hand-curated for v1. Future cycles may A/B-test wording or surface refinement based on observed user-correction patterns (deferred).
- **Cross-vault preferences sharing.** Out of scope for v0.76.0. If a future cycle wants user-preferences.md to be shared across consumer vaults (e.g., personal preferences identical across personal-vault and consulting-vault), the file shape supports a top-level `inherits_from:` field — defer until the need is concrete.
