# v0.120.0 — live-render recurring MINOR — result

## Shipped

User reported six issues on the recurring-tasks surface (post-v0.119.1 deploy) and explicitly
opted into the live-render approach the original v0.118.1 postmortem item #5 had identified as
the right long-term fix. Bundled into v0.120.0 MINOR.

### Six fixes

1. **Templater expression in registry frontmatter.** `Recurring Tasks.md` template carried
   `created_at: "<% tp.file.creation_date("YYYY-MM-DDTHH:mm:ssZ") %>"`. The installer
   materializes the file as a plain string copy — Templater never executes over it, so the
   literal text was visible in both accuris's `spice/to-do/Recurring Tasks.md` and headspace's
   `ranch/templates/Recurring Tasks.md`. Fix: remove the field. The registry doesn't need a
   `created_at` — its mtime / git history is the canonical source of when it was created.

2. **`+ Recurring` button behavior.** Clicked `Recurring` on `ToDoLeafActions` opened the
   `ToDoCreateTask` dialog with the recurring tab preselected. User feedback: the registry
   markdown is the source of truth; the dialog round-trip is friction. Fix: button now calls
   `app.workspace.openLinkText('spice/to-do/Recurring Tasks.md', '', false)` — opens the file
   directly. Failure-tolerant (Notice if open throws).

3. **Blank lines between tasks on the daily.** `ToDoCreateTask` was emitting
   `\n${line}\n\n` when inserting a new task under the SectionLabel anchor — the trailing
   `\n\n` produced a blank line between consecutive task entries. Fix: emit `\n${line}\n`
   (single trailing newline). The label-block / first-task gap is unchanged; only inter-task
   spacing is tightened.

4. **`Recurring Today` → `Recurring` label.** Cosmetic rename in the SectionLabel emit path
   (`insertRecurringIntoToday`) + the new live-render path. Both `Recurring Today` (legacy)
   and `Recurring` (new) labels are recognized by the merge/strip migration regexes for
   backwards compat.

5. **Leading blank line between SectionLabel and first task.** The legacy
   `insertRecurringIntoToday` emitted `[label-block]\n\n[task-line]\n\n` — the extra blank
   created visual noise between the section header and the first task. Fix: emit
   `[label-block]\n[task-line]\n` (no leading blank, no trailing blank between tasks).
   Live-render path renders rows directly into `dv.container` with `padding:2px 0` — no
   inter-row blank by default.

### Architecture shift — live-render replaces materialization

`ToDoDailyRecurring.render()` no longer writes to today's daily. Previous architecture:
- Parse registry → compute hashes → materialize matching task lines INTO today's daily →
  write sentinel → on subsequent renders, additive-merge new tasks into existing block.

New architecture (v0.8.0):
- On every render, read registry → filter matches via `matchesToday` → render matching tasks
  inline into `dv.container` via DOM nodes (no file writes). The render output IS the
  visible section.

Consequences:
- Mid-day-added recurring tasks appear on next render (no sentinel to invalidate; postmortem
  item #5 closed).
- No more duplicate-block bugs (no insert path to multi-call).
- No `materialize_once` data-loss risk for the registry (the registry is read-only at render
  time; user mutations are preserved indefinitely).
- Per-day completion state for recurring tasks is no longer tracked on the daily (the row is
  read-only; clicking opens the registry). If per-day completion tracking becomes desired
  later, can be added via a sidecar completion log without re-introducing materialization.
- Legacy `materialize()` / `insertRecurringIntoToday` static helpers preserved for harness
  regression coverage but not invoked from the live path.

### Heal migration — `stripPersistedRecurringSection`

Wired into `applyToDoBlueprintMigration` pipeline immediately after the v0.119.0/v0.119.1
migrations (those become no-ops once strip has run). Walks every `spice/to-do/**/ToDo-*.md`:
1. Removes every `<!-- recurring-materialized-... -->` sentinel.
2. For each `Recurring Today` / `Recurring` SectionLabel dataviewjs block: drops the block
   AND every line after it until the next dataviewjs block / H1-H2 / EOF.
3. `.sauce-backup/<ts>/` snapshot before write. Failure-loud per-file. Idempotent.

After this migration runs, the live-render path is the only source of recurring-task rows
on the daily.

## Carry-forwards

- **Per-day completion tracking for recurring tasks** (if desired). The live-render shift
  removes the per-day mutable checkbox copy. A future cycle could add a sidecar completion
  log (e.g., `spice/to-do/<year>/<month>/.recurring-completions-<date>.json`) read by
  `ToDoDailyRecurring._renderRow` to show check state. Demand-gated.
- **Registry editor UX**. Now that `+ Recurring` opens the registry markdown directly, a
  follow-up could ship a richer in-line "+ New entry" affordance at the top of the registry
  (vs free-form markdown editing). Demand-gated.
- **Live-render adoption elsewhere**. The pattern (read source on render, emit into
  `dv.container`) could absorb `ToDoDailyCarryover`'s persisted carryover section too. That's
  a larger surface change and probably a separate cycle.

## Lessons

1. **Postmortem item #5 was load-bearing.** The original v0.118.1 cycle postmortem flagged
   materialize-once as fragile; v0.119.0 + v0.119.1 patched around it (additive sentinel,
   merge migration). The user's v0.120.0 ask reverts to the postmortem's recommendation:
   replace materialization with live render. Three patches into a fragile design is the
   signal to redesign, not the next-patch shape.
2. **Templater expression literal in materialized files is a known trap.** The registry
   template's `created_at: "<% tp.file.creation_date(...) %>"` shipped to consumer vaults
   as literal text because the installer doesn't run Templater. Future templates should
   either (a) use installer substitution tokens (`{{now.ISO}}`) for date fields, or (b) omit
   non-load-bearing date fields entirely. The to-do registry takes path (b).
3. **Architecture shifts can shrink test surfaces.** The materialize-→ live-render shift
   means HC-V0119-SENT-* / HC-V0119-INSERT-* / HC-V0119-MIGRATE-* / HC-V0119-MERGE-* are
   all backwards-compat regression tests for code paths the live render never hits.
   They're preserved (still pass) but represent "ensures the legacy helpers still work
   for harness coverage" rather than "ensures production correctness." Future cleanup
   could retire them once the v0.7.x → v0.8.0 transition has soaked.
