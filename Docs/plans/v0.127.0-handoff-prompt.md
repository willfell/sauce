2. **New Task in a meeting routes to today's daily To-Do, not the meeting's Action Items.** Reproduced on `spice/meetings/notes/2026/06-June/another-test-meeting-2026-06-23.md` and `test-meeting-with-project-2026-06-23.md`. The task created via the leaf-action ends up at `spice/to-do/2026/06-June/ToDo-2026-06-23.md` instead of the meeting's `## Action Items` section. **Root cause:** `meeting-leaf-actions.js _onNewTask` calls `customJS.ToDoCreateTask.open({ preselectTab: "one-shot", preselectDestination: dest })` — the `one-shot` tab semantics in ToDoCreateTask write to today's daily To-Do, not the source note. The v0.125.0 design explicitly chose this delegation; the user wants it changed.

   **User-chosen routing**: task should be appended to the **meeting note's `## Action Items` section** AND, when the meeting has a `project: "[[X]]"` frontmatter, ALSO appended to that project's `<Project> To-Do.md`. Today's daily To-Do stays untouched. Both writes are first-class; not a single-destination toggle.

3. **Stale project hubs don't show meetings.** Only `graphene/Graphene.md` and `thread/Thread.md` (out of 21 `type: project` notes in the vault) carry the modern `ProjectMeetingsPanel` dataviewjs block. The other 19 — including `databricks/Databricks.md` which the user actively uses — won't auto-list meetings assigned to them.

   Audit results (already done; trust these):
   ```
   pmp=1 graphene/Graphene.md
   pmp=1 thread/Thread.md
   pmp=0 (everyone else, 19 projects)
   ```
   Needs a heal that injects `ProjectMeetingsPanel` (and any other current chrome blocks the project blueprint declares) into stale project hubs. Or a sub-skill that migrates them on demand. Decide which is appropriate during design.

4. **Projects.md hub defaults are wrong.** Today the hub at `spice/projects/Projects.md` defaults to filtering out `done` / `superseded` / `cancelled` statuses and to some non-recency sort. User wants:
   - **Show ALL projects by default** (no status filter, including done/superseded/cancelled).
   - **Default sort: most-recently-modified-file-anywhere-under-the-project's-folder DESCENDING** — so projects with active work bubble to the top regardless of their `status_changed_at` frontmatter. Use the project folder's deepest-mtime across all files inside, not the project hub note's mtime alone.
