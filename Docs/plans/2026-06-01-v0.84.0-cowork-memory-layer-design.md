## 1. Scope

Ship the FOUNDATION of a continuous-memory layer for cowork. Today, every scheduled orchestrator (morning-briefing, midday-tripwire, eod-review, weekly-review, monthly-review) starts from a cold context — re-gathers everything from MCPs at fire time, doesn't know what happened since the last fire of any cadence. The memory layer makes each cadence walk in with continuity.

This cycle ships **Tier 0 + Tier 1** of the eventual multi-tier memory architecture:

- **Tier 0 — hourly tick** (`cowork:capture-tick`): every hour during waking hours (default 7am-10pm), captures lean deltas across the engagement's MCP kinds (calendar/email/chat/finance/projects/threads as per the user's `prefs.priorities`).
- **Tier 1 — daily synthesis** (`cowork:synthesize-day`): fires at EOD (default 15min after typical eod-review slot), compresses the day's ticks + today's atomic notes into a pattern + carry-forward note.
- **Consumer wire-through** — `cowork:morning-briefing` gains a pre-flight step reading yesterday's daily synthesis + last 4-6 overnight ticks as "Yesterday at a glance" context.

Tier 2 (weekly synthesis), Tier 3 (monthly synthesis), and wire-through of midday-tripwire/eod-review/weekly-review/monthly-review to also read recent memory are explicitly **deferred to v0.85.0+**.

Out of scope:

- New per-kind lean-gather sub-skill variants (`gather-calendar-light` etc.). Tick reuses existing gather skills with tight `range` windows.
- New gather skills (e.g., `gather-github`, `gather-ado` first-class). Custom-kind ADO/GitHub continue to route via `gather-from-served-by`.
- Voice contract or hard rules CHANGES — tick + synthesis adopt the existing voice contract from user-preferences.md without modifying it.
- Smart Connections semantic retrieval over memory notes. Future cycles can layer this on top.
- Memory note pruning / compression. Memory accumulates indefinitely until a future retention policy ships.
- Headspace eod-review monochrome-callout issue — post-deploy validation point; will surface a clean reproducer if it persists after tonight's eod-review fire on the post-v0.83.0 SKILL.md. v0.84.1 PATCH candidate if needed.

## 2. Architecture

### 2.1 Two new orchestrators + one wire-through

| Orchestrator | Cadence | Pre-flight reads | Gather phase | Write target |
|---|---|---|---|---|
| `cowork:capture-tick` (NEW) | hourly per engagement, 7am-10pm | check-vault-routing, date-context, read-user-preferences, vault-config; existing day memory file (if present, to determine `range.start = last_tick_at`) | iterates `prefs.priorities`; for each kind, invokes the existing canonical gather skill OR `gather-from-served-by` with `range: { start: <last_tick_at>, end: <now> }` | APPEND a tick callout to `spice/cowork/memory/<engagement_id>/YYYY/MM-MMMM/YYYY-MM-DD/memory.md` (creates the file on first tick of day) |
| `cowork:synthesize-day` (NEW) | EOD per engagement (15min after eod-review slot) | check-vault-routing, date-context, read-user-preferences, vault-config; today's full memory file (all ticks); today's atomic notes (morning-briefing, midday-tripwire, eod-review, finance) | NONE — pure synthesis from already-gathered tick data; uses personality voice contract for narrative composition | REPLACE the placeholder synthesis section at the top of today's `memory.md` with real content; set `synthesized: true`, `synthesis_at` |
| `cowork:morning-briefing` (MODIFY) | unchanged | gains NEW pre-flight step 3a (between date-context @ step 3 and read-user-preferences @ step 3b): read yesterday's `memory.md` synthesis section + last 4-6 overnight ticks; inject as `Yesterday at a glance` callout in the prompt body composition | unchanged | unchanged |

### 2.2 Why reuse existing gather skills rather than ship lean-mode variants

The user's framing: "a lean take on all MCPs that are used for all tasks." The cleanest interpretation is "run the morning-briefing engine, but with a 1-hour window." Most existing gather skills already support range-scoped queries through their `range`, `since`, `lookback_start`, or analogous parameters. The tick orchestrator just invokes them with `range: { start: <last_tick_at>, end: <now> }` instead of a full-day range.

The custom-kind path (ADO/GitHub) continues to route through `gather-from-served-by` with the microscope contract (if present) or the `what_matters` block — same as morning-briefing. The microscope contract MAY include guidance like "for the tick cadence, surface only changes in last hour" — but the contract itself is USER-owned, not changed by this cycle.

This means:
- No new gather sub-skills shipped this cycle.
- No prose changes to existing gather sub-skills.
- The "lean variant" of each gather emerges naturally from the tight `range` window.
- Future cycles MAY add explicit `mode: "tick"` to gather sub-skills if the natural-range approach produces unwieldy output. For v0.84.0, the natural approach is sufficient.

### 2.3 Single-file-per-day write contract (rather than file-per-tick)

The original design proposed 16 separate tick files per day (`HH-tick.md` × N). The user revised this: "lets make sure that these hourly dumps for the day are tracked in one note for the day."

The single-file model:
- Each day per engagement = ONE memory note at `spice/cowork/memory/<engagement_id>/YYYY/MM-MMMM/YYYY-MM-DD/memory.md`.
- The tick orchestrator READs-OR-CREATEs this file. On create, scaffolds frontmatter + the empty synthesis placeholder + the `## Ticks` section header. On read, parses frontmatter to determine `last_tick_at` for the next gather range.
- Each tick APPENDS one collapsed `[!example]-` callout titled `HH:MM Tick` to the `## Ticks` section.
- Frontmatter is updated each tick: `tick_count` increments, `last_tick_at` advances.
- The synthesize-day orchestrator REPLACEs the placeholder synthesis section (between H1 and `## Ticks`) with real content. Sets `synthesized: true`, `synthesis_at`.

Benefits:
- Single file per day = easier for downstream orchestrators (morning-briefing) to read. One Read call instead of glob+read+merge.
- Single file = simpler vault discoverability (one entry per day in activity-feed).
- Append-only writes (within a day) = minimal concurrency risk. Two ticks running concurrently is unlikely with hourly cadence; if it does happen, the second writer would see the first's tick in the read-back and append after it.

### 2.4 Memory note shape (full example)

```yaml
---
type: cowork-memory
engagement_id: headspace
day: 2026-06-02
created_at: 2026-06-02T07:00:00-06:00
last_tick_at: 2026-06-02T22:00:00-06:00
tick_count: 16
synthesized: true
synthesis_at: 2026-06-02T19:15:00-06:00
summary: <≤200 chars day-pattern one-liner; written by synthesize-day; before synthesis, written by the latest tick as a running summary>
---

# Daily memory — Wednesday, June 2, 2026

> [!info]- Today's pattern (synthesis)
> {{2-3 paragraph day-pattern, voice-applied per personality contract — generated by cowork:synthesize-day at EOD; before EOD, this section reads "Synthesis pending — will fire at <synthesize-day cron time>."}}

> [!tip] Carry-forward to tomorrow's morning-briefing
> - {{bullet 1 — synthesized priority/lead}}
> - {{bullet 2 — open loop or follow-up}}
> - {{bullet 3 — contextual flag tomorrow's gather should know about}}

## Ticks

> [!example]- 07:00 Tick
> **Calendar:** Next event: 9am — Dev standup.
> **Email:** 2 new threads (Diana, Will Sr.); none reply-owed.
> **Chat:** 1 new from Momma; quiet cadence flag cleared.
> **Threads:** No changes since last tick (file unchanged).
> **Projects:** No status changes since last tick.

> [!example]- 08:00 Tick
> **Calendar:** In standup (9am-9:30am).
> **Email:** No new threads.
> **Chat:** No new messages.
> **Projects:** Ticket 705679 status moved → In Review.

> [!example]- 09:00 Tick
> **Calendar:** Next event: 2pm — 1:1 with Manager.
> **Email:** 1 new thread (Boss); reply-owed.
> **Chat:** No new messages.

(...16 ticks total, in chronological order)
```

Notes on the shape:

- **Synthesis at TOP** (collapsed by default with `[!info]-`) because morning-briefing reads it first. Pattern callout above the ticks lets a human-reader open the note + understand the day at a glance without scrolling through 16 tick blocks.
- **Carry-forward block** as `[!tip]` matches existing eod-review's "next action" convention. Limited to 3 bullets — keeps morning-briefing's injection lean.
- **Each tick as collapsed `[!example]-`** — collapsed by default to avoid 80+ visible callouts. Title `HH:MM Tick` for sortability. Body uses `**KindTitle:**` bold-prefix lines per kind. Kinds with no delta omitted entirely.
- **Per-kind callout_type styling within ticks does NOT apply** — the per-kind styling from v0.82.0 is for atomic-note callouts in morning-briefing/midday-tripwire/eod-review where each kind gets its own top-level callout. Within a tick callout, all kinds share one container, so per-kind styling is moot. Memory note is BACKGROUND consumption; aesthetic concerns are secondary.

### 2.5 morning-briefing wire-through

New pre-flight step 3a (between current step 3 `date-context` and current step 3b `read-user-preferences`):

> **3a. Read recent memory.** Compose `<yesterday-memory-path>` = `spice/cowork/memory/<engagement_id>/<yesterday-YYYY>/<yesterday-MM-MMMM>/<yesterday-YYYY-MM-DD>/memory.md`. Read via the Read tool; treat not-found as absent (set `yesterday_memory = null`). If present, parse frontmatter; extract `summary`, `synthesis_at`, `tick_count`; extract synthesis section body (text between H1 and `## Ticks`) as `yesterday_synthesis`; extract carry-forward `[!tip]` callout body as `yesterday_carry_forward`. ALSO read `<today-memory-path>` = `spice/cowork/memory/<engagement_id>/<today-YYYY>/<today-MM-MMMM>/<today-YYYY-MM-DD>/memory.md`. If present, parse `## Ticks` section; extract up to the last 6 tick callouts (chronological-reverse, most-recent first) as `overnight_ticks_summary`. If neither file exists (memory layer hasn't fired yet for this engagement), set both to `null` and continue silently — no degradation of morning-briefing's existing behavior.

In `## Write` step (the body composition step ~14), after the existing synopsis callout, inject IF non-empty:

```
> [!example]+ Yesterday at a glance
> {{yesterday_carry_forward bullets verbatim}}
> 
> {{yesterday_synthesis paragraph(s) condensed to ~2-3 sentences if longer than 4}}

> [!example]+ Overnight
> {{For each tick in overnight_ticks_summary (oldest-first), one bullet: "HH:00 — <kindlist one-liner derived from the tick body's bold-prefix lines>"}}
```

Both callouts are skipped cleanly if their data was null (backward-compat with vaults that haven't run tick/synthesize yet).

The wire-through is intentionally minimal: morning-briefing's existing dispatch, gather, decide, write phases are unchanged. Only the pre-flight + body composition gain the new context-injection.

### 2.6 Tick range determination

The tick orchestrator's gather phase needs to know "since when?" for each kind's range query. Logic:

1. If today's memory file exists AND `last_tick_at` is set in frontmatter AND it's same calendar day: `range.start = last_tick_at`.
2. Else (first tick of day OR memory file missing): `range.start = <today-YYYY-MM-DD>T00:00:00<timezone>` (start of day).
3. `range.end = <now>`.

This means the first tick of the day captures everything from midnight to 7am (overnight period). Subsequent ticks capture 1-hour windows. Synthesis at EOD then has both the overnight window AND the 16 hourly windows.

If the memory file was created/written by a v0.84.0 tick AND then somehow corrupted (e.g., user manually edited frontmatter), the orchestrator falls back to range.start = start-of-day. Defensive default; no error.

### 2.7 Cowork hub discoverability

Memory notes are BACKGROUND — they shouldn't surface on the daily note or in the main cowork hub view, but should be discoverable. Three integration points:

1. **Activity-feed mechanism recognition:** Add `cowork-memory` to the canonical types the activity-feed mechanism's `_canonical-vocab.json` `display_names` map recognizes. Existing Daily Hub / Weekly Hub / Monthly Hub renderers will then surface memory notes in their Recent Activity sections alongside cowork-morning-briefing / cowork-eod-review etc. without additional code changes.
2. **Resolver row in Cowork.md:** New `claude_surface[]` entry adds `Cowork Memory | spice/cowork/memory/ | /cowork memory` to the Cowork.md resolvers table. Navigation pointer for users + Claude; no new slash command (the path renders as the directory landing).
3. **No daily-note linkage:** Memory notes do NOT link from `spice/cowork/daily/...` atomic notes (morning-briefing, midday-tripwire, eod-review). Keeps the daily atomic notes uncluttered. Discoverability is via the hub + Recent Activity, not embedded wikilinks.

### 2.8 Cadence registration extension

`onboard-scheduled-jobs/SKILL.md` gains 2 new orchestrator entries in its cadence-walk: `tick` and `synthesize-day`. Default cron suggestions:

- **tick:** `0 7-22 * * *` (top of every hour 7am-10pm, 16 ticks/day) — captures waking hours; skips overnight silence.
- **synthesize-day:** `15 19 * * *` (15 minutes after the typical 19:00 EOD slot, so eod-review fires first then synthesize compresses).

These defaults live in `engagement-types/{personal,w2-fte,consulting}.json` under `default_cadences`:

```json
"default_cadences": {
  "morning": true,
  "midday":  <existing per-type>,
  "eod":     true,
  "weekly":  true,
  "monthly": <existing per-type>,
  "tick": true,
  "synthesize_day": true
}
```

All 3 engagement types default both new cadences to `true` (memory layer is universally valuable; per-engagement opt-out via `onboard-scheduled-jobs` walk if user wants).

`supported_cadences` array in each engagement-type JSON also extended: `["morning", "midday", "eod", "weekly", "monthly", "tick", "synthesize_day"]`.

## 6. Risks + mitigations

### 6.1 New orchestrator + new canonical type at the same cycle

New canonical type (`cowork-memory`) means new rule_fragment in cowork's manifest. The rule_fragment must include:
- `naming_pattern: "^memory\\.md$"`
- required_frontmatter: `type` (equals `cowork-memory`), `engagement_id`, `day` (YYYY-MM-DD regex), `created_at`, `summary`. Optional: `last_tick_at`, `tick_count`, `synthesized`, `synthesis_at`.

The new orchestrators must respect this contract on write. The `audit` mechanism will validate consumer memory notes against the rule_fragment.

**Mitigation:** in S2 (capture-tick) + S3 (synthesize-day), include a `## Pre-write self-check` section in each orchestrator SKILL.md asserting the required frontmatter fields are present before write. Mirror the v0.74.0 cowork-orchestrator-rigor pattern (5 structural markers + frontmatter contract check). On miss, return `failed:contract-violation:<field>`.

### 6.2 Concurrent tick writes (race condition)

If two tick orchestrators fire concurrently for the same engagement on the same day (e.g., a missed tick catches up while the next tick fires on schedule), both would Read-Or-Create the day memory file, then both append. The append order would depend on race-write ordering.

**Mitigation:** acceptable for v0.84.0. Hourly cadence makes concurrent fires rare. If a tick happens to append in the wrong chronological order, the synthesis at EOD sorts ticks by `HH:MM` extracted from the callout title. No data loss; minor cosmetic out-of-order in the source markdown that the user might notice if they expand the note.

A future cycle could add file-lock semantics or atomic-rename writes if real races surface in production.

### 6.3 Memory file growth (vault size)

Each tick appends ~5-15 lines. Daily file ends up ~150-300 lines. Year-long accumulation per engagement = ~365 files × ~200 lines = ~73,000 lines per engagement. Across 4 vaults × 1 engagement each ≈ 300k lines of memory content.

**Mitigation:** acceptable. Markdown files; tractable on disk. Future cycles can ship a retention/compression policy. For v0.84.0, no pruning.

### 6.4 Morning-briefing prompt-body inflation

Adding 2 new callouts (Yesterday at a glance + Overnight) increases the morning-briefing's prompt body. For agents with constrained context windows, this could push the prompt over budget.

**Mitigation:** the new callouts are capped:
- `Yesterday at a glance` includes carry-forward bullets (3 max per design) + synthesis paragraph (compressed to ~2-3 sentences if the source is longer).
- `Overnight` includes up to 6 tick one-liners, each ~10-15 words.

Total addition: ~150-300 words. Acceptable. If real overflow surfaces, a future cycle can add a `morning_briefing_recent_memory_lines` config option.

### 6.5 Tick MCP failure handling

Tick fires across 5-6 MCP kinds per engagement. If any MCP is unreachable (calendar offline, ADO outage), the tick must NOT fail entirely — it should write a partial tick with `[!warning]` blocks for skipped kinds, matching the existing morning-briefing graceful-degradation pattern from v0.78.0.

**Mitigation:** tick orchestrator's Gather phase uses the same `composeWarningCallout` shape as morning-briefing for `mcps_entry.connected == false`, `served_by_unreachable`, etc. Each tick is best-effort; warnings are surfaced but don't abort.

### 6.6 Consumer setup post-deploy

After v0.84.0 deploys, consumers MUST re-run `cowork:onboard-scheduled-jobs` to register the 2 new cadences. Without re-onboarding, tick + synthesize-day never fire and the memory layer is dark.

**Mitigation:** install.md upgrade section explicitly instructs to re-run onboard-scheduled-jobs after `sauce update --bump-pins`. onboard-scheduled-jobs is idempotent — existing engagements get the 2 new cadence questions added to the walk; previously-answered cadences are skipped.

### 6.7 FLN-v83-2 (--bump-pins flag bug) still open

v0.83.0 deploy hit FLN-v83-2 — `--bump-pins` failed to bump cowork's subscription pin on the user's accuris-other-machine vault. v0.84.0 deploy will hit the same bug if it's not fixed. The workaround (manual jq edit of `ranch/platform-subscription.json`) is documented in `Docs/prompts/2026-06-02-post-v0.83.0-next-cycle-handoff.md`.

**Mitigation:** install.md upgrade section for v0.84.0 calls out the workaround. v0.84.1 PATCH cycle should prioritize the FLN-v83-2 fix.

## 9. Open questions resolved during brainstorm (2026-06-01)

| Question | Decision | Why |
|---|---|---|
| Output mode: inline / atomic-note / both? | Atomic-note (single file per day per engagement) | User vision: "permanent state of memory… everywhere, all jobs read it" |
| Tick payload depth: lean / lean+calendar / multi-source? | Multi-source (run all MCPs that morning-briefing uses, but with 1-hour range) | "Lean take on all MCPs that are used for all tasks" |
| Tick cadence: hourly all day / waking hours / 2h cadence? | Waking hours 7am-10pm hourly (16 ticks/day) | Captures everything that actually happens; skips overnight silence |
| MB context depth: synthesis only / ticks only / both? | Both (yesterday's synthesis + last 4-6 overnight ticks) | Maximum continuity; ticks fill the gap between EOD synthesis and morning briefing |
| File layout: file-per-tick / single-file-per-day? | Single file per (engagement, day); ticks appended | User explicit: "tracked in one note for the day" |
| Tick shape: deltas-only / always-emit / hybrid? | Deltas-only — omit kinds with empty output | Keeps ticks short overnight; synthesis pattern emerges from time-series |
| Hub integration: prominent / background / hidden? | Background — discoverable through hub + Recent Activity, not surfaced on daily note | User explicit: "background, you have to find it to see the info, but it's there" |
| Per-kind styling within memory note: replicate v0.82.0 callout_type / single example callout? | Single collapsed `[!example]-` per tick with bold-prefix kind lines inside | 16 ticks × 5 kinds = 80 callouts/day if per-kind; too noisy; memory is Claude-consumption, not aesthetic |
