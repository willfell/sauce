1. **Stale `vault-config.md mcp_map`** said `gmail: missing` + `gcal: missing` from the 2026-05-12 bootstrap. The LLM trusted that signal even though the user moved to M365 a month ago. Accuris doesn't use Google Workspace at all.
2. **ADO served_by mismatch** between user-preferences `accuris-ado` (legacy alias) and actual MCP namespace `1151913a-530a-4a36-a5f6-3bedcab4e4da`.
3. **Deferred MCP tools didn't get loaded** — the LLM saw the connector but didn't load the specific tools (`chat_message_search`, `outlook_calendar_search`, etc.) needed for gather operations. Result: said "tools need explicit loading" and gave up.

Data-level fixes already applied to the accuris vault (vault-config.md frontmatter repair + mcp_map refresh; user-preferences.md ADO UUID update). v0.91.3 ships the STRUCTURAL fixes so this class of failure doesn't recur on accuris, headspace, or future vaults.

Bonus signal: today's weekly review run **succeeded** because the LLM didn't read the (long) orchestrator SKILL.md and just gathered data directly. That suggests the orchestrator prose burden is approaching the LLM-attention ceiling.

## 1. Fix A — trust user-preferences.mcps over vault-config.mcp_map

In 5 orchestrators (morning-briefing, midday-tripwire, eod-review, weekly-review, monthly-review), add to the dispatch-plan composition step (Step 3c) immediately before the priority loop:

```markdown
**Connectivity signal authority (v0.91.3):** trust `prefs.mcps[<kind>]` (read at Step 3c) for the `served_by` namespace + `connected` status of each kind. Do NOT trust `vault-config.md mcp_map` for connectivity — that field is bootstrap-time-only, stale-prone, and reflects what was detected at first install (often months out of date). It's an audit hint, not a runtime signal. For each `kind` in `prefs.priorities`, the dispatch_plan reads `prefs.mcps[kind].served_by` for the namespace and cross-references with the runtime `reachable_namespaces` set (extracted from your tool list per Step 3c) for the final action. vault-config.mcp_map is ignored.
```

## 2. Fix B — explicit deferred-tool loading before gather

In 5 orchestrators, add to the top of the `## Gather` section, after the existing `MANDATORY:` v0.90.2 prefs-loop paragraph:

```markdown
**Deferred-tool loading (v0.91.3, MANDATORY before priority loop):** for each kind in `dispatch_plan` with `action == "gather_from_served_by"` or `action == "gather_canonical"`, identify the served_by namespace and LOAD the required MCP tools from that namespace via the Tool Search / Load mechanism BEFORE invoking any gather sub-skill. Common namespaces and their tools:
- **M365** (UUID like `45224a84-...`): `chat_message_search`, `outlook_calendar_search`, `outlook_email_search` (capability-based detection per mcp-skill-map v2.0.0 — same UUID serves chat / calendar / email)
- **ADO** (UUID like `1151913a-...`): `list_workitems`, `search_workitems`, `get_workitem`
- **github**: `search_pull_requests`, `search_issues`, `list_pulls`, `get_pull_request`

If a deferred tool isn't loaded when a gather sub-skill needs it, the sub-skill cannot execute and you'll fall back to the warning path (silently degrading the briefing to "MCP unavailable" copy). Load tools UPFRONT in one batch so all subsequent gather invocations have their tools available. This is the v0.91.3 deterministic fix for the "tools need explicit loading" failure mode that produced today's empty accuris morning briefing.
```

## 3. Fix C — dataviewjs structural verify regex tightening

### C.1 In 5 write-run-note sub-skills

Update the `**Body checks (regex-scan the composed body string):**` first bullet to require the canonical invocation pattern:

OLD:
```
- [ ] First non-frontmatter line opens a `SpaceNavButtons` dataviewjs fence (i.e. the line starts with ` ```dataviewjs` and is followed within 3 lines by `class: "SpaceNavButtons"`)
```

NEW:
```
- [ ] First non-frontmatter line opens a dataviewjs fence containing the CANONICAL SpaceNavButtons invocation EXACTLY:
   ` ```dataviewjs` (opening fence)
   `await dv.view("ranch/views/customjs-guard", { class: "SpaceNavButtons" });`
   ` ``` ` (closing fence)
   REJECT any other invocation pattern. In particular, REJECT patterns like `const { SpaceNavButtons } = customJS; SpaceNavButtons(dv, {...})` — those produce a runtime TypeError ("SpaceNavButtons is not a function") because `SpaceNavButtons` is a class registered on `customJS`, not a directly-callable export. The customjs-guard view pattern is the only canonical invocation; it loads SpaceNavButtons + handles the customJS-not-defined fallback.
```

### C.2 In 5 orchestrators Step 17 (re-read + structural verify)

Update the regex from the current substring check to the canonical pattern:

OLD: `/```dataviewjs\n[\s\S]*?SpaceNavButtons[\s\S]*?```/`

NEW: `/```dataviewjs\s*\n\s*await\s+dv\.view\(\s*["']ranch\/views\/customjs-guard["']\s*,\s*\{\s*class:\s*["']SpaceNavButtons["']\s*\}\s*\)/`

This catches the canonical invocation deterministically. The LLM-hallucinated `const { SpaceNavButtons } = customJS; SpaceNavButtons(dv, {...})` won't match — Step 17 will delete the file + emit Notice `cowork:<orchestrator> aborted -- contract-violation: invalid-dataviewjs-block`.
