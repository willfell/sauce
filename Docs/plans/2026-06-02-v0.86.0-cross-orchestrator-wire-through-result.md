## Summary

**MINOR closing FLN-v84-2 (deferred at v0.84.0): cross-orchestrator memory wire-through.** v0.85.0 shipped the load-bearing `cowork:read-memory` sub-skill + a byte-identical morning-briefing refactor as the structured-output primitive. v0.86.0 applies the same pre-flight 3a + body-composition pattern to the 4 remaining atomic-note orchestrators — midday-tripwire / eod-review / weekly-review / monthly-review — so 5 of 5 atomic-note orchestrators now consume Tier 0/1/2 memory per day. Memory-read frequency amplifies 5× per engagement per day: a single v0.85.0 morning briefing → 5 reads daily across the wire-through cycle.

Each orchestrator gains a pre-flight step 3a invoking `cowork:read-memory` with the appropriate tier+window (midday `tier: "tick", window: "today", limit_ticks: 4`; eod dual — `tier: "tick", limit_ticks: 16` + `tier: "day", window: "today"`; weekly `tier: "week", window: "this-week"`; monthly `tier: "week", window: { start: <month-start-iso>, end: <today-iso> }`), plus a body-composition step that pipes the structured output through a new per-orchestrator pure helper — `composeMidamMemoryCallout`, `composeEodMemoryCallout` (dual output), `composeWeeklyMemoryCallout`, `composeMonthlyMemoryCallout`. Each helper is byte-identical to a golden fixture; null-data gating preserves backward-compat (when a memory file is absent, the callout silently omits and the orchestrator body proceeds unchanged).

## NEW lessons

1. **Memory amplification works.** A single cycle takes per-engagement memory-read frequency from 1× (v0.85.0: morning-briefing only) to 5× (v0.86.0: morning-briefing + midday-tripwire + eod-review + weekly-review + monthly-review). The wire-through pattern itself is mechanical once the structured-output primitive (`cowork:read-memory`) is load-bearing; v0.85.0's investment in C3..C5 golden fixtures + 5-edge-case parser hardening paid off as zero-friction copy-and-adapt across the 4 sites. **Lesson:** when a load-bearing primitive ships with golden-fixture byte-identical contracts, future cycles that fan it out across additional call-sites become mostly-mechanical — the parser hardening + structured-output API + byte-identical posture do the load-bearing work; per-call-site work reduces to writing each call's compose helper + fixtures.

2. **Helper-extract per orchestrator over single consolidated switch-based composer was empirically the right call.** Each orchestrator's body context differs enough to justify separation — midday surfaces tick-log only; eod surfaces dual (tick-log + day-synthesis); weekly surfaces week-synthesis + carry-forward bullets; monthly aggregates multiple week_synthesis records. A single consolidated `composeMemoryCallouts(orchestrator, output)` switch-based composer would have collapsed these into a less-readable per-branch shape and made each callout's null-data gate harder to express. 4 separate helpers (composeMidamMemoryCallout / composeEodMemoryCallout / composeWeeklyMemoryCallout / composeMonthlyMemoryCallout) each remain small + focused + independently testable. **Lesson:** prefer N small focused helpers over 1 large switch-based composer when each call-site's output shape differs meaningfully; consolidation is a refactor candidate only if/when patterns prove uniform across multiple cycles. See FLN-v86-1 for the deferred consolidation question.

3. **eod-review's dual read-memory invocation → dual helper output.** The pattern mirrors v0.85.0 `composeMemoryCallouts`'s dual signature (`{ yesterdayCalloutMd, overnightCalloutMd }`) but for a different read pair (today's ticks + today's day-synthesis vs v0.85.0's yesterday-day + today-overnight-ticks). Reusable for future dual-source orchestrators where the body needs to surface two distinct memory tiers side-by-side without coupling their null-data gates. **Lesson:** when a single orchestrator needs to surface multiple memory tiers, return a structured `{ field1Md, field2Md, ... }` object from the helper rather than a single concatenated string — each field's null-data gate stays independent + the SKILL.md prose can insert them at different body positions.

4. **monthly-review's `window: { start, end }` structured object distinguishes from string-window orchestrators.** Provides month-boundary precision that string tags like `"this-week"` / `"today"` can't. Without it, monthly-review would either (a) over-collect (`window: "this-month"` semantic doesn't exist) or (b) under-collect (use `"this-week"` which captures only the current week). The structured `{ start, end }` object lets the caller specify exactly the month-to-date range. **Lesson:** when an orchestrator's natural temporal window doesn't fit the canonical string-window vocabulary, ship the structured-object alternative on the same `window:` field rather than inventing a new field — read-memory's parser branches cleanly on `typeof window === "string"` vs `typeof window === "object"`.

5. **Stash + dogfood install collision.** During this cycle the workshop dogfood install (`node platform/install.js --vault . --auto-approve`) writes to `CLAUDE.md`, `ranch/claude-surface-registry.json`, and `ranch/platform-installed.json` that aren't idempotent with `git stash` semantics — stashing across an install boundary, doing other work, then unstashing leaves those files in a divergent state vs the install's actual disk state. Future cycles that need selective drift management should use `git checkout HEAD -- <files>` for the specific files they want to restore, not `git stash` across install boundaries. **Lesson:** stash + dogfood install collide because install writes are post-commit-state-dependent rather than working-tree-dependent. See FLN-v86-2 for the codification candidate.
