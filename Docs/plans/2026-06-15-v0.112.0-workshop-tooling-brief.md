# v0.112.0 brief — workshop tooling

## The ask

Every fresh Claude session pays a 5-10 tool-call tax to re-derive the workshop's current state: read `platform/manifest.json`, scan `git log`, parse `Docs/agent-guides/cycle-status.md` (often stale), figure out which `Docs/plans/*-result.md` is the most recent close, check `git status` for uncommitted in-flight work, run a harness or two to confirm gates. Bundle 1 of the v0.111.x brainstorm closes that gap with four small additive artifacts.

Direct beneficiaries: Claude sessions (compute + latency savings); the user (faster context handoff between sessions); future workshop contributors (no oral-history dependence).

## Success criteria

1. `node scripts/workshop-status.js` (or `npm run status`) prints a compact one-screen summary in under 1 second covering: workshop version, blueprint versions, branch + sync state, recent commits, uncommitted state, harness counts (cached if recent), in-flight cycle pointers from `Docs/plans/*.md`.
2. `node scripts/regen-cycle-status.js` updates `Docs/agent-guides/cycle-status.md § Current` from the most recent `Docs/plans/*-result.md` + `Docs/cycle-history.md`. Idempotent. Dry-run mode (`--check`) exits non-zero if drift detected (CI gate candidate).
3. `node scripts/scaffold-behavioral-harness.js <cycle-id> <topic>` emits `platform/test/run-<cycle-id>-<topic>.js` with the canonical DOM stub + Dataview-proxy stub + verdict block + section comment marker — copy-paste from v0.110.3 zero-dep template.
4. `Docs/agent-guides/dev-workflow.md` surfaces `scripts/dev-sync.sh` + brew-vs-local-clone + per-vault subscription cadence + the three new scripts. Linked from `CLAUDE.md`'s "Further reading" router.
5. HC test family `caseV0112Tooling*` ≥ 8 sub-asserts proving each artifact exists + is wired.
6. Workshop self-install dogfood: exit 0, history records `tooling_v0112` info events.
7. Preflight: whole-suite GREEN preserved.

## Non-goals

- **No `sauce` CLI extension** (verb dispatcher). The existing `cmd-status.js` is consumer-vault-side; the new workshop-status is dev-side. Conflating them would require a brew tap bump (still stale at 0.84.0) before consumers see it. Keep as `npm run status` for now; promote to `sauce workshop-status` after brew tap bumps.
- **No replacement of `dev-sync.sh`.** It already works; just document + cross-link.
- **No CI gate on `regen-cycle-status.js --check`.** Surface the dry-run mode but don't wire it into `release:preflight` yet — drift right now is multi-cycle (cycle-status still says v0.108.0). Wire after one clean run.
- **No interactive scaffolder.** Args-only invocation. Zero dependencies.
- **No tags or pushes for the v0.110.3 → v0.111.3 chain.** User decision; out of this cycle.
- **No brew tap formula bump.** Brainstorm #17 — separate cycle.

## Out-of-scope risks acknowledged

- **`regen-cycle-status.js` content shape inference might miss outliers.** Mitigation: format heuristics + dry-run mode + `--check` returns diff. If a result doc breaks the parser, the script falls back to "verbatim append" rather than mangled rewrite.
- **`workshop-status.js` re-running harnesses every invocation is too slow.** Mitigation: by default skip harness execution; show last-known counts cached in `.workshop-status-cache.json` (gitignored). `--fresh` flag runs harnesses for the live number.
- **Scaffold script overwrites existing harness files.** Mitigation: refuse to write if target path exists; `--force` flag for explicit overwrite.

## Action required from user post-deploy

1. Try `npm run status` from the workshop root. Confirm it reads correctly.
2. Try `npm run regen-cycle-status -- --check` to see how stale the current cycle-status is (expected: many cycles drifted).
3. Pick whether to run `npm run regen-cycle-status` (no `--check`) to auto-update, OR keep manual control.
4. Test the scaffold script the next time a behavioral harness is needed.
