# v0.110.0 design — migration regression net (foundation cycle)

## 0. Versioning posture

This cycle's tentative label is **v0.110.0**. Rationale:

- `main` currently at v0.108.0 (closed 2026-06-15).
- Another in-flight cycle (`feature/v0.109.0-projects-overhaul`) holds v0.109.0.
- If projects-overhaul merges before this one, this cycle lands as v0.110.0. If this one merges first, v0.109.0 is reassigned. Branch name (`cycle/migration-regression-net`) intentionally omits the version label so renaming is cheap.
- This PR does **not** bump `workshop_version`. The bump lands in a post-merge commit on `main` (matches existing build-test-verify.md convention).

## 1. Scope

**Goal:** Build a migration regression net for sauce. A checked-in synthetic seed vault represents "what a typical consumer looks like at the last released `workshop_version`". A new harness copies the seed to a tmp dir, runs the headless installer, and asserts on resulting state (structural shape + frontmatter + critical body prose + .sauce-backup snapshots + idempotency). Each future cycle adds input data + asserts for its new migrations. Workflow shifts from direct-push-to-main toward feature-branch + PR + CI gate.

**Driver:** Today's 22 harnesses catch unit-level regressions; the dogfood self-install catches manifest-order / materialization-path drift. Neither exhaustively exercises **migration safety on a vault-from-prior-state**. As blueprint schemas evolve (finance debt sub-area, project sections, cowork verbal feedback, etc.) the risk is silent data corruption on consumer vaults during install. The seed-vault harness closes that gap.

**In scope (this PR — foundation):**

1. `platform/test/seed-vault/` — synthetic Sauce-shaped consumer vault, generated from a bootstrap+install run at v0.108.0, committed to the repo.
2. `platform/test/run-seed-migrations.js` — new 23rd harness. Same hand-rolled `assertTrue` / `assertEqual` pattern as existing run-*.js. Zero-dep.
3. `platform/test/helpers/seed-vault-helpers.js` — frontmatter parse, body substring, file-shape, diff utilities.
4. `Scripts/rebaseline-seed.js` — copies seed → tmp → runs current install → writes the result back. Prints a diff summary.
5. `Scripts/seed-prev-snapshot.js` — moves current `seed-vault/` → `seed-vault-prev/` at cycle close (safety net against shipped-bugs-baked-into-seed).
6. `package.json` — add `seed:rebaseline` + `seed:prev` scripts; add `run-seed-migrations.js` to `release:preflight` (CI auto-picks this up via existing `ci.yml`).
7. `.github/pull_request_template.md` — reminds authors to extend the seed when adding migrations.
8. Docs updates: `Docs/agent-guides/build-test-verify.md` (release workflow + branch-PR-gate section), `Docs/agent-guides/asking-before-acting.md` (workflow shift), `Docs/landmines.md` (new landmine #25 — "Don't manually edit `seed-vault/` without re-running rebaseline").

**Out of scope (deferred to follow-up cycles):**

- Backfilling `HC-V0XYZ-SEED-MIGRATE-*` assertion families for past migrations (v0.95+). Incremental; one cycle's worth at a time.
- GitHub branch-protection rule on `main` requiring the new check — user sets this manually via the GitHub UI or `gh api` (documented in build-test-verify.md, not in this PR).
- Retiring direct-push-to-main convention. The CI gate on PRs is **the preferred path** going forward; direct-push remains possible (admin override) for prose-only / cycle-close commits.
- Obsidian-runtime widget rendering tests. The new harness is headless (Node only); widget visual checks remain manual per existing dogfood pattern.

## 3. Cycle lifecycle (new normal)

The foundation that this PR delivers, ratified into the cycle convention:

1. **Start:** create branch `cycle/v0.X.Y-<topic>` off `origin/main`.
2. **During cycle:** when adding a migration, extend `seed-vault/` with input data at the *pre-migration schema* + add `HC-V0XYZ-SEED-*` assert family to `run-seed-migrations.js`.
3. **Each push:** GitHub Actions runs full `release:preflight` (22 harnesses + new one + dogfood). Red → CI fails; PR cannot merge (once branch protection is enabled).
4. **PR review:** seed-vault diff is reviewable inline. Self-merge for now (no second reviewer required).
5. **Merge to main:** post-merge, maintainer commits cycle-close artifacts on main directly: workshop_version bump (`platform/manifest.json` + `package.json` + `ranch/platform-subscription.json` lockstep), cycle-history.md append, cycle-status.md update, prompts/handoff doc.
6. **Tag:** annotated `v0.X.Y` on main (existing USER APPROVAL gate). `release.yml` fires → bump-tap chain.
7. **Rebaseline:** maintainer runs `npm run seed:prev && npm run seed:rebaseline` on main. Single bookkeeping commit `chore(seed): rebaseline to v0.X.Y`. Seed forward-ratchets; prev snapshot archives the just-prior state.

**Skip-version property:** falls out automatically. The seed represents "last released" but the install always runs every migration in the chain. So a seed at v0.95 → install at v0.110 exercises every migration from v0.95.x onward in order. Skip-version isn't a separate test path; it's the same path.

## 4. Initial seed contents (this cycle)

For the foundation cycle, the seed represents **"fresh consumer at v0.108.0 (the currently-released version)"**. Generated by:

1. Run `node platform/cli/sauce-cli.js bootstrap --vault <tmp> --non-interactive --no-register --mechanisms=all` against an empty tmp directory.
2. Configure the bootstrapped vault to subscribe to **every** blueprint (so all materialized surfaces exist).
3. Run `node platform/install.js --vault <tmp> --auto-approve`.
4. Copy the resulting vault into `platform/test/seed-vault/`.

Synthetic engagement: id `test`, no real personal data, neutral fixtures. Subscribes to every blueprint at the v0.108.0 pin so all materialized surfaces exist: cowork, finance, daily, weekly, monthly, scratch, meetings, project, to-do.

**No prior-schema input data is needed for the foundation cycle.** The infrastructure ships first; future cycles ship the migrations that exercise it. The first cycle that adds a migration will:
- Extend `seed-vault/` with a hand-authored note at the pre-migration schema.
- Add an `HC-V0XYZ-SEED-MIGRATE-*` assert family covering: migration applied, expected new state, `.sauce-backup/<ts>/` snapshot exists, pre-existing user content preserved bit-for-bit.

**Hand-authored user content fixtures** (added in this PR to anchor the "preserve user content" assertions):
- 1 note under `spice/daily/` with non-templated body (e.g. journaling prose).
- 1 note under `spice/scratch/` with non-templated body.
- 1 note under `spice/meetings/` with frontmatter + body.

These provide concrete files the preservation assertions check.

| Family | Approx count | Covers |

## 7. Risks + mitigations

1. **Seed install fails on first CI run** — mitigation: generate seed from install output, so it's self-consistent by construction. Test locally before pushing.
2. **CI is untested for the new harness** — mitigation: existing `ci.yml` already runs `release:preflight` on PR. Adding the new harness to the chain is a one-line change. First PR push is the first CI run; iterate if red.
3. **Rebaseline ratchets in bugs** — mitigation: `seed-vault-prev/` snapshot at every cycle close. If a regression is found later, you can compare against the prior state.
4. **Workflow shift surprises future-me / other sessions** — mitigation: landmine #25 + asking-before-acting.md entry + build-test-verify.md "Branch + PR workflow" section + PR template.
5. **No Claude trailer in commits** — locked into memory (`feedback_no_claude_commit_trailer.md`). Respect in commit messages.
6. **Seed vault size in repo** — mitigation: ~80 files of small markdown/JSON. Negligible. Easy to grep, easy to diff.
7. **Cross-platform path handling** — mitigation: zero-dep Node, use `path.join` + `os.tmpdir`. CI runs macOS + Ubuntu matrix per existing `ci.yml`; both must pass.
