# v0.127.0 — task interactions + four post-v0.126.1 fixes (design)

## Mission

Bundle the four post-v0.126.1 bugs the user repro'd alongside a NEW cross-blueprint `task-interactions` mechanism that turns task lines into first-class editable objects across every surface in the to-do ecosystem. Ships click-to-edit on raw `## Today` checkboxes via the same modal that creates them. Reuses `ToDoCreateTask`'s one-shot modal in a new edit mode so the create UX and the edit UX share one widget — updates to the modal touch every consumer.

The cycle thesis: the inline-dataview-field grammar (`- [ ] x [project:: [[Y]]] [priority:: high] [due:: Z]`) emitted by `ToDoCreateTask.serializePayloadToLine` is a universal task language already; what's missing is one parser, one writer, and one editor that consume it. v0.127.0 introduces the contract layer.

## §A — Args-scrub heal

### Root cause recap

v0.126.1 fixed the PeopleRendering `args: [dv, …]` double-prepend in the meetings + people blueprint **source** (templates + inline_body). But 411 existing leaf notes in the accuris vault were materialized BEFORE the fix and still carry the bad pattern on-disk. v0.126.1's `applyNoteChromeHeal` is insert-only — it never rewrites existing content.

### Fix

Extend `_healNoteChromeBody` in `platform/install.js` with one new transformation step. Step 4 runs AFTER the existing step 3 (drop dividers before SectionLabels), fence-aware, idempotent. Regex pass per line at fence-depth 0 only:

```
const PEOPLE_RENDERING_BAD = /(class:\s*"PeopleRendering"[\s\S]{0,200}?args:\s*\[)\s*dv\s*,\s*/g;
```

The replacement strips the `dv,` token immediately after the opening `[` in the `args:` array. The match is bounded by `{0,200}` between `class: "PeopleRendering"` and `args:` so it only fires inside a single dataviewjs invocation block; we do not rewrite a stray `[dv,` outside a PeopleRendering call. Fence depth is already tracked by the line-scanner in `_healNoteChromeBody`'s step 2 — we reuse that bookkeeping.

Extend the heal roots list from:

```
const roots = ["spice/meetings", "spice/scratch", "spice/to-do"];
```

to:

```
const roots = ["spice/meetings", "spice/scratch", "spice/to-do", "spice/people"];
```

`_noteChromeFrontmatterType` already returns `"person"` for `type: person` frontmatter, but the existing heal driver `if (!["meeting", "scratch", "scratch-day", "to-do"].includes(type)) continue;` filter excludes person notes. Extend the allowed types to `["meeting", "scratch", "scratch-day", "to-do", "person"]`. People notes only execute step 4 (args-scrub) because steps 1-3 are meeting-only or already idempotent on non-meeting types.

Idempotent: after first pass, no `args: [dv,` remains inside a PeopleRendering block; the regex finds nothing on re-run; `after === before` short-circuits the write.

### Why this and not a new helper

Per the brainstorm: `_healNoteChromeBody` is already the canonical body-transform surface (three bundled transforms today); `applyNoteChromeHeal` is the canonical driver (per-note try/catch, `.sauce-backup`, history posture). Adding a fourth transform plus one root is one line each in two existing functions, fewer new harness fixtures, no new wired step.

### `ranch/entity-create-registry.json` is regenerated, not scrubbed

The handoff flagged that the seed vault's registry contains the buggy pattern. This is OK: `entity-create-registry.json` is rebuilt on every install from each blueprint's manifest. Once v0.127.0's manifests are clean (they already are — v0.126.1 fixed them), the next install regenerates a clean registry. The scrub-heal only touches `.md` content notes under `spice/**`.

### Acceptance for §A

1. Workshop dogfood (`node platform/install.js --vault . --auto-approve`) exits 0 with history entries `step: note_chrome_heal, action: healed` for any seed-vault notes that carried the old pattern.
2. Behavioral harness asserts `_healNoteChromeBody(badPersonNote, "person")` strips the `dv,` token.
3. Idempotency: second `_healNoteChromeBody` pass on the healed output returns `after === before`.
4. Content-safety: a person note whose body contains a raw `args: [dv, somethingElse]` string OUTSIDE a PeopleRendering block is left untouched (the regex is bounded to PeopleRendering by the `class: "PeopleRendering"` lookbehind window).

## §B — `task-interactions@0.1.0` mechanism

### Why a mechanism, not a blueprint helper

`TaskInteractions` is consumed by meetings (§C), to-do (§F), and is positioned for project consumption in a later cycle (rich task rows in `ProjectMeetingsPanel`). Per code-conventions, cross-cutting code that multiple blueprints consume is a mechanism. Same shape as `section-label`, `breadcrumb`, `accent-button`, `people-rendering` (single-class CustomJS mechanisms).

### Mechanism layout

```
platform/mechanisms/task-interactions/
├── manifest.json                  // declares the CustomJS class + scripts_path materialization
├── task-interactions.js           // the class body
└── (no view; not a Dataview dispatcher consumer)
```

`task-interactions.js` materializes to `{{scripts_path}}/task-interactions.js` (canonical mechanism pattern, mirrors `people-rendering`). Workshop dogfood subscribes to it via `ranch/platform-subscription.json`.

### Public API

The class is a **single instance** under `customJS.TaskInteractions` (per FLN-todo-13 — customjs stores instances, not constructors). Eight callable methods.

#### `static parseTaskLine(line: string) → ParsedTask | null`

Parses a single `- [ ] ` line into a structured payload:

```
ParsedTask = {
  raw: string,                    // verbatim input line
  title: string,                  // text after the `- [ ] ` prefix, before the first inline field
  project: string | null,         // contents of [project:: [[NAME]]] — wikilink-stripped to "NAME"
  priority: 'low'|'medium'|'high'|'highest' | null,
  due: 'YYYY-MM-DD' | null,
  scheduled: 'YYYY-MM-DD' | null,
  recurrence: string | null,      // raw grammar string per RecurrenceParser
}
```

Returns `null` if the line doesn't match `^- \[[ x]\] `. Handles completed `- [x]` (parsing succeeds; consumer decides whether to act). Does not touch the surrounding file — pure string → object. The parser is the inverse of `ToDoCreateTask.serializePayloadToLine`; the test pair must hold:

```
parseTaskLine(serializePayloadToLine(payload)) ≈ payload          // round-trip
serializePayloadToLine(parseTaskLine(line)) === line              // for any line emitted by the serializer
```

Bidirectional round-trip is asserted in the new behavioral harness.

Instance delegator pattern: `parseTaskLine(line) { return TaskInteractions.parseTaskLine(line); }` per `TaskParser`'s precedent (customjs needs instance methods).

#### `static serializeTaskLine(payload) → string`

Thin re-export of `ToDoCreateTask.serializePayloadToLine` semantics so consumers can call `TaskInteractions.serializeTaskLine(payload)` without reaching into the to-do blueprint. Initial implementation delegates: `if (window.customJS?.ToDoCreateTask?.serializePayloadToLine) return customJS.ToDoCreateTask.serializePayloadToLine(payload);` with an inline fallback that re-implements the one-shot mode (5 lines) for cold-load safety.

#### `static actionItemsAnchor() → string`

Returns the canonical sentinel: `<!-- ACTION_ITEMS_MARKER -->`. Single source of truth; consumers grep for `TaskInteractions.actionItemsAnchor()` rather than hardcoding the string.

#### `static todayCaptureAnchor() → string`

Returns `<!-- TODAY_CAPTURE_MARKER -->`. Same pattern. Used by §F to find the daily-note free-form section.

#### `static injectActionItemsMarker(body: string) → string`

Pure body transformer. If `body` does not already contain `actionItemsAnchor()`, locates the `class: "SectionLabel", args: [{ text: "Action Items" }]` block and inserts the marker on its OWN LINE immediately BEFORE the opening ``` fence of that block. Adds exactly one blank line before the marker. Idempotent (guarded by `body.includes(anchor)`).

If neither the marker nor a matching SectionLabel block is found, returns body unchanged. (Old notes that never had Action Items at all are left alone — they'll get the chrome via existing `_healNoteChromeBody` step 2 first, then this step on the next pass.)

#### `async appendTask(filePath: string, payload: ParsedTask, opts?) → Promise<{ ok: boolean, reason?: string }>`

The universal writer. Inspects the destination file's `type:` frontmatter and dispatches:

- `type: meeting` → calls `injectActionItemsMarker` if needed, then inserts the serialized task line immediately BEFORE the marker (one line above). New tasks accumulate above the marker → above the Action Items SectionLabel block visually.
- `type: project-todo` → appends under the file's "Owned Tasks" SectionLabel block (current `Project To-Do.md` template). Insertion point: end-of-file IF no other tasks present; otherwise after the last existing `- [ ] ` / `- [x] ` line in the "Owned Tasks" range.
- `type: to-do` (daily note) → appends under the `## Today` SectionLabel block (`text: "Today"` from `Today To-Do.md` template — the `top: true` block above ToDoDailyCarryover). New tasks attach below any existing user-typed checkboxes in that section. v0.127.0 ALSO injects a `<!-- TODAY_CAPTURE_MARKER -->` sentinel into the template so the writer can anchor precisely (see §F).
- `type: to-do-recurring` → out of scope for v0.127.0; falls through to `{ ok: false, reason: "recurring writes go via ToDoCreateTask" }`. The recurring registry already has a stable writer in `ToDoCreateTask._submit`; no duplication needed.

Uses `app.vault.process(file, (content) => ...)` (Obsidian's atomic-write pattern; mirrors `app.fileManager.processFrontMatter`'s contract for body). Falls back to `app.vault.read` + `app.vault.modify` if `process` is unavailable (older API surfaces).

Returns `{ ok: true }` on success; `{ ok: false, reason }` on every failure path (file not found, type missing, unknown type, marker not found AND no fallback anchor, write threw). Never throws — consumers (meeting-leaf-actions, today-capture-editable-list) decide UX from the result.

#### `async replaceTaskAt(filePath: string, lineIdx: number, newLine: string) → Promise<{ ok: boolean, reason?: string }>`

Used by §F's click-to-edit. Reads the file, splits by `\n`, swaps line at `lineIdx`, writes back via `app.vault.process`. Guard: the line at `lineIdx` MUST match `^- \[[ x]\] ` before the swap; if not, returns `{ ok: false, reason: "line mismatch" }` so a stale lineIdx (file changed since the editor opened) is a recoverable error, not a corruption.

#### `static findTaskLines(content: string, sectionAnchor?: string) → Array<{ idx, line, parsed }>`

Helper for renderers: walks a file content string and returns every `- [ ]` / `- [x]` line within the optional anchor scope. `sectionAnchor` can be `"todayCapture"` (scans between `todayCaptureAnchor()` and next SectionLabel/EOF), `"actionItems"` (scans between `actionItemsAnchor()` and next SectionLabel/EOF), or undefined (whole file).

Fence-aware: lines inside a fenced code block (depth > 0) are skipped — Obsidian renders fenced `- [ ]` as code, not tasks.

### Sentinel-marker injection on creation paths

For NEW meeting notes (Templater template + inline_body), the marker ships in the source. Both surfaces grow a `<!-- ACTION_ITEMS_MARKER -->` line on its own line immediately BEFORE the existing Action Items SectionLabel block.

For NEW daily To-Do notes (Templater `Today To-Do.md`), a `<!-- TODAY_CAPTURE_MARKER -->` line is added immediately AFTER the `SectionLabel("Today", top: true)` block's closing fence.

For EXISTING notes, `_healNoteChromeBody` calls `customJS.TaskInteractions.injectActionItemsMarker(body)` (when type=meeting) and a sibling `injectTodayCaptureMarker(body)` (when type=to-do) as a NEW step 5 in the body transform. Idempotent via the substring guard inside the injector. Adds the marker only — no other changes.

(Note: `_healNoteChromeBody` is in `install.js` which runs in a Templater-Node context where `customJS` may not be defined. We don't actually call `customJS.TaskInteractions.injectActionItemsMarker` from install.js; instead, we **inline the sentinel literal** in `install.js` as a pair of constants `ACTION_ITEMS_MARKER` and `TODAY_CAPTURE_MARKER`. The mechanism's `actionItemsAnchor()` returns the same string. One source of truth at the mechanism; install.js carries a code-comment cross-reference: `// Mirrors task-interactions@0.1.0's TaskInteractions.actionItemsAnchor()`.)

## §C — Meeting New Task → dual write

### Wire-up

`meeting-leaf-actions.js` `_onNewTask` rewrite:

```
_onNewTask(dv) {
  const cur = dv.current && dv.current();
  if (!cur || !cur.file) { new Notice("Open a meeting note to use this action."); return; }
  const meetingPath = cur.file.path;
  const projectName = MeetingLeafActions.stripWikilink(cur.project);
  this._openTaskModal(dv, async (payload) => {
    // payload = { title, priority?, due?, scheduled? }   (project is forced by the meeting context)
    const line = customJS.TaskInteractions.serializeTaskLine({
      mode: 'one-shot',
      title: payload.title,
      destination: projectName
        ? { type: 'project', slug: this._slugFor(projectName, dv), name: projectName }
        : 'today',                                         // destination only drives the inline [project::] field
      priority: payload.priority,
      due: payload.due,
      scheduled: payload.scheduled,
    });
    // Always write to the meeting note's Action Items.
    const mRes = await customJS.TaskInteractions.appendTask(meetingPath, payload, { sectionAnchor: 'actionItems', serializedLine: line });
    // Conditionally write to the project To-Do.
    let pRes = null;
    if (projectName) {
      const projectTodoPath = this._projectTodoPath(projectName, dv);
      if (app.vault.getAbstractFileByPath(projectTodoPath)) {
        pRes = await customJS.TaskInteractions.appendTask(projectTodoPath, payload, { sectionAnchor: 'ownedTasks', serializedLine: line });
      } else {
        pRes = { ok: false, reason: 'project-todo-missing' };
      }
    }
    this._noticeDualWrite(meetingPath, projectName, mRes, pRes);
  });
}
```

`_openTaskModal` is a NEW small modal (reuses the existing `_openModal` pattern + a minimal version of `ToDoCreateTask`'s one-shot fields). It does NOT use `ToDoCreateTask.open()` directly because that modal's submit path is hardwired to its own destination logic. The fields surface: title (required), due (optional date input), priority (optional chip row). Project is fixed by meeting context (display the project name as a read-only chip at top: "Will be linked to: Databricks").

`_projectTodoPath(name, dv)`: walks `dv.pages('"spice/projects"')` to find the project hub whose `file.name === name`, then returns `${hub.file.folder}/${name} To-Do.md`. The to-do filename convention is `<HubName> To-Do.md` (per `ToDoCreateTask.destinationPath` line 68).

`_noticeDualWrite(meetingPath, projectName, mRes, pRes)`: emits one of these Notice messages:

- Both succeed: `Added to <meeting basename> and <project> To-Do`.
- Meeting only (no project): `Added to <meeting basename>`.
- Meeting OK + project To-Do missing: `Added to <meeting basename>; <project> To-Do not found`.
- Meeting fails: `Could not write to meeting: <reason>` (Notice + console.error).
- Meeting OK + project write fails (other reason): `Added to <meeting basename>; could not update <project> To-Do: <reason>`.

## §D — `ProjectMeetingsPanel` heal

### New installer step

`applyProjectMeetingsPanelHeal(tp, manifest, variables, history, git)` follows the `applyDocsHubButtonRepair` pattern (per-project walk):

1. Walk `spice/projects/` looking for directories one level deep.
2. For each `spice/projects/<slug>/` find a `.md` file directly inside (not nested) whose frontmatter `type: project`. That's the hub note.
3. Read its body. If `class: "ProjectMeetingsPanel"` is already present, skip with `info, action: skipped_already_healed`.
4. Else locate the closing fence of the `class: "ProjectStatusWidget"` block. Insert a `\n\n\`\`\`dataviewjs\nawait dv.view("ranch/views/customjs-guard", { class: "ProjectMeetingsPanel" });\n\`\`\`` block immediately after that fence.
5. Fallback when ProjectStatusWidget is absent: locate the closing fence of `class: "ProjectNavButtons"`. If that's absent too, locate the first dataviewjs block's closing fence. If NO dataviewjs blocks at all, skip with `warning, reason: no_anchor_found`.
6. `.sauce-backup` snapshot before write (mirrors `applyNoteChromeHeal`). Atomic write. Failure-loud history.

### Wire-up

Add `await applyProjectMeetingsPanelHeal(tp, manifest, variables, history, git);` to the install sequence in `install.js` AFTER `applyDocsHubButtonRepair` (the canonical project-hub-repair neighborhood) and BEFORE the project-sections heals (which read project hubs and benefit from chrome being current).

### Why insert-only, not full reshape

Per landmine #16 + cycle norm: heals are insert-only + idempotent. A full chrome reshape would clobber any user edits between blocks. Inserting one block at a stable anchor is reversible (consumer can delete it) and never touches surrounding text. The cost is the panel appears in roughly the right place, but visual perfection is a follow-up cycle if needed.

### Acceptance for §D

1. New behavioral harness `platform/test/run-v0127-project-hub-heal.js` covers:
   - Stale hub with ProjectStatusWidget → panel inserted directly after status fence.
   - Stale hub with no ProjectStatusWidget but has ProjectNavButtons → panel inserted after nav-buttons fence.
   - Already-healed hub → second pass is a no-op (`after === before`).
   - Hub with NO dataviewjs blocks at all → warning history, no write.
2. Workshop dogfood: seed-vault projects (`my-cool-project`, `Legacy Project`) get healed appropriately.
3. Manual smoke: in accuris vault, `spice/projects/databricks/Databricks.md` after install shows the meetings panel listing `test-meeting-with-project-2026-06-23.md`.

Refactor:

```
const PRIORITY = { ... };                              // KEEP — used as tiebreaker
const sorted = [...pages].sort((a, b) => {
  const ea = lookup.get(a.file.path);
  const eb = lookup.get(b.file.path);
  // Primary: latestMtime DESC (most recent activity first).
  const ma = ea?.latestMtime?.ts ?? 0;
  const mb = eb?.latestMtime?.ts ?? 0;
  if (mb !== ma) return mb - ma;
  // Tiebreaker (rare): status priority ASC then status_changed_at DESC.
  const pa = PRIORITY[a.status] ?? 99;
  const pb = PRIORITY[b.status] ?? 99;
  if (pa !== pb) return pa - pb;
  const da = String(a.status_changed_at || "1970-01-01");
  const db = String(b.status_changed_at || "1970-01-01");
  return db.localeCompare(da);
});
```

`latestMtime` is a Dataview Luxon DateTime; `.ts` is the millisecond epoch. Fallback to `0` for null-safety (shouldn't happen — every project hub has at least its own mtime — but the cycle's hygiene posture is "never trust the data").

This sort applies WITHIN each group when `_groupBy !== "none"`. Group ordering (status / team / product) is unchanged (still uses `STATUS_ORDER` or alpha).

## §F — Click-to-edit on `## Today` raw checkboxes

### Surface

A NEW CustomJS class `TodayCaptureEditableList` ships in the to-do blueprint. Renders on daily to-do notes (between `SectionLabel("Today", top: true)` and `ToDoDailyCarryover`). Reads the file body, calls `TaskInteractions.findTaskLines(content, "todayCapture")`, renders a clickable row per task.

Row shape:

```
[ ]  Task title text         [project: Databricks] [due: 2026-06-24] [priority: high]  ✎
```

- Native-looking checkbox left (mirrors how Obsidian renders raw `- [ ]` in reading view).
- Title in the middle.
- Inline metadata chips on the right (project / due / priority / scheduled / recurrence) — only shown when set.
- Pencil icon at far right → click → opens the existing `ToDoCreateTask` modal in NEW edit mode.

### Editing pivot — extend `ToDoCreateTask.open`

`ToDoCreateTask.open(opts)` currently accepts `preselectTab` + `preselectDestination`. Extend with a new `editExisting` option:

```
ToDoCreateTask.open({
  editExisting: {
    filePath: '<absolute path>',
    lineIdx: <0-based line number in the file>,
    parsed: ParsedTask                              // from TaskInteractions.parseTaskLine
  }
});
```

When `editExisting` is set:

1. Modal opens on the one-shot tab (recurring is out of scope for raw-checkbox edit — recurring lives in `Recurring Tasks.md`).
2. Initial state is populated from `parsed`: `state.title = parsed.title`, `state.priority = parsed.priority || ''`, `state.due = parsed.due || ''`, `state.scheduled = parsed.scheduled || ''`, `state.destination = parsed.project ? { type: 'project', slug: <derive>, name: parsed.project } : 'today'`.
3. The submit button label changes from `Create` to `Save`.
4. Submit handler dispatches:
   - `editExisting` path: serialize via the existing `serializePayloadToLine`, call `customJS.TaskInteractions.replaceTaskAt(filePath, lineIdx, newLine)`. On success: Notice + close modal + open/focus the file (reuses the existing v0.8.3 `OpenHelpers.forceLeafPreview` pattern).
   - Create path (no `editExisting`): unchanged from today.
5. Destination select disabled in edit mode (you can't move a task across files via the inline modal; that's a follow-up). Project select for the `[project::]` field stays enabled — user CAN reassign the project without moving the file.

The modal's existing `_renderOneShotTab` (or equivalent submit-button rendering) gates `submit.textContent = state.editExisting ? 'Save' : 'Create'`.

### Wire-up

`Today To-Do.md` template grows the new block immediately after the `SectionLabel("Today", top: true)` block + the `<!-- TODAY_CAPTURE_MARKER -->` sentinel:

```
```dataviewjs

## Universal task contract — what this gives us

After v0.127.0, every task line emitted on the platform comes from one serializer and parses with one parser. Three immediate downstream wins (not built in v0.127.0; available for free):

1. **Recurring → meeting:** a recurring task fired into today's daily can be edited via the same modal; metadata stays consistent.
2. **Project To-Do click-to-edit:** dropping `TodayCaptureEditableList` into `Project To-Do.md` (it's already type-dispatched) gives project To-Do notes the same edit UX without further work. We won't ship that block in v0.127.0 (scope discipline) but the mechanism is ready.
3. **Cross-blueprint task search:** because every task line is regular, a future widget that aggregates "all tasks where `[project:: [[X]]]`" works identically on daily / project / meeting / recurring without per-source parsers.
