# v0.98.2 — feedback-loop closure — result

## TL;DR

Closes the loop the user's 2026-06-10 vision described: ticks + knobs + prose captured by v0.98.1's EOD Rail L now get INGESTED nightly by the existing `reconcile-cowork` cadence and APPLIED to the files that shape tomorrow's briefs. Three structural moves landed in one MINOR cycle:

1. **Capture completes (v=2).** Rail L gains the explicit per-item DOWNVOTE list ("Didn't like:") the vision asked for, under a `<!-- cowork:feedback-capture v=2 -->` sentinel; the item-ID → identity registry is persisted in the EOD sidecar (`feedback_capture.items[]`) at schema 1.2.0 additive.
2. **Ingest inside the existing nightly reconciler.** Step 3 of `reconcile-cowork` extended to parse BOTH `rating-block` AND `feedback-capture` (v=1 + v=2) sentinels — RESTORES EOD signal to per-kind learning, which v0.98.1's sentinel switch had silently broken. NEW Step 3.5 (deterministic rollup via `ingest-feedback-helper.js`) + NEW Step 3.6 (inline LLM free-text intent extraction, validated by deterministic rules); NEW Steps 5.5 / 5.6 apply non-weight deltas + sweep voice-proposal approvals from yesterday's morning brief.
3. **Apply with audit trail.** `learned_weights` schema 2 → 3 (nested per-kind entity maps) updates directly in `user-preferences.md` frontmatter with clamp + `.bak`; microscope `## What matters` appends only; voice corrections PROPOSED to `memory/<eng>/voice-proposals.md` and approved by tick-to-approve in the next morning brief; coverage gaps queue to `memory/<eng>/coverage-queue.md`; every delta logs to `memory/<eng>/feedback-deltas.md` with a source quote.

No new scheduled job; no contract bump (0.35.1 holds — wrapper template substitution refreshes against updated OI sources); no new installer write surface under user-owned paths (all new per-engagement files are runtime-created by the reconciler session via Obsidian MCP — Safeguard 3 CI stays green by construction).

## Discoveries and lessons

### 1. Plan fixture hashes must be computed, not invented

The plan listed `_itemId("chat","chat:c1:t1") = "item-chat-31bc2eb"` for HC-V0982-INGEST-A1's fixture, but the real hash (per the deterministic SHA-1 in `compose-body-helper.js`) is `item-chat-10f069a`. The plan flagged the placeholder with a `# compute me` instruction at the fixture site (per v0.98.1 lesson #2's "verify shape contracts at design time" carry-forward, now extended to fixture hashes), so the implementer caught it cleanly at S1.1. **Lesson: plans should always mark fixture hash placeholders with an explicit compute-me instruction. This plan did — worked as designed. Future plans should follow the same convention rather than treat any hash literal as ground truth.**

### 2. Rewriting a regex-scan block can orphan loop variable declarations

S1.3 rewrote the tick-extraction block in `parseFeedbackCapture` to add the section state machine for Mattered/Didn't-like. The rewrite removed a `let m;` declaration that was used ONLY in the new tick block — but the (unchanged) knob-extraction loop further down ALSO used `m` and was implicitly relying on the outer `let` for safety. Result: `m` became an implicit global in the knob loop, with subtle aliasing if the function ran multiple times in a single Node process. Caught by S1.3.1 quality review on `bf67bd4` → `4ea47e7` (one-line fix: redeclare `let m;` at the top of the knob loop). All HC-V0982-PARSE asserts stayed GREEN throughout — the implicit global wasn't load-bearing for correctness, but was a latent bug. **Lesson: when replacing PART of a function, grep the remainder for identifiers the removed lines declared. The pattern `git diff <stage> -- <file> | grep '^-.*let \|^-.*const \|^-.*var '` lists every variable declaration the change deletes; check each name against the unchanged code below it.**

### 3. Intentionally-parallel parser implementations need cross-reference comments

`compose-feedback-capture-helper.js`'s `_parsePrior` and `learn-from-checks-helper.js`'s `parseFeedbackCapture` carry MIRRORED section state machines (both walk Mattered → Didn't-like → knob row → free-text fence in order, with identical regex anchors). They serve different purposes — compose-side preserves prior UI state for re-fire idempotency; reconciler-side extracts ingest signal — but their state machines MUST stay in sync, or compose-side will preserve state the reconciler can't parse. S1.4 added cross-reference comments at the top of each implementation pointing at the other (`// MIRRORS compose-feedback-capture-helper.js _parsePrior section state machine; keep in sync`). **Lesson: when two helpers carry intentionally-parallel implementations of the same shape contract, BOTH sides should carry cross-reference comments naming the sibling and the invariant. Future editors who touch one without grepping for the other are the realistic failure mode.**

### 4. `validateSidecar`'s real signature is `(payload, schemaPath)` not `(payload, cadence)`

The plan's S1.6 one-liner showed `validateSidecar(sidecarPayload, cadence)` expecting the helper to look up the schema file from the cadence string. The real signature in `validate-sidecar-helper.js` is `validateSidecar(payload, schemaPath)` — caller supplies the literal path. S1.6 adapted at implementation time by computing the schema path from cadence (`data/schemas/${cadence}@1.0.0.json`) in the caller. Zero harness impact (the contract still passes the right schema), but the plan's one-liner would have produced a `schema not found` runtime error at first ingest fire. **Lesson: the standing verify-helpers-before-design lesson (Discovery 2 from v0.94.0; sauce CLAUDE.md's `feedback_verify_helper_behavior_before_design` memory) applies to PLANS, not just designs. Plan one-liners that name a helper call should grep `function <name>` first and copy the real signature into the plan, even when the design narrative is correct.**

### 5. PRE-EXISTING: live headspace 2026-06-10 eod-review sidecar FAILS schema validation

While stash-verifying the v0.98.2 deploy posture against the consumer vaults' current EOD sidecars, the live headspace `2026-06-10/eod-review.cowork.json` was found to carry `coverage_gap: []` (array) where the schema's shape is `coverage_gap: { expected, surfaced, skipped }` (object). The sidecar was emitted by the cron LLM on 2026-06-10 (v0.98.0 era) under a prior fire. The `write-atomic-note-helper.js` validate-then-write gate should have rejected the payload — but the sidecar landed on disk, so either the gate did not run on that fire or it was bypassed by an LLM session that skipped the helper entirely. This predates v0.98.2 and is NOT a regression introduced by this cycle. Queued as a v0.98.2.x / v0.99.0 observability candidate: `cowork:doctor` (already on the v0.99.0+ roadmap) would catch this class of fire-time deviation by scanning sidecar conformance across the corpus and surfacing anomalies in a dedicated callout. **Lesson: the deterministic-helpers-for-shape posture (cowork-vision § 11.1) is only as strong as the gate's actual invocation. When an LLM session can bypass a deterministic gate, the gate is advisory, not enforceable. The remediation isn't to add MORE gates — it's to add OBSERVABILITY on whether they ran (`cowork:doctor`).**

### 6. New shared-clause substitution tokens must be registered in the HC-V0970-T-3 allowlist

The v0.98.2 OI layer (S1.5) introduces two NEW substitution tokens for the voice-proposals callout: `{{$voice_proposals_count}}` and `{{$voice_proposal_lines}}`. The wrapper-template substitution validator (v0.97.0 Rail T) carries a HC assert (`HC-V0970-T-3`) that enforces an allowlist of known tokens — any token in the OI not on the allowlist trips the validator at preflight. S1.5 surfaced this when the `_shared-clauses.md` `voice_proposals_callout_template` block introduced both new tokens; the allowlist needed two entries added in the same commit. Caught at S1.5 dogfood; would have been a preflight RED otherwise. **Lesson: any new `{{$<token>}}` substitution token added to a shared clause or orchestrator-instructions file MUST also be added to the `compose-scheduled-job-wrappers-helper.js` allowlist (the `KNOWN_SUBSTITUTION_TOKENS` constant) in the same commit. Future cycles touching OI prose with new tokens should grep `KNOWN_SUBSTITUTION_TOKENS` as part of the pre-design audit.**
