## Problem A — orchestrator body-composition prose-attention ceiling

### Symptom

Orchestrator Step 14 at `platform/blueprints/cowork/skills/orchestrators/morning-briefing/SKILL.md:292` (consumer materialization at `.claude/skills/cowork/morning-briefing/SKILL.md`) specifies:

> `SpaceNavButtons → [!info]- Today at a glance synopsis → memory callouts → ordered_blocks[] → engagement-type-aspect blocks → [!tip] Today's focus closing`

The LLM ran the gather steps (5–12b) correctly + composed correct content + emitted correct frontmatter + correct dvjs + correct path. But Step 14 itself — the body-shape contract — was skipped. The LLM produced plain `##` markdown sections instead of admonition-callout wrappers.

### Root cause

Orchestrator SKILL.md is >500 lines. Step 14 is buried at line 292 surrounded by exception-handling prose for engagement-template fallback / sentinel detection / voice contract / semantic interpolation. The LLM's attention budget exhausted on the hardened (top-of-file) rules + the in-line gather instructions + the inline user-prompt body; Step 14's composition spec didn't reach actionable salience.

This is structurally identical to:
- v0.90.2's wrong-path failure on accuris-laptop (Step 16 write spec ignored, daily-blueprint path used instead)
- v0.91.2's wrong-frontmatter failure (Step 16 frontmatter spec ignored, `cowork-run-note` used instead of `cowork-morning-briefing`)
- v0.91.3's hallucinated SpaceNavButtons invocation (Step 17 pattern spec ignored, broken `const { SpaceNavButtons } = customJS` shape emitted)

Pattern: long-orchestrator prose contracts get dropped in favor of higher-salience signals. The v0.91.x stack added DETERMINISTIC write-guards (path / frontmatter / dvjs canonical pattern) in sub-skills as backstops for the corresponding prose contracts. The body-shape contract has no such backstop.

### Constraint

Same machine ran weekly-review the same day and produced rich, correctly-structured output **without consulting the orchestrator at all** (per user's session observation). That run worked because the user-prompt body was directly executable. The morning-briefing orchestrator's prose burden is now load-bearing for cases where the user-prompt body isn't sufficient on its own — and that prose burden has crossed the LLM-attention ceiling.

### Direction (decided 2026-06-05, awaiting brainstorm)

User selected "v0.92.0 composer sub-skill" path during the conversational triage. Architecture sketch (NOT YET FINALIZED — needs brainstorm):

- NEW sub-skill `cowork:compose-body` reachable as a normal sub-skill.
- NEW pure helper `compose-body-helper.js` exports `composeBody({ cadence, synopsis_md, memory_callouts: { yesterday_md, overnight_md, echoes_md, backlink_md }, ordered_blocks: [{ kind, callout_type, title, body_md }], engagement_type_blocks: [{ kind, body_md }], focus_md }) → { body_md }`. Pure shape composer; deterministic; emits canonical callout-wrapped markdown byte-identical to golden fixtures.
- Orchestrator Step 14 becomes: "Build structured composeBody input from gather outputs. Invoke `cowork:compose-body`. Pass returned `body_md` to write-run-note." Step 14 prose shrinks from ~30 lines to ~5.
- NEW body-shape write-guard in 5 write-run-note sub-skills `## Pre-write self-check`: REJECTS bodies missing the canonical callout markers. Returns `failed:contract-violation:wrong-body-shape:<which>` on miss.
- Orchestrators slim from ~500+ lines to ~50-line dispatchers (longer-term refactor candidate; v0.92.0 may not get all the way there, but the composer makes the path possible).

Open questions for brainstorm:
- One shared `cowork:compose-body` vs 5 per-cadence composers?
- Should the composer also emit the memory callouts directly, or take them as inputs from the existing `composeMemoryCallouts` / `composeSemanticEchoesCallout` helpers and stitch?
- Does the body-shape write-guard reject hard, or warn + repair (composer fallback)?
- Migration approach: ship v0.92.0 with composer + write-guard simultaneously, or split into S1/S2?
- Where does the canonical callout-type mapping live? Currently in `read-user-preferences-helper.js` per v0.82.0; composer should consume from there, not duplicate.

## Problem B — Cowork scheduled-job wrapper drift

### Symptom

Cowork (claude.ai's scheduled-task feature) is the cron runtime for the 5 daily/weekly/monthly cadences. The scheduled task's prompt body is set in claude.ai's UI and lives outside the sauce vault entirely. No mechanism in v0.91.x detects when the Cowork wrapper drifts from canonical structure — the user has to remember to re-paste after every v-bump that changes the wrapper requirements.

### Drift surface

The canonical wrapper structure is currently maintained as conversational artifacts:
- Workshop session 2026-06-05 produced `Planning/cowork-scheduled-job-wrappers-v0.91.3.md` in the accuris vault as the source of truth for the 5 v0.91.3-aligned wrappers.
- User manually paste-replaces each Cowork task body when shipping a v-bump that touches the wrapper contract.
- No automated check that the Cowork-side wrapper matches the canonical for the current sauce/cowork version.

### Versioned-contract risk

Each new v-bump that adds an enforcement layer (v0.91.1 path guard, v0.91.2 frontmatter guard, v0.91.3 connectivity + deferred-tool + dvjs canonical) ideally adds a corresponding clause to the Cowork wrapper as belt-and-suspenders. Wrapper drift makes the cron run with stale enforcement.

### Direction (awaiting brainstorm)

NEW user-invocable skill `cowork:sync-scheduled-jobs` reachable via `/cowork sync-scheduled-jobs [<engagement_id>]`. Sketch (NOT YET DESIGNED):

- Reads current sauce version + cowork version + engagement context (user-preferences, vault-config, engagement-types/<type>/scheduled-jobs.json if a manifest schema is designed).
- Invokes NEW pure helper `compose-scheduled-job-wrappers-helper.js` exporting `composeWrappers({ engagement, sauce_version, cowork_version, prefs, vault_config }) → { wrappers: [{ task_name, schedule, body_md }, ...] }`.
- Writes the 5 wrappers to a versioned, paste-ready file at `Planning/cowork-scheduled-job-wrappers-<engagement_id>-v<sauce_version>.md` (or `spice/cowork/prompts/_scheduled-job-wrappers-current.md` — naming TBD).
- Emits a per-cadence summary with task name + schedule + first-few-lines preview.
- User opens the file, copy-pastes each fenced block into claude.ai Cowork UI.
- Optional Phase 2: emit a "diff your current Cowork wrappers vs. canonical" prompt the user pastes each current wrapper into for a drift report.

Open questions for brainstorm:
- One file with all 5 cadences, or 5 separate files?
- Frontmatter convention so the consumer can `dataview` the file's age / version freshness?
- How does the canonical contract evolve — encoded in helper code, or in a versioned `scheduled-job-contract.json`?
- Cross-engagement sharing: accuris uses M365 / ADO UUID; headspace uses Apple-MCP / iMessage. Each engagement's wrapper differs in the CONNECTIVITY clause but is identical in OUTPUT PATH + FRONTMATTER + DATAVIEWJS + SUB-SKILL prose. Architecture should not duplicate.
- Does this skill live under `cowork:` namespace or elevate to a top-level `platform:` mechanism since it touches cron config that's claude.ai-side?
