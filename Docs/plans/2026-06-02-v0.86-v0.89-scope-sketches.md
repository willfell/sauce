# v0.86 → v0.89+ scope sketches

Lightweight forward-look at the next four cycles after v0.85.0. Each sketch is sized to onboard the session that picks up that cycle — orchestrators / sub-skills shipped, new canonical types if any, cross-stage dependencies, and the design questions worth revisiting when the cycle is up. **None of these are spec-grade.** The cycle-active session will brainstorm + write a full design doc following the v0.85.0 pattern.

The strict-sequence v0.85 → v0.86 → v0.87 → v0.88 → v0.89 ordering is locked per `Docs/plans/2026-06-02-memory-leverage-sequencing-decision.md`. Cycles MUST land in order — downstream primitives + memory volume are load-bearing.

## v0.86.0 — cross-orchestrator memory wire-through (FLN-v84-2)

**Codename:** cross-orchestrator-memory-wire-through.
**Cycle shape:** MINOR (4 orchestrator surface changes; no new orchestrator or sub-skill).
**Versions estimate:** workshop `0.85.0 → 0.86.0`; cowork `0.24.0 → 0.25.0`.

### Scope

Apply the v0.85.0 morning-briefing pre-flight 3a + body-composition pattern to the four remaining atomic-note orchestrators that produce user-facing daily output:

- `cowork:midday-tripwire` — reads last 4h of memory (since morning-briefing fired)
- `cowork:eod-review` — reads today's full memory (all ticks + day_synthesis if synthesize-day has fired earlier in EOD chain)
- `cowork:weekly-review` — reads this week's day_syntheses (Mon–today) + last week's week_synthesis if synthesize-week has fired
- `cowork:monthly-review` — reads this month's week_syntheses

Each orchestrator gains a pre-flight step 3a (same shape as MB's, invoking `cowork:read-memory` with the appropriate window) + body composition that injects memory callouts via a new compose helper per orchestrator (`composeMiddamMemoryCallout`, `composeEodMemoryCallout`, etc.). All null-data-gated; absent memory = clean skip.

### New surfaces (read-only consumers)

- **No new orchestrators, sub-skills, or canonical types.** Pure wire-through.
- **New compose helpers (4):** one per orchestrator's memory callout shape. Each is a thin pure function returning a string; mirrors v0.85.0 `composeMemoryCallouts`. Golden-fixture tests per orchestrator.
- **HC strategy:** ~16 sub-asserts across A (pre-flight refactor per orchestrator, 4 cases) + B (compose helper golden-fixtures, 8 cases) + C (null-data backward-compat per orchestrator, 4 cases).

### Cross-stage dependencies

- **Needs v0.85.0's `cowork:read-memory` API.** v0.86.0 is structurally trivial if the API shape is stable.
- **Needs memory volume.** Between v0.85.0 close and v0.86.0 open, accumulated memory ≈ 1–2 weeks × 4 vaults. Wire-through becomes more valuable as more memory exists; null-data gate handles the sparse cases.
- **Engagement-types schema unchanged.** No new cadences (the 4 orchestrators already have their cadences); no schema bump.

### Open design questions to revisit at cycle-time

1. **Time-window per orchestrator.** Roadmap suggests midday=4h, eod=today, weekly=this-week, monthly=this-month. Refine at design-time based on actual MB-output utility observed during the v0.85 → v0.86 interval.
2. **Tier-2 wire-through vs Tier-1-only.** Weekly-review reading `cowork:read-memory({tier: "week", window: "last-week"})` may be more valuable than reading raw daily ticks. Decide at design-time which tier each orchestrator consumes.
3. **Compose helper consolidation vs per-orchestrator.** 4 nearly-identical compose helpers could collapse into one `composeMemoryCallout({orchestrator, output}) -> string` with switch logic. Decide based on whether each orchestrator's callout shape diverges meaningfully or stays uniform.
4. **Bundling Tier 3 (`cowork:synthesize-month`)?** If Tier 3 hasn't shipped yet (and isn't shipping in v0.85.0), v0.86.0 could fold it in alongside the monthly-review wire-through (synthesize-month + monthly-review reading it). Adds ~3 stages. Decide at design-time.

## v0.87.0 — semantic-retrieval over memory (FLN-v84-4)

**Codename:** semantic-memory-retrieval.
**Cycle shape:** MINOR (1 new sub-skill + optional wire-through to MB pre-flight).
**Versions estimate:** workshop `0.86.0 → 0.87.0`; cowork `0.25.0 → 0.26.0`; smart-connections-bridge `0.1.1 → 0.2.0` (if API needed).

### Scope

Add semantic retrieval over the accumulated memory corpus. Today (v0.85+v0.86): every memory-aware orchestrator reads the **most-recent** memory window (yesterday / today / this-week / this-month). v0.87.0 adds: also retrieve the **closest historical analogue** via SC embeddings.

Concretely:

- **NEW `cowork:gather-semantic-memory` sub-skill** — Wraps `smart-connections-bridge@0.1.1`'s existing `query` interface. Inputs: `{ anchor_text, engagement_id, top_k: 3, exclude_window: "last-30d", min_similarity: 0.7 }`. Anchor text is typically composed from today's gather output (calendar events + email subjects + chat-thread titles) or the previous orchestrator's compose helper output. Returns: `{ matches: [{ path, similarity_score, day, synthesis_excerpt }, ...] }`.
- **Optional MB wire-through.** Add an optional pre-flight step 3b after step 3a: invoke `cowork:gather-semantic-memory` with anchor = today's calendar+email summary, top_k=2. If non-empty, body composition gains a `[!quote]- Echoes from your record` callout listing the matches with brief synthesis excerpts + wikilinks.

### New surfaces

- **`cowork:gather-semantic-memory`** sub-skill at `platform/blueprints/cowork/skills/skills/gather-semantic-memory/SKILL.md`.
- **(Optional) MB pre-flight step 3b** + new compose helper `composeSemanticEchoesCallout` if wire-through is in scope.
- **sc-bridge enhancement (if needed):** v0.87.0 may need a `--corpus-filter <prefix>` arg to scope retrieval to `spice/cowork/memory/**` only (avoid retrieval matches against non-memory notes). Bumps sc-bridge minor.
- **HC strategy:** ~10–14 sub-asserts. A (sub-skill structure, ~4) + B (sc-bridge integration smoke, ~3, fixture-driven), C (MB optional wire-through prose-lint if shipped, ~3), D (manifest + claude_surface, ~2).

### Cross-stage dependencies

- **Needs v0.86.0's wire-through.** v0.86.0 amplifies memory-volume (4 more orchestrators reading daily → more memory accumulates faster). Without it, v0.87.0 retrieval has thin signal.
- **Needs ≥1 week of accumulated memory.** SC embeddings are computed by Smart Connections plugin in the vault; retrieval quality depends on corpus size. Roughly: 100+ memory files per engagement before retrieval is meaningfully useful. v0.85+v0.86 should put 1+ engagement at this threshold by v0.87 open.
- **Needs smart-connections-bridge stability.** Currently `@0.1.1`. v0.75.0 cycle hardened the bridge; v0.87.0 design must verify no regressions accumulated.

### Open design questions to revisit at cycle-time

1. **Invocation pattern: auto-include in MB pre-flight vs USER-INVOCATION skill.** Auto-include: MB always pulls top-2 semantic matches, prepends to body. USER-INVOCATION: ship `/cowork recall <query>` slash command + sub-skill; user explicitly invokes when curious. Auto-include gives compounding intelligence by default; user-invocation respects user agency. Could ship both.
2. **Embedding granularity.** SC embeds files. Tier 0/1 memory files contain 16 ticks + a synthesis — one file is mixed-content. Options: (a) embed the whole memory.md (simplest; SC default); (b) extract synthesis paragraph only + embed; (c) embed per-tick callout. Pick at design-time based on retrieval-quality experiments.
3. **Retrieval depth + recency boost.** Top-K = 2 or 3. Recency boost? (Penalize hits older than 6 months.) Engagement-id filter? (Personal queries shouldn't retrieve w2-fte memory.)
4. **Failure mode: SC plugin not installed / not indexed.** Existing sc-bridge surfaces this. Graceful null return + Notice. Required for backward-compat with vaults that haven't installed SC.
5. **Tier 2 / Tier 3 retrieval surface.** Tier 2 weekly syntheses are higher-signal than raw daily memory files. Configure retrieval to prefer Tier 2 results when available; fall through to Tier 1 only when Tier 2 corpus is thin.

## v0.88.0 — distill-week + auto-update user-preferences

**Codename:** distill-week-and-prefs-auto-update.
**Cycle shape:** MINOR (1 new orchestrator + new canonical type optional + USER-file write contract).
**Versions estimate:** workshop `0.87.0 → 0.88.0`; cowork `0.26.0 → 0.27.0`.

### Scope

Closes the "getting smarter" feedback loop. Each Friday after `cowork:synthesize-week` fires, run `cowork:distill-week` — scans the week's memory + synthesis for recurring patterns (people, topics, MCP-priority shifts, voice-rule violations) and **proposes** updates to the user's `user-preferences.md` interactively.

Concretely:

- **NEW `cowork:distill-week`** orchestrator (Friday cron after synthesize-week, e.g., 17:30 MT). Reads this week's Tier 1 + Tier 2 memory via `cowork:read-memory`. Extracts:
  - **Person frequency.** Names mentioned ≥10× across the week in carry-forward bullets or synthesis paragraphs. If a person isn't in `prefs.inner_circle_people`, propose adding them.
  - **MCP-priority shifts.** Kinds that produced significant carry-forward signal vs kinds that rarely appeared. Propose `prefs.mcps.<kind>.priority` adjustments.
  - **Voice-contract patterns.** Words / phrasings that appeared frequently across orchestrator outputs but aren't in `prefs.personality.hard_rules[]`. Propose additions if the user is consistent.
- **Proposal output:** writes to a new transient file `spice/cowork/memory/<engagement_id>/<YYYY>/<MM-MMMM>/<YYYY-Www>/distill-proposals.md`. Each proposal is a `[!question]+` callout with the proposed delta + a Yes/No interaction button (via existing entity-create UI patterns or a new `cowork:apply-distillation` skill). User reviews + accepts/rejects per-proposal.
- **Apply-distillation flow:** when user accepts, the distill-proposals → applied flow writes through `cowork:edit-microscope`'s existing USER-file write contract (mirrors v0.79.0 pattern). `user-preferences.md` is a `materialize_once: true` file; the platform never overwrites it; only the user-driven distill-apply flow modifies it.

### New surfaces

- **`cowork:distill-week`** orchestrator at `platform/blueprints/cowork/skills/orchestrators/distill-week/SKILL.md`.
- **`cowork:apply-distillation`** sub-skill at `platform/blueprints/cowork/skills/skills/apply-distillation/SKILL.md` (handles the user-accept-then-write flow against user-preferences.md).
- **Optional new canonical type `cowork-distillation`** for the proposal files. Rule_fragment scopes `spice/cowork/memory/**/distill-proposals.md`. Adds activity-feed display_name "Distillation proposals."
- **HC strategy:** ~16–20 sub-asserts. A (distill-week orchestrator structure, ~5) + B (apply-distillation sub-skill structure, ~4) + C (extractor logic per category: person-freq, MCP-priority, voice-rule patterns; ~6) + D (USER-file write contract integrity — preserves prior content, atomic-write, .bak; ~3) + E (manifest + canonical-type, ~2).

### Cross-stage dependencies

- **Needs v0.85.0's Tier 2 syntheses.** Distill-week operates on Tier 2 outputs; without them, signal is too noisy across raw daily data.
- **Needs v0.87.0's semantic retrieval (for entity de-duplication).** Person-frequency extraction needs to recognize "Jason" and "Jason Batai" and "@Jason B." as the same entity. SC embeddings + a thresholded similarity match handles this. Without v0.87.0, the extractor would need its own name-resolution logic; cleaner to use semantic retrieval as the entity-dedup primitive.
- **Needs the v0.79.0 USER-file write contract** (edit-microscope precedent). Existing `cowork:edit-microscope` writes to user-preferences.md adjacent surfaces; v0.88.0's `apply-distillation` reuses the same write contract.

### Open design questions to revisit at cycle-time

1. **Write contract: ONE update at a time vs BATCH diff.** One-at-a-time: each proposal is a separate `[!question]+` callout with its own Yes/No. User clicks Yes → write that one update → next proposal. BATCH: full proposal set rendered as one diff (red/green lines); user reviews + clicks single Accept or Reject. ONE-AT-A-TIME is lower-risk (each accept is a tiny atomic change). BATCH is faster but rejections of one item require re-running the whole flow.
2. **Distillation cadence: weekly only vs include monthly.** Friday weekly is the foundation; should distill also fire monthly (e.g., last Friday of the month) for cross-week pattern detection (e.g., MCP-priority shifts that took 3 weeks to manifest)? Adds ~2 stages.
3. **Extractor categories: which to ship first.** Person-frequency is highest-confidence (count-based, easy to validate). MCP-priority and voice-rule pattern detection are softer signals. Ship person-frequency-only as v0.88.0 MVP; defer MCP-priority + voice-rule to v0.88.1 or later.
4. **Rollback semantics for prefs updates.** Each apply-distillation write should backup the prior `user-preferences.md` to `<file>.sauce-backup` (single-deep). Documentation in install.md upgrade section so user knows recovery path.
5. **Cross-engagement learning.** Should distill-week aggregate across engagements? E.g., a person mentioned 5× in personal + 5× in headspace = 10× total → propose inner_circle promotion for personal engagement. v0.88.0 MVP: per-engagement isolation; cross-engagement learning deferred.

## v0.89.0+ — retro views + insights surfacing

**Codename:** retros-and-insights.
**Cycle shape:** MINOR (2 new orchestrators + new view mechanism + hub-integration).
**Versions estimate:** workshop `0.88.0 → 0.89.0`; cowork `0.27.0 → 0.28.0`; styling unchanged unless new retro callout styles needed.

### Scope

Surface the accumulated intelligence to the **user** in narrative + visual form. By v0.89.0, the system has months of memory + weekly syntheses + distilled prefs updates. The user should be able to:

- **Run retros** on demand or on schedule:
  - `cowork:retro --weekly` — narrative reflection across this week's memory + synthesis
  - `cowork:retro --monthly` — narrative reflection across this month's weekly syntheses
  - `cowork:retro --quarterly` — narrative reflection across 3 months
- **See insights** on the cowork hub:
  - Pattern callouts: "You've mentioned Jason 27× across 4 weeks — should he be inner_circle?" (recapped from distill-week proposals)
  - Streaks: "You've completed your morning-briefing 14 days in a row."
  - Reminders: "You wrote a microscope contract for chat 3 months ago — does it still match how you use chat now?"

Concretely:

- **NEW `cowork:retro`** orchestrator with scope opt (`weekly` / `monthly` / `quarterly`). Reads memory at the appropriate tier; composes a voice-applied narrative reflection. Writes to `spice/cowork/memory/<engagement_id>/<YYYY>/<MM-MMMM>/<scope>-retro-<YYYY-MM-DD>.md` (or similar — design at cycle-time).
- **NEW `cowork:insights`** orchestrator (daily, lightweight). Reads recent distill-proposals + this week's synthesis + this month's weekly syntheses. Composes pattern callouts for the cowork hub.
- **NEW dataviewjs view at `ranch/views/cowork-insights/view.js`** — renders the insights callouts inline on Cowork.md.

### New surfaces

- **`cowork:retro`** orchestrator.
- **`cowork:insights`** orchestrator (or sub-skill, depending on whether it has its own cadence).
- **NEW dataviewjs view** for hub-integration.
- **Optional new canonical type `cowork-retro`** for retro narrative files.
- **HC strategy:** ~14–18 sub-asserts. A (retro orchestrator, ~5) + B (insights orchestrator, ~4) + C (view renders correctly with fixture data, ~3) + D (hub-integration in Cowork.md, ~2) + E (canonical type + rule_fragment if introduced, ~2).

### Cross-stage dependencies

- **Needs all of v0.85.0–v0.88.0.** Retro reads multiple tiers; insights pulls from distilled proposals + Tier 2 syntheses. Without the full memory-leverage arc, this cycle has no signal.
- **Memory volume.** Retro narratives are most valuable with months of memory. v0.89.0 ships with 8+ weeks of accumulated memory across engagements (v0.85 → v0.88 = ~8 weeks of calendar time).
- **No new mechanisms needed.** dataviewjs view is a pure helper; activity-feed mechanism already handles the new canonical type if added.

### Open design questions to revisit at cycle-time

1. **Retro cadence + scope per engagement-type.** Personal engagement may want quarterly retros; w2-fte may only run weekly. Engagement-types schema bump to add `retro_scopes[]` field? Or per-engagement config in vault-config.md?
2. **Insights surface: hub-embed vs separate note.** Hub-embed: `Cowork.md` gains an Insights section with dataviewjs renderer. Separate note: `spice/cowork/insights/insights.md` updated by the insights orchestrator. Hub-embed is the lighter UX.
3. **Streak tracking.** Counts of consecutive days for each orchestrator's fire. Needs persistence; options: (a) frontmatter on a sentinel note `spice/cowork/insights/streaks.md`; (b) computed at insights-fire from looking at recent atomic-note timestamps. (b) is stateless + cleaner.
4. **Reminders: contract-staleness detection.** "Microscope for chat was last edited 90+ days ago — review?" Requires git-mtime or frontmatter `last_edited_at` on microscope.md. v0.79.0 microscope contracts don't currently track this; adding it is a small bump.
5. **Privacy / sensitivity filters.** Retros may surface emotionally-heavy moments. Voice contract should respect (`personality.hard_rules` already handles tone constraints). Filter sensitive entities from cross-engagement retros (e.g., w2-fte retro doesn't surface inner_circle people from personal engagement).
6. **Anti-pattern surfacing.** Retros should also flag negative patterns — e.g., 4 weeks of no eod-review fires on consulting engagement. Distillation can flag these; retros narrate them. Design-time decision on voice + framing.

## Beyond v0.89.0+ — open candidates not yet scoped to a cycle

Aligned with `Docs/agent-guides/cycle-status.md` in-flight queue. Documented here for traceability with the memory-leverage arc:

- **FLN-v84-3 — memory retention / compression policy.** When does Tier 0/1 data get pruned or replaced by its Tier 2 synthesis? Design-only cycle; depends on memory-layer telemetry from v0.89+ deployments.
- **Cross-vault memory aggregation.** A user with multiple vaults (personal + accuris + headspace) — does cowork's read-memory cross vault boundaries? Probably not (each vault has its own engagement scope), but the user may want a cross-vault retro view.
- **Memory-driven new-mechanism extraction.** As cowork's memory layer becomes substantial, the `gather-semantic-memory` + `read-memory` sub-skills become reusable across blueprints (e.g., projects blueprint could read memory for project-relevant context). Extract to a top-level `memory-layer@0.1.0` mechanism?
- **Memory export / archival.** Year-end "snapshot" of accumulated memory for offline review or pre-archival sanitization. Not memory-leverage core but a natural follow-on.

## Convention reminders (across all 4 cycles)

Per `Docs/agent-guides/build-test-verify.md` + `Docs/landmines.md`:

- **Direct-push to `origin/main`** per established cycle convention.
- **One commit per stage.** Conventional-commits. **NO `Co-Authored-By` trailer.**
- **Explicit `git add <paths>`** per stage — NEVER `git add -A` (landmine).
- **Dogfood install** after any SKILL.md / manifest change: `node platform/install.js --vault . --auto-approve`. Stage regenerated `ranch/` + `.claude/` in the same stage commit.
- **`npm run release:preflight` ALL GREEN** required before each stage advance + at cycle close.
- **USER APPROVAL** required before any annotated tag push.
- **Re-run `cowork:onboard-scheduled-jobs`** on consumer vaults after `sauce update --bump-pins` for any cycle that adds a new cadence.
- **22 landmines** non-negotiable (Docs/landmines.md). Most relevant for the memory-leverage arc: #16 (in-cycle bump rule), #23 (`created_at` authoritative not mtime), #12 (.obsidian/.claude allowlist).
- **FLN-v841-1 test-pin pattern.** Any cycle that bumps a manifest version must grep exact-version pins across the test suite at S0 — not at S7.
