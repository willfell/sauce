# v0.95.0 — cowork-spine MINOR design

## Problem

Five orchestrator SKILL.md files (morning-briefing / midday-tripwire / eod-review / weekly-review / monthly-review, ~330 lines each) carry **byte-identical copies of the dispatch-plan pseudocode** (~100 lines per file, ~500 lines of duplication). The same conceptual pre-flight step wears different sub-step labels across files: morning-briefing has `3a memory / 3b semantic-echoes / 3c read-prefs / 3d dispatch / 3e inner-circle`; the other four have `3a memory / 3b read-prefs / 3c dispatch / 3d inner-circle` (semantic-echoes is absent). Same logical pre-flight step shows up as 3b in one orchestrator and 3c in another. Per-kind callout titles ("Today's calendar", "Email triage", "Chat (Teams)") are inlined in each orchestrator's compose-body step.

The `render_aspects` knob surface is a flat 6-key per-engagement-type map (`finance_block`, `invoice_prep`, `ai_committee`, `kanban_projects`, `inner_circle_imessage`, `semantic_related`) where each value is `"include"` or `"skip"`. Engagement-type discriminators leak into skill code: `gather-imessage` early-exits for non-personal engagements; `tripwire_aspects` is hard-coded per type. To "reorder connectors per cadence per engagement," a user has to fork the engagement-type JSON — there is no per-engagement override layer.

A helper file `platform/blueprints/cowork/helpers/dispatch-plan-helper.js` (v0.78.0) ALREADY EXISTS and exports `planDispatch`, `decideDispatchMode`, `composeVoiceContract`, `composeWarningCallout` — but it is only used by HC-V0780 test harness cases. Each of the 5 orchestrator SKILL.md bodies inlines the pseudocode verbatim because **production agents execute the pseudocode directly; they do not invoke the helper**. The cohesion gap is the *sub-skill body* that would route production agents through the helper.

The compounding-assistant North Star (per `Docs/cowork-vision.md`) requires the spine: cohesion (so dispatch + voice + microscope logic has one home), composability (so users reorder knobs per cadence), and a generalizability posture (so engagement-types are knob bundles, not runtime predicates). v0.95.0 ships the spine; v0.95.0.x → v0.96.0+ cascade voice, bootstrap, memory write-side, observability.

## Approach

Single workshop MINOR cycle (v0.94.x → 0.95.0) bundling one cowork blueprint MINOR (0.31.2 → 0.32.0) + one NEW sub-skill + one NEW pure helper-wrapping orchestrator body + one NEW data file + one NEW agent-guide + a schema delta on `vault-config.md`. No mechanism bumps — cohesion + knobs are cowork-internal.

### Why workshop MINOR (not PATCH)

Cowork grows new public surface — a new sub-skill that orchestrators publicly READ, a new data file, a new agent-guide. The engagement.overrides schema is a new contract for consumers. MINOR is correct per sauce convention.

### Why cowork MINOR (not PATCH)

New sub-skill body (`skills/skills/plan-dispatch/SKILL.md`), new helper exports, new data file. The schema delta on `vault-config.md`'s engagement record (additive `overrides:` block) does not break existing vault-configs (the field is optional and backward-compat-read). MINOR per the cowork blueprint convention used in v0.27.0, v0.28.0, v0.29.0.

### Why the engagement.overrides schema is backward-compat for one cycle (not two)

Existing consumer vaults today have `engagement.type` set + per-type fields (cc_active_cards / manager / stakeholders / etc.). v0.95.0's read pass treats the absence of an `overrides:` block as "use the bundle defaults verbatim" — the behavior is unchanged for any engagement that doesn't add overrides. v0.95.1 ships `sauce update --migrate-config` which adds an empty `overrides: {}` block to every engagement in vault-config.md (so the field is canonical) and drops backward-compat reads (any vault-config.md without `overrides:` at that point is a bug, not an old shape). One-cycle window keeps the helper readable; locking the schema for the platform's life would let the back-compat code rot.

### Why cohesion + knob refactor bundle (not two cycles)

Brainstorm option-1 vs option-2 decision (locked 2026-06-07): both refactors touch the same 5 orchestrator SKILL.md bodies. Splitting means two refactor passes on the same files within a few cycles — each pass risks shipping a regression. Bundling means one careful refactor, one preflight green window, one consumer-vault deploy verification window. The blast-radius mitigation is per-orchestrator commits inside S1.4 (each orchestrator's refactor is a separate commit; if one fails dogfood, it can ship alone or revert without losing the rest).

### Why `dispatch-plan-helper.js` already exists but ISN'T used in production today

Found during the 2026-06-07 brainstorm (v0.93.3 lesson 5.1 — grep + read every helper the design references). The helper's docstring says:

> A helper at `platform/blueprints/cowork/helpers/dispatch-plan-helper.js` exports `planDispatch`, `decideDispatchMode`, `composeVoiceContract`, `composeWarningCallout` for the HC-V0780-C* / D* harness cases. Production agents in consumer vaults execute step 3d's algorithm directly — they do NOT depend on the helper file existing.

The gap is that consumer vaults receive the helper file (via `files[]` with `tag: "platform"`) but no SKILL.md tells the LLM to invoke it. v0.95.0 closes the gap by authoring `skills/skills/plan-dispatch/SKILL.md` whose `## Steps` section guides the LLM to require + invoke the helper. This is structurally identical to how every other cowork sub-skill works (read-user-preferences, resolve-inner-circle, compose-body, etc.).

## The new `cowork:plan-dispatch` sub-skill (contract)

### File
`platform/blueprints/cowork/skills/skills/plan-dispatch/SKILL.md`

### Inputs
```
{
  engagement_id:        string,    // required — match an entry in vault-config.md
  cadence:              string,    // required — "morning" | "midday" | "eod" | "weekly" | "monthly"
  reachable_namespaces: string[],  // required — set extracted from agent's tool list (per-orchestrator pre-flight step 3d.1)
  vault_root:           string,    // optional — vault path (defaults to cwd-based resolution)
}
```

### Outputs (the 7-key contract returned)
```
{
  dispatch_plan:    [...],   // ordered kind entries, cadence-aware via cadence_order; same per-entry shape as today's planDispatch return
  voice_contract:   "...",   // composed personality + hard-rules header string (today's composeVoiceContract output)
  microscopes:      {...},   // kind_name → microscope body (read at compose time, today via step 3d.2b)
  siblings:         {...},   // kind_name → [{name, body}] (today via step 3d.2c)
  allowlist:        {...},   // inner-circle resolver output { resolved, unresolved, phone_filter_list } (today via step 3e)
  render_aspects:   {...},   // FINAL composed (type_bundle ⨁ overrides ⨁ ad_hoc)
  cadence_order:    [...],   // FINAL composed for THIS cadence
  kind_titles:      {...},   // kind_name → title (kind-titles.json + per-kind microscope title overrides)
  dispatch_mode:    "prefs"|"legacy",  // legacy mode supported through v0.95.0; v0.95.1 may drop
  prefs_status:     "...",   // pass-through from read-user-preferences for orchestrator's Notice composition
}
```

### `## Steps` (authoritative; abbreviated for design)

1. READ `.claude/skills/cowork/skills/check-vault-routing/SKILL.md` ... `{ required: ["obsidian"] }` (mirrors today's orchestrator pre-flight step 1)
2. READ `.claude/skills/cowork/skills/read-user-preferences/SKILL.md` ... `{}` → capture `prefs_result`
3. Read `vault-config.md` engagement record by id; capture `engagement` + `overrides` (when present)
4. Read engagement-type JSON at `spice/cowork/context/engagement-types/<engagement.type>.json`; capture as `bundle`
5. Compose final preferences: invoke `composeFinalPreferences({ bundle, overrides, ad_hoc_prefs })` (NEW helper export) → returns `{ render_aspects, cadence_order, voice, microscopes_registry, tripwire_aspects }`. (Schema delta — see § The composeFinalPreferences contract.)
6. Read `data/kind-titles.json` via NEW `loadKindTitles({ vault_root })` helper export → returns `kind_titles` map.
7. Read per-kind microscope files at `spice/cowork/prompts/per-mcp/<kind>/microscope.md` (today's step 3d.2b). The microscopes_registry from step 5 controls which kinds are read; absent registry falls back to filesystem scan (backward-compat).
8. Read per-kind siblings (today's step 3d.2c).
9. Invoke `planDispatch({ prefs, reachableNamespaces, mcpSkillMap, microscopes })` (existing helper) → `dispatch_plan[]`.
10. Reorder `dispatch_plan[]` per `cadence_order[cadence]` if specified in final preferences.
11. Invoke `composeVoiceContract(prefs.personality, prefs.effective_hard_rules)` → `voice_contract`.
12. Read `engagement.inner_circle_people[]` and call `cowork:resolve-person` per name (today's step 3e). Invoke `composeInnerCircleAllowlist(resolverOutputs)` → `allowlist`.
13. Return the 7-key contract.

### The `composeFinalPreferences` contract (NEW helper export)

```js
function composeFinalPreferences({ bundle, overrides, ad_hoc_prefs }) {
  // Bundle = engagement-type JSON (e.g. personal.json) parsed.
  // Overrides = engagement.overrides block from vault-config.md (may be absent).
  // ad_hoc_prefs = optional runtime overrides (e.g. user-preferences.md priorities reorder).

  // Composition order: bundle.render_aspects ⨁ overrides.render_aspects ⨁ ad_hoc.render_aspects
  // For arrays (cadence_order, tripwire_aspects): overrides REPLACES bundle (not merge)
  // For objects (render_aspects, voice, microscopes): overrides MERGES with bundle (override wins per-key)

  return {
    render_aspects: { ... },       // merged
    cadence_order: { ... },        // per-cadence; bundle provides defaults; overrides replaces per-cadence
    voice: { ... },                // merged (vibe, formality, length, pep_talk, notes)
    microscopes_registry: { ... }, // kind_name -> microscope file path (or filesystem scan when absent)
    tripwire_aspects: [ ... ],     // overrides REPLACES bundle's tripwire_aspects array
  };
}
```

### Backward-compat behavior

When the engagement record has NO `overrides:` block, `composeFinalPreferences` falls through to bundle defaults verbatim — observable behavior unchanged from v0.94.x. New cadence_order key when absent: defaults to canonical insertion order of `prefs.priorities` (today's behavior).

## The cohesion sweep (what each orchestrator becomes)

Pre-flight steps 3a/3b/3c/3d/3e in each orchestrator (~100 lines of pseudocode) collapse to ONE invocation:

```
3a. **Read recent memory.** [unchanged — cadence-specific tier/window]
3b. **Plan dispatch.** READ `.claude/skills/cowork/skills/plan-dispatch/SKILL.md` in full and
    follow its `## Steps` section with { engagement_id, cadence: "<cadence>", reachable_namespaces }.
    Capture the 7-key result as `plan`. If plan.dispatch_mode == "legacy", emit fallback Notice
    per existing template; legacy gather sequence (steps 5-12 below) fires unchanged.
3c. **(reserved)** — no inline dispatch logic. plan.allowlist + plan.dispatch_plan + plan.voice_contract
    are the inputs to Gather + Write phases.
4. READ `.claude/skills/cowork/skills/ensure-daily-note/SKILL.md` [unchanged].
```

The Gather phase reads `plan.dispatch_plan` and iterates exactly as today, except it consults `plan.kind_titles[kind_name]` instead of inlining the kind→title map. The Write phase consults `plan.voice_contract` exactly as today (step 14b — prepend to prompt_body) plus `plan.microscopes` and `plan.allowlist`. No semantic change to the gather/write/verify phases.

Morning-briefing keeps its `3b. Gather semantic echoes` step (today only present in morning-briefing); it becomes `3a.5. Gather semantic echoes` (sub-step of memory phase) for clarity. The other 4 cadences gain the ability to add semantic echoes by setting `render_aspects.semantic_related = "include"` in their cadence override (today only morning-briefing has it).

### Why per-orchestrator step numbering converges

After the refactor, all 5 orchestrators have:
- 1, 1b (verbal commitment) — unchanged
- 2 (resolve engagement, read engagement-type bundle) — unchanged (but consults the bundle WITHOUT type-discriminating skill code)
- 3 (date-context) — unchanged
- 3a (memory read) — unchanged shape; cadence-specific tier/window
- 3a.5 (semantic echoes — ONLY when render_aspects.semantic_related == "include"; morning-briefing today)
- 3b (plan-dispatch invocation — single READ; produces all of dispatch_plan, voice_contract, microscopes, siblings, allowlist, render_aspects, cadence_order, kind_titles)
- 4 (ensure-daily-note) — unchanged

The drift surface area drops from "5 orchestrators × ~5 sub-steps each, each potentially renumbered" to "5 orchestrators × 1 sub-skill READ each."

## The canonical orchestrator template

`Docs/agent-guides/cowork-orchestrator-template.md` (NEW). Captures:

1. Required H1 + `[!warning]+ CRITICAL: output path` callout (v0.90.2 invariant)
2. Required sections in order: `## Inputs` → `## Pre-flight` → `## Gather` → (optional `## Decide` for midday only) → `## Write` → `## Verify` → `## State` (optional — midday omits) → `## Done` → `## Harness testing`
3. Required Pre-flight steps in order: `1, 1b, 2, 3, 3a, [3a.5], 3b, 4`
4. The `cowork:plan-dispatch` invocation contract at step 3b
5. Required body-shape regex set (SpaceNavButtons canonical pattern + `[!info]-` synopsis + `[!example]+` per-section + `[!tip]` close)
6. Failure-token vocabulary: `failed:contract-violation:<field>` | `failed:filesystem:<reason>` | `failed:write-undersized:<bytes>` | `failed:compose-body:<status>`

A v0.96.0+ candidate skill `cowork:audit-cohesion` could read this template and validate the 5 orchestrators against it; v0.95.0 ships the template as a doc-only contract.
