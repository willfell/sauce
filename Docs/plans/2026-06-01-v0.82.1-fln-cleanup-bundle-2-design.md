## 2. Per-FLN design

### 2.1 FLN-v82-2 — per-source reset before fragment loop

**Problem.** `applyRuleFragment` at `platform/install.js:1303` reads the existing rule file, then unconditionally pushes `frag.fragment` into `existing.contributions[sourceName]`. Every install re-runs every fragment → file grows monotonically. HEAD-of-v0.82.0 has `ranch/rules/cowork.json` at **7,929 lines / 281 entries / 16 group-keys** (~13× duplication).

**S0 discovery (2026-06-01 evening).** The bloat has TWO shapes, not one:

| Shape | Group count | Bodies per group | Bloat pattern |
| --- | --- | --- | --- |
| `scope: {path_glob: "..."}` (object) | 15 groups | 1 unique body | Each duplicated ~13× |
| `scope: "..."` (string) + `naming_pattern` field | 1 supergroup, 7 scopes | **3 body variants per scope** (manifest evolved over cycles, old variants never cleaned up) | Each variant duplicated ~1× / 1× / 11× |

A naive `(path_glob, extends)` dedup key would (a) miss the string-scope entries entirely (path_glob is undefined), and (b) collapse all 91 of them to one entry, randomly keeping the OLDEST body variant — catastrophic data loss.

**Design — per-source reset before fragment loop.**

The fundamental insight: the rules file should reflect EXACTLY what the current manifest declares. Re-installs should rewrite this source's contributions from scratch, not append to a growing pile. Per-fragment dedup logic is the wrong abstraction; per-source replacement is the right one.

Implementation:

1. **NEW helper `resetSourceContributions(tp, target, sourceName, variables, history, git)`** in `install.js`. Reads `<rules_path>/<target>.json`, sets `existing.contributions[sourceName] = []`, writes back. Handles missing file as no-op. Same C4-malformed-JSON guard as `applyRuleFragment`.
2. **Modify the per-item install loop** (`install.js` around line 1043) — before the `for (const frag of mech.rule_fragments || [])` loop, collect all unique `target`s the mech contributes to, then call `resetSourceContributions(tp, target, mech.name, ...)` once per (source, target) pair.
3. **`applyRuleFragment` body: UNCHANGED.** It still appends per-call, preserving the HC-RF1/2/3 contract (legacy-shape wrap; multi-fragment-same-source accumulation).

**Why this design.**

- `applyRuleFragment` stays a per-fragment append helper. HC-RF1/2/3 tests stay green without modification.
- The "reset once per source per install run" responsibility lives in the caller (the install loop), which is the right scope — install loop knows when a source begins processing.
- Within one install run, the loop calls reset → appends N fragments → final array contains exactly N entries.
- Across install runs, each run resets before appending, so files always match the current manifest.

**Cleanup mechanic.** No separate cleanup commit. When S8's dogfood install runs against today's bloated `ranch/rules/cowork.json`, the per-item reset wipes cowork's contributions, then the fragment loop re-populates with the current manifest's ~20 fragments. Git diff at S8 shows `ranch/rules/cowork.json: 7929 → ~600 lines deleted`.

**Risk replacing the original "dedup-key over-broad" risk.** The new design's failure mode is different: if a non-cowork source had legitimately-orphaned entries in the rules file (entries that came from an old version of the source that's no longer in the manifest), this reset would wipe them. That's actually the desired behavior (orphaned-entry cleanup), but worth documenting.

### 2.2 FLN-v82-3 — `parseYamlIsh` hyphenated-key support

**Problem.** `context-builder-dry-run.js:35`'s flat-key regex `/^([a-z_]+):\s*(.*)$/` silently drops keys with hyphens. Custom MCP kinds with hyphens — `lharries-whatsapp`, `sharepoint-online`, `microsoft-graph` — can't appear in `user-preferences.md` today. Surfaced during HC-V0820-A4 authoring (had to switch test kind from `my-custom-kind` to `notion` for parser compatibility).

**Design.** Widen the regex to `/^([a-z_][a-z0-9_-]*):\s*(.*)$/`. First char retains the `[a-z_]` constraint (no leading hyphen or digit); remaining chars accept `[a-z0-9_-]`. One-line change.

**Test home.** HC-V0821-B1 lands in `run-helper-cases.js` (the canonical home for cowork-helper unit tests, alongside the existing applyRuleFragment cases). Exercises `_parseYamlIsh` via the `module.exports._parseYamlIsh` accessor already wired at `context-builder-dry-run.js:352`.

**No version bump.** This is a code path inside a helper file. The helper is `require()`'d by both test code (test loads via relative path) and the live skill body (production load path). Neither is gated by cowork's version short-circuit at `install.js:223`. Workshop dogfood at S9 re-materializes the helper if it's listed in cowork's `files[]` (verify at S0). If a hidden version-gate test surfaces, scope expands to cowork 0.21.0 → 0.21.1 — but the v0.79.0/v0.80.0/v0.82.0 precedent is that helper-file changes don't gate.

### 2.3 FLN-v81-1 — semver-helper extraction

**Problem.** Three test files duplicate `/^0\.(8|9|[12]\d)\.\d+$/` to assert cowork version ≥ 0.8.0. Pattern accepts 0.8.x through 0.29.x. Bumping cowork past 0.29.x will require touching all three files — repeat of the v0.81.0 widen-from-0.19.x scramble.

**Design.** Pure refactor — no behavior change, no failing test.

1. **NEW file:** `platform/test/helpers/semver-helper.js`. Exports:
   - `versionAtLeast(actualStr, minStr) → boolean` — parses both as `MAJOR.MINOR.PATCH`, compares numerically. Returns `false` for malformed inputs.
   - `parseSemver(str) → {major, minor, patch} | null` — internal but exported for tests.
2. **Refactor 3 sites** to use `versionAtLeast(m.version, '0.8.0')`:
   - `platform/test/run-claude-surface.js:562`
   - `platform/test/run-cowork-smoke.js:435`
   - `platform/test/run-helper-cases.js:6880`

Assertion messages preserved verbatim. No new test cases added (the helper is exercised indirectly via the three existing assertions).

**Out of scope.** The narrower patterns at `run-helper-cases.js:6702/6718/6732` (people 0.3.x-0.4.x; products 0.2.x-0.3.x; teams 0.2.x-0.3.x). FLN-v81-1's named scope is cowork-specific. Refactoring those is a separate follow-up cleanup.

### 2.4 FLN-v79-5 — CS-MIG-1 manifest-derivation

**Problem.** The CS-MIG-1 case at `run-claude-surface.js:556-606` hardcodes four counts (47 total, 38 skill, 3 command, 6 resolver). Every claude_surface[] addition forces a lockstep bump in this file. v0.79.0/v0.80.0/v0.81.0 each had this bump as a stage chore (v0.81.0's S7 was the most recent: 37→38 skill, 46→47 contributions).

**Design.** Convert hardcoded counts to manifest-derived expectations.

```js
// At top of caseCSMIG1CoworkAggregation()
const cs = bpMan.claude_surface || [];
const expected = {
  skill: cs.filter(e => e.kind === "skill").length,
  command: cs.filter(e => e.kind === "command").length,
  resolver: cs.filter(e => e.kind === "claude_md_row" && e.table === "resolvers").length,
  total: cs.length,
};

// Replace hardcoded counts:
assertEq("CS-MIG-1: contributions match manifest claude_surface[] length",
  out.registry.contributions["cowork"].length, expected.total);
assertEq("CS-MIG-1: skill entries match manifest", skillEntries.length, expected.skill);
assertEq("CS-MIG-1: command entries match manifest", cmdEntries.length, expected.command);
assertEq("CS-MIG-1: resolver rows match manifest", coworkRows.length, expected.resolver);
```

**Sentinel tradeoff (accepted).** Hardcoded counts catch unintentional manifest deletions ("someone accidentally drops a claude_surface[] entry → CI red → review forces verification"). Derived counts only catch aggregator drops, not intentional manifest changes. Mitigation: the existing dest-substitution assertions (lines 587-590) continue to validate that each skill dest starts with `.claude/skills/cowork/`, which catches structural aggregator bugs.

**Assertion message wording.** Drop the hardcoded `"47 contributions (38 skill + 3 command + 6 claude_md_row)"` parenthetical; the manifest is the source of truth now. Keep the case name `caseCSMIG1CoworkAggregation` and the test ID `CS-MIG-1` — this is a mechanic refactor, not a new case.

**CS-MIG-1 count change posture: UNCHANGED** because manifest still has 47 entries. Only the assertion mechanic changes.
