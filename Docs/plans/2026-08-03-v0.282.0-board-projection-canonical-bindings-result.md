## Root cause

**Mode 1 — mints born un-projectable.** `card-intake`'s `projectPrefix` derived
the vault-relative project prefix from *caller input* (`spec.source_board`),
collapsing to `''` for the absolute `board_path` the intake skill actually
passes. Atlases got an absolute `source_board`/`kanban_board` and a
project-relative `epic_board`; slices got a project-relative
`task_parent`/`source_board`. None satisfy `canonicalWorkspacePath`, so every
projection threw `does not bind its canonical parent board`.

**Mode 2 — discard orphans its own line.** `discardCardCore` took its board
target only from a *successful* `canonicalEpicProjection`. Any refusal (including
a Mode-1 atlas) fell back to the parent board, which carries no slice lines — so
it removed nothing and unlinked the note anyway. The surviving sub-board line
then made every later projection of that epic throw `epic slice <X> note is
missing`. Mode 1 manufactures Mode 2; each orphan then poisons the epic
independently.

## Process

systematic-debugging → TDD. Mode 1 was **verified live, not assumed**: a
reproduction minted a fresh epic through the real intake rail into a canonical
vault shape using the skill's exact arguments and ran the real
`canonicalEpicProjection` against the result — absolute `source_board`,
project-relative backlinks, `PROJECTION THREW`. A read-only sweep of all 63
epics on the live board then confirmed the cascade (the 2 orphaned sub-board
lines sat in the same epic as the absolute atlas), and a cross-vault scan found
the same rot in `ero-sauce/planner-agent-integration` and
`headspace-sauce/spice/projects/sauce` — which is why the heal shipped as a
reusable verb rather than a one-off script.

All three increments were driven red → green with the failure watched:

1. Intake bindings — 6 assertions red (each wrong field, plus the projection

2. Discard orphan — red on `discard targets the slice's OWN epic sub-board`,
   then green.
3. `heal-epic-bindings` — red on `commandHealEpicBindings is not a function`,
   then green.

## Carry-forward

- **`run-sticky-notes-render-guards.js` is flaky on `main`.** Measured on an
  unmodified base tree: **3 of 6 runs failed** with `PERF-7-HARNESS:
  asynchronous fixtures did not finish`. It is inside `release:preflight`, so it
  can wedge `prepare-release` on merge. Deliberately not fixed here (this cycle
  stays isolated to the control plane). Needs its own cycle: the harness's async
  fixture completion is racing rather than awaited.
- **Concurrent vault writers vs. the heal.** The live `ero-egnyte-mcp` board was
  being actively mutated by another session *during* this cycle (dozens of notes
  rewritten mid-investigation; the `Build Observability` atlas and its two orphan
  lines were repaired by that other writer between the diagnosis and the heal
  dry-run). `heal-epic-bindings` takes the selector lock, but a non-coordinator
  writer (a live Codex session, Obsidian Sync from another machine) is outside
  that boundary. Running the heal against a board with a live loop session is
  unsafe; there is currently no cross-process guard for that.
- **`canonicalEpicSurface` now refuses legacy epics.** With `route.board_ref`
  vault-relative, intake's direct-execution path refuses to route into an epic
  whose atlas still carries a project-relative `epic_board`. That is correct
  (it prevents minting more slices into an un-projectable epic) and the heal is
  the remedy, but it means un-healed vaults will see intake refusals rather than
  silent breakage.
