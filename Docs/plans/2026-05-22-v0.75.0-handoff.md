## v0.75.1 carry-forwards (real issues surfaced during deploy)

### §1 — `--bump-pins` should detect brew install when `workshop_path` is null

**Symptom:** all 4 consumer vaults have `workshop_path: null` in their `ranch/platform-installed.json` — even after years of normal updates. `sauce update --bump-pins` fails with:

```
TypeError [ERR_INVALID_ARG_TYPE]: The "path" argument must be of type string. Received undefined
    at Object.join (node:path:1339:7)
    at handleBumpPins (.../cmd-update.js:30:39)
```

**Fix:** in `platform/cli/cmd-update.js`, when `installed.workshop_path` is null, fall back to one of:
- `process.execPath` ancestry walking — find the `libexec` ancestor of the running sauce binary.
- Hardcoded `brew --prefix sauce` evaluation — `/opt/homebrew/opt/sauce/libexec` (the symlink that auto-follows the current version).
- An explicit `--workshop-path <path>` CLI override.

Probably best to use `process.execPath` ancestry since it's the only path that knows where the running binary came from. The handler is at `cmd-update.js:30`-ish. Add a `getWorkshopPath(installed)` helper that returns `installed.workshop_path || resolveBrewWorkshopPath()`.

**Side note:** The workshop's own self-install (`node platform/test/run-install.js .`) hits the same null-workshop_path issue when `sauce update --bump-pins` is called from the workshop dir. This is technically a different case (workshop-as-vault) but the same fallback fix handles both.

### §2 — Standard `sauce update` git-fetch step is broken for brew-distributed sauce

**Symptom:** after `sauce update --bump-pins` writes the new subscription file, the handler falls through to the "standard sauce update flow" (`cmd-update.js:128`-ish) which calls `git fetch origin main` against the consumer vault. Consumer vaults aren't git repos → fatal: not a git repository.

This is a **pre-existing bug**, not introduced by v0.75.0. The git-fetch path assumes the pre-v0.36 `pantry/` git-checkout layout. Modern brew-distributed sauce has pantry shipped via brew; nothing to fetch.

**Workaround used during this deploy:** run `sauce reinstall --vault <path>` after `sauce update --bump-pins`. `reinstall` is the brew-era equivalent of the legacy `update`'s git-pull-then-materialize flow.

**Fix:** in `platform/cli/cmd-update.js`, detect brew-distributed context (presence of `/opt/homebrew/Cellar/sauce/.../libexec` in `process.execPath`, or absence of `.git/` in the vault) and skip the git-fetch/reset steps; jump straight to the materialization step (which `cmd-reinstall.js` already implements). Reuse `cmd-reinstall.js`'s implementation; `cmd-update.js` becomes a thin wrapper that calls reinstall under the new layout.

### §3 — New mechanism subscription doesn't auto-add on bump-pins (design-intent; documentation only)

This is **correct behavior** per v0.75.0 design (`--bump-pins` preserves opt-in subscriptions). New-in-workshop mechanisms get a "(new in workshop — not subscribed, skipped)" line in the diff output. The user has to opt in explicitly.

For v0.75.0 deploy I worked around this by `jq`-adding `smart-connections-bridge` to each subscription before running `--bump-pins`. For future cycles: document this in `commands/install.md`'s upgrade section as an explicit step the user runs.

Possible v0.75.x: a `sauce update --subscribe <mechanism>=<version>` flag that explicitly subscribes a single new mechanism.

### §4 — sc-bridge `--quiet` / `--json` flags parsed but inert

Already noted during S6 review. The flags exist in the argv parser but no codepath consumes them. The bridge's stdout is JSON regardless; stderr warnings (e.g., "skipping unparseable") are unsuppressable. Polish target for v0.75.x.

### §5 — `installed workshop_version` field in `platform-installed.json` stays null after reinstall

Per-blueprint and per-mechanism versions DO update; only the top-level `workshop_version` field on `platform-installed.json` doesn't get refreshed. Pre-existing tracking issue; unrelated to v0.75.0. Worth investigating during a v0.75.x cleanup pass.

### §6 — Bridge cold-start latency: no data yet

`@xenova/transformers` cold-load takes ~1.7s on macOS arm64 (S0 measurement). For morning-briefing's 5-event cap, that's ~8s aggregate worst case if each call cold-loads. The bridge does not cache across invocations in v0.1.0.

Data point we want: first real morning-briefing fire's wall-clock from "cron tick" to "atomic note written". If it's >15s consistently, prioritize `--batch` (JSON-on-stdin) + `.local/cache/sc-bridge-index.bin` in v0.75.1. If it's tolerable, defer.
