**164 untracked findings aggregate.** Classifying each by who wrote its `status_changed_at` — the coordinator emits `…THH:MM:SS.mmmZ` and nothing else does — split them **64 coordinator-stamped** (all before this clone's ledger epoch: cross-clone residue from the 2026-07-31 machine migration, legitimate and not locally actionable) against **100 foreign-stamped** (99 with a non-coordinator stamp shape, 1 — `EM-5` — with no stamp at all). Of the 100 foreign: 85 are the pre-retirement `ero_loop` era on egnyte, 11 are sauce's pre-shared-rail era (latest 2026-07-26), 1 is an `in_progress` note rather than a completion, and 3 are `EM-4/5/6` — stamped `2026-07-31`, merged as PR #126 on 2026-08-03.

**The frequency verdict was negative.** Under the current shared rail (2026-08-01 onward) out-of-band completion has occurred **exactly once, covering three slices, in four days**. That sample cannot size a verb, and it emphatically cannot justify batch-claim.

### What justified the cycle instead

`platform/mechanisms/kanban-status-sync/kanban-status-sync.js:120` — `KanbanStatusSyncInit` runs at **vault boot in all three consumer vaults**, discovers every note carrying `kanban-plugin: board` (the delivery epic boards do), and rewrites `status`, `status_prev`, and `status_changed_at` (bare date) through `processFrontMatter` whenever a card's column changed.

So dragging a slice into *Completed* in Obsidian is a completion the ledger never sees, produced by shipped, sanctioned platform code, on a path the coordinator's repo-local `.git/sauce-autoloop/locks` cannot observe. The bare-date signature on the foreign stamps is that mechanism's signature.

**This is the finding that sized the cycle: an always-on, one-gesture leak in every vault — not the rare batch-PR event the program doc predicted.** The Director's decision was to legitimize the gesture rather than forbid it, because it is one the Director uses deliberately. The batch-PR frequency was never the justification.

## What shipped

1. **The `adopted` authority tier** — `delivery.topology.resolveSliceAuthority` gained an `adopted` operand and a third source. `hasRecord && adopted && ledgerStatus === 'completed'` → `{status: 'completed', doneProven: false, source: 'adopted', demoted: false}`; every other case is byte-for-byte today's rules. `assertProjectableStatus` now accepts a `completed` verdict that is `doneProven === true` **or** `source === 'adopted'`, and nothing else. `doneProven` still means exactly "carries successful deployment receipts" and is `false` for every adopted record, permanently. The invariant that matters survives: the board still cannot mark itself done.
2. **The `adopt` verb** — `adopt --card <exact name> --pr <n> --merge-sha <40-hex> --reason <why> --json`. It ratifies a declaration already sitting unrecorded on the board; it never invents one. Refusals, all before any mutation: `adopt_record_exists`, `adopt_card_not_found`, `adopt_not_declared_complete`, `adopt_sha_unreachable`, `adopt_pr_not_merged`, `adopt_pr_mismatch`, `adopt_pr_not_found`, `adopt_reason_required`, `adopt_conflict`. One ledger record, `phase: 'adopted'`, carrying `adoption: {pr, merge_sha, reason, verified, adopted_at}`, then the standard epic projection refresh — `persist`, `attemptProjection`, `persist`, exactly like park/resume/amend-contract, which is what refreshes the stale `kanban_column` a Kanban drag leaves behind, rolls the epic atlas up, and establishes the record's first `card_note_sha` baseline. Literal replay is `no_op: true` and never projects.
3. **Provenance classification in `board-health`** — `untrackedMemberFinding` gained `stamp` and `provenance`, with a class-specific `remedy`: `cross-clone: no action in this clone` for coordinator provenance, **`adopt`** for foreign. The receipt gains `untracked_members_by_provenance: {coordinator, foreign}` so 164 undifferentiated findings collapse to a readable pair. `healthy` is unaffected — this is classification, not a check.
4. **Foreign-write detection** — `card_note_sha` (sha256 of the bytes actually on disk after any coordinator write of a tracked card's note) and `foreign_write: {detected_at, expected_sha, actual_sha}`, plus a sixth `board-health` check, `foreign_writes`.
5. **Concurrent-modification guards** — `heal-epic-bindings --apply` gained genuine second-writer detection; `restructure` and `reconcile-metadata --parked-rebind` gained a stable shared error code for a condition they already detected.

## Director ruling: `phase: 'completed'` was unshippable

The spec's §4.2 said an adopted record gets `phase: 'completed'`. **It does not, and could not.**

`completed` is a **card-status vocabulary word, not a ledger phase**. A record carrying it as a phase is simultaneously:

- **invisible to `projectionMapping`**, which has no `completed` entry — so the adoption never reaches the board and the epic never rolls up, defeating the entire point of the verb; and
- **permanently active** in `activeRecords()`, which excludes only `TERMINAL` phases — so an adopted card blocks sibling-slice claims and counts against `MAX_ACTIVE` forever, wedging the loop.

The Director's ruling introduced a **genuine new ledger phase, `adopted`**: added to `TERMINAL` and to `projectionMapping` as `{column: 'Completed', status: 'completed', complete: true}`, so an adopted record is excluded from `activeRecords()` exactly like `deployed`. Both `resolveSliceAuthority` call sites pass `adopted: Boolean(record.adoption)`, so no consumer needs to special-case adoption.

One consequence had to be chased down in-cycle: `effectiveProjectionMapping`'s legacy-completion demotion would have demoted the freshly-projectable `adopted` phase straight back to `implementing` on every read — `commandStatus` would wedge on phantom `board_drift`/`projection_problems`, and the advertised drift remedy (single-card reconcile) would rewrite the board line and note frontmatter back to in-progress, **permanently un-completing an adopted slice on every repair pass**. Records carrying `adoption` are now exempt from that demotion.

## Spec interpretations and divergences (Director-visible)

The design spec has been amended in place with a dated **Post-implementation corrections** section rather than silently rewritten. The divergences:

- **`adopt_pr_not_found` is new** and not in the spec's refusal list. The degrade to `verified: 'git'` is reserved for **genuine `gh` unavailability** — spawn `ENOENT` (execFileSync with no shell, so a missing binary is always `ENOENT`), or gh reporting it is not authenticated. Every other gh failure — network errors, rate limits, HTTP 401, `EACCES`, a JSON parse failure, or gh answering successfully that the PR does not exist or is invalid — **refuses**. Fail-closed is deliberate: an unrecognized gh failure means "this PR reference could not be verified", not "gh must be down". A present-but-wrong PR is never durably recorded at a degraded tier. `adopt_card_not_found` likewise covers a named card with no note under `cards_root`.
- **`card_note_sha` stamping is broader than §6.1 described.** It is stamped through one shared helper (`stampCardNoteSha`) wherever the coordinator writes a tracked card's note — `projectCard` (including the refresh `adopt` runs), `heal-epic-bindings --apply`, the discard dependent scan, `reconcile-metadata` (single-card and `--contract-frontmatter-restamp --apply`), `reconcile-dependencies --apply`, and `restructure` — so the coordinator never reports its own repair as a foreign write. `restructure` stamps inside its `card_path` rebind, the one ledger-touching step of a member move, so the hash describes the bytes at the note's **final** path; its scaffold writes refuse any pre-existing target and therefore never touch a tracked card's note. The helper always re-reads the file after the write attempt, so the recorded hash reflects bytes actually on disk rather than merely intended bytes. **`heal-epic-bindings` is therefore now a ledger writer**, which its own docstring previously denied; it persists only when it actually stamped something, so a run that touches nothing tracked stays a genuine no-op write. A detected `foreign_write` forces ledger persistence and appears on `commandReconcile`'s receipt.
- **`foreign_writes` detection semantics.** The finding is **edge-triggered on detection but level-triggered within the ledger for a window**: it lives on the record from detection until the next projection of that card clears it, and board-health never clears it itself. A still-diverged note therefore reports **once** and is then re-baselined, not continuously. The sixth check reports **only projectable phases** — `projectCard` is the only thing that ever clears the finding and it requires a phase with a board projection, so a finding on a `discarded`/`failed`/`cancelled` record could never be cleared and would hold an hourly unattended sweep unhealthy forever. A finding no projection can resolve is not actionable and must not hold the board unhealthy.
- **§6.2 is narrower than it reads for two of the three verbs.** `restructure` and `reconcile-metadata --parked-rebind` **already** detected a second writer correctly via their crash-recovery preimage machinery. What changed is only the **error shape**: their third-state failures now refuse with `concurrent_modification` under `restructure-refused` / `reconcile-metadata-refused` instead of throwing a bare `Error`, so a caller can machine-identify the condition. Crash-recovery resume paths are byte-for-byte unchanged. Containment guards, operand validation, and literal-replay refusals were deliberately **not** converted — they are not second-writer conditions. Only `heal-epic-bindings` gained genuinely new detection: `planEpicBindingHeal` records `preimage_sha` for every file it reads, and `--apply` re-reads each target immediately before writing, refusing with the changed paths named and **zero vault and zero ledger writes** if anything moved. A target **deleted or renamed** between plan and apply refuses through that same code rather than leaking `ENOENT` — a vanished target is evidence of a concurrent writer, not a separate failure mode.
- The spec's §6.2 framing that the doc warning "becomes an enforced precondition" is now literally true: the prose sentence in `delivery-board.md` ("never run `--apply` against a board with a live loop session or an active cross-machine sync") has been replaced by a description of the enforced guard.
- **`schemas-index.json` judgment call.** `adoption`, `card_note_sha`, and `foreign_write` are durable per-card ledger fields, but the registry has no dedicated coordinator-ledger-record entry. They were registered **description-only** by extending the `autoloop-card-lease` entry's `notes` (the one entry describing per-card coordinator state-record fields), explicitly framed as sibling fields with independent lifecycles. **No schema version was bumped.** A future cycle may prefer to split them into their own `learned-state-schema` entry.

## Deliberately deferred: batch-claim / variable slice granularity

Scope item 3 was **deferred, not dropped**. One out-of-band incident in four days under the shared rail cannot size a batch-claim mechanism; building it on that evidence would be prediction, not measurement. The `adopt` verb covers the observed case (`EM-4/5/6`, PR #126) with recorded provenance. **It remains available as a later cycle** — and the provenance classification shipped here is precisely the instrument that would size it, since `untracked_members_by_provenance` now separates real out-of-band completions from cross-clone residue without a throwaway script.

## Final whole-branch review — fix wave (2026-08-05)

A whole-branch review before close found four things and they were fixed on the branch, not deferred.

1. **`adopt` never projected, and three shipped documents said it did.** `commandAdopt` wrote one record and returned; the spec, this result doc, and `delivery-board.md` all described "the standard epic projection refresh". That gap was not cosmetic. The motivating gesture is a Director dragging a slice into *Completed* in Obsidian, and `KanbanStatusSync` rewrites only `status`/`status_prev`/`status_changed_at` — never `kanban_column`, never the epic atlas, never the parent board. Reproduced on a scaffold, a record-only adopt left `projectionMetadataProblem` reporting `expected_column "Completed"` vs `actual "In Progress"` and `projectionBoardDrift` reporting `expected_status "done"` vs `actual "active"`, and `batch-runner.js` `readiness()` **throws** on either being non-empty: using the verb exactly as documented stopped the unattended loop until someone ran `reconcile`. `adopt` now follows the park/resume/amend-contract discipline — persist, `attemptProjection`, persist — so the projection's own record mutations (`projection_reconciled_at` and the `card_note_sha` baseline an adopted record otherwise never had) are durable. The literal-replay path still returns before any projection; a replaying adopt that re-projected would re-stamp `status_changed_at` on every call. `AD-KANBAN-DRAG` pins the chain end to end on a **real on-disk ledger under the real nested locks** (`selector` held while `attemptProjection` takes `completion-projection`), and the nesting was additionally verified by a genuine CLI run in a throwaway clone: zero locks left behind, clean `status` afterwards.
2. **A verb was named that does not emit the code.** `delivery-board.md` said `reconcile-metadata --apply` emits `concurrent_modification`. It does not — all four such refusals live in `commandRebindParkedMetadata`, i.e. `--parked-rebind --apply`. Corrected, and the known-open count below corrected with it.
3. **The "every coordinator write" invariant was false for three writers.** `reconcile-dependencies --apply` (the direct sibling of the discard dependent scan, which *is* stamped), `reconcile-metadata --contract-frontmatter-restamp --apply`, and `restructure` all wrote tracked card notes without stamping `card_note_sha`, so running any of them made the next projection report a foreign writer that was the coordinator itself. All three now stamp through the same single helper. `restructure` stamps inside `rebindTrackedCardPath` — the one ledger-touching step of a member move, already under the card gate lock with the pass's own persist — so the hash describes the bytes at the note's **final** path after the move and the `card_path` rebind, with no second write path bolted on. `restructure`'s scaffold writes are the one genuine exemption: they refuse any pre-existing target, so they only ever create fresh epic surfaces. `FW-DEPS`/`FW-RESTAMP`/`FW-RESTRUCTURE` each drive the real command against a real on-disk ledger with a genuine pre-write baseline and re-read the record from disk.
4. **Cycle-close artifacts were incomplete.** Items 4, 5 and 8 of the nine-item list in `build-test-verify.md` were missing and are now written; see § Cycle-close artifacts below.

Every assertion added in this wave was watched fail against the unfixed code first, for the reason it names — the rule this cycle learned twice the hard way.

## Lessons worth carrying

**Two separate rounds shipped tests that could not fail for the right reason.** Both were caught only by mutation-testing the assertions — deliberately breaking the implementation and confirming the test went red for the stated reason:

1. A test injected `readState: () => state` and then asserted on that same live in-memory object. It passed whether or not the coordinator ever persisted anything, proving nothing about the durability it claimed to pin. Fixed by asserting against the re-read on-disk ledger (`fix(coordinator): persist card_note_sha stamps and foreign-write clears to the on-disk ledger`).
2. A test used a regex where **exact-byte equality** was the property under test. It survived a write that changed the bytes, so the "byte-clean, zero writes" refusal guarantee was unverified (`fix(coordinator): close heal-epic-bindings concurrent-modification gaps found by mutation testing`).

The rule: **a passing test is evidence only once you have watched it fail for the reason it names.** Assertions on injected live objects, and substring/regex assertions standing in for byte equality, are the two shapes that most reliably pass vacuously.

**Evidence discipline (carried from workstream 2, and it fired again here.)** The first full preflight of this cycle was run in the background while documentation files were still being edited; `GA-P1G-ORDINARY-RELEASE` asserts the claimed worktree stays byte-clean, read the mid-edit tree, and went red on the doc files themselves. The suite's own exit code (`… > log 2>&1; echo "exit=$?"`) is what surfaced it — a `tail` pipeline would have reported the tail's zero. Preflight must be run against a **committed, clean tree**.
