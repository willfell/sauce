# MeetingLeafActions polish — design (v0.126.1 PATCH)

## Mission

Real-user repro after v0.126.0 surfaced six related bugs in the meeting-leaf-actions surface — three pre-existing, three v0.126.0-introduced or v0.126.0-exposed. All live in `helpers/meeting-leaf-actions.js` + the two creation paths (Templater `Meeting.md` template and `new_entity_buttons[0].inline_body` in the meetings manifest). This patch cycle fixes all six in one ship.

## The six bugs

### 1. `PeopleRendering.renderMentionList: unknown mode undefined` snackbar on every load (HIGH)

Pre-existing since v0.88.0 when PeopleRendering was added. The dataviewjs invocation in both the Templater template and the v0.126.0 inline_body passes `args: [dv, { mode: "mentioned_in_note", ... }, { style: "chips" }]`. But the customjs-guard view wrapper at `ranch/views/customjs-guard/view.js` already prepends `dv` to the call: `await target.call(klass, dv, ...args)`. So the actual call becomes `renderMentionList(dv, dv, { mode... }, { style })`, which binds `query = dv` (no `.mode` property), trips the unknown-mode branch, and fires `new Notice(...)` on every render.

**Fix:** drop the leading `dv` from `args`. Correct call: `args: [{ mode: "mentioned_in_note", notePath: dv.current().file.path, scopePath: "spice/people" }, { style: "chips" }]`. Apply to BOTH `templates/Meeting.md` and `manifest.json` inline_body. Pure call-signature fix; PeopleRendering itself unchanged.

**Audit-scope expansion (FLN-v126.1-A):** A repo grep for `renderMentionList` revealed the same `args: [dv, ...]` mistake in TWO MORE places, both in the `people` blueprint — every Person note has been silently firing two unknown-mode notices on every render (Meetings + Daily Mentions sections). So this cycle also patches:

- `platform/blueprints/people/templates/Template, People.md` — two invocations.
- `platform/blueprints/people/manifest.json` `new_entity_buttons[].inline_body` — two invocations (matches the template).

People blueprint version bumps too: `people` 0.6.0 → 0.6.1 (PATCH). Same description-append + lockstep pattern as meetings.

This bug has been firing on every Templater-created meeting AND every Person note since v0.88.0 — nobody noticed because they hit "dismiss" and moved on. v0.126.0 spread it to button-created meetings too. The fix is one source-line per invocation.

### 2. Edit Attendees search box doesn't filter the list (MEDIUM UX)

`_onEditAttendees` builds the people list with `[...new Set([...people, ...selected])].sort().forEach(renderRow)` and ships an `addInput` text field at the bottom — but never wires `addInput.oninput` to re-render the list with a filter. Result: typing in the box has no effect on the visible list. Only exact-match selection by full name works (and only if you happen to remember the exact case + spelling).

**Fix:** wire `addInput.oninput` to a `redrawList(filter)` helper that clears `list` and re-runs `renderRow` only for entries whose name (case-insensitive) contains the filter string. Initial render uses empty filter. Selected entries always show, even when filtered out (so a typo doesn't make picked people disappear).

### 3. "Add" creates a stub silently with no confirmation (MEDIUM UX)

Currently the `Add` button always calls `vault.create` on whatever is in `addInput.value`. With Bug 2 fixed, this becomes: if the user types "Henry Watson" intending to search-and-select an existing person, but Henry isn't in `spice/people/`, the filter shows an empty list, the user gives up and clicks Add — and a fresh `Henry Watson.md` stub is created without any confirmation.

**Fix:** the `Add` button is enabled only when (a) the input is non-empty AND (b) no entry in `people[]` matches the input exactly (case-insensitive). When enabled, its label becomes `Add "<typed name>" as new person`. When disabled, label stays `Add` and the button is greyed out. This makes the create-stub intent explicit and surfaces "you're about to make a brand new person" before the click.

### 4. Attendees bullet list shows nothing (LOW VISUAL)

The v0.126.0 inline_body emitted a `-` placeholder bullet between the PeopleRendering chip block and the Agenda SectionLabel. The placeholder is a literal markdown dash — it doesn't render attendees. The Templater template's matching block populates it from the suggester loop's `attendees` array at creation. The button path can't (attendees start empty), so the `-` stays a forever-orphan dash that confuses the visual hierarchy.

**Decision: drop the bullet stub.** The PeopleRendering chip block is the canonical attendees display once Bug 1 is fixed. The bullet list was redundant even when populated. Removing it from both the Templater template AND inline_body cleans up both creation paths.

(User chose "Keep chips only — delete the static `-` stubs" via AskUserQuestion.)

### 5. Sections vanish after returning to the note from New Task (LOW; LIKELY DERIVATIVE OF BUG 1)

After clicking New Task → ToDoCreateTask dialog → task created in today's ToDo note → user navigates back to the meeting note, all SectionLabel sections + chip block appear empty. The note's on-disk content is unchanged (verified by re-reading the file post-navigation), so this is a render-layer issue.

**Hypothesis:** Bug 1's `new Notice` throw on every PeopleRendering invocation is aborting downstream dataviewjs block dispatch in some Obsidian view-modes (Live Preview most likely). Fixing Bug 1 should incidentally fix Bug 5 because no Notice fires and no exception propagates.

**Fallback:** if Bug 5 persists after Bug 1 fix, instrument the MeetingLeafActions render path (check `dv.container.__meetingLeafRenderGen` collisions, log block-dispatch order, check for `cssclasses: wide` × Live Preview interactions). If the fix isn't trivial after instrumentation, document as a known issue and defer to v0.127.0.

### 6. Missing `---` dividers around MeetingLeafActions row (COSMETIC)

The leaf-action button row sits flush against SpaceNavButtons above and the Attendees SectionLabel below. Standard chrome grammar (per `Docs/agent-guides/note-chrome.md`) separates leaf-action rows from nav and content with horizontal rules. Currently no dividers — visually crammed.

**Fix:** insert `---` lines before and after the MeetingLeafActions dataviewjs block in both Templater template and inline_body.

## Out of scope (deferred)

- A live dataviewjs bullet-list view of `attendees:` frontmatter (rejected per user choice; chips are the canonical display).
- Per-attendee chip click-to-link (deferred — chips currently render via PeopleRendering's existing chip mode; adding click handlers is its own design).
- The same PeopleRendering args bug almost certainly affects other blueprints that invoke renderMentionList. Out of scope here; audit + fix in a follow-up audit cycle.
- A behavioral test that loads the rendered note in a JSDOM/Playwright shell and asserts no Notice fires (worth doing but adds dependency surface).
