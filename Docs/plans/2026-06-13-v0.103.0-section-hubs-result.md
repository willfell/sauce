# v0.103.0 — section hubs — result

## TL;DR

v0.102.0's Confluence-style Docs Hub renders every section as a bucket on ONE note. User observation post-dogfood on accuris: "how am I to know what is in which section within Docs?" Reframe: each section becomes a first-class entity with its own hub note. **`Docs.md` becomes a sections INDEX** (lists sections + dashboard widgets — does NOT list docs). **Each section folder gets a `<Section Name>.md` hub** that lists THIS section's docs + sub-sections + has its own `+ New Doc` and `+ New Sub-Section` buttons. File system mirrors the hierarchy, capped at 2 nesting levels (project → section → sub-section → docs). **Breadcrumb on every node** — clickable wikilink trail rendered at the top of `Docs.md`, every Section Hub, every Sub-Section Hub, and every doc-note. Migration heals existing v0.102.0 vaults end-to-end. Workshop 0.102.0 → **0.103.0**; project blueprint 1.16.0 → **1.17.0**; all other mechanism/blueprint versions UNCHANGED. ## Lessons (cycle-distinct)

### 1. Reframe-driven cycles need a "what observation broke the previous model?" headline — captured at design time, restated at result close

v0.102.0 shipped the Confluence-style Docs Hub two days ago — design Section 1 was explicit that "rows on one page" was a deliberate aesthetic choice over a tree. ONE day of accuris dogfood inverted the call: with 31 docs across 5+ sections on `global-k8s`, the user could not answer "what's in which section" from the buckets alone. The brainstorm framing was a single sentence ("how am I to know what is in which section?") and that sentence drove the whole reframe: sections become first-class entities; `Docs.md` becomes a sections INDEX, not a flat list; the hierarchy lives on the filesystem AND in the UI. **Lesson:** when a cycle is reframe-driven (vs. fast-follow), the user-observation that broke the previous model belongs in the design TL;DR + the result doc + the cycle-history entry verbatim. It anchors future readers in WHY the model changed, and prevents the next cycle from re-litigating the old shape under amnesia.

### 2. `_migrateDocNote` breadcrumb injection's frontmatter-end probe is LF-only (Windows-line-ending gotcha latent for now)

`_migrateDocNote` uses `out.indexOf("---\n", 4)` to find the closing fence of the doc-note's leading frontmatter so the breadcrumb block can be inserted immediately after. The probe matches the literal 4-char sequence `-`, `-`, `-`, `\n`. On a CRLF file (Windows-edited doc-note synced through Obsidian Sync or Dropbox), the close is `---\r\n` — the `\n` after the dashes is preceded by `\r`, so the LF-only probe walks past it and either matches a later occurrence (unlikely) or returns `-1`, in which case the breadcrumb block is silently skipped (no injection, but no failure either). The two consumer vaults this ships against (accuris, headspace) are both macOS-edited so the latent bug doesn't fire today. **Lesson:** treat string-anchored frontmatter probes as LF-only by default; for any string-match against frontmatter that needs to round-trip cleanly on Windows-edited content, normalize line endings first OR widen the probe to `/---\r?\n/`. Add a v0.103.x carry-forward to harden this probe before any cross-platform deploy.

### 3. EntityCreate `folder_prefix` double-slash safety is guaranteed by `_ensureFolder`'s `split("/").filter(Boolean)` — verified at S3 before the manifest grew sub_section_slug

The doc-note entity-create entry's `destination.folder_prefix` now composes `docs/{{prompts.section_slug}}/{{prompts.sub_section_slug}}/`. When the user doesn't supply a sub-section (depth-1 doc), `prompts.sub_section_slug` resolves to the empty string and the literal output becomes `docs/knowledge//`. The instinct at S3 was to either (a) make the trailing segment conditional via templating, or (b) post-process the path to collapse double-slashes. Neither was needed: `entity-create.js`'s `_ensureFolder(folder)` already does `folder.split("/").filter(Boolean)` which removes empty parts, so `docs/knowledge//` → `["docs", "knowledge"]` → walks `docs` then `docs/knowledge`. Confirmed by reading `_ensureFolder` at lines 619-630 BEFORE shipping the manifest extension. **Lesson:** v0.94.0's "verify helpers before design asserts them" rule (already a memory) applies equally to "verify helpers before manifest extensions assume them" — the folder_prefix safety is load-bearing on a helper invariant, not on the manifest schema, and a one-line code read was the difference between shipping cleanly and burning an S3.1.1 polish commit on a problem that didn't exist.
