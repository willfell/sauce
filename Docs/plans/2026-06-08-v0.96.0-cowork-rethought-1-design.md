## 0. Origin

Surfaced 2026-06-08 via remote-control invocation `cowork-rethought-1`, driven by an external feedback report critiquing cowork as "prose all the way down." The report proposed two foundations + five hardening layers:

**Two foundations:**
1. Replace the 6-layer prose "defense in depth" with ONE JSON schema emitted via Claude's structured outputs + ONE deterministic Node/TS writer-validator.
2. Build a markdown-stored checkmark-driven preference-learning loop — per-user online learning-to-rank over per-item features.

**Five hardening layers:** connector auto-discovery via MCP `tools/list`, memory salience/decay, cost/cadence robustness, cron heartbeat + watchdog, versioning CI.

The 2026-06-08 brainstorm session made these binding decisions:

1. **Scope:** pick highest-leverage 1-2 ideas (rejected "design the full vision" + "surgical 1 idea"). User picked THREE candidates from the menu:
   - Checkmark preference learning (the report's centerpiece + closest existing analog to queued `auto-update-prefs` slot)
   - Deterministic writer + structured-output schema (prose-defense cleanup)
   - MCP auto-discovery + generic kinds (platform-generalizability alignment)
2. **Sequencing:** one bundled MINOR (`v0.96.0`), not three sequenced cycles.
3. **Learning depth:** MVP per-kind boost/cull (rejected mid-tier per-item logistic regression + full L2R with Thompson sampling).
4. **Tick surface:** per-kind rating callout at end of each atomic note (rejected per-item inline checkboxes + Daily Hub aggregator pane).
5. **Discovery posture:** auto-detect + user confirms (rejected zero-interview + augment-only).
6. **Approach:** three-rail bundled (rejected foundation-first sequenced inside-cycle + D+L-only).
7. **Writer variant inside Rail W:** W1 sidecar determinism (rejected W2 full structured-output API rewrite for this cycle — parks for cowork-rethought-2).

The report's other workstreams (memory salience, cron heartbeat, versioning CI, full L2R) park for cowork-rethought-2 or queue as separate small cycles.

## 1. Scope

Ship three independent "rails" wired together by minimal interlocks, as one bundled v0.96.0 MINOR.

### 1.1 The three rails

- **Rail W (sidecar determinism):** Every atomic note gets a `<basename>.cowork.json` sidecar with structured metadata. Verify pass replaces regex with JSON-schema validation. `body_assertions[]` retires. Per-cadence write-run-note skills become thin shims around a generic writer with cadence-specific schema files.
- **Rail D (MCP auto-discovery):** plan-dispatch enumerates connected MCPs at fire time, classifies each into a known kind via deterministic patterns + LLM fallback (cached). User-preferences.mcps becomes auto-populated; context-builder pre-fills from classification. New unconfirmed MCPs surface in a `detected unconfigured` callout.
- **Rail L (per-kind preference learning):** Compose-body emits a `> [!todo]+ Was today useful?` rating callout. A new `cowork:learn-from-checks` sub-skill, fired post-synthesize-day, scans yesterday's atomic notes for ticks and updates per-engagement per-kind weights in `user-preferences.md` frontmatter. plan-dispatch consults learned weights when ordering `dispatch_plan[]`.

### 1.2 What ships

- **Rail W:** structured sidecar per atomic note (`.cowork.json`), 6 schema files (5 cadences + 1 cold-MB variant), 2 new helpers (`write-atomic-note-helper.js`, `validate-sidecar-helper.js`), retirement of `body_assertions[]` + regex Verify pass + half of the verbal-commitment Notice content

- **Bootstrap-vault:** 1 new Y/N question (Rail L; default Y), pre-fill of context-builder answers from Rail D classification
- **Migration:** lazy/forward-only — pre-cycle atomic notes survive without sidecars; Rail L scanner degrades to per-kind aggregate signal for pre-cycle notes

## 3. Rail W design — sidecar determinism

### 3.1 Behavior

Every atomic note gets a `<basename>.cowork.json` sidecar capturing structured metadata about what was surfaced. The markdown file stays the user-facing artifact. Verify pass validates the sidecar against a cadence-specific JSON schema; on schema-fail, both files are deleted and the orchestrator aborts.

### 3.2 Sidecar location + naming

```
spice/cowork/daily/2026/06-June/2026-06-08/
├── morning-briefing.md              ← user-facing, unchanged shape
├── morning-briefing.cowork.json     ← NEW: structured payload
├── eod-review.md
├── eod-review.cowork.json
└── ...
```

The `.cowork.json` suffix avoids collisions with other `.json` files in Obsidian vaults, makes the sidecars easy to grep/exclude from Obsidian indexing, and clearly attributes ownership.

### 3.3 Sidecar schema (v1.0.0)

```json
{
  "schema_version": "1.0.0",
  "generated_by": "cowork:morning-briefing@2.0.0",
  "generated_at": "2026-06-08T08:00:14-06:00",
  "cadence": "morning-briefing",
  "engagement_id": "personal",
  "frontmatter": { /* mirror of .md frontmatter, fully-typed */ },
  "surfaced_kinds": ["calendar", "email", "projects", "threads"],
  "surfaced_items": [
    {
      "item_id": "cal-2026-06-08-0900-standup",
      "kind": "calendar",
      "callout_type": "example",
      "title": "9:00 AM Standup",
      "features": {
        "time_of_day_bucket": "morning",
        "sender_or_organizer_inner_circle": true,
        "recency_bucket": "today",
        "subject_recurring": true,
        "is_warning": false
      }
    }
  ],
  "render_aspects_applied": ["finance_block:skip", "anti_echo:include", "semantic_related:include"],
  "memory_used": { "yesterday_present": true, "drift_warning_present": false, "echoes_count": 2 },
  "plan_dispatch": {
    "mode": "prefs",
    "kinds_dispatched": 5,
    "warnings_emitted": 0,
    "classifier_cache_hit": true,
    "pending_confirmations_count": 0
  }
}
```

`item_id` shape: `<kind-prefix>-<deterministic-hash>` where the hash is derived from gather-specific stable fields (event UID for calendar, message-id for email, kanban card path for projects). Stable across same-day re-fires.

### 3.4 Surface changes

**Gather sub-skills** (the heavy lift): each gather sub-skill grows a structured return alongside markdown. `output: { markdown, status, items: [{item_id, kind, callout_type, title, features}], ... }`.

| Sub-skill | Items emitted | Feature-pull source |
|---|---|---|
| `gather-calendar` | One per event | UID + organizer + time-of-day + recurring flag |
| `gather-gmail` | One per thread | message-id + sender inner-circle flag + thread length |
| `gather-imessage` | One per conversation | chat-id + counterpart inner-circle flag |
| `gather-finance-*` | One per merchant / account | merchant-id + amount-bucket + recurring flag |
| `gather-projects` | One per active card | card-path + recency |
| `gather-threads` | One per open thread | thread-id from active-threads.md |
| `gather-weather` | One single item | n/a (single block) |
| `gather-semantic-*` | One per echo / related note | source-path + similarity-bucket |
| `gather-from-served-by` | One per surfaced item | feature inference via kind classifier |

**compose-body changes:** accepts `ordered_blocks[].items[]` payloads alongside markdown; assembles sidecar JSON; returns `{ body_md, sidecar_json, status }` instead of `{ body_md, body_assertions, status }`.

**write-run-note-* (5 files):** writes both `.md` and `.cowork.json` atomically (md first, then sidecar; cleanup if either fails). New `write-atomic-note-helper.js` does the actual I/O.

**Verify pass (orchestrator Step 17):** retires the regex scan. Replaced by `validateSidecar(sidecar_json, schemas/<cadence>@<version>.json)`. On failure: delete .md + .cowork.json, emit Notice with the JSON-schema-validator's structured error, exit non-zero.

**body_assertions[]:** retired. Subsumed by schema validation.

**Verbal commitment Notice:** survives but slimmer. Drops the PATH + TYPE bullets (now enforced deterministically by the writer + schema). Keeps the VOICE + MICROSCOPES bullets (LLM-behavior invariants the writer can't enforce).

**CRITICAL callout in SKILL.md:** trimmed from each orchestrator. Path/frontmatter-shape sections retire; voice/microscope-discipline sections stay.

Rail L's scanner detects missing sidecars and degrades gracefully — counts the note as "surfaced something" but can't attribute the tick to specific items, so falls back to per-kind aggregate signal. After ~7 days of new-format notes, learning has enough signal.

## 4. Rail D design — MCP auto-discovery

### 4.1 The kind classifier

Ships as `data/kind-patterns.json`. Three-stage matching, deterministic:

```json
{
  "schema_version": "1.0.0",
  "kinds": {
    "calendar": {
      "tool_name_patterns": ["*calendar*", "list_events", "create_event", "suggest_time"],
      "namespace_patterns": ["*calendar*", "*Calendar*"],
      "callout_type": "example",
      "default_priority": 10
    },
    "email": {
      "tool_name_patterns": ["*email*", "*gmail*", "*mail*", "search_threads", "list_drafts"],
      "namespace_patterns": ["*Gmail*", "*gmail*", "*Outlook*", "*M365*"],
      "callout_type": "example",
      "default_priority": 20
    }
    /* + chat, finance, messages, docs, weather, vault */
  }
}
```

**Matching algorithm in `kind-classifier-helper.js`:**

1. For each reachable namespace (`mcp__<ns>__*`), enumerate its tool names.
2. Score each (namespace, kind) pair: count tool-name pattern matches + namespace pattern matches.
3. Top-scoring kind wins per namespace if score ≥ 2; otherwise marked `unclassified`.
4. `unclassified` namespaces get one LLM-classification fallback call (session model, in-loop — no separate API key). Cached per-namespace-name per-workshop-version in `spice/cowork/data/kind-classifier-cache.json`.

**Why deterministic-first + LLM fallback:** the 8 canonical kinds cover everything we ship microscopes for. LLM fallback is for genuinely new MCPs. Cache makes the cost essentially zero after first sighting.

### 4.2 Where classification runs

**a. At plan-dispatch (every cron fire).** Before composing `dispatch_plan[]`, plan-dispatch calls `classifyConnectedKinds(reachable_namespaces)` → returns `{ kind → [namespaces], unclassified: [...], new_since_last_fire: [...] }`. Becomes input to `composeFinalPreferences`.

**b. At bootstrap-vault (interactive).** Bootstrap calls the same helper; pre-fills context-builder interview answers from the classification.

### 4.3 The "detected unconfigured" flow

When plan-dispatch sees a `new_since_last_fire` namespace classified into a known kind:

1. plan-dispatch result picks up `pending_confirmations: [{ namespace, classified_as, suggested_priority, suggested_what_matters }]`. compose-body emits ONE `> [!info]+ Cowork detected a new MCP` callout near the top of the atomic note. Opt-out via `engagement.overrides.render_aspects.new_mcp_notice: "skip"` (default: include).
2. A new `pending-mcps.md` file in `spice/cowork/context/<engagement_id>/` accumulates the queue. Re-bootstrap reads from here.

The MCP is **NOT auto-added** to `user-preferences.mcps[]` until the user explicitly confirms via context-builder or by hand-editing. Detection notice caps at 7 days; after that the in-note notice is dropped but the entry stays in pending-mcps.md.

### 4.4 Auto-fill on bootstrap

`context-builder` SKILL.md gets Section 0: "I've auto-detected these MCPs. For each, I'll show you my best-guess kind, priority, and what-matters baseline. Press Enter to accept each, or type the override." Per-kind baselines come from `spice/cowork/context/engagement-shared-templates/<kind>/baseline.json` — extend any missing kinds (docs, weather).

Time-to-bootstrap drops from "10-15 minutes per-MCP" to "30 seconds confirming auto-detected list + tweaking outliers." Matches the platform-generalizability intent memory note.

### 4.5 Surface changes

- 1 new helper: `kind-classifier-helper.js` (~200 lines)
- 1 new data file: `data/kind-patterns.json` (~150 lines)
- 1 new runtime cache: `data/kind-classifier-cache.json` (managed by helper)
- Per-kind `engagement-shared-templates/<kind>/baseline.json` files (extend missing: docs, weather)
- `plan-dispatch` SKILL.md: adds Step 0 + threading of `pending_confirmations[]` (14th contract key)
- `compose-body` SKILL.md: handles the new "detected unconfigured" callout
- `context-builder` SKILL.md: Section 0 for auto-fill
- `bootstrap-vault` SKILL.md: invokes auto-fill
- `gather-from-served-by` SKILL.md: classification-aware fallback when a kind has no microscope

**~12 files touched. Stage estimate: 5-7 stages.**

### 4.6 Edge cases

- **MCP transiently unreachable.** Classification cache TTL is "until next sighting." After 7 days unreachable, plan-dispatch emits "MCP previously classified as <kind> has been unreachable for 7 days. Investigate or remove from priorities."
- **LLM classifier returns "I don't know."** Falls through to `unclassified`; surfaced in detection callout for manual classification.
- **Two MCP servers serve the same kind.** Both classified the same; `user-preferences.mcps.<kind>.served_by` accommodates an array, OR user picks one as canonical. Default: pick the one with more recent activity.
- **Bootstrap re-run after auto-classifier ships.** Existing user-preferences.mcps entries PRESERVED; new entries surface as "I also detected these new MCPs you haven't confirmed yet."

## 5. Rail L design — per-kind preference learning

### 5.1 Behavior

Every atomic note ends with a low-friction per-kind rating callout. `cowork:learn-from-checks` (new sub-skill) fires post-`synthesize-day`, scans yesterday's atomic notes + sidecars, updates per-engagement per-kind weights in `user-preferences.md`. plan-dispatch consults learned weights when ordering `dispatch_plan[]`.

### 5.2 Where weights live

Inside `user-preferences.md` frontmatter:

```yaml
---
type: cowork-user-preferences
priorities: [calendar, email, projects, threads, finance]
personality: { ... }
mcps: { ... }
# NEW in v0.96.0:
learned_weights:
  schema_version: "1.0.0"
  engagement_id: "personal"
  per_kind:
    calendar:   { weight: 1.20, ticks: 18, skips: 4, warmup: false, last_updated: "2026-06-08" }
    email:      { weight: 0.85, ticks: 7,  skips: 15, warmup: false, last_updated: "2026-06-08" }
    projects:   { weight: 1.45, ticks: 22, skips: 2, warmup: false, last_updated: "2026-06-08" }
    threads:    { weight: 1.00, ticks: 0,  skips: 0, warmup: true,  last_updated: "2026-06-08" }
    finance:    { weight: 0.30, ticks: 1,  skips: 18, warmup: false, last_updated: "2026-06-08" }
  totals:
    notes_scanned: 24
    notes_with_any_tick: 19
    warmup_until: "2026-06-15"
    upgrade_notice_emitted: true
---
```

Frontmatter (not sidecar): user-hand-editable, Obsidian-native, survives `sauce update` via `materialize_once: true`.

Per-engagement scope: keyed in `learned_weights.engagement_id`. Cross-engagement contamination forbidden.

### 5.3 The update formula

Each scanned atomic note contributes ONE observation per surfaced kind:

```
observation = {
  kind: "calendar",
  ticked: true | false,
  surfaced_at: "2026-06-08T08:00:14-06:00",
  note_age_days: 1,
}
```

Update per kind, per day:

```
w_new = w_old * decay + lr * (tick_count - 0.5 * skip_count) / (tick_count + skip_count + smoothing)

where:
  decay     = 0.98       (slow forgetting)
  lr        = 0.15       (learning rate per-day-batch)
  smoothing = 5          (Laplace smoothing prevents whipsaw)
  clamp(w)  = [0.10, 3.00] (no kind zeroed or runaway)
```

**Why `-0.5 * skip_count` (not `-1.0`):** asymmetric weighting matches positive-unlabeled insight. Ticks are clear positive evidence; skips are weak negative.

Worked examples:
- calendar, 1 tick / 0 skips: `w_new = 1.20 * 0.98 + 0.15 * (1 - 0) / (1 + 0 + 5) = 1.176 + 0.025 = 1.201`
- email, 0 ticks / 1 skip: `w_new = 0.85 * 0.98 + 0.15 * (0 - 0.5) / (0 + 1 + 5) = 0.833 - 0.0125 = 0.820`

Small moves per day; clear orderings after 7-14 days.

### 5.4 Warmup

First 7 days (or ≥7 ticked-or-skipped observations, whichever comes second):
- Update formula runs (data collected).
- plan-dispatch IGNORES weights when ordering (falls back to `priorities[]` array order).
- Rating callout still emits.

After warmup: `warmup: false`; plan-dispatch consults `weight` for ordering when deviation from baseline 1.00 exceeds ±0.20.

### 5.5 Exploration / exploitation

MVP: weights influence ORDER, never CULL. Lowest-weight kind still surfaces (if in `priorities[]`).

```
effective_priority = base_priority - (weight * 5)
```

**Must-surface backstop:** every 14 days, the lowest-weight kind in `priorities[]` is force-surfaced for one fire even if `effective_priority` would have demoted it below the cutoff. Catches "are you sure you don't want this?" without explicit exploration.

Proper Thompson sampling parks for cowork-rethought-2.

### 5.6 How weights feed back into plan-dispatch

Inside `composeFinalPreferences` (existing helper):

```
for kind in user_preferences.priorities:
  base_priority = priorities.indexOf(kind) * 10
  weight = learned_weights.per_kind[kind]?.weight ?? 1.00
  warmup = learned_weights.per_kind[kind]?.warmup ?? true

  effective_priority = if warmup OR abs(weight - 1.00) <= 0.20:
                         base_priority
                       else:
                         base_priority - (weight * 5)

  dispatch_plan.push({ kind, effective_priority, ... })

dispatch_plan.sort_by(effective_priority asc)
```

### 5.7 The rating callout

Emitted by compose-body between `> [!tip] Today's focus` and the nav-buttons block:

```markdown
> [!todo]+ Was today useful?
> Tick the kinds that surfaced something you cared about. (One tick per kind per day; learned weights live in `spice/cowork/context/user-preferences.md`.)
> - [ ] Calendar
> - [ ] Email
> - [ ] Projects
> - [ ] Threads
> - [ ] Finance
> <!-- cowork:rating-block schema=1.0.0 cadence=morning-briefing day=2026-06-08 -->
```

Properties:
1. **Order matches today's `surfaced_kinds[]`** — only kinds that actually emitted in this atomic note appear.
2. **HTML comment sentinel** — schema + cadence + day for scanner. Invisible in Obsidian rendering.
3. **Idempotent re-fires:** re-fire preserves user-ticked state by reading prior file and re-emitting same `[x]`/`[ ]` state where item titles match.

### 5.8 The scanner: `cowork:learn-from-checks`

New sub-skill. Fires once per day per engagement, called by `cowork:synthesize-day` as a final post-step.

```
Steps:
1. Read all atomic notes from spice/cowork/daily/<yesterday>/ for this engagement.
2. For each: find cowork:rating-block sentinel; parse checkboxes.
3. Cross-reference against <basename>.cowork.json sidecar's surfaced_kinds[].
4. Per (kind, ticked): increment counters in working set.
5. Apply update formula (§5.3) to user-preferences.md learned_weights frontmatter.
6. Update warmup state (§5.4).
7. Emit structured warning to today's memory.md `warnings:` on anomalies (zero ticks 5 days, sudden cliff).
```

Pure data operation. No MCP calls, no LLM call. ~150-200 lines (`learn-from-checks-helper.js`).

### 5.9 Bootstrap-vault Y/N question

One new question per engagement:

### 6.5 Graceful degradation

- **W fails:** writer deletes both files, abort. No cascade.
- **D fails:** plan-dispatch falls back to legacy mode (no `pending_confirmations[]`). Sidecar reports `plan_dispatch.mode = "legacy-classifier-fallback"`. Cycle still emits atomic note.
- **L fails:** `learned_weights` unchanged from yesterday. Next plan-dispatch uses stale-but-valid weights. Warning in memory.md.
- **L's rating callout missing in atomic note:** scanner silently skips note; warning logged.

No single-rail failure cascades into another rail's failure. Load-bearing.

### 7.2 Migration for existing engagements

2. **Runs classifier once during `sauce update`**, writes initial `kind-classifier-cache.json`.

No vault-config.md schema migration. Existing engagement records valid. `engagement.overrides.render_aspects.new_mcp_notice` additive.

### 7.3 First 7 days post-upgrade

- **Day 0:** migration runs. Next cron fire emits upgrade-notice + rating callout. All weights baseline 1.00, warmup: true.

## 9. Trade-offs

### 9.1 Accepted

1. **Bundled-MINOR risk.** 25-32 stages, 3 rails — comparable to v0.78 (cowork-consumption) which shipped ~28 stages. Risk: long cycle, partial-ship pressure. Mitigation: each rail RED-tests independently; a Rail W blow-up doesn't have to kill D + L (they can ship as PATCH while W reincubates).
2. **W1 not W2.** Sidecar determinism (W1) gets 80% of the report's reliability benefit at 50% of the risk. Full structured-output API rewrite (W2) parks for cowork-rethought-2 when 30+ days of W1 sidecars provide validation corpus.
3. **MVP per-kind learning, not per-item L2R.** Per-kind captures the dominant signal at ~half the implementation cost. Item-level features collected in sidecars but unused for ranking in MVP — reserved for cowork-rethought-2 when proper Thompson sampling + PU correction ship.
4. **Default-on for Rail L.** Departs from v0.95.1's all-knobs-default-skip posture. Rationale per Section 2.5: high-value user-visible surfaces earn default-on; high-noise auxiliary callouts default-skip. Bootstrap Y/N still gives explicit opt-out at engagement create time.
5. **One-day-lag learning.** Yesterday's ticks influence today's plan-dispatch. Faster feedback (same-day) would require post-fire updates which whipsaw on noisy days.
6. **~30 stage cycle.** Large but cohesive. The three rails compose at the design boundaries — splitting across cycles forces designing the interlocks twice.
7. **Default-on detection callout.** Adds one new callout type to every atomic note WHEN a new MCP is detected. Acceptable noise because it only fires on the (rare) detection event.
8. **Pre-cycle atomic notes degrade gracefully.** No retroactive sidecar generation. Acceptable because Rail L is forward-looking.

### 9.2 Rejected (this brainstorm)

1. **Approach B (foundation-first sequenced inside cycle).** W → D → L strict ordering. Rejected because the interlocks are thin (5 coupling points) — sequencing doesn't reduce risk meaningfully and slows everything.
2. **Approach C (D + L only, skip W).** Half the size. Rejected because the report's centerpiece IS the two foundations (writer + learner). Cutting the writer would leave the prose-defense cleanup as debt for the next cycle.
3. **Per-item inline checkboxes inside each kind's callout.** Per-kind MVP loop ignores item-level signal anyway. Clutters callouts. Harder to parse.
4. **Daily Hub aggregator pane with thumb buttons.** Higher infra cost (CustomJS + button wiring + ratings file). Same effective signal as in-note callout.
5. **Zero-interview auto-detection (no user confirms).** Highest risk of silent misclassification. Rejected for "auto-detect, user confirms" middle ground.
6. **Augment-only auto-detection (keep full interview).** Lowest behavior change but misses the platform-generalizability intent.
7. **Mid-tier per-item logistic regression.** ~12-14 stages just for Rail L. Rejected for MVP per-kind boost/cull.
8. **Full L2R + Thompson sampling + PU correction.** ~18-20 stages just for Rail L. Rejected; parks for cowork-rethought-2.
9. **W2 (full structured-output API rewrite) in this cycle.** Doubles per-fire token cost, needs API key in cron env, harder to debug. Parks for cowork-rethought-2.
10. **Cross-engagement weight contamination.** Explicitly forbidden. Each engagement learns independently.
