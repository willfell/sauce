## Per-workstream narrative

### Workstream A — `_resolveWorkshopPath` walks from `__filename`

**What shipped:** `platform/cli/cmd-update.js:22` changed from
`(hooks && hooks._execPath) || process.execPath` to
`(hooks && hooks._callerFile) || __filename`. The ancestry-walk anchor
is now cmd-update.js's own source file path. On real brew installs the
file lives at `/opt/homebrew/Cellar/sauce/<version>/libexec/platform/cli/cmd-update.js`;
the walk finds `libexec` at depth 2 and validates the sibling `platform/`
exists. Test hook renamed from `_execPath` to `_callerFile`.

**What we learned:** The v0.75.1 cycle's HC-V0751-B3 test exercised the
hook (`_execPath`) but the hook was the only source-of-truth that ever
fired in tests — real `process.execPath` lookups never happen in CI
because the test always supplies a mock. The bug was hidden by the mock.
Every real `sauce update --bump-pins` against a v0.75.1+ consumer vault
required the explicit `--workshop-path` override; the failure mode was
visible only post-deploy. Lesson: when a four-source precedence helper
is tested entirely through the test hook, also exercise the un-hooked
real-execPath path in at least one harness case (or make the
test-default reproduce the real-world layout). Closes v0.75.1
carry-forward §1.

### Workstream B — stale `workshop_path` invalidation

**What shipped:** After reading `installed.workshop_path`, probe for
`platform/manifest.json` at that path with `fs.existsSync`. If absent
(stale path — happens when brew cleans up an old keg after upgrade),
fall through to the ancestry walk instead of returning the dead path.
Eliminates the downstream `workshop manifest not parseable` failure
when a v0.76.0+ vault has an `installed.workshop_path` pinned to a
no-longer-existing keg directory. HC-V0760-B4 covers the new behavior.

**What we learned:** Trust-but-verify is the right pattern for any
persisted absolute path. `installed.workshop_path` was assumed valid
once written — but the brew lifecycle silently invalidates it on
`brew cleanup`. The probe (`platform/manifest.json` existence) is a
cheap canary: if the file is there, the directory is a real workshop;
if it's gone, the path is stale. Folded into the same commit as
Workstream A (`04ee3d4`) because both touch the same helper. Closes
v0.75.1 carry-forward §2.

has no semantic_related step and is not affected. Closes v0.75.1

### Workstream D — eod/weekly/monthly engagement-template prompt fallback

**What shipped:** When `spice/cowork/prompts/<orch>.md` is empty
(user-cleared or never-seeded), the Write step now reads
`spice/cowork/context/engagement-templates/<engagement.type>/prompts/<orch>.md`
as a fallback before falling through to the "No prompt body to drive
content" stub. Mirrors morning-briefing's implicit behavior (which
relied on `onboard-scheduled-jobs` seeding the user prompts from
engagement-template defaults at install time — this is the explicit
fire-time fallback for the case where seeding didn't happen or the user
cleared their prompt). `prompt_source` frontmatter records which source
drove the run (`user` vs `engagement-template`). The stub now fires
only when BOTH user AND engagement-template prompts are empty,
preserving the explicit "do-nothing" semantic. HC-V0760-D1..D3 cover all
three orchestrators.

**What we learned:** Stock-vs-user content flow needs explicit fire-time
fallback at the consumer side, not just implicit one-time seeding at
install time. Morning-briefing relied on the install-time seeding alone
and quietly stub-fired whenever the seeding missed or the user
emptied the file. The fire-time fallback is the right pattern because
it's resilient to any state of the user file. Carry-forward to v0.77.0:
apply the same explicit fallback to morning-briefing + midday-tripwire
for parity (S6 only covered three of the five orchestrators). Closes
v0.75.1 carry-forward §4.

During the writing-plans pass, scanning `install.js` for related logic

existing per-file flags before inventing new ones. The
`writing-plans` step caught what would otherwise have been a duplicate
implementation. See Lesson #1 below.

### Workstream F — `cowork:context-builder` skill

**What shipped:** New orchestrator-tier skill at
`platform/blueprints/cowork/skills/orchestrators/context-builder/SKILL.md`
(294 lines): pre-flight (confirm vault-config.md exists; read current
user-preferences.md; read mcp-skill-map.json); detect (enumerate
`mcp__*` tool namespaces; map to MCP-kinds via skill-map);
interview (4 inline question sets — calendar 3, gmail 4, imessage 3,
finance 4 = 14 hand-curated questions; each specifies prompt text,
options or free-text input, and output field path); plus cross-cutting
priorities + personality questions; write (compose new
user-preferences.md from question answers via the helper). Companion
artifact: `platform/blueprints/cowork/content/context/mcp-skill-map.json`
(MCP-namespace → gather-skill regex mapping; 4 entries: calendar, gmail,
imessage, finance). Companion helper:
`platform/blueprints/cowork/helpers/context-builder-dry-run.js` (169
lines) — minimal YAML-ish parser + composer + merge logic. The same code
path serves the live skill body AND HC-V0760-F1..F2 (first-run dry-run
emits expected file; re-run with `per_mcp_actions: { calendar: 'Skip' }`
is byte-identical for the calendar block).

**What we learned:** The minimal YAML-ish parser had a quoted-scalar
round-trip bug initially: `JSON.stringify(x)` on list items wrote
`["conflicts"]` and the parser then preserved literal quotes in
subsequent reads, producing `[\"\"conflicts\"\"]` on the second pass.
The fix:
`.split(",").map(s => s.trim().replace(/^["']|["']$/g, ""))` strips
surrounding quotes after the split. Lesson: minimal YAML parsers must
handle quoted AND unquoted scalars symmetrically. See Lesson #4 below.
The skill is functionally complete for v0.76.0; v0.77.0 will add
`cowork:read-user-preferences` (the consumer-side sub-skill that the 5
atomic-note orchestrators will use to apply priorities + personality
to their narrative output).

### Workstream G — boundary contract agent-guide

**What shipped:** New `Docs/agent-guides/cowork-customization-contract.md`
(80 lines): enumerates STOCK files (overwritten by `sauce update`),
USER files (preserved across `sauce update` via either bootstrap-vault
seeding or `materialize_once: true`), and a third "USER-DRAFTABLE WITH
BACKUP" category for the 5 cowork prompts (which are in `files[]`
WITHOUT `materialize_once: true` — meaning `sauce reinstall` overwrites
them, but install.js's v0.2.0 Option B mechanic writes the prior
content to `<path>.bak` first). The contract also documents the
procedure for adding new USER files (update the table + the
HC-V0760-A1 array lockstep), the rationale for keeping USER files out
of `files[]` (or carrying `materialize_once`), and a v0.77.0 candidate:
decide whether the 5 prompts should be promoted to strict-USER or
formalized as the hybrid behavior.

**What we learned:** The third "USER-DRAFTABLE WITH BACKUP" category
surfaced ONLY when HC-V0760-A1 was implemented in S7 and the implementer
hit the actual install.js behavior empirically — the boundary between
STOCK and USER is not strictly binary in cowork's current state. The
contract documents the truth (hybrid behavior with .bak backup) rather
than aspirational binary. This is also why HC-V0760-A1's
`FOCUSED_USER_PATHS` list covers nine paths (including the 5
prompts) — the harness is the lockstep gate against silent drift of
the contract. Lesson: write the empirical contract first; refine
toward aspirational binary in subsequent cycles. See Lesson #2 below.

### Workstream H — onboard-scheduled-jobs auto-delegation

**What shipped:** A new "Phase: ensure user-preferences captured" added
to `cowork:onboard-scheduled-jobs` SKILL.md between bootstrap-vault
and cron-registration. Probes `user-preferences.md`; if absent OR
seed-stamped (`updated_by: install.js`), delegates to
`cowork:context-builder` via skill-invoke. If previously captured by
the user (`updated_by != install.js`), offers an update path but
defaults to skip. Realizes the user's brief: "all in one skill invoke
from claude cowork". HC-V0760-H1 covers the SKILL.md references +
gate condition. Same commit as Workstream G (`0fdf11b`) because both
landed atomically.

**What we learned:** The seed-stamp condition (`updated_by:
install.js`) is the right signal for "user has not yet personalized" —
it's set by the `materialize_once`-protected install-time seed and
overwritten only when context-builder writes its first user-driven
state. Cleaner than file-existence probing (the file always exists
after first install). Onboard becomes the "one orchestrator that runs
everything" entry point: bootstrap-vault → context-builder (if needed)
→ cron-registration. v0.77.0 will add atomic-note-orchestrator
consumption of user-preferences.md, and the cycle ends with all 6
cowork orchestrators interlocked.

## Lessons learned

1. **`materialize_once` already existed; scan before inventing.** The
   v0.76.0 design committed to a new `preserve_if_exists` manifest flag
   for the `user-preferences.md` preservation. During writing-plans,
   the design-pass discovered `install.js` lines 941-957 already
   implemented `materialize_once: true` (added v0.59.9 for kanban-board
   protection). The semantics were identical to what `preserve_if_exists`
   was going to do. Reused the existing flag; no new code; one fewer
   harness case needed (E2 deleted). Saved ~15 lines of new code +
   ~30 minutes of implementation work + the cognitive overhead of
   reconciling two near-identical manifest flags forever. Lesson: scan
   `install.js` for existing per-file flags before inventing new ones.
   The design-review pass is the right place to catch this kind of
   prior-art duplication.

2. **5 cowork prompts are USER-draftable-with-backup, not strict USER.**
   S7's HC-V0760-A1 preservation harness implementer discovered the 5
   `spice/cowork/prompts/<orch>.md` files are in cowork's `files[]`
   WITHOUT `materialize_once: true` — meaning every `sauce reinstall`
   overwrites them. Install.js's v0.2.0 Option B mechanic does write the
   prior content to `<path>.bak` first (so user edits are recoverable),
   but the live file gets replaced. The v0.76.0 boundary contract
   documents this hybrid behavior in a third "USER-DRAFTABLE WITH
   BACKUP" section rather than forcing it into the binary STOCK/USER
   classification. v0.77.0 candidate: decide whether to promote to
   strict-USER (add `materialize_once`) OR formalize the `.bak` behavior
   as the intentional contract for prompts (they're documents users
   draft but expect to be re-seeded when the engagement-template
   defaults change in a future workshop update). The contract is
   discoverable in code today; the question is whether to lift it into
   the manifest schema.

3. **Canonical text alignment has a single source of truth.** S3 first
   wrote HC-V0760-C2 + HC-V0760-C4 asserting `"Semantic index absent or
   anchor not indexed..."` WITHOUT the `"Smart Connections "` prefix.
   S4's implementer caught the discrepancy against morning-briefing's
   v0.75.1 H fix AND gather-semantic-related's contract (both use
   `"Smart Connections index absent..."`) and corrected the regex
   literals in the same commit as the SKILL.md edits. Lesson: canonical
   text shared across orchestrators lives in the sub-skill's
   `## Orchestrator integration contract` section — and tests should
   derive from the canonical, not paraphrase from the spec description.
   Future cycles that touch text shared across orchestrators should
   `grep` the existing canonical FIRST before deriving from the
   workstream spec.

4. **YAML round-trip requires quote-stripping.** S10's
   `context-builder-dry-run.js` minimal YAML-ish parser initially failed
   HC-V0760-F2 because `JSON.stringify(x)` on list items wrote
   `["conflicts"]` and the parser then preserved literal quotes in
   subsequent reads, producing `[\"\"conflicts\"\"]` on the second pass.
   The fix:
   `.split(",").map(s => s.trim().replace(/^["']|["']$/g, ""))` strips
   surrounding quotes after the split. Lesson: minimal YAML parsers
   MUST handle quoted AND unquoted scalars symmetrically. Either
   reach for a real YAML library OR commit to consistent quote-stripping
   discipline at every read/write boundary. This kind of round-trip
   bug surfaces only on the second invocation, so single-pass tests
   would miss it — HC-V0760-F2's re-run-byte-identical assertion is
   what caught the bug.

5. **TDD red-green discipline held across 8 workstreams.** All seven
   failing-test stages (S1, S3, S5, S7, S8, S11) landed with the
   expected FAILs (S7 was actually a regression-coverage test, not a
   strict failing-first — but the new HC-V0760-A1 case was failing
   pre-S13 manifest wiring); all seven implementation stages (S2, S4,
   S6, S7-pass-via-S13, S10, S12) turned them green. No implementation
   stage introduced unexpected regressions in the pre-existing harness
   suite. This is the fifth consecutive cycle (v0.73.0, v0.74.0,
   v0.75.0, v0.75.1, v0.76.0) where full TDD discipline held across all
   workstreams. The pattern works; the cost (one extra commit per
   workstream) is bounded.

6. **Subagent-driven execution scaled to 14 implementer dispatches.**
   The full cycle (S0-S14 + TAG) executed via
   `subagent-driven-development`. 14 implementer subagents dispatched
   (S0 read-only verification + S1-S13 + S14 cycle-close). Reviews were
   lightweight (preflight + grep verification at the end of each stage)
   instead of formal `spec-reviewer` + `code-quality-reviewer`
   subagents per stage; this kept the budget reasonable and the cycle
   pace fast. Each subagent received the full stage text inline
   (~30-100 lines per prompt) so no plan-file reading was needed in the
   subagent context. The plan file (`-plan.md`, 2586 lines) acts as
   the master coordination doc but never enters a subagent's context
   window directly.

7. **Cross-workstream parity is a recurring carry-forward pattern.**
   v0.75.1's H morning-briefing fix did not propagate to eod-review +
   weekly-review even though both integrate the same gather skill —
   v0.76.0's Workstream C closed that gap. v0.76.0's Workstream D
   added engagement-template prompt fallback to eod/weekly/monthly but
   morning-briefing already had implicit fallback (via
   onboard-scheduled-jobs seeding) and midday-tripwire was scoped out
   — both need the explicit fire-time fallback for full parity in
   v0.77.0. Lesson: whenever a fix touches one of N similar
   orchestrators, the carry-forward list MUST include parity work for
   the other N-1. Document this explicitly in the cycle-close result
   to make the parity work visible.

8. **`workshop_path` validity is a lifecycle invariant the brew tap
   silently breaks.** v0.75.1 stored `installed.workshop_path` as a
   one-shot setting; v0.76.0 makes it a probe-and-fallback pattern
   because `brew cleanup` invalidates the path between sauce upgrades.
   The right model is: any persisted absolute path that the consumer
   stored from a prior runtime MUST be re-validated before use.
   Generalize: the "trust persisted absolute paths" pattern is wrong
   for any path that crosses a lifecycle boundary (brew kegs, ephemeral
   sessions, container restarts). The
   `fs.existsSync(path.join(dir, "platform", "manifest.json"))` probe
   is the canary; other persisted-path fields should adopt similar

9. **The 8-workstream minor-cycle is a good unit.** v0.76.0 packs 4

   release can absorb both maintenance AND forward work IF the two
   classes don't share files or harnesses.

10. **The 14-question hand-curated interview is enough for v1.** The
    user's brief specified hand-curated questions per MCP-kind for v1

    overwhelming the user. Each question is short (one-line prompt,

    user-preferences.md ends up being ~10 lines of structured YAML-ish.
    The right balance was found empirically by writing out the
    composed file in S10 + iterating on field shape. Lesson:
    structured-interview content benefits from writing the OUTPUT
    file shape first, then deriving questions backward from required
    fields.
