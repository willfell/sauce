# v0.96.2 daily-dashboard-tskeys-hotfix — result

## Origin

Workflow run `wzr3g3uad` (post-v0.96.1, 2026-06-09) diagnosed a class of cron-driven timestamp drift in the cowork blueprint:

- Cowork atomic notes carry a semantic `day:` frontmatter field (canonical day-of-action, YYYY-MM-DD).
- They also carry `created_at` — a wall-clock ISO timestamp captured when the cron actually fired.
- For most cadences the two agree. But EOD cron firing past midnight (e.g. cron with `0 23 * * *` actually running at 04:10 next morning, or DST transitions, or retries) stamps `created_at` on the NEXT calendar day while `day:` still names the intended day.

Concrete case from the diagnosis: a Monday 2026-06-08 EOD note carried `day: "2026-06-08"` + `created_at: "2026-06-09T04:10:00-06:00"`. The Monday daily-note Activity panel did NOT surface it because `SpaceDailyDashboard` was bucketing by `created_at` (line 373 of `space-daily-dashboard.js`: `tsKeys: ["created_at", "status_changed_at"]`, line 426 `inWindow` reading `p.created_at` directly).

## Key implementation decision — `day` is authoritative when present

The straightforward read of the prompt suggested mirroring activity-feed's OR-semantics: iterate tsKeys, return TRUE on the first in-window match. But DASH-3 forced a re-think.

Scenario:
- Page: `{ day: "2026-06-08", created_at: "2026-06-09T04:10:00-06:00" }`
- Tuesday window: 2026-06-09T00:00 .. 2026-06-09T23:59
- OR-semantics: `day:"2026-06-08"` slice-compare `"2026-06-08" >= "2026-06-09"` → FALSE. Loop continues. `created_at:"2026-06-09T04:10"` → in window → TRUE. Page surfaces on Tuesday.
- Combined with Monday-window TRUE for `day:"2026-06-08"`, the page would double-surface on BOTH days.

Authoritative-when-present semantics (what we shipped):
- `day` is present → use ONLY `day`. Monday: TRUE. Tuesday: FALSE. Single source of truth.
- `day` is absent → OR-semantics over `created_at` + `status_changed_at` (matches pre-v0.13.6 behavior + activity-feed kanban semantics for status_changed_at).
- Both fields absent → mtime fallback (legacy pages).

This adds a thin layer to the predicate but matches the user's stated invariant: "day takes precedence over created_at". The semantic frontmatter field becomes the canonical day-of-action when set; wall-clock timestamps are advisory secondary.

1. **Activity-feed mechanism's own inWindow uses pure OR-semantics** (`platform/mechanisms/activity-feed/activity-feed.js` lines 349-376). With the dashboard pre-count gated to count the page on Monday-only via the authoritative-`day` logic, `hasContent` is correct. But activity-feed's render-time inWindow will still match the page on BOTH Monday and Tuesday — `day:"2026-06-08"` matches Monday's slice and `created_at:"2026-06-09T04:10"` matches Tuesday's full-ISO range. A v0.97 follow-up should add authoritative-day semantics to activity-feed itself: when `day` is in the tsKeys list AND a page has `day:` set, use ONLY `day` for that page's window check.
