## 4 — The 5 sub-themes catalogued

Each sub-theme is its own future cycle. Subthemes were enumerated as the response to the user's reframe — they decompose the platform-direction question into shippable units.

### Sub-theme 1 — Platform de-personalization (PATCH, v0.93.4 candidate)

**Scope:** Strip accuris-specific names/repos/IDs from `/platform/blueprints/cowork/helpers/fixtures/compose-body/case-*/` AND `/platform/test/fixtures/v0900-discover-people/case-*/`. Replace with generic placeholders (Person A, Repo X, Engagement Y, ADO-XXXXX). Reword SKILL.md prose that references "accuris production morning-briefing run on 2026-06-05" to a generic example. Update README files (`/platform/mechanisms/people-identity/README.md`) that show "Stefan de P." canonicalization examples.

**Why now:** Highest-leverage tactical answer to "works for any user." Pure hygiene, no functional change, low risk. Prepares the platform's identity for new users / contributors / OSS-style cloning.

**Stages:** ~3-4. Cycle-history convention: workshop PATCH, no mechanism bumps (because no behavior changes), test fixture overhauls land in S1.x with golden-fixture regen.

**Dependencies:** None.

**Open design questions:**
- What placeholders to use? `Person A/B/C` is generic but bland. `Alice/Bob/Carol` is classic but Western-coded. Consider Spanish/Japanese/multilingual names to signal globalness, or numeric IDs (`User-001`) for full neutrality.
- Should test-fixture file names also be renamed (e.g., `case-a-accuris-vault-config.md` → `case-a-generic-w2-vault-config.md`)?
- Are there ANY hardcoded references in shipped runtime code (not just fixtures)? Audit needed.

### Sub-theme 2 — Connector / knob ergonomics (MINOR, v0.94.0 candidate)

**Scope:** The BIG ONE. Audit which knobs (personality, microscope, styling, people, connector ordering) are currently first-class per-engagement vs hard-coupled to engagement-type defaults. Design a config schema where users can REORDER + TUNE connectors per cadence per engagement WITHOUT editing engagement-type JSONs.

**Why this is big:** It directly answers the user's "in the order that they want, how they want it" intent. It probably reshapes the engagement-type manifest contract — connector ordering becomes a per-engagement list (not a per-engagement-type default), render_aspects become more granular knobs, personality becomes a first-class property (not buried in context files).

**Stages:** ~5-7. Cowork MINOR (likely 0.32.0 from current 0.31.2). Probably touches: engagement-type manifests, vault-config.md schema, render-aspects contract, several orchestrator SKILL.md preflight steps, and the bootstrap-vault skill.

**Dependencies:** Should land AFTER Sub-theme 1 (de-personalization) so the fixture surface is generic before we restructure the knob schema. Might also informally depend on Sub-theme 5 (vault-config schema migration) — if the schema changes, existing consumer vaults need a migration path.

**Open design questions (for the v0.94.0 brainstorm):**
- What's the right TAXONOMY for knobs? Currently mixed: render_aspects (per-engagement-type defaults), personality (per-engagement context file), people (per-engagement context file). Should they all become a unified "preferences" tree?
- How does the user REORDER connectors? Drag-drop UI is out of scope (no UI). Editing JSON is fine but ergonomically poor. A `/cowork tune` skill that interviews the user and writes preferences? A `priority:` field on each render_aspect that defaults to type-default but is per-engagement-overridable?
- Cross-cadence consistency: if user reorders connectors in morning-briefing, should weekly-review inherit the new order? Or is reordering per-cadence?
- Backward compatibility: how do existing engagement-types ride the new schema? (Probably need Sub-theme 5 alongside.)

### Sub-theme 4 — Cross-machine wrapper alignment (MINOR, v0.95.0 candidate)

**Scope:** Parameterize scheduled-job wrappers (user-home, vault-relative paths, engagement_id resolution) so the SAME wrapper body renders the SAME atomic note regardless of which machine fires the cron. Today, wrappers contain `/Users/willfellhoelter/...` OR `/Users/willfell/...` baked at sync-time; if the user moves machines, the wrapper points at the wrong vault.

**Why this matters:** The user's reframe explicitly called out "consistency on both machines." `v0.93.0`+`v0.93.1`'s `/cowork sync-scheduled-jobs` orchestrator + scheduled-tasks-MCP push already automate WRAPPER UPDATES but they still bake machine-local paths at sync time. v0.95.0 would generalize the wrapper bodies so they're machine-independent.

**Stages:** ~4-6. Touches `compose-scheduled-job-wrappers-helper.js`, `scheduled-job-contract.json`, the sync orchestrator, possibly `vault-config.md` to declare which machines a vault syncs to.

**Dependencies:** None hard. Could ship before or after Sub-theme 2/5. Independent.

**Open design questions:**
- How does the wrapper resolve `<user-home>` at fire time? `$HOME`? A `vault-config.machines[]` declaring known-good paths per hostname? Both?
- Does the wrapper assume Obsidian Sync (vault has same RELATIVE path tree on every machine)? Yes likely — that's how cowork already works.
- What about `engagement_id` paths? Today they're vault-relative (`spice/cowork/context/<engagement>/`) so already portable. Verify.

### Sub-theme 5 — vault-config schema migration (PATCH, v0.94.1 candidate)

**Scope:** Add `sauce update --migrate-config` (or `sauce migrate-config`) to bring an existing vault-config.md from a prior cowork schema (e.g., v0.2.1) up to current (v0.32.0 or whatever Sub-theme 2 produces). Both consumer vaults today say cowork v0.2.1 in vault-config.md while workshop's cowork manifest is v0.31.2 — they've never been migrated.

**Why this matters:** When Sub-theme 2 reshapes the engagement-type schema or vault-config schema, existing consumers can't just re-run `sauce update --bump-pins` and have their content survive. A targeted migrator preserves user-edited fields while moving them to the new schema.

**Stages:** ~3. Touches `platform/install.js` or a new top-level migrator script, possibly `bootstrap.js`'s vault-config-rendering logic.

**Dependencies:** Should land AFTER Sub-theme 2 so the migrator knows what schema to migrate TO.

**Open design questions:**
- What's the migration policy on conflict? If user manually edited a field that the new schema removes, do we preserve in a sidecar (`.migrated-from-v0.2.1`)? Abort with notice? Best-effort merge?
- Versioning: does vault-config.md need a `schema_version:` front-matter field so the migrator knows what to migrate FROM? Probably yes.

## 8 — Open questions queued for follow-on brainstorms

In addition to the per-sub-theme questions in § 4, these are cross-cutting questions that arose during the brainstorm and should be addressed in either Sub-theme 2's brainstorm or a separate strategic-direction discussion:

1. **The "any user" claim.** Sauce currently distributes via Homebrew tap (willfellhoelter/homebrew-sauce). Is the long-term distribution model "personal-public" (anyone CAN install but it's still tailored), OR "true OSS multi-user" (anyone SHOULD install + customize)? Affects how aggressively to de-personalize platform code.
2. **Engagement-type taxonomy.** Today we have `w2-fte` + `personal` + a few others. Should the taxonomy be richer (`w2-fte/saas`, `w2-fte/enterprise`, `contractor`, `student`, `retiree`) or thinner (one generic "professional" + one generic "personal")? Sub-theme 2's knob refactor might obviate the taxonomy entirely (engagement-types become bundles of knobs, not first-class categories).
3. **Documentation catch-up (Shape F from the prior handoff).** `why.md`, `how.md`, `use.md`, `architecture.md`, `README.md` are 2-4 weeks stale (no mention of body-composer, sync-scheduled-jobs, memory layer, semantic retrieval, people-cohesion). Not in the 5-sub-theme sequencing but should land at some point. Probably folded into v0.94.0's cycle-close (since the knob refactor touches the foundational story).
4. **The willfell laptop scheduled-task fleet.** Today the user has scheduled tasks configured in claude.ai (managed via `/cowork sync-scheduled-jobs`). Are those tasks shared across both machines or duplicated? Sub-theme 4's cross-machine wrapper alignment touches this.
5. **`brand-voice.md` and `people.md` on accuris.** Headspace has them; accuris doesn't. Is this a deliberate choice (accuris uses corporate default voice, no inner-circle personalization), OR a population gap (user just hasn't filled them in)? Should the bootstrap-vault flow prompt more aggressively?
