# v0.98.1 — questionnaire expansion + free-text capture — result

## TL;DR

Replaces the EOD-only Rail L coarse kind-checkbox rating block with a richer capture surface: stable per-item `^item-<kind>-<7-char-sha>` block-IDs emitted by compose-body, per-item ticks pointing at those block-IDs, per-kind 3-position frequency knobs (`less / same / more`), and a tagged fenced `` ```feedback…``` `` free-text block under a `<!-- cowork:feedback-capture v=1 -->` sentinel. Capture-only — no `learned_weights` writes, no voice updates, no parse-back loop. The first cycle that EXPLICITLY guards user-authored cowork content via automated forbidden-paths CI (Safeguard 3). v0.98.2 closes the loop via a `cowork:ingest-feedback` sub-skill.

EOD-review is the only cadence with the new Rail L shape. Morning-briefing / midday-tripwire / weekly-review / monthly-review keep today's `{{shared.rating_callout_template}}` invocation unchanged.

## Goal

Per the user direction captured during the 2026-06-10 brainstorm (after v0.98.0 closed):

> "just saying thumbs up isn't enough. what if we added a section for didn't like? what if there was a section where i could provide feedback, and another job took what i liked, what i didn't like, my feedback, then updated the relevant files so that all scheduled jobs would then adjust the next day?"

The vision spans two cycles: v0.98.1 captures the signal in a parseable shape; v0.98.2 ingests the signal and applies deltas to `learned_weights` / microscopes / `what_matters` with an audit trail. This result covers v0.98.1 only.

## Discoveries and lessons

### 1. Bare fence shape for feedback block

The design sketched `> `-prefixed fences inside the callout; the S1.1 asserts authored an implicit bare-fence contract; the S1.2 implementer landed bare fences + made `_parsePrior` tolerant of both shapes. The two are functionally and parse-equivalent. Visual UX deferred: if deployed briefs show poor callout visual containment (fence lines rendering outside the callout boundary in Obsidian reading mode), a v0.98.1.x PATCH tightens to `> `-prefixed fences throughout.

### 2. Item-ID emission opt-in via `block.items[]`

Discovered at S1.3: the existing block shape in compose-body was `body_md` strings (no structured items). The implementer made item-ID emission opt-in when `block.items[]` is present; the other 8 compose-body fixtures stayed byte-identical because they don't carry `items[]`. This is cleaner than the plan's "extend all per-kind callouts" approach and avoids retroactive coupling between the compose-body surface and per-item feedback semantics.

### 3. S1.5 scope expansion — compose-body cadence dispatch

The plan's S1.5 only covered OI prose changes to eod-review. But for production EOD fires to actually route to `composeFeedbackCapture`, `compose-body-helper.js` needed cadence-based dispatch logic: `cadence === "eod-review"` + `surfaced_items_by_kind` present → `composeFeedbackCapture`; else → `composeRatingCallout`. Added at S1.5. The eod-review OI Step 3e also gained the `items[]` contract clause at S1.5 (not S1.2 as originally staged). **Lesson: when adding a new composition path, trace the dispatch chain from the OI layer through to the helper before staging — the OI change and the helper routing change are a single atomic unit.**

### 4. SKILL.md two-location reconciliation

The plan's S1.2 prompt wrote the new SKILL.md to the workshop runtime path `.claude/skills/cowork/skills/compose-feedback-capture/SKILL.md` (correct for LLM use, wrong for source-of-truth). The blueprint source `platform/blueprints/cowork/skills/skills/compose-feedback-capture/SKILL.md` was an empty stub until S1.7 created a placeholder. S1.7.1 reconciled by copying the full 66-line content to the blueprint source; S2 dogfood install regenerated the runtime from the now-canonical source. **Lesson: new SKILL.md content ALWAYS belongs in the blueprint source first; runtime is derived. When the plan's implementation step writes to runtime directly, flag it for immediate reconciliation.**

### 5. ranch/platform-subscription.json blueprints[].cowork.version pin missed in S1.7

The S1.7 plan's `jq` command bumped the workshop workshop_version and the `blueprints[].cowork.version` in the manifest catalogue but missed the `ranch/platform-subscription.json` blueprints row's `cowork.version` entry. Caught by 3 failing harness tests; fixed in S1.7. **Lesson: the VERSION-pin sweep jq automation must include `ranch/platform-subscription.json` blueprints[].cowork.version alongside the other version fields. Future cycles should include this in the sweep checklist explicitly.**

### 6. Scripts/ vs scripts/ gitignore conflict

macOS case-insensitive filesystem: the gitignore entry covering `/scripts/` matched `/Scripts/` via case-folding, hiding the new Safeguard 3 guard until the path was verified with `git status`. The guard was placed at `scripts/check-files-forbidden-paths.js` (lowercase, matches existing scripts/ tree). **Lesson: on macOS, gitignore case-insensitive matching is a landmine for any new top-level directory. Verify with `git status -s` immediately after creating a new file under a directory that shares a name-pattern with any gitignore entry.**

### v0.98.2 reconciler free-text + per-item-tick ingest

Goal: close the loop. The `cowork:ingest-feedback` sub-skill reads captured feedback corpus (EOD sidecars with `feedback_capture.sentinel_version === "v=1"`), produces structured deltas, and applies them to `learned_weights` / microscopes / `what_matters` with an audit trail. Voice/personality changes are PROPOSED, never auto-applied.

Key design moves sketched in v0.98.0 design § Forward arc:
- **Parse structured signal (deterministic).** Per-item ticks → looked up against item-ID hash registry → rolled up per-kind, per-person, per-channel weight nudges. Frequency knobs → direct weight delta.
- **Parse free-text (LLM pass).** NEW sub-skill `cowork:ingest-feedback` runs an LLM pass (Sonnet 4.6 — cost-fast) with a structured-output prompt: extract per-person/channel/topic uprank/downrank, voice corrections, coverage gaps, and other intents as deltas with proposed write-targets.
- **Apply with audit trail.** Deltas logged to `spice/cowork/memory/<engagement>/feedback-deltas.md`. Numeric updates: applied directly. Voice changes: PROPOSED only.
- **`learned_weights` schema_version 2 → 3.** v0.98.2 bumps the schema; v0.98.1 EXPLICITLY stays at version 2 (capture-only).

**5 open questions for v0.98.2 brainstorm:**

1. **learned_weights schema 3 shape.** Flat `per_person.<name>.weight` per-kind, or nested under per-kind (`per_kind.chat.per_person.<name>.weight`)?
2. **Voice change apply mechanism.** Proposed-in-next-brief vs explicit slash command (`/cowork apply-voice-deltas`)?
3. **Free-text LLM model.** Sonnet 4.6 (cheap, fast — recommended) vs Opus 4.7 (smarter)?
4. **Reconciler cadence for feedback ingest.** Daily vs weekly?
5. **Per-item DOWNVOTE row (NEW from 2026-06-10 user vision).** Should Rail L gain a second row per kind for per-item dislikes alongside per-item likes? Sub-question: same item-IDs with a separate `downvote:` prefix, or a separate downvote-specific ID scheme?
