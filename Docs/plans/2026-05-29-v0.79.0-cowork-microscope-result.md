## What shipped

### WS-A — Microscope (per-kind deep gather contracts)
- **`spice/cowork/prompts/per-mcp/<kind>/microscope.md`** — a USER-OWNED contract file authored on demand by the new `cowork:edit-microscope` skill. NOT in cowork's `files[]` (preservation by construction); `sauce update`/`reinstall` never touch it. Same posture as `bootstrap-vault`-seeded files.
- **`cowork:edit-microscope`** orchestrator (`/cowork microscope <kind>`) — MCP-tool-aware iterative capture loop: enumerates the kind's `served_by` tools, consent-gated samples real data, surfaces gaps with resolution paths (resolvable-in-gather / mcp-ceiling / user-supplied), composes the contract. Helper `platform/blueprints/cowork/helpers/edit-microscope-helper.js` exports pure functions `resolveKind`, `classifyGap`, `composeMicroscope`.
- **Dispatch routing.** When `microscopes[kind_name]` is present and non-empty, the 5 atomic-note orchestrators (morning-briefing / midday-tripwire / eod-review / weekly-review / monthly-review) force that kind through `cowork:gather-from-served-by` with the microscope body as the deep `what_matters` and the kind's prior `notes` carried as `baseline_notes`. Covers canonical and override kinds uniformly. With no microscope present + no `hard_rules` + prior styling, behavior is byte-clean v0.78.x.

### WS-B — Hard rules + no_emojis
- `personality.hard_rules[]` + `personality.no_emojis: true` parse in `cowork:read-user-preferences` → composed into one ordered `effective_hard_rules[]` (`hard_rules` + canonical no-emoji rule when `no_emojis` is true).
- Propagated to **all three output layers**:
  1. Voice contract prefix (`composeVoiceContract(personality, effectiveHardRules)`) — appends a `Hard rules (non-negotiable, …)` block; now emits even when personality is all-null but rules exist.
  2. `gather-from-served-by` dispatch — new `hard_rules[]` input + `## Hard rules` SKILL.md section binding callout TITLE + BODY; helper echoes back `hard_rules_applied[]`.
  3. `write-run-note-*` skeleton (all 5) — adaptive-skeleton paragraph binding hard rules to `[!example]+` / `[!info]` / `[!tip]` titles + bodies. Canonical `[!warning]` strings exempt.

### WS-C — Admonition fix (styling)
- New vendored snippet `platform/mechanisms/styling/assets/snippets/sauce-callouts.css` defines per-type `--callout-color` for info / note / tip / success / warning / caution / example / quote / danger across light (`rose-pine-light` hues) + dark (`melange-dark` hues). Wired via the existing `applySnippets` helper (manifest `snippets[]` entry mirrors convenience's `sauce-tasks-icons` pattern) + `appearance.enabledCssSnippets`. Styling **0.1.2 → 0.2.0** (additive MINOR).
- Materialized in the workshop dogfood: `.obsidian/snippets/sauce-callouts.css` (2235 bytes) registered alongside `customjs-loader`, `sauce-tasks-icons`, `sauce-daily-dashboard`.

### WS-D — MCP-depth audit (doc only)
- **iMessage:** number→name gap is **resolvable-in-gather** via `search_contacts` — encoded as a `classifyGap` heuristic + the edit-microscope SKILL.md instruction template. No swap needed.
- **WhatsApp:** privacy-capped MCP is an **mcp-ceiling** — `edit-microscope` surfaces the gap live and names `lharries/whatsapp-mcp` (whatsmeow-backed; message-level depth) as the user-side connector swap.

## Sequencing observations + corrections (for next-cycle learning)

- **Landmine #16's real teeth.** Every per-stage `node platform/install.js --vault . --auto-approve` invocation in S2/S4/S6/S8/S9/S11 was effectively a no-op for re-materialization. install.js exports `async function(tp)` (Templater entrypoint) and has no CLI handler — the flags were silently ignored. The correct dogfood invocation is `node platform/test/run-install.js . --auto-approve`. Even with the correct invocation, install.js short-circuits per item when `installedEntry.version === sub.version` (landmine #16). So mid-cycle `.claude/skills/cowork/*` materialization was deferred to S15 (when the styling subscription pin bumped → install processed AND the global claude_surface_aggregate + materializeClaudeSurface step regenerated all cowork SKILL.md dests with the accumulated v0.79.0 source content) and S16 (when cowork version bumped 0.17.0→0.18.0). The plan's S15.8/S16.5 `git add ranch/ .claude/` instruction was correct; it just captured a larger delta in S15 than the plan's author anticipated.
- **Plan vs design file-map for HC-F1.** The plan's S12 file-map listed `run-install.js`; the design §7 + the actual `HC-V0760-A1` + `FOCUSED_USER_PATHS` location put it in `run-cowork-smoke.js`. Resolved by splitting: `FOCUSED_USER_PATHS` extension landed in run-cowork-smoke.js (structural fail-closed guard on the real cowork manifest); HC-V0790-F1 landed in run-install.js as a real install→reinstall test mirroring `caseV0760E1`'s synthetic-workshop scaffold (behavioral guard on the install.js mechanic). Together they fully cover the design intent.
- **B3/D1 fixture below the 80-char floor.** The plan's `agent_markdown` for HC-V0790-B3 (and reused in D1) was 78 chars — under `gather-from-served-by-helper.js`'s `md.length < 80` floor, so B3 would have stayed `failed:bad-output` even after S4. Padded both fixtures identically to 106 chars by adding one more grounded bullet (`> - Dining $38 at Sushi Den`). Test intent (reach status `"ready"`, echo `hard_rules_applied`) preserved.
- **S11.4 orchestrator dest shape.** Orchestrators flatten to `{{skills_dir}}/<name>/SKILL.md` (no `skills/orchestrators/` segment); only sub-skills nest. The plan's S11.4 node-script proposal used the nested form and would have created a dest-path mismatch. Corrected to mirror the real `morning-briefing` / `bootstrap-vault` / `context-builder` dest pattern.
- **VISUAL verification (S15.6) not performed.** Remote-control session — no Obsidian UI access. The snippet is materialized at `.obsidian/snippets/sauce-callouts.css` and registered in `appearance.enabledCssSnippets`, but only the user's eye can confirm the rendered colors are distinct. Open the workshop vault in Obsidian; view any note with `> [!info]` + `> [!warning]` + `> [!tip]` + `> [!example]` callouts and confirm four distinct hues. If still monochrome, the theme's Monochrome Style-Setting override may need toggling in `platform/mechanisms/styling/data/style-settings-default.json` (carry-forward note).
