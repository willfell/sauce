# v0.93.3 — required-plugins PATCH design

## Problem

Two Obsidian community plugins are de-facto required by current sauce behavior but are NOT enforced by the platform installer:

1. **`new-tab-default-page`** (chrisgrieser/obsidian-new-tab-default-page) makes every new tab land on the active daily note in Reading Mode. The `convenience` mechanism already owns adjacent "what happens when you open a tab" behavior (`alwaysOpenInNewTab`, `Cmd+T → daily-notes:goto-today`, `defaultViewMode: preview`), but does not install or configure this plugin. The user has it working in `accuris-sauce` and wants every consumer vault to get the same behavior automatically.

2. **`smart-connections`** (brianpetro/obsidian-smart-connections) writes the `.smart-env/multi/*.ajson` vector index that the `smart-connections-bridge` mechanism reads via its Node CLI (`sc-bridge.js`). Scheduled jobs and skills (`cowork:gather-semantic-related`, `cowork:gather-semantic-memory`) depend on that index. The bridge mechanism ships the reader but does not declare the plugin as a prerequisite, so a vault that subscribes to the bridge without manually installing SC silently produces empty / stale results. **Observed in production:** the headspace-sauce 2026-06-07 morning-briefing emits `[!warning]+ Semantic index not available` — the orchestrator tried to fetch Echoes, but SC isn't installed.

Both gaps are one-line manifest deltas on existing mechanisms.

## Approach

Single PATCH workshop cycle absorbing two MINOR mechanism bumps + an S0 baseline-cleanup stage to reconcile post-v0.93.2 working-tree drift.

| Surface | Before | After | Bump kind |
| --- | --- | --- | --- |
| `convenience` mechanism | 0.2.4 | 0.3.0 | MINOR mechanism (new behavior: install + configure new-tab-default-page) |
| `smart-connections-bridge` mechanism | 0.1.1 | 0.2.0 | MINOR mechanism (new behavior: declare smart-connections required) |
| `workshop_version` | 0.93.2 | 0.93.3 | PATCH workshop |
| `package.json` version | 0.93.2 | 0.93.3 | PATCH (lockstep) |

No new mechanism. No new installer helper. No new shipped file.

### Why PATCH at workshop level (mechanism MINOR underneath)

The mechanisms grow new behavior (install + configure additional plugins) — that's their MINOR bump. The workshop simply ships the new manifests; no new platform-level surface (`applyExternalPlugins` + `applyCommunityPluginData` already handle everything). Workshop PATCH = no new mechanism, no new helper, no new public API; existing mechanisms may grow internally. Matches sauce convention.

### Why convenience (not a new mechanism)

The `convenience` mechanism already owns the "open-in-new-tab + daily + preview-mode" cluster:
- `app_settings.alwaysOpenInNewTab: true` (platform manifest, works in concert)
- `hotkeys: [{command_id: "daily-notes:goto-today", modifiers: ["Mod"], key: "t"}]`
- `community_plugin_settings: [{id: "dataview", settings: {…}}, {id: "obsidian-tasks-plugin", settings: {…}}]`

Adding `new-tab-default-page` here is one cohesive cycle. A dedicated mechanism would split related behavior across two files for no gain.

### Why mark `smart-connections` as `required: true`

The `required: true` flag is consumed by `_externalPluginsSatisfied` in `platform/install.js` (used today by `applyVendoredThemes`, `applyAppearance`, `applyStyleSettings`). The bridge mechanism currently ships only `files[]` (the sc-bridge.js copy), which does not check that gate — so `required: true` does NOT currently change install behavior. We still mark it required because:

1. **Forward-looking documentation of intent.** If a future cycle adds vendored CSS, appearance settings, or style-settings defaults to the bridge, the gate will already be in place.
2. **Audit clarity.** A reader scanning the manifest sees that the bridge has a hard dependency on the SC plugin, not a soft one.

The actual SC install is driven by `applyExternalPlugins` (which installs ALL `external_plugins[].id` regardless of `required`), so the plugin still lands in `community-plugins.json` and on disk.

### Why no SC settings entry

Accuris-sauce's `.obsidian/plugins/smart-connections/data.json` is essentially empty (`installed_at` + `last_version` only). The user's actual SC config is the plugin's own defaults. Baking `community_plugin_settings[]` for SC would:
- carry a schema the SC author may change between plugin minor versions
- fight the plugin's first-run wizard
- require enumerating exact keys to lock

Install-only is the lighter-touch correct choice. A future cycle can add settings if/when specific keys need locking.

## Out of scope

- **No change to `foundational_plugins[]` in platform manifest.** Both plugins are mechanism-scoped — consumers that disable `convenience` or `smart-connections-bridge` should not get them. Mechanism-scoped is correct.
- **No CSS / snippet / hotkey changes.** new-tab-default-page is self-contained.
- **No SC settings baked.** Install-only (see "Why no SC settings entry" above).
- **No Echoes warning reword.** The `[!warning]+ Semantic index not available` message on headspace will be replaced when SC indexes after install. Rewording the cold-corpus message ("Semantic memory warming up — Echoes will appear once Smart Connections has indexed") was considered for this cycle and explicitly DEFERRED to a follow-up — it touches `cowork:gather-semantic-related` (or wherever the warning originates), which is its own design discussion. Captured as a candidate in the post-v0.93.3 handoff.
- **No migration logic.** Idempotent install: vaults that already have either plugin installed manually keep their existing settings; the writer is `mergeCommunityPlugins` (union + dedupe) + `applyCommunityPluginData` (diff-with-backup overwrite).
- **No new installer helper.** `applyExternalPlugins` + `applyCommunityPluginData` already do everything we need.
- **No de-personalization, knob refactor, cross-machine wrapper portability, or vault-config migration.** Those are queued as sub-themes for v0.93.4 / v0.94.0 / v0.94.1 / v0.94.2 cycles per the brainstorm sequencing.

## Risks & mitigations

| Risk | Mitigation |
| --- | --- |
| new-tab-default-page's data.json schema changes between plugin versions, breaking our baked settings | Schema is small (4 keys) and stable across recent plugin versions. `applyCommunityPluginData` writes `.sauce-backup` before overwriting, so user / next cycle can adapt. |
| SC plugin id changes upstream | Obsidian's community-plugins.json id is the canonical key; the SC plugin is well-established and the id `smart-connections` has been stable since 1.x. Low risk. |
| `required: true` on SC causes installer to refuse on existing vaults where SC isn't installed yet | This is the intended posture — but the same install pass also runs `applyExternalPlugins` BEFORE `applyCommunityPluginData` (verified: `install.js:1071` then `install.js:1080`), so SC will be installed in the same run before its required-flag is checked. |
| Workshop self-install fails because the workshop vault somehow lacks one of these plugins | Workshop is a consumer of itself, so the same install pass installs the plugin if absent. Pre-flight: the workshop vault already has both plugins (verified in accuris; workshop dogfood follows same path). |
| S0 cleanup misinterprets working-tree changes and discards real intent | S0 explicitly investigates each modified file before commit-or-revert decision; the 2 untracked plan docs are preserved (renamed under v0.93.3 names per `supersedes:` front-matter); test-file deltas are inspected line-by-line before either revert-to-HEAD or regen-fixtures. |
| Headspace's cold-corpus "Semantic index not available" warning persists after v0.93.3 ships, leaving the visible gap unfixed | This is acknowledged — SC needs a warm-up cycle (10-30 min on first run) before Echoes light up. The warning is technically correct; reword is queued for a follow-up cycle. User has accepted this trade-off. |
