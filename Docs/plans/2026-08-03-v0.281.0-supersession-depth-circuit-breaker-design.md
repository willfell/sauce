# Supersession-depth circuit-breaker — design

**Cycle:** v0.281.0 · **Date:** 2026-08-03 · **Component:** delivery 0.5.0 → 0.6.0

## Problem

Guardrail #1 (v0.280.0) caps a *single* card's scope and a successor's
`carried_findings` breadth at mint. It does not bound how many times a lineage
may be superseded. A live ero-egnyte-mcp run proved the gap: one `TV-2` slice
spun **27 supersessions and merged nothing** (`TV-2 → TV-2b → … → TV-2aa`).

## Root cause (systematic-debugging Phase 1)

A convergence-free adversarial treadmill:

1. `loop:run`/`loop:execute` rule: review quorum refutes → one same-card repair →
   **second** refutation → supersede-at-mint. The "never a third patch" cap is
   **per-card and resets on every successor** — no lineage memory.
2. The failing slice was a program ("Schema v2 metadata migration": auth, HMAC
   IDs, indexing, deletion labels, replay, restore, Copilot compat, over 4.3M
   files). An adversarial review asked to *refute* always finds a new, genuine
   edge case on a surface that broad. Each `discard_reason` was a distinct
   "second independent correctness/regression-risk refutation" — the prior fix
   verified `pass`; a new issue surfaced. It never runs out.

Two independent supersession-creation surfaces existed, neither depth-aware:

| Surface | Where | Guard | Chain-depth data |
| --- | --- | --- | --- |
| Successor **mint** | `card-intake.js` `validateSupersede`/`run` | `carried_findings` size only | none in scope |
| Predecessor **tombstone** (`superseded_by`) | `codex-coordinator.js` `discardCardCore` — the single chokepoint every `superseded_by` write funnels through | none | full (`state.cards` + `resolveSupersessionTail`) |

The depth data lives exactly where the guard was missing.

## Approach

1. **Registry threshold** — `policies.slice_scope_caps.supersession_depth = 3`
   (tunable; `0`/absent disables). Thresholds stay in the registry, never as JS
   literals.
2. **Hard guard in `commandDiscard`** — a fresh supersession (`--superseded-by`)
   whose lineage is already at the ceiling is refused **before any write**,
   returning `action: awaiting_user_decision` / `reason:
   supersession_depth_exceeded` with a decompose remediation.
   `supersessionChainDepth(card, state)` walks `superseded_by` backward through
   the ledger. **Gated to `commandDiscard` only** — `commandReap` calls
   `discardCardCore` directly, so corpse cleanup of an already-settled deep chain
   is never blocked (this resolves the reap-ripple concern that deferred the
   guardrail originally).
3. **Read-only `supersession-depth` query** — lets `loop:run`/`loop:execute`
   fail-fast *before* minting a successor the discard would then refuse (no
   orphaned successor left behind).
4. **Skills aligned** — the "second refutation → supersede" step probes the
   query first and escalates to the Director at the ceiling instead of minting.

Every skill routes supersession through the same two scripts (intake mint →
coordinator discard); the hard guard on the discard chokepoint makes the cap
un-bypassable even if a skill forgets the probe. Defense in depth.

## Non-goals / deferred

- **Board-projection bug (DEFERRED to its own cycle).** The same run surfaced a
  separate, larger control-plane bug: some epic atlases carry non-canonical
  (absolute) `source_board`/`kanban_board` paths that the projection contract
  rejects ("does not bind its canonical parent board"), and supersession
  discards can leave a deleted slice's line on the epic sub-board ("slice note
  missing") which poisons that epic's projection forever. Root-caused to
  `card-intake.js` `renderEpicAtlas`/`projectPrefix` writing caller-supplied
  paths verbatim + a discard sub-board cleanup gap. Fixing it robustly needs
  intake path canonicalization + discard orphan-pruning + a cross-vault data
  heal of the ero-egnyte-mcp board — isolated to its own cycle so this
  control-plane change ships alone with its own tests.
