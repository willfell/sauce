## 1. Scope

### 1.1 §1 NEW mechanism `people-identity@0.1.0`

**Location.** `platform/mechanisms/people-identity/{manifest.json, people-identity.js, README.md}` (new directory).

**Class `PeopleIdentity`** (loaded via `customjs-guard` per landmines #1/#2 cold-load TDZ).

Public API (LITERAL signatures):

```js
resolvePerson(input) → personLink | null
findByAlias(type, value) → personLink | null
getAliases(personLink) → Array<{type, value}>
listAliasesOfType(type) → Array<{personLink, value}>
```

Semantics:

- `resolvePerson(input)` — accepts string. Match priority: (1) basename exact (`spice/people/<input>.md`); (2) typed-alias exact match across all person notes (any type); (3) case-insensitive basename; (4) case-insensitive alias. Returns wikilink-format string (`"[[Stefan de Pagter]]"`) or `null`. NEVER throws.
- `findByAlias(type, value)` — type-constrained variant. Skips fuzzy / basename paths. Returns null on miss.
- `getAliases(personLink)` — reads the person note's frontmatter via `app.metadataCache.getFileCache`. Normalizes: typed-object entries pass through; bare-string entries become `{type: "name", value: <string>}`. Returns `[]` if note missing.
- `listAliasesOfType(type)` — walks all `spice/people/*.md`, collects aliases of given type. Used by morning-briefing for inner-circle phone-list build-out (via the sub-skill which exposes the same data to agent context).

Resolution-collision policy: if multiple person notes claim the same alias value (e.g. two people both list `name: "Steve"`), `resolvePerson` returns the FIRST match in folder-sort order AND emits `console.warn("people-identity: alias collision for <input> → [<p1>, <p2>]")`. Validator audit rule promotion to error is deferred (see §9).

No backlink writes; pure read. Module-directory invariant per landmine #19: `spice/people/` hardcoded; never parameterized.

**Manifest.**

```json
{
  "name": "people-identity",
  "version": "0.1.0",
  "kind": "mechanism",
  "module_directory": null,
  "customjs_classes": ["PeopleIdentity"],
  "depends_on": [
    { "name": "customjs-guard", "range": ">=1.0.0" }
  ],
  "files": [
    { "source": "people-identity.js", "dest": "{{scripts_path}}/mechanisms/people-identity.js" }
  ]
}
```

No new install-side helpers required. No `claude_surface[]` entries this cycle (no slash command, no in-vault skill body).

**Out of scope for §1.1.**

- No in-Obsidian callers added in this cycle. The mechanism ships forward-looking; slice E will be its first in-Obsidian consumer.
- No collision-as-audit-error promotion. Warning-only; future cycle.
- No alias-index caching for >500-person vaults. FLN candidate.

### 1.3 §3 NEW sub-skill `cowork:resolve-person`

**Location.** `platform/blueprints/cowork/skills/skills/resolve-person/SKILL.md` (sub-skill tier — nested `skills/skills/` per FLN-v79-4 dest convention; see `Docs/agent-guides/architecture.md`).

**Contract.**

Inputs:

- `input` (string, required): the name / handle / email / alias to resolve.
- `prefer_type` (string, optional): one of `"phone" | "email" | "name" | "handle"`. When set, the resolver runs `findByAlias`-equivalent first; falls back to general resolve on miss.
- `engagement_id` (string, optional): contextual; reserved for future per-engagement scoping (NOT used in resolution logic this cycle — included so call sites don't have to be re-edited at slice E).

Outputs:

- `resolved` (boolean): true iff a person was found.
- `person_link` (string | null): wikilink-format on hit (`"[[Stefan de Pagter]]"`), null on miss.
- `person_basename` (string | null): basename without wikilink syntax (`"Stefan de Pagter"`).
- `matched_via` (string | null): one of `"basename_exact" | "alias_exact:<type>" | "basename_ci" | "alias_ci:<type>" | null`.
- `collision_warning` (string | null): present when multiple matches; pipe-separated candidate basenames.
- `aliases_by_type` (object): `{ phone: string[], email: string[], name: string[], handle: string[] }` aliases of the resolved person, grouped by type. Empty arrays on miss.

Implementation: uses `mcp__obsidian__obsidian_list_files_in_dir` for `spice/people/` + `mcp__obsidian__obsidian_get_file_contents` (frontmatter-only mode where MCP supports it; else full read) to scan candidates. Caches the in-vault person-list per skill invocation only (no cross-invocation cache — gather skills run fresh per tick). Honors back-compat (bare-string aliases = name type).

Failure modes (NEVER throws):

- `input` empty → `{resolved: false, person_link: null, person_basename: null, matched_via: null, aliases_by_type: {phone: [], email: [], name: [], handle: []}}`.
- `spice/people/` doesn't exist → same null shape, stderr `cowork:resolve-person: people directory missing`.
- MCP read fails → same null shape, stderr `cowork:resolve-person: read failure on <path>`.

NEW pure helper `composeResolverOutput(personData, matchContext) → ResolvedOutput` if S2 implementation surfaces enough shape complexity to warrant extraction (default: inline in SKILL.md guidance — decision deferred to plan stage).

## 2. Data flow

### 2.1 Person resolution at gather-time — before vs after

**Before (gather-imessage example):**

1. Morning-briefing reads `engagement.inner_circle_people: ["Stefan de P.", "Patryk"]`.
2. Passes string list to gather-imessage as `inner_circle` — but signature expects E.164 phones. Filter silently matches nothing (or matches by accident if a name string substring-matches a phone display).
3. apple-mcp returns inbound threads with `displayName` field resolved from Contacts: `"Stefan de Pagter"`, `"+13035551212"` (unmatched), `"+17205559999"` (unmatched).
4. Step 6 composes bullets: `**Stefan de Pagter** - [HH:MM] - <preview>`, `**+13035551212** - …`, `**+17205559999** - …`.
5. Atomic note pastes the callout. Person notes accumulate ZERO backlinks. `**Stefan de Pagter**` plaintext is invisible to brain-map rollups.

**After:**

1. Morning-briefing reads `engagement.inner_circle_people: ["Stefan de P.", "Patryk"]`.
2. NEW Step 2 inner-circle resolution. For each name: `cowork:resolve-person { input: "Stefan de P.", prefer_type: "name" }` returns `{resolved: true, person_link: "[[Stefan de Pagter]]", person_basename: "Stefan de Pagter", matched_via: "alias_exact:name", aliases_by_type: {phone: ["+13035551212"], email: ["stefan@x.com"], name: ["Stefan de P."], handle: []}}`. Union all `aliases_by_type.phone` into `inner_circle_phones: ["+13035551212", "+17205551313"]`.
3. Pass `inner_circle: "+13035551212,+17205551313"` to gather-imessage (existing E.164 contract preserved).
4. apple-mcp returns inbound threads with `displayName`.
5. NEW Step 6.5 per-thread resolution. For each thread, `cowork:resolve-person { input: "Stefan de Pagter" || handle, prefer_type: "phone" || "name" }` returns either `{resolved: true, person_link: "[[Stefan de Pagter]]"}` or `{resolved: false, ...}`.
6. Step 6 composes bullets: on hit `**[[Stefan de Pagter]]** - [HH:MM] - <preview>`; on miss `**+17205559999** - [HH:MM] - <preview>` (plaintext fallback).
7. Atomic note pastes the callout. Person notes accumulate backlinks at every render that resolves. Brain-map signal density compounds.

## 3. Edge cases & migration

### 3.1 Pre-existing person notes — alias schema back-compat

| Existing frontmatter | New resolver behavior | Migration |
|---|---|---|
| `aliases: []` (empty array) | Treated as no aliases; basename-only match works. | None needed. |
| `aliases:` (absent / null) | Treated as no aliases. | None needed. |
| `aliases: ["Steve", "Stevie"]` (bare strings) | Each bare string → `{type: "name", value: <string>}` at read time. Resolver hits via `alias_exact:name`. | None needed (back-compat path). Optional: rewrite manually. |
| `aliases: [{type: "phone", value: "+1303..."}]` (typed) | Direct typed match. | None needed. |
| `aliases: ["Steve", {type: "phone", value: "+1303..."}]` (mixed) | Both forms parse per-entry. | None needed. |
| `aliases: [{type: "unknown", value: "x"}]` (unrecognized type) | Opaque; `findByAlias("unknown", "x")` works; not surfaced in `aliases_by_type` for known types. | None needed. |

**No vault-walk migration in this cycle.** Back-compat covers existing data.

### 3.2 Resolver collision policy

When `resolvePerson(input)` matches multiple person notes:

- Returns the FIRST match in folder-sort order. Deterministic.
- Emits `console.warn("people-identity: alias collision for '<input>' → ['Steve A.md', 'Steve B.md']")` (Obsidian side) or stderr `cowork:resolve-person: collision for '<input>'` (agent side).
- `collision_warning` field populated in `resolve-person` sub-skill output.
- Gather skill behavior: emit `[[Person]]` for the first match. Notice surfaced via the orchestrator's existing `warnings:` propagation pattern.
- Future audit-error promotion deferred (FLN candidate; see §9).

### 3.3 Resolver miss → emit plaintext

When resolver returns `{resolved: false, person_link: null}`:

| Gather skill | Plaintext emission |
|---|---|
| `gather-imessage` | `**<displayName || handle>**` (current pre-cycle behavior) |
| `gather-gmail` | `**<sender_name>**` (current pre-cycle behavior) |
| `gather-calendar` | `<localpart>@…` truncated (current pre-cycle behavior) |

No new visible UX on miss. The atomic note looks identical to today for unresolved mentions.

### 3.4 Voice-rule + LLM free-form mention

Body composition by the LLM may mention a person OUTSIDE the gather-skill output paths (e.g., summarizing prior threads, narrating context). The `wikilink_people` voice rule instructs the LLM to emit `[[Person Name]]` for any KNOWN-resolved person.

Definition of "known-resolved" at body-composition time:

- A person whose wikilink already appears in the gathered callouts in the SAME atomic note, OR
- A person whose name appears in the engagement's `inner_circle_people` field (passed into the voice contract as resolved-link list).

This is a finite, explicit allow-list. Risk: LLM may emit `[[Name]]` for an unresolved person, creating a dangling wikilink. Acceptable per the locked "plaintext on miss" choice — dangling wikilinks render with red text and the user can fix them. NOT a regression vs today. Risk: LLM may emit `[[Wrong Name]]` if it confuses two people. Same risk as today's `**Wrong Name**`; voice rule does not amplify.

### 3.5 Inner-circle name unresolved

When `inner_circle_people: ["Stefan de P.", "Patryk", "GhostPerson"]` and `GhostPerson` doesn't resolve:

1. Morning-briefing emits Notice `cowork: inner-circle name "GhostPerson" unresolved; not included in iMessage filter`.
2. iMessage filter list excludes any phone aliases that would have come from GhostPerson — but GhostPerson had none anyway.
3. Atomic note frontmatter gets `warnings: ["inner_circle_unresolved:GhostPerson"]` entry (v0.85.0 plumbing).
4. User fixes by either (a) creating `spice/people/GhostPerson.md`, (b) adding a `name: "GhostPerson"` alias to an existing person, or (c) removing the name from `inner_circle_people`.

### 3.6 Gather skill called for engagement type without iMessage

`gather-imessage` is already type-gated (only fires for `engagement.type == "personal"`). Inner-circle resolution in morning-briefing follows the same gate: don't bother resolving names for engagement types that won't use iMessage. Adds an early-exit in §1.6 Step 2 ahead of the resolution loop.

### 3.7 Resolver called for engagement_id input — reserved field

`cowork:resolve-person` accepts `engagement_id` as optional input but doesn't use it in resolution this cycle. Documented in SKILL.md as "reserved for future per-engagement scoping (e.g., slice E may filter resolution to people mentioned in this engagement's atomic notes)." Call sites in §1.4 + §1.6 pass `engagement_id` even though it's a no-op now, so slice E doesn't have to re-edit every call site.

### 3.8 Cross-blueprint version interlock

- `people@0.6.0` requires `people-identity@>=0.1.0` (NEW depends_on entry).
- `cowork@0.27.0` adds `people@>=0.6.0` depends_on (the sub-skill assumes the typed-alias schema convention is documented in the people manifest's rule fragment for validator coverage).
- cowork does NOT add a depends_on on `people-identity` (cowork's customjs side doesn't call PeopleIdentity directly; the sub-skill is agent-side and reads frontmatter via MCP).
- `people-identity@0.1.0` has no upstream blueprint dep.

### 3.9 Rollback

| Path | Safe? |
|---|---|
| `cowork@0.27.0 → 0.26.0` | Safe. Gather skills revert to pre-cycle bullet shape; atomic notes stop emitting wikilinks. Already-emitted wikilinks remain valid (Obsidian doesn't un-resolve them). |

### 3.10 Migration of consumer vault `inner_circle_people` strings

No migration. Existing strings stay strings. Resolver consumes them at gather-time. If a string doesn't match any person, the user gets a Notice (§3.5) prompting them to fix it.

### 3.11 Edge — large person directory

If a vault has >500 person notes, the resolver walks `spice/people/*.md` per gather-skill invocation. Per-invocation cost: ~500 frontmatter reads via MCP. Acceptable for daily ticks. Slice E may need a cached index if it walks per-mention rather than per-invocation. FLN candidate; no test fixture at scale this cycle.
