## Standing lessons this cycle reinforced

- **A structural install-time migration (moving/renaming files) belongs in `platform/install.js`
  as a Node-side function using the `VaultAdapter` contract**, not as a runtime customjs class —
  even if a superficially-similar sibling blueprint (sticky-notes' `StickyDayMigrate`) is a
  runtime class, because that one only patches a frontmatter field in place; it never
  moves/renames/creates files. Grep for the actual precedent doing the SAME kind of write
  (`applyScratchToStickyNotesMigration` was the right model here, not `StickyDayMigrate`) before
  designing a migration's shape.
- **When a migration's target folder name is already derivable from the source file's own
  existing path** (a flat note already sitting inside its correct `YYYY/MM-MMMM/` folder), reuse
  that path segment instead of recomputing a month name — avoids needing any date-library
  dependency in the Node-side installer, which doesn't have `window.moment` available.
- **Subagent test-writers may need to add environment stubs (`global.window`/`global.customJS`)
  that the plan's literal test text omitted** if the helper under test calls browser/Obsidian
  globals — check for the established stub pattern in a sibling test file
  (`run-sticky-notes-chrome-bar.js` here) rather than inventing one.
- **`run-helper-cases.js` has hardcoded fixture assertions that reference specific file paths
  and frontmatter shapes** (`FA4-TEMPLATES` here) — any cycle that renames/retires a template
  file MUST grep `run-helper-cases.js` for the old filename before declaring preflight green;
  a structural rename can silently break an assertion that isn't obviously related to the
  blueprint being touched.
