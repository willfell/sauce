## Open questions for v0.98.2 brainstorm (5)

1. **learned_weights schema 3 shape.** Flat `per_person.<name>.weight` per-kind (simple, no nesting), or nested under per-kind (`per_kind.chat.per_person.<name>.weight`)? Flat is simpler to read / write; nested enables per-kind isolation when the same person appears in chat AND email AND calendar with different weights.

2. **Voice change apply mechanism.** When ingest proposes voice/personality updates (e.g., "stop surfacing Diana's emails"), how should the user approve them? Option A: proposed-in-next-brief as a `[!note]+ Cowork proposes voice updates` callout; Option B: explicit slash command `/cowork apply-voice-deltas` that the user runs when ready. Option A is lower-friction but risks surprise mutations; Option B is explicit but adds a step.

3. **Free-text LLM model.** `cowork:ingest-feedback`'s structured-output prompt runs against the user's prose. Recommended: Sonnet 4.6 (cost-fast, runs in under 2s, good at instruction-following). Alternative: Opus 4.7 (smarter, slower, higher cost). Lean: Sonnet 4.6 for the default; allow per-engagement override.

4. **Reconciler cadence for feedback ingest.** Should `cowork:ingest-feedback` fire daily (reconciler cadence) or weekly (synthesize-week cadence)? Daily gives faster signal loop; weekly batches more signal per LLM call and reduces noise from single-day fluctuations. Lean: daily during the first 30 days of deployment (warmup window), then weekly.

5. **Per-item DOWNVOTE row (NEW — from 2026-06-10 user vision).** The current Rail L only has per-item LIKE ticks (checkbox → "this mattered"). The user explicitly asked "what if we added a section for didn't like?". Should Rail L gain a second `- [ ]` row per kind for per-item dislikes alongside per-item likes? Sub-questions: (a) same `^item-<kind>-<sha>` block-IDs for downvotes, or a separate `^downvote-<kind>-<sha>` scheme? (b) Does this belong in v0.98.1.x PATCH (additive row only) or v0.98.2 (ship with ingest logic that reads both rows)?

### v0.98.2 reconciler free-text + per-item-tick ingest (NEXT)

Per v0.98.0 design § Forward arc + v0.98.1 result doc § Carry-forward:

- **Parse structured signal (deterministic).** Per-item ticks → looked up against item-ID hash registry → rolled up per-kind, per-person, per-channel weight nudges. Frequency knobs → direct ±0.05 weight delta.
- **Parse free-text (LLM pass).** NEW sub-skill `cowork:ingest-feedback` runs an LLM pass (Sonnet 4.6 recommended) with a structured-output prompt: extract per-person/channel/topic uprank/downrank, voice corrections, coverage gaps, other intents as deltas with proposed write-targets.
- **Apply with audit trail.** Numeric deltas applied directly to `learned_weights`. Microscope `what_matters` strings: append-only. Personality/voice changes: PROPOSED only — surface in next-day morning brief as a callout. Coverage gaps: written to `spice/cowork/memory/<engagement>/coverage-queue.md`. All deltas logged to `spice/cowork/memory/<engagement>/feedback-deltas.md`.
- **`learned_weights` schema 2 → 3.** v0.98.2 bumps; v0.98.1 EXPLICITLY stays at 2.
- **Sizing.** MINOR; needs full brainstorm + design phase. 5 open questions above must be resolved before the design is locked.
