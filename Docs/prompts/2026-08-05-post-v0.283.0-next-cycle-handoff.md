## What workstream 4 is actually about

Coordinator state lives in `.git/sauce-autoloop/state.json` — **local per
clone**. Two consequences the last three workstreams kept running into:

1. A board member with a coordinator-format `status_changed_at` stamp and no
   local record is *not* drift; it means another clone's ledger holds the
   record. `board-health` had to grow a whole provenance classification
   (`untracked_members_by_provenance`) to say "64 of these 164 findings are not
   actionable here" — a workaround for the ledger's locality, not a feature.
2. `adopt` exists partly because there is no way to reconstruct what happened
   from evidence. The rail's memory is a file on one machine.

The design question is whether the ledger becomes vault-resident, or becomes
**reconstructable from evidence** (boards + merged PRs + merge SHAs — the same
provenance `adopt` already records), or stays local with the locality made
explicit everywhere. Reconstructability is the more interesting option and is
now partly instrumented: `adoption.{pr, merge_sha, verified}` is exactly the
shape a rebuild would consume.

**Size it from data again.** Workstream 3's frequency verdict was *negative* —
out-of-band completion happened once in four days — and the cycle was justified
by a different measurement entirely (`KanbanStatusSyncInit` running at vault
boot in every consumer vault). Run `board-health --json` against the loop-bound
repos and read `untracked_members_by_provenance` before designing anything. Do
not build for a predicted failure rate.

## Test-authoring rule this program learned the hard way

Workstream 3 shipped **two separate rounds** of tests that could not fail for
the reason they named, both caught only by mutation-testing the assertion:

- a test that injected `readState: () => state` and then asserted on that same
  live in-memory object — it passed whether or not anything was ever persisted;
- a test that used a regex where **exact byte equality** was the property under
  test — it survived a write that changed the bytes.

**A passing test is evidence only once you have watched it fail for the reason
it names.** Assertions on injected live objects, and substring/regex assertions
standing in for byte equality, are the two shapes that most reliably pass
vacuously. For anything touching the ledger, assert against a **re-read
on-disk** ledger with real `readState`/`writeState`, and prefer the real
`withLock` over an injected one when lock nesting is part of what you are
claiming.
