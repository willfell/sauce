**Surface to brainstorm (carry-forward from the v0.89.0 handoff §Workstream 2; expanded with v0.89.1 hindsight):**

- **Skill name + invocation pattern.** `cowork:discover-people`? Top-level `/discover-people`? Sub-command of `/cowork`? Mirrors `cowork:bootstrap-vault`'s positioning?
- **Connector-agnostic detection.** Use mcp-skill-map.json v2.0.0 capability matching (in cowork@0.27.x). For each "kind" present (chat / email / calendar / chat-alt / ado / github / etc.), run kind-specific discovery.
- **Per-kind discovery logic.** Chat: extract `from.displayName` distinct senders over last 30 days, frequency + reply-owed counts. Email: extract sender emails over last 30 days. Calendar: extract attendee emails from past + upcoming events. GitHub: PR authors / reviewers / assignees. ADO: ticket assignees / commenters. Each kind has different MCP tool signatures.
- **Aggregation + scoring.** Cross-kind dedup (Stefan as Teams sender + Outlook sender + calendar attendee + GitHub PR reviewer → ONE person). Scoring: frequency by kind, recency, "reply owed" count, mention-of-Will count. Output: ranked candidates with confidence + signal explanation.
- **Cross-reference against existing person notes.** Use `cowork:resolve-person` (already shipped v0.89.0) per candidate. On hit → enrich existing note with newly-discovered typed aliases (e.g., add a discovered phone alias). On miss → propose new stub person note. Detect cross-kind handle duplicates before stubbing.
- **Inner-circle classification.** Score-based threshold? User-confirm interactive prompt per candidate? Auto-classify based on engagement scope (the accuris engagement's `calendar_id`-scoped events vs out-of-scope events)?
- **Vault writes.** Person-note creation via `entity-create` programmatic API (slice C scope from v0.89.0 design but deferred). Vault-config updates to engagements' `inner_circle_people` arrays. Optionally microscope contract updates (add the discovered inner-circle name to chat/people-aliases.md and similar). Dry-run / rollback story?

Per-engagement scope rules need to be explicit (engagement.calendar_id, engagement.gmail_label, engagement.work_email, etc.). Discovered people that don't fit any engagement → "unscoped" bucket.
- **Privacy / scope guardrails.** When running on accuris's M365 connector, do NOT pull from connectors associated with the user's personal life (gmail.com, iMessage personal). Engagement-scoped MCPs is the v0.85.x/v0.86.x territory; needs to integrate cleanly.
- **Repeatability.** Re-run after 30 days: add net-new people, don't duplicate. Idempotent updates. Don't blow away user hand-edits to inner_circle_people.
- **User interaction surface.** Fully autonomous? Confirmation per candidate? Batch confirmation? Slack-style interactive review? Atomic-note-style "Here are 25 proposed updates — apply / skip / edit"?
