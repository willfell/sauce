## Workstream A — FLN-v88-8 audit + cleanup

**Problem.** Every install-side helper that merges entries from a blueprint manifest into a consumer-vault state file is potentially additive-only. v0.88.2 closed the case for `applyTemplaterFolderTemplates` by introducing `removed_templater_folder_templates` + `applyTemplaterFolderTemplateRemovals`. The same pattern needs to be applied (or proven unnecessary) for every sibling helper:

- `applyTemplaterFolderTemplates` ← already fixed in v0.88.2
- `applyTemplaterStartupTemplates` — find its call site + implementation; assess
- `applyTemplaterHotkeys` — same
- `applyTemplaterFolderTemplateHotkeys` (if it exists) — same
- `applySlashCommanderBindings` — same
- Any `nav_buttons` install-side merger
- `applyClaudeSurface` (claude_surface[] — slash commands + skills + claude.md table rows)
- `applyCustomJsStartupScripts`
- `applyCommunityPluginData`
- `applyCorePluginSettings` (probably immutable user config — but verify)
- `applyExternalPlugins` (subscribe-only — probably safe)
- The customjs_classes registration path (`customJS` global)
- Any registry entries (e.g. `ranch/entity-create-registry.json`, `ranch/claude-surface-registry.json`, `ranch/nav-buttons-registry.json`)

**Approach options to brainstorm:**

1. **Per-helper symmetric cleanup**. Each `applyXxx` gets a counterpart `applyXxxRemovals` + a matching `removed_<x>: [...]` manifest field. Mirrors v0.88.2 exactly. Pro: minimal-blast-radius per helper; explicit declaration is auditable. Con: N new fields + N new helpers; manifest surface grows; future blueprints have to remember to declare.
2. **Generalized `pre_install_cleanup` directive**. One manifest field like `pre_install_cleanup: [{ kind: "templater_folder_template", folder: "spice/people" }, { kind: "templater_hotkey", id: "..." }, ...]` + one dispatcher in install.js that routes per `kind`. Pro: extensible via new `kind` values; central registry. Con: more complex; harder to reason about; one wrong `kind` mis-classifies the cleanup.
3. **Compute-orphans-from-installed-history**. Every blueprint install records what it added in `platform-installed.json`. The installer reads the previous install record and computes "entries this blueprint USED to add but doesn't anymore" → cleanup. Pro: declarative-by-omission; blueprint authors don't need to remember anything. Con: history file is large (3.8MB on accuris); requires confident history-shape contract; subtle around manual user edits.
4. **Lazy — only fix surfaces that have a known regression**. Audit each helper once. If it has a known case where a blueprint retired an entry that's still active in consumer vaults, add the cleanup directive. If not, document the limitation in landmines.md and move on. Pro: smallest surface change; YAGNI. Con: latent regressions when blueprints retire entries the audit didn't predict.

**Bonus consideration — `--bump-pins` drift.** The active-pantry-vs-libexec mismatch is technically a separate bug but touches the same install layer. Should it be folded into Workstream A's cycle, or kept as its own FLN-v88-9?

**Scope estimate.** Probably a MINOR cycle (~5-8 stages) if Approach 1 or 4. MAJOR-feeling if Approach 2 or 3.

## Workstream B — Cowork ↔ People integration

**Problem.** Cowork's scheduled jobs (morning-briefing, midday-tripwire, eod-review, weekly-review, monthly-review, synthesize-day, synthesize-week, distill-week-when-shipped) produce output that mentions humans as **plain text strings** (`**Will**`, `**Stefan**`, `**Patryk Szelagowski**`). They don't emit `[[Person]]` wikilinks. Person notes accumulate zero backlinks from cowork activity, even though cowork is the workshop's primary signal source about who-was-doing-what-when. The brain-map that slice E will eventually build has no data to feed on.

This is **slice D of the original people-cohesion arc** (wikilink-in-output convention) — possibly bundled with **slice C** (cowork auto-stub people) since they're tightly coupled (you can't emit `[[Patryk Szelagowski]]` reliably if Patryk hasn't been stubbed yet).

**What's already in place:**

- `cowork:gather-imessage` sub-skill — pulls iMessage threads, emits `**[Contact display]**` plain text. (`platform/blueprints/cowork/skills/skills/gather-imessage/SKILL.md`.)
- `cowork:gather-gmail` sub-skill — similar pattern for Gmail.
- `cowork:gather-calendar` sub-skill — similar.
- `engagement_field_offer` `people.inner_circle_people: string[]` — comma-separated list of names used for iMessage filtering. NOT linked to person notes.
- `people-rendering@0.1.0` mechanism with `PeopleRendering.renderChip(parent, personLink, opts)`, `renderCard`, `renderMentionList`, `extractMentions` — already extracts `[[Person]]` wikilinks from markdown bodies and resolves them against `spice/people/*.md`. Read this mechanism first.
- `app.metadataCache.getFirstLinkpathDest(linkpath, "")` is the canonical resolution path used by people-rendering.
- v0.88.0 + v0.88.2 mean person creation is now clean. Stubs created from gather skills will land correctly.

**What's missing:**

- A reusable resolver: `resolvePerson(handle | email | name | alias) → personLink | null` callable from gather skills. Probably a new mechanism: `people-identity@0.1.0` (or extend `people-rendering`).
- Aliases as typed entries in person frontmatter: `aliases: [{type: "phone", value: "+13035551212"}, {type: "email", value: "x@y.com"}, {type: "name", value: "Steve"}]`. Currently `aliases:` is an empty string array with no convention.
- A `stub-person` operation gather skills can call when a contact doesn't resolve. Should probably use `entity-create` programmatically (or a new dedicated helper) so the stub lands at `spice/people/<Name>.md` with `type: person`, `created_at`, `aliases: [{type: "<source>", value: "<handle>"}]`, and a `provenance: { source: "imessage", first_seen: <ISO> }` field for audit.
- Wikilink-emission convention for cowork writers — replace `**Name**` with `[[Name]]` in the body composition stage of every atomic-note orchestrator.
- A naming convention for handle-only contacts (phone numbers, opaque email aliases): do we create `spice/people/+13035551212.md` and rely on the user to rename later? Or skip stub creation until a real name is known? Slice B's identity-resolution mechanism implicitly answers this.

**Forward-reference from v0.88.0 design §9 (verbatim):**

> - **Slice B — identity-resolution mechanism.** New mechanism `people-identity` (or extension to `people-rendering`) exposing `resolvePerson(handle | email | alias) → personLink | null`. Aliases list extended with typed entries.
> - **Slice C — cowork auto-stub people.** Gather-imessage / gather-gmail / gather-calendar pipe unknown contacts through `resolvePerson`; on miss, create a stub via entity-create's API (not Templater) with the source handle as the first alias. Stub gets a `provenance: { source: "imessage", first_seen: <ISO> }` field.
> - **Slice D — wikilink-in-output convention.** Cowork writers (morning briefing, EOD review, weekly synth, monthly review) replace `**[Contact name]**` plain text with `[[Person Name]]` wikilinks. Person notes accumulate backlinks → brain map starts emerging.
> - **Slice E — brain-map fields + rollups.** Person notes gain dataviewjs blocks for: last-interaction-date, interaction-frequency, co-occurrence top-3, engagement-context, semantic similarity.

**The user's framing (verbatim from the handoff message):**

> "incorporating people more prompting wise within the claude cowork mechanisms that we have going on with scheduled jobs"

This phrasing suggests Workstream B should focus on:

1. **Prompt-engineering side** — every cowork sub-skill / orchestrator that mentions humans should be instructed (in its prompt body) to emit `[[Person Name]]` wikilinks. This is the writing-side convention.
2. **Resolution side** — the prompt also needs to be told *how* to resolve unknown contacts (handle → existing person, or stub-new-person if no match).
3. **Reference side** — once accumulated, person notes should be reverse-readable: which cowork tick first mentioned this person? What's the frequency over the last 30 days? That's slice E territory but slice D unlocks it.

**Open design questions to brainstorm:**

- Slice B + C + D together (one big cycle), or B then C then D (three smaller)?
- Where does the resolver live — extend `people-rendering` or new `people-identity` mechanism?
- Alias schema — typed objects (`{type, value}`) or flat strings with prefix conventions (`"phone:+1303..."`)?
- Stub naming for handle-only contacts — what's the canonical filename when there's no name yet?
- Should `bootstrap.engagement_field_offer.people.inner_circle_people: string[]` be migrated to `[[Person]]` wikilinks (linked to person notes), or kept as a flat string list filtered post-resolution?
- Cowork prompt template — central voice block update vs. per-orchestrator carry?
- Backfill — populate person backlinks for the last N days of memory.md / synthesis.md, or only forward from this cycle?
