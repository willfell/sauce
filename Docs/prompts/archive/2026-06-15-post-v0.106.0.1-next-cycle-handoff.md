## Investigation: Finance Blueprint mis-routed task-note — **one-off, NOT widespread**

User report: clicked "+ Add a card" on `headspace-sauce/spice/projects/sauce/sauce-board.md`, typed "Finance Blueprint" — file landed at `docs/knowledge/Finance Blueprint.md` instead of the expected `tasks/Finance Blueprint/Finance Blueprint.md`.

**Findings:**
- The mis-routed file has BOTH `type: doc-note` frontmatter AND kanban metadata (`kanban_board`, `kanban_column`, `status`, `status_changed_at`). Unusual mix.
- The body has SpaceNavButtons + ProjectNavButtons but NO breadcrumb block — pre-v0.103.0 template shape.
- Scan across both consumer vaults (`headspace-sauce`, `accuris-sauce`):
  ```bash
  find spice/projects -path "*/docs/*" -name "*.md" -exec grep -l "kanban_board" {} \;
  ```
  Returns exactly ONE file (the Finance Blueprint instance). All other consumer vaults clean.
- The expected location IS intact: `tasks/Finance Blueprint/Finance Blueprint.md` (created Jun 14 15:49) + `tasks/Finance Blueprint/board/` subfolder with prior task-board content.
- The mis-routed doc-note was created 5 minutes later (15:54:47).

**Most plausible root cause:** the user (a) navigated into a section hub (`Knowledge.md`), (b) clicked `+ New Doc`, (c) typed "Finance Blueprint" which matched the kanban card name they'd already created earlier. The doc-note entity-create wrote to `docs/knowledge/`. Then the **kanban-status-sync mechanism** (which watches files referenced from kanban boards and writes status frontmatter into them) saw a file named "Finance Blueprint" referenced from the board and stamped kanban fields onto it.

**Recommendation:** treat as a user-confused-flow incident, not a code bug. Cleanup options:
1. Delete the mis-routed `docs/knowledge/Finance Blueprint.md` (the canonical task-note + board already exist at `tasks/Finance Blueprint/`).
2. OR add a small safety check in the doc-note entity-create flow: if a wikilink-equivalent task-note already exists at `spice/projects/<slug>/tasks/<title>/<title>.md`, prompt the user "A task with this title already exists — open that instead?"

Earmark Option 2 as a small v0.107.x patch idea — not P0.

## v0.107.0 design brief — projects visual overhaul

The user spelled out the overhaul in detail. Brainstorm session at the start of the next cycle MUST cover each of these. **Quote-level capture follows so a fresh session has zero context loss.**

### A. Projects Hub (`spice/projects/Projects.md`)

> "loading up the actual Projects hub spice/projects/Projects.md — it doesn't look too bad, but potentially adding in that search bar like you did with the other mechanism, would be great."

- **Decision:** add the **DocSearch-equivalent filter strip** above the projects card grid. Reuse the DocSearch pattern (permanent strip + transient results container, persistent filter state, debounce) — just scoped to projects (filter on `type: project` notes by name + tags).
- **Implementation:** new helper `ProjectsHubSearch` OR generalize DocSearch into a reusable `EntitySearch` mechanism (decide at brainstorm).

### B. Project page (`<Project Name>.md` — e.g. `Global K8s.md`)

Current shape (verbatim from user):
```
Status → ProjectStatusWidget
Workstreams → ProjectWorkstreamManager
Mentions → BacklinkPanel
Project Notes & Referenced By → ProjectNotesCards + ProjectReferencedByCards
```

**User-requested changes:**

1. **Status section** — remove the `## Status` H2 label (keep the widget). User: "Status is fine, but we don't need the 'Status' above it, as well as it doesn't need that match gap vertically between other sections." Tighten vertical spacing.

2. **Workstreams** — keep, but move LOWER. User: "I just believe that it should maybe go lower?"

3. **Mentions section** — REMOVE entirely. User: "The mentions section should go away."

4. **Project Notes & Referenced By callout** — REMOVE entirely. User: "The project notes and referenced by should go away as well."

5. **NEW Meetings section** — add. User: "There should be a 'Meetings' Section, showing a list of cards of meetings that are connected to the project, showing maybe 3 Max, displaying the people who attended, to do items for it, etc, like we do visually within `await dv.view('ranch/views/customjs-guard', { class: 'SpaceDailyDashboard' });` for meetings."
   - **Read first:** look at `SpaceDailyDashboard` helper's meeting-card rendering — that's the visual reference.
   - Cap at 3 meeting cards. Each shows attendees + action items (open task count) + maybe summary line.
   - This is DIFFERENT from the v0.102.0 `ProjectMeetingsPanel` (which only showed date + name + attendee count). v0.107.0 enriches per the SpaceDailyDashboard pattern.

### C. Docs landing (`Docs.md`)

> "It's not bad, but sections should have maybe some more meta data within it, not sure what, but it just looks bland. Like, showing details of last updated, and ordering that way would be good."

- Section cards on `Docs.md` currently show name + doc-count meta. Add:
  - Last-updated timestamp (most recent doc-note mtime in the section)
  - Order section cards by last-updated DESC
  - Possibly: most recent doc title as a subtitle
- Implementation: extend `ProjectDocsIndex._renderResults()` section card synthesis to compute and include the last-updated field. Sort `sections` array by computed last-updated before rendering.

### D. Section Hub UI standardization (`SectionHub`)

> "Opening up a section.. visually it's not bad, But the styling for Sub-Sections and Docs just... could usually have a spice up. Every use of 'Sub-sections' - that text, that's within `await customJS.SectionHub.render(dv);` could utilize a makover, as it tends to just look bleh? Maybe a '---' would help with that around these sections to separate things, as well as making the text smaller. They're everywhere in this blueprint and it needs to be fixed"

- **Headings** ("Sub-sections", "Docs") look bleh and inconsistent. Replace `dv.header(3, …)` with a custom small-text styled label + `---` separator above. Apply consistently to `SectionHub`, `ProjectDocsIndex`, and the new project-page Meetings section.
- **Build a shared `SectionLabel` rendering primitive** (e.g. a `_renderSectionLabel(parent, text)` helper) and use it in every project-blueprint helper that draws a section label. Standardization.

### E. Breadcrumb everywhere + marker visibility cleanup

> "do you see how within some notes, there is `await dv.view('ranch/views/customjs-guard', { class: 'Breadcrumb' });` like within spice/projects/global-k8s/docs/knowledge/testing-knowledge.md — well, I really like it, and I want that implemented every where it can as well, while trying to remove the `<!-- breadcrumb-v1.17.0 -->` that shows, I hate when that shit shows, but functionality wise it's very useful."

**Two parallel asks:**

1. **Add Breadcrumb to every project-related note** that doesn't already have one. This means:
   - Project hub (`<Project Name>.md`) — currently NO breadcrumb. Add as first block.
   - `Docs.md` — has it (added v0.103.0). Keep.
   - Section hub / sub-section hub — has it. Keep.
   - Doc-note — has it (v0.103.0 migration added it via marker). v0.105.0 removed the marker from the template (Issue 2) but existing migrated docs still carry the marker.
   - Project Map, Project Board — currently no breadcrumb. Add.
   - Task notes — add.

2. **Remove the `<!-- breadcrumb-v1.17.0 -->` marker from existing migrated doc-notes.** This marker:
   - Lives at the top of every doc-note migrated by v0.103.0's `applyProjectSectionsHubMigration._migrateDocNote`.
   - Was the idempotency guard for the migration step.
   - Is visible in source-mode editing and clutters the view.
   - Should be stripped — once v0.103.0 migration has run, the marker has done its job and can be removed.
   - Migration step needs to (a) stop injecting the marker on FUTURE runs (already removed from doc-note template in v0.105.0); (b) emit a new install step `applyDocNoteBreadcrumbMarkerCleanup` that walks every doc-note + strips the marker (idempotent — if absent, no-op).

### F. Standardization / consistency

> "Standardization on appearence, UI / Nav Patterns, ensuring it's consistent for projects will be great. That's what I'm looking for."

- Audit every project-blueprint helper. Establish a small set of shared rendering primitives:
  - `Breadcrumb` (already exists — extend usage)
  - `SectionLabel` (new — replaces all per-helper `dv.header(3, …)` calls)
  - `EntitySearch` (potential — generalize DocSearch for projects hub)
  - `MetaChipStrip` (potential — generalize the dashboard chips for any hub-like surface)
- Document the standard in `Docs/agent-guides/project-blueprint-ui.md` (new agent-guide file) so future helpers conform.
