## Two workstreams up for brainstorm in the next session

### Workstream 1 — v0.89.1 PATCH: wire `cowork:resolve-person` into `gather-from-served-by`

**Problem.** Per the audit, microscope-driven vaults (accuris, possibly others) don't get v0.89.0's gather-time resolver-call + wikilink-emit because `gather-from-served-by` was untouched by v0.89.0. Voice rule still applies but soft.

**Surface to brainstorm:**

- WHERE in gather-from-served-by's dispatch should the resolver call happen? Per-sender-during-output-composition? Pre-flight aggregation pass? The dispatch contract is currently passed verbatim to the called LLM — needs a Step that says "before emitting any bullet that names a person, call cowork:resolve-person; on hit emit [[Person]], on miss emit plaintext."
- Does this require updating the **microscope contracts** the user has already authored (so they instruct wikilink emission), OR is updating gather-from-served-by's SKILL.md prose + the dispatch envelope sufficient? Microscope contracts are user-owned and shouldn't be force-overwritten.
- New input to gather-from-served-by — `engagement_id` + `inner_circle_people` so it can know who's worth resolving aggressively vs treating as ambient.
- Coverage: does this Path also automatically work for any custom-kind microscopes (e.g. accuris's ado / github kinds)? They mention people too. The fix should be general, not chat/calendar/email-specific.

**Versioning.** PATCH (`cowork 0.27.0 → 0.27.1`) if scope is purely additive prose changes to gather-from-served-by. MINOR (`cowork 0.27.0 → 0.28.0`) if it introduces a new helper or formal microscope-authoring guidance update.

**Scope estimate.** 4–5 stages if PATCH, 6–8 stages if MINOR with microscope authoring contract update.

### Workstream 2 — NEW connector-agnostic people-discovery skill

**Problem.** Setting up `inner_circle_people` + creating person notes + adding typed aliases is currently 100% manual per-vault. The user has 11+ canonical inner-circle people in the accuris chat microscope, but only 1 (`Stefan de Pagter`) populated in vault-config + with typed aliases. Manual setup doesn't scale.

**User framing (verbatim):** "let's also think about a potential skill / prompt that's baked into sauce, that we can hit with a prompt within claude, that will go through and utilize mcp tools to figure people, determine inner circle and other people, and go through and start updating the vault so that all scheduled jobs are baked in with people — no matter what vault you're in no matter what connector you're using."

**Surface to brainstorm:**

- **Skill name + invocation pattern.** `cowork:discover-people`? `cowork:bootstrap-people`? `people:discover`? Top-level slash command `/discover-people`? Sub-command of `/cowork`?
- **Connector-agnostic detection.** Use mcp-skill-map.json v2.0.0 capability matching (already in v0.27.0 cowork; checks tool-name presence not namespace regex). For each "kind" present (chat / email / calendar / chat-alt / etc), run kind-specific discovery.
- **Per-kind discovery logic.** Chat: extract `from.displayName` distinct senders over last 30 days, with frequency + reply-owed counts. Email: extract sender emails over last 30 days. Calendar: extract attendee emails from past + upcoming events. GitHub: PR authors / reviewers / assignees. ADO: ticket assignees / commenters. Each kind has different MCP tool signatures and surfaces different identifying signals.
- **Aggregation + scoring.** Cross-kind aggregation — Stefan as a Teams sender (chat) + Outlook sender (email) + calendar attendee + maybe github PR reviewer all need to dedupe to ONE person. Scoring: frequency by kind, recency, "reply owed" count, mention-of-Will count. Output: ranked candidates with confidence + signal explanation.
- **Cross-reference against existing person notes.** Use `cowork:resolve-person` for each candidate. On hit → enrich existing note with newly-discovered typed aliases (e.g., add a `phone` alias from chat handle). On miss → propose new stub person note. Detect cross-kind handle duplicates (Stefan's email vs his Teams display name) before stubbing.
- **Inner-circle classification.** Score-based threshold? User-confirm interactive prompt per candidate? Auto-classify based on engagement scope (the accuris engagement's `calendar_id`-scoped events vs out-of-scope events)?
- **Vault writes.** Person-note creation via `entity-create` programmatic API (slice C scope from v0.89.0 design but deferred). Vault-config updates to engagements' `inner_circle_people` arrays. Optionally microscope contract updates (add the discovered inner-circle name to chat/people-aliases.md and similar). What's the rollback / dry-run story?
- **Engagement scoping.** Person discovered via accuris work email + work calendar should be classified under accuris engagement's inner_circle, NOT the user's personal engagement. Per-engagement scope rules need to be explicit (engagement.calendar_id, engagement.gmail_label, engagement.work_email, etc.). Discovered people that don't fit any engagement → "unscoped" bucket.
- **Privacy / scope guardrails.** When running on accuris's M365 connector, the skill should NOT pull from connectors associated with the user's personal life (gmail.com, iMessage personal). Engagement-scoped MCPs is the v0.85.x/v0.86.x territory; needs to integrate cleanly.
- **Repeatability.** Re-run after 30 days: should add net-new people, not duplicate. Idempotent updates. Don't blow away user hand-edits to inner_circle_people.
- **User interaction surface.** Fully autonomous? Confirmation per candidate? Batch confirmation? Slack-style interactive review? Atomic-note-style "Here are 25 proposed updates — apply / skip / edit"?

**Versioning.** Almost certainly MINOR — new sub-skill = new files[] entry in cowork manifest + new claude_surface entry. `cowork 0.27.0 → 0.28.0` (assuming WS1 is PATCH 0.27.1) or `cowork 0.27.0 → 0.29.0` (if WS1 is MINOR 0.28.0). Possibly involves `entity-create` PATCH bump for programmatic API exposure if the skill creates person notes via that path.

**Scope estimate.** 10–14 stages depending on UX choices. Bigger than v0.89.0 was.
