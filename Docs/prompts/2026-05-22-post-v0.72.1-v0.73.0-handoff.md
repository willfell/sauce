## The bug you're fixing

**User report (verbatim, accuris consumer vault):**
> "When I load up the daily note, with information showing up on the daily activity feed - when scrolling down it resets and goes back to the top of the page - it's an infinite loop of this happening, and ruins the actual utilization of it. Activity section: sometimes auto-open, sometimes auto-collapsed. Items inside don't show until I click the section, click it again. Everytime it gets choppy these smart-connections logs flood."

**What I've confirmed:**

1. **Headspace consumer vault is fine.** No scroll resets, no choppiness. Difference: headspace doesn't have the `smart-connections` plugin enabled. Accuris does.

2. **Our v0.72.1 cache is working as designed.** On Friday 2026-05-22, `syncAllBoards` is hitting the cached path: zero writes. So our code is no longer mutating card frontmatter today. The 283-card write storm on accuris was Thursday 2026-05-21 (one-time).

3. **Re-renders are still happening despite zero writes from us.** This means an EXTERNAL trigger is causing Dataview to invalidate the daily-note's dataviewjs subscription, which re-executes the block and rebuilds the DOM. Best-guess cause: `smart-connections` is still chewing through its embedding backlog and its file-system activity is the trigger. Strong correlation in user logs.

4. **The "double-click to show items" is a separate rendering race**, likely pre-existing: `await customJS.ActivityFeed.render(...)` returns before `customJS.BeaconCards.render(...)` finishes painting child rows. By the time the user toggles the `<details>` element open/closed/open, painting has completed.

**What the user has NOT yet done:** they have NOT temporarily disabled smart-connections to confirm causation. We're proceeding under the strong-correlation assumption. If they do confirm/refute mid-cycle, adjust accordingly. The fix below is value-add regardless.

## What you're shipping — v0.73.0

Three architectural changes plus an efficiency audit pass on `activity-feed.js`. All in one cycle.

### Part A — Move `syncAllBoards` out of the dashboard render

Goal: remove our code from the hot path of every dataviewjs re-execution.

**Implementation:**

1. **New customjs class `KanbanStatusSyncInit`** with an `async onload()` method that:
   - Waits for `app.plugins.plugins.dataview?.api` to become available (retry-with-backoff, max ~30s)
   - Computes `today` from `window.moment().format("YYYY-MM-DD")` (or native Date fallback)
   - Calls `customJS.KanbanStatusSync.syncAllBoards(dv, today)`
   - Logs success/failure to console; emits a `new Notice("Kanban status synced")` only on actual writes (not no-ops)
   - Is **idempotent** — safe to re-invoke. The KanbanStatusSync session cache (v0.1.1) already enforces this.

2. **Add `customjs_startup_scripts: ["KanbanStatusSyncInit"]`** to `kanban-status-sync/manifest.json`. The installer propagates this to each consumer's `.obsidian/plugins/customjs/data.json` `startupScriptNames[]` (workshop precedent: `ProjectTaskCreateListenerInit`, `ToDoMigrateInit`).

3. **Add the class to `customjs_classes`** array on the manifest. Final list: `["KanbanStatusSync", "KanbanStatusSyncInit"]`.

4. **Add a new file entry** to `manifest.json` `files[]`:
   ```json
   { "source": "kanban-status-sync-init.js", "dest": "{{scripts_path}}/kanban-status-sync/kanban-status-sync-init.js" }
   ```

5. **REMOVE the `syncAllBoards` call** from `platform/blueprints/daily/helpers/space-daily-dashboard.js`. Find the v0.12.0 sync shim (just before `await customJS.ActivityFeed.render(activityShim, { ... })` in the activity-section block). Delete the whole `if (customJS && customJS.KanbanStatusSync && ...)` wrapper. The activity-feed call stays unchanged (still passes `tsKeys`).

6. **Update space-daily-dashboard.js's docstring** at the top of the file to note: "v0.13.0 (sauce v0.73.0): syncAllBoards moved out of render to KanbanStatusSyncInit startup script. Dashboard renders read pre-synced frontmatter."

**Bump** `kanban-status-sync` to `0.2.0` (minor — new class, behavior change). Bump `daily` blueprint to `0.13.0` (minor — removed inline sync call).

### Part B — Persist `<details>` open/closed state across re-renders

Goal: when the dashboard re-renders (caused by external triggers we can't prevent), the user's chosen open/collapsed state for each section/group sticks.

**Implementation:**

1. **State file:** `ranch/cache/dashboard-section-state.json`. Schema:
   ```json
   {
     "_version": 1,
     "states": {
       "sauce-daily-dashboard:activity": true,
       "sauce-daily-dashboard:tasks": true,
       "sauce-daily-dashboard:meetings": false,
       "sauce-activity-feed:cowork": true,
       "sauce-activity-feed:scratch": false
     }
   }
   ```

   Keys are namespaced by section family (`sauce-daily-dashboard:<sectionName>` for top-level Tasks/Meetings/Activity panels, `sauce-activity-feed:<groupKey>` for inner groups like `cowork`/`project`/`kanban`/`scratch`).

   Values are `true` for open, `false` for closed.

2. **`_renderSection` (space-daily-dashboard.js):** Read state from the JSON file. If a key exists for this section, override the passed-in `defaultOpen`. Attach a `toggle` event handler to the created `<details>` element that writes the new state back. Use `app.vault.adapter.read`/`write` for the JSON file; `try`/`catch` and silently default to `defaultOpen` if file missing or unreadable.

3. **Activity-feed framed renderer (`activity-feed.js`):** Same pattern for each inner-group `<details>` element. Use the group's `bucketKey` (after `bucketRules`) as the persistence key. Read on render; toggle handler writes back.

4. **Atomic state file writes:** if multiple toggles fire in quick succession, last-write-wins is fine — no merge logic needed. Just stringify-and-write the full state object on each toggle.

5. **No new mechanism for state persistence** — it's a couple of helper functions added to the relevant files. Keep it lightweight.

**Bump** `activity-feed` to `0.7.0` (minor — new state-persistence behavior). Bump `daily` blueprint (also bumped by Part A) to reflect the new dependency range: `activity-feed >=0.7.0`.

### Part C — Manual re-sync command

Goal: a user who moves a card mid-session and wants to see it immediately in the feed can trigger a sync without restarting Obsidian.

**Implementation:**

1. **Register a Slash Commander command** OR an Obsidian command palette entry. The latter is simpler — customjs can register Obsidian commands via `app.commands.addCommand` in the init script. Add to `KanbanStatusSyncInit.onload()`:

   ```javascript
   app.commands.addCommand({
     id: "kanban-status-sync:resync-now",
     name: "Sauce: Re-sync kanban boards",
     callback: async () => {
       // Bypass the once-per-day cache
       customJS.KanbanStatusSync._lastSyncDay = null;
       customJS.KanbanStatusSync._lastSyncResult = null;
       const dv = app.plugins.plugins.dataview?.api;
       if (!dv) {
         new Notice("Kanban re-sync: Dataview not available");
         return;
       }
       const today = window.moment ? window.moment().format("YYYY-MM-DD") : new Date().toISOString().slice(0,10);
       const r = await customJS.KanbanStatusSync.syncAllBoards(dv, today);
       new Notice(`Kanban re-sync: ${r.synced} synced, ${r.archived} archived across ${r.boards} boards`);
     }
   });
   ```

2. The command is discoverable via Cmd+P → "Sauce: Re-sync kanban boards".

### Part D — Activity-feed efficiency audit + tightening

Goal: review and improve `platform/mechanisms/activity-feed/activity-feed.js` for code-utilization efficiency. This is open-ended cleanup; aim for measurable improvements, not refactoring for its own sake.

**Checklist (review the file end-to-end and address each):**

1. **DataArray vs Array boundaries.** `dv.pages()` returns a Dataview `DataArray` (Proxy). Verify we never call `Array.isArray()` on one (would return false — landmine). Make sure we only call `.array()` ONCE per query path; multiple `.array()` calls on the same DataArray are wasteful (each materializes the whole thing). Look for places where we could chain `.where().sort().limit().array()` instead of materializing early.

2. **`_query` redundancy.** The current `inWindow` predicate iterates `tsKeysOpt`. Verify it short-circuits correctly: if the first `tsKey` matches and is in-window, return true immediately without checking the rest. Confirm the `anyFieldPresent` mtime-suppression flag is set as early as possible.

3. **`pickLatest` allocations.** Currently scans every child against `tsKeysOpt`. For rollups with many children (e.g., kanban with 283 cards yesterday), this is O(N × K). Confirm it's not iterating uselessly; consider caching the per-child resolved timestamp.

4. **Bucket-merge sort.** When `bucketRules` are applied, the merged-bucket pages are re-sorted by `created_at` desc. Verify this sort runs once per bucket, not per page.

5. **`metaBuilder` / `getSubtitle` precedence.** Confirm only one fires per row; verify the precedence rule (metaBuilder wins) is documented and enforced in code, not just in the manifest description.

6. **`groupPreviewBuilder` invocation.** Currently fires only for `defaultClosed` groups. With Part B's persisted state, "default closed" may change at runtime per the user's preference. Decide: should `groupPreviewBuilder` fire for any group that's CURRENTLY closed (per state), or only the originally-`defaultClosed` set? Pick one and document.

7. **DOM allocations in framed renderer.** The framed renderer creates a `.sauce-group` wrapper, `.sauce-group-line`, `.sauce-group-row`s, etc. for each group. Check for unnecessary intermediate elements; flatten where possible. Reduce per-row allocations if any.

8. **`_resolveTimeWindow` native-Date fallback.** The current implementation has explicit branches for `window.moment` and a native-Date fallback. Verify the fallback is reachable + correct. Consider whether keeping the dual-path is worth the complexity (Obsidian guarantees `window.moment` is present at runtime; the fallback is only for the Node test harness).

9. **Manifest description bloat.** The manifest description is now ~3000 chars of cumulative changelog. Trim aggressively — keep the latest 2-3 versions inline, move pre-v0.5.0 history to a comment block in the source file (or to a separate CHANGELOG.md if we want to start that pattern).

10. **Harness tightening.** Look for low-value AF asserts (those that just check the regex matches a string, with no semantic verification). Replace with runtime asserts where feasible. Add at least 2 new runtime asserts that exercise:
    - The `tsKeys` multi-key path with at least 3 keys present
    - The `groupPreviewBuilder` invocation against a default-closed group
    - The `_renderActivityMeta` Luxon time format path (the duck-type fix from v0.8.0)

**Bump** `activity-feed` to `0.7.0` (same minor as Part B — they ship together) or to `0.8.0` if Part D's audit reveals breaking changes (rare; aim for backward-compatible).
