# v0.89.0 — typed-aliases upgrade (optional, manual)

The v0.89.0 cycle introduces a typed-object alias schema for `spice/people/<Name>.md` frontmatter `aliases:` arrays. **Existing bare-string aliases keep working** — the resolver normalizes them to `{type: "name", value: <string>}` at read time, so you don't need to migrate.

This note documents the OPTIONAL upgrade path for users who want to typed-ify their existing bare-string entries to get the full benefit of phone / email / handle typing.

## Why typed entries help

The typed shape unlocks per-type resolver queries (`findByAlias("phone", "+1303...")`, `aliases_by_type.phone`), which the new `cowork:resolve-person` sub-skill uses for:

- **Morning-briefing inner-circle resolution** — translating `inner_circle_people: ["Stefan de P."]` to the E.164 phone list `gather-imessage` filters on. Without a typed `phone` alias on Stefan's person note, the inner-circle filter won't include his number.
- **Gather-gmail sender resolution** — matching `stefan@example.com` against a typed `email` alias resolves the sender to the right person note even if the display name differs.
- **Gather-calendar attendee resolution** — same email-based lookup for calendar attendees.

Untyped bare strings continue to work for name-based resolution (e.g. matching a contact's `displayName`), but they don't surface in `aliases_by_type.phone` / `.email` / `.handle`.

## Migration recipe

For each person note where you want richer matching:

1. Open `spice/people/<Name>.md`.
2. In the frontmatter `aliases:` block, identify each existing bare-string entry. Decide its type:
   - Phone numbers → `{type: phone, value: "+1303..."}`
   - Email addresses → `{type: email, value: "x@y.com"}`
   - Name variations → `{type: name, value: "Steve"}`
   - Other identifiers (e.g. Slack handles, GitHub usernames) → `{type: handle, value: "@stefan"}`
3. Replace each bare string with its typed equivalent.

**Example.** Before:

```yaml
aliases:
  - "Stefan de P."
  - "+13035551212"
  - "stefan@example.com"
```

After:

```yaml
aliases:
  - {type: name,  value: "Stefan de P."}
  - {type: phone, value: "+13035551212"}
  - {type: email, value: "stefan@example.com"}
```

Both forms parse correctly; only the typed form unlocks the per-type queries.

## Mixed forms are fine

You can mix typed and bare entries in the same list:

```yaml
aliases:
  - {type: phone, value: "+13035551212"}
  - "Stevie"
```

The bare string becomes `{type: "name", value: "Stevie"}` at read time. There's no penalty to leaving some entries bare; only the resolver's per-type lookups skip them.

## Cross-person collision warning

The resolver emits `console.warn("people-identity: alias collision for ...")` (and the sub-skill emits `collision_warning` in its output) when multiple person notes claim the same alias value. The first match in folder-sort order wins. Future cycles may promote collisions to a validator audit-error; for now, the warning is advisory.
